# fix-data-integrity-alert-actionability

> `specs/fix-event-ingestion-identity-guard.md:37` が本 spec を「未作成・後に作る予定」として参照している。本 spec の作成でその参照が解消される。

## 背景

2026-09-05 の監査で、**イベント汚染が 2026-08-17 以降ずっと検出されていたのに、誰も気づかなかった**ことが確定した。

`lib/data-integrity/audit.ts:179` は全 finished 試合に `eventTotalsMatchFinalScore` を適用し、`cron-audit-data-integrity`（日 12:30 JST）で Discord へ通知している。**検出は動いていた。**

問題は通知の中身にある。`lib/llm/notify.ts` の `notifyDataIntegrityReport` は次を送る。

```
🧪 データ整合性 週次監査
生成日時: {timestamp}
1. 重複イベント: groups={n} matches={n}
2. スコア不一致: matches={n}
3. finished イベント0件: matches={n}
4. draft滞留: total={n} recent7d={n}
5. 順位表 stale: competitions={n} {slugs}
対応: 異常値がある場合は該当データを確認し、修正は個別specで対応してください
```

**件数だけで、match_id も URL も重大度も無い。** どの試合か、公開中か、記事があるかが分からない。「該当データを確認し」と書いてあるが、確認する対象を特定する手段が通知に無い。

さらに当時の Discord には `collect-news-links` が 1 日 13〜25 件を流していた（D027）。**行動可能でない通知が、大量の通知に埋もれた。**

**これは「検出が無かった」問題ではなく「検出が行動可能な形で出ていなかった」問題である。** 再発防止として、検出器を足すのではなく通知を直す。

## 変更詳細

### 1. 重大度の区別

現在は 5 項目を横並びで出している。**公開中のコンテンツに影響するものを分ける。**

| 区分 | 条件 |
|---|---|
| **要対応** | スコア不一致・重複イベントのうち、**published な recap を持つ試合** |
| 記録 | 上記以外（コンテンツ無し、draft のみ、順位表 stale、draft 滞留） |

**「要対応」が 0 件なら、その旨を 1 行で書く。** 0 件の週も送る（沈黙を「異常なし」と読ませない。`project_llm_credit_outage_silent` の教訓）。

### 2. 対象の特定

「要対応」の各件について、次を出す。

- `match_id`
- `https://www.trylinerugby.com/matches/<match_id>` 形式の URL
- 対戦カードと大会
- 検出内容（期待値と実測値。例: 最終スコア 56–17 に対しイベント合計 32–35）

**Discord のメッセージ上限は 2,000 文字**で、既存の `truncateDiscordMessageContent`（`lib/llm/notify.ts:31-41`）が切り詰める。**要対応が多いと切れる。**

上限を超える場合は、**要対応の先頭 N 件を出し、残件数を明記する**。切り詰めで末尾が欠けるのではなく、**意図的に件数を絞ったことが読み手に分かる形にする**。N は名前付き定数で定義する。

### 3. 継続の可視化

**同じ試合が何週連続で検出されているかを出す。** 今回の汚染は 3 週間放置された。初回検出と継続を区別できれば、放置に気づける。

`pipeline_runs` や既存テーブルに履歴が無い場合、**本 spec で新しいテーブルを作らない。** 代わりに「初回検出時刻が分からない」ことを通知に明記し、履歴の保持は別 spec とする。

## 受け入れ条件

**テスト実行の条件**: 既定の `pnpm test` は `vitest.config.ts` の `exclude` により `tests/db/**` を実行しない。除外されていない新規ファイルに DB をモックしたテストを置くか、除外を外した実行コマンドを用意し、**PR 本文に実行コマンドと結果を貼ること。**

1. スコア不一致かつ published recap を持つ試合が 1 件あるとき、通知に **match_id と `https://www.trylinerugby.com/matches/<id>` 形式の URL が含まれる**ことを検証するテストがある
2. 同ケースで、期待値（最終スコア）と実測値（イベント合計）の両方が通知に含まれることを検証するテストがある
3. スコア不一致だが **published recap を持たない**試合は「要対応」に入らないことを検証するテストがある
4. 要対応が 0 件のときも通知が送信され、0 件であることが明示されることを検証するテストがある
5. 要対応が多数（例 50 件）のとき、**先頭 N 件と残件数が出て、2,000 文字以内に収まる**ことを検証するテストがある。末尾が切り詰めで欠けない
6. N が名前付き定数として定義されている
7. 既存の 5 項目の件数が引き続き通知に含まれる（検査自体を減らしていない）
8. `lib/data-integrity/audit.ts` の検査ロジックに差分が無い（通知に必要なフィールドの追加を除く）
9. 新しいテーブル・マイグレーションを作っていない
10. `pnpm typecheck` が green
