# feat-style-guard-shadow-mode

## 背景

`fix-qa-japanese-quality-threshold` ・ `feat-ai-style-phrase-lint` ・ `feat-recent-article-similarity-check`（当初specとして検討したが未実装のまま撤回）を検討する過程で、GPT-5.6の追加調査（2026-07-20）により重大なリスクが判明した:

- 現在のretry機構（`lib/llm/stages/generate-narrative.ts` の `NARRATIVE_TEMPERATURE_SEQUENCE = [0.7, 0.9, 0.4]`、最大3回）は、**具体的な失敗理由を次の生成試行にフィードバックしていない**（実コード確認済み、`lib/llm/pipeline.ts:237` 付近でフィードバックされるのは入力にない人名等のエンティティ違反のみ）。温度を変えて同じプロンプト構造で再実行するだけ
- `japanese_quality >= 4` ・ AI文体定型句ゼロ・過去記事との類似度低下、をいきなり全てhard gate化すると、同じ失敗パターンを繰り返してdraft化する記事が急増するリスクがある
- 固定構成（recap見出し完全固定・preview 1,500字下限）と厳格なスタイル条件は、事実が少ない試合で特に競合しやすい

このため、**まず影響を計測してから段階的に導入する**方針に変更する。本specはその第一段階（計測のみ、公開判定には一切影響しない）。

## スコープ

対象:
- 以下3種類の判定ロジックを実装するが、**いずれも既存の `resolveVerdict()` の判定結果を変更しない**（ログ・記録のみ）:
  1. `japanese_quality` が3の場合のフラグ記録（既存のQAスコアをそのまま記録するだけでよい。新規ロジック不要な場合は集計クエリのみでよい）
  2. AI文体定型句の検出（「ことが浮き彫りになった」「という形となった」「と言えるだろう」「今後の戦いに注目したい」「目が離せない」等の候補リストを対象に、決定的パターンマッチでスコアを算出）
  3. 直近記事との類似度チェック（冒頭200字・見出し・最終段落を、直近の同一 `content_type` ・ `language` のpublished記事20〜50件と文字n-gram Jaccard類似度で比較）
- 上記の判定結果を `match_content.qa_scores`（既存JSONBカラム）に追記する形、または新規の記録先（実装時に既存スキーマとの整合性を見て判断）に保存する
- 直近50〜100件のpublished記事（recap・preview両方、日本語）に対して**一括で判定をかけ直すバッチスクリプト**を用意し、「新ルールを本番導入した場合に何件がretry/reject相当になるか」を集計してOwnerに報告できるようにする

対象外:
- `resolveVerdict()` の変更（判定結果への影響は一切なし。これは `feat-style-guard-gated-rollout.md`（別spec、本spec完了後にOwnerが判断してから着手）の対象）
- note記事への適用

## LLM 連携

- 追加のLLM呼び出しは発生させない（決定的な文字列処理・既存QAスコアの読み取りのみ）。バッチスクリプトも既存published記事の `content_md` を読むだけで、新規LLM呼び出しは発生しない。コスト増加なし

## 受け入れ条件

1. 3種類の判定ロジックが実装され、それぞれ単体テストで正しく判定できることを確認する
2. バッチスクリプトを実行すると、直近50〜100件のpublished記事に対する判定結果（各記事がどのルールにどう引っかかったか）が集計され、レポート形式（JSON/Markdown等）で出力されることを確認する
3. 本spec実装後、既存のコンテンツ生成・公開フローの挙動が一切変わっていないことを回帰テストで確認する（`resolveVerdict()` の既存テストが全て通ること）
4. `pnpm test` / `pnpm tsc --noEmit` / `pnpm lint` が通る
5. バッチスクリプトの実行結果をOwnerに報告する（「新ルールなら直近N件中何件がretry相当になるか」を提示すること）

## 未解決の質問

- 判定結果の記録先（`qa_scores` への追記 vs 新テーブル）は実装時にCodexが既存スキーマを見て判断してよい
- 集計結果を見たOwnerが「導入しても問題ない」と判断すれば `feat-style-guard-gated-rollout.md` に進む。「retry率が高すぎる」と判断すれば、判定ロジック自体（閾値・検出パターン）の見直しが先になる
