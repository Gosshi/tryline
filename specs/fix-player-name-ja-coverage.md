# 選手の日本語表記が 0.4% しか存在せず、記事ごとにカタカナが変わる

## 背景

2026-08-21、同じ試合のプレビューを同じ素材で再生成したところ、**選手名のカタカナが総取り替えになった。**

| 選手 | 18:45 版 | 22:06 版 |
|---|---|---|
| Malcolm Marx | マークス | **マルクス** |
| Wilco Louw | ラウ | **ルー** |
| Josh Moorby | ムーアビー | **ムービー** |
| Fabian Holland | ファビアン・ホランド | **フィジアン・ホランド** |
| Paul de Villiers | デ・ヴィリアーズ | **デフィリアス** |
| Cobus Reinach | ライナッハ | **レイナハ** |

### 原因は DB に日本語表記が無いこと

本番実測（2026-08-23）。

| 対象 | 総数 | `name_ja` 保有 | 割合 |
|---|---|---|---|
| `players` 全体 | 2,456 | **11** | **0.4%** |
| ラインアップに登場する選手 | 1,927 | 11 | 0.6% |
| 得点イベントに登場する選手 | 936 | 9 | 1.0% |

**11人は日本代表選手**である（`feat-preview-player-kanji-glossary.md` / PR #600 で漢字表記をバックフィルした分）。**それ以外の全選手が空。**

### プロンプトは設計どおり動いている

`lib/llm/prompts/shared-prompt-blocks.ts:42-46`

```
選手名は、日本語表記グロッサリにある場合は、入力データと表記が異なる場合も指定の漢字表記を必ず使うこと。
グロッサリにない選手でも、入力データ（projected_lineups・match_events・sourced_facts）に日本語表記がある場合はその表記をそのまま使い、漢字をカタカナに変換しないこと。
どちらにも日本語表記がない選手はカタカナで記載すること。アルファベット表記は禁止。
```

グロッサリは `buildJapanesePlayerNameGlossary`（`lib/llm/stages/assemble.ts:476`）が `players.name_ja` から組み立てる。**0.4% しか埋まっていないため、ほぼ全選手が3行目のフォールバックに落ちる。**

`sourced_facts` の `fact_ja` にカタカナが含まれることはあるが、**あれ自体が LLM 生成で毎回変わる**ため、安定した拠り所にならない。

**バグではない。設計どおりに動いて、データが無いだけ。**

### 何が損なわれるか

**1. 検索流入。** 同じ選手が記事ごとに違う表記になる。「マルコム・マークス」で検索した読者に「マルコム・マルクス」の記事は当たらない。**日本語で海外ラグビーを追えることが Tryline の立ち位置**であり、選手名は最も検索される語である。

**2. 読者の信頼。** 同一記事内では一貫するが、**記事をまたぐと別人のように見える。** 再生成のたびに変わるため、過去記事との整合も取れない。

**3. 明確な誤り。** 「フィジアン・ホランド」（Fabian → フェイビアン/ファビアン）、「デフィリアス」（de Villiers → デ・ヴィリアーズ）は読みとして誤っている。

## スコープ

対象:

- 選手の日本語表記を**一度決めたら固定する**仕組み
- 新規登録される選手に表記が入る経路
- 既存2,445人分のバックフィル手順（**実行は段階的に**）

対象外:

- **日本代表選手11名の漢字表記の変更。** `feat-preview-player-kanji-glossary.md` の結果を維持する
- チーム名・大会名の日本語表記（既に別経路で解決済み）
- プロンプトの表記ルール（`shared-prompt-blocks.ts:42-46`）の文面変更。**グロッサリが埋まれば1行目で解決する**
- `players.slug` の正規化（下記「未解決の質問」参照）
- 重複した選手行の統合（同上）
- 既存記事の再生成

## データモデル変更

**なし。`players.name_ja` は既に存在する。** 埋まっていないだけ。

## API サーフェス

### 1. 表記の生成と固定

**一度生成したら二度と変えないこと**が要件である。記事ごとに変わるのが今の問題であり、**バックフィルのたびに変わるなら何も解決しない。**

実装方式は判断してよいが、以下を満たすこと。

- `players.name_ja` が既に入っている選手を**上書きしない**
- 同じ選手に対して**べき等**である（再実行しても値が変わらない）
- 生成に LLM を使う場合、**バッチで処理してコストを抑える**

### 2. 新規選手の登録経路

`ingest-lineups` / `ingest-squads` は未登録選手を `players` に追加する（`lib/db/player-slug.ts` 経由）。**追加時点で `name_ja` が入る形が望ましい。**

ただし取り込みは同期的な cron であり、LLM 呼び出しを挟むと遅くなる。**取り込み時に入れるか、後追いのバッチにするかは判断してよい。** 後追いにする場合、**未設定の選手が記事に登場する窓が残る**ことを PR 本文に明記すること。

### 3. バックフィル

**段階実行を必須とする。**

1. **少件数（20人程度）で試し焼き** → Owner が読みを検品
2. 問題なければ全件

`content-regen` スキルの「少件数の試し焼き→検品→全件」と同じ原則である（2026-06-12 の297件 draft 化事故の再発防止）。

**表記の誤りは記事に残り続ける**ため、コンテンツ再生成より慎重に扱うこと。

### 4. 読みの正確性（重要）

ラグビーの選手名には **アフリカーンス語・マオリ語・トンガ語・サモア語・フィジー語**由来のものが多い。**英語読みでカタカナ化すると誤る。**

- `Louw` → ルー（英語読み）ではなく **ラウ**（アフリカーンス）
- `de Villiers` → デフィリアスではなく **デ・ヴィリアーズ**
- `Nortjé` → ノルチェ
- マオリ語・パシフィカ系の名前も同様

**プロンプトに言語背景を考慮させること。** 所属チームの国は `teams` から辿れる。

## UI サーフェス

なし。ただし**選手ページの表記が安定する**という副次効果がある。

## LLM 連携

新規の LLM 呼び出しを**追加する**。変換系なので `MODELS.FAST`（`lib/llm/models.ts`）を使うこと。**モデル ID を直書きしない。**

**コスト見積もりを PR 本文に書くこと。** 対象は最大2,445人。バッチサイズと想定トークンから概算を出し、**試し焼き20人での実測**も併記すること。

**一度きりのバックフィル＋新規選手のみの継続処理**なので、恒常的なコスト増は小さいはずである。その前提が正しいかを見積もりで確認すること。

## 受け入れ条件

1. `players.name_ja` が既に入っている選手を上書きしない。**日本代表11名の漢字表記が変わらない**ことをテストで担保する。
2. 同じ選手に対してべき等である（再実行で値が変わらない）。
3. 20人程度の試し焼きができる（件数を指定して実行できる）。
4. `Wilco Louw` → ラウ、`Paul de Villiers` → デ・ヴィリアーズ のように、**英語読みではない言語背景が反映される**。試し焼きの出力で Owner が検品できる。
5. 生成に `lib/llm/models.ts` の定数を使っている。モデル ID の直書きが無い。
6. `buildJapanesePlayerNameGlossary` が `name_ja` を拾い、プロンプトのグロッサリに載ることをテストで確認できる。
7. `pnpm lint` / `pnpm tsc --noEmit` / `pnpm test` / `pnpm build` がすべて clean。
8. **全件バックフィルは実施しない。** 試し焼きの提示までが Codex の作業。全件実行は Owner の承認後。
9. **既存記事の再生成は実施しない。**

## 未解決の質問

1. **既存記事をどうするか。** 表記が安定しても、**過去記事は古い表記のまま**である。全件再生成はコストが大きい。**表記の揺れが実際に検索流入へ与えた影響を測ってから判断する**のが現実的。GSC で選手名クエリを見る価値がある。

2. **`players.slug` にダイアクリティカルマークの欠落がある。** `Ruan Nortjé` の slug が `ruan-nortj` になっている（`é` が落ちている）。`lib/db/player-slug.ts` の正規化の問題で、**URL とマッチングの両方に影響する。** 本 spec の対象外だが、選手ページの品質としては同根。別 spec の候補。

3. **重複した選手行がある。** `cheslin-kolbe` と `cheslin-kolbe-2`、`damian-de-allende` と `-2` など6組以上を確認している。`resolveAvailablePlayerSlugs` の衝突回避が同一人物に別 slug を与えたものとみられる。**`name_ja` を入れる前に統合すべきか、入れてから統合するか**は Owner の判断。

4. **読みの検証を誰がするか。** 2,445人分の読みを人が全部確認するのは非現実的である。試し焼き20人で方式の妥当性を見たうえで、**主要選手（代表クラス）だけ重点確認する**のが落とし所になる可能性が高い。
