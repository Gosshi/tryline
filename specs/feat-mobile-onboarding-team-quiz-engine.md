# feat-mobile-onboarding-team-quiz-engine: 代表チーム診断オンボーディング(Stage C-1: 診断基盤)

対象リポジトリ: **tryline-mobile** のみ(クライアント側完結。データモデル・BFF 変更なし)。**`feat-mobile-onboarding-team-picker`(Stage A)のマージ後に着手する後続spec**。`feat-mobile-onboarding-favorites-sync`(Stage B)とは独立(順不同)。

## 背景

`feat-mobile-onboarding-team-picker`(Stage A/直接選択)の背景で、5問のプレースタイル診断は「将来、直接選択に迷うユーザー向けの追加入口として別specで検討する」として対象外にしていた。GPT(2026-07-23)による再提案で、診断ロジックの型(仕組み)とラグビー知識に依存する中身(設問文言・チームスコア・特徴文等)を分離する設計が示された。これにより、Stage Aと同じ「コンテンツ未確定で着手できない」問題を避けられる。

本specは**Stage C-1: 診断の仕組みのみ**を対象とする。実在チームの評価・設問文言の最終稿・チームの特徴文などの「ラグビー知識に依存する中身」は本specの対象外とし、後続の `feat-mobile-onboarding-team-quiz-content`(Stage C-2、未作成)で扱う。**Stage C-1の完了条件に、ラグビーに関する内容の正確性は含めない。**

**対象国(Owner確定、2026-07-24)**: 初期対象は2026-07-20時点のWorld Rugby男子ランキング上位12か国の固定マスタとする(南アフリカ・ニュージーランド・アイルランド・フランス・イングランド・スコットランド・アルゼンチン・オーストラリア・フィジー・日本・ウェールズ・イタリア)。ランキング変動による自動追加・削除は行わない。対象国の変更は、Stage C-2相当のコンテンツ・スコアリングレビューを経て実施する。

**スコアリングは疎(sparse)に設計する**: 各選択肢は12チーム全部に配点するのではなく、相性の強い3〜5チームにのみ加点する。5問×5選択肢なら最大25選択肢×4チーム程度=100組が実質のレビュー対象になり、12チーム×5〜8軸のような密な評価マトリクスより設計・レビューの負担が小さい。

## スコープ

対象:
1. **診断データ型の定義**: 設問・選択肢・チームプロフィールをコードに直書きせず、差し替え可能なデータとして分離する

   ```ts
   type Question = {
     id: string;
     text: string;
     options: {
       id: string;
       label: string;
       scores: Record<string, number>;
     }[];
   };

   type TeamProfile = {
     id: string;
     name: string;
     shortDescription: string;
     recommendationReason: string;
   };
   ```

2. **診断UI**: 1問1画面、単一選択式。戻る・スキップ・最初からやり直すが可能
3. **スコアリング**: 回答ごとに`scores`を加算し、合計点上位1〜3チームを算出する。同点時の処理(例: 元のチーム配列順で決定的にタイブレークする)を実装する
4. **固定12チームマスタ**: 上記「対象国」の12チームをコード上の固定リスト(またはJSON等の静的データ)として定義する。ランキングAPIから動的取得しない
5. **診断結果画面**: 最も相性の良い1チーム＋次点2チームを提示し、`recommendationReason`(短い推薦理由)を表示する。ユーザーが提示結果から最終的に選ぶ(自動確定しない)。各チームから、Web版のチーム詳細ページ(`https://www.trylinerugby.com/teams/{slug}`相当)または関連試合(既存の`calendar`データをそのチームで絞り込んだもの)へのリンクを用意する
6. **お気に入りとしての保存**: 選択結果を`pendingFavoritesStore`(Stage Aで実装済み)に保存する(直接選択フローと同じ永続化経路を再利用する)
7. **対象外チームへの逃げ道**: 12チームに含まれないチームが好きなユーザー向けに、結果画面に「この診断は一部の代表チームを対象としています。すでに応援したいチームがある場合は一覧から直接選択できます」のような文言と、直接選択画面への導線を用意する
8. **開発・テスト用のダミーデータ**: 本specの実装・テストは仮の設問・仮の配点(12チームの枠は使ってよいが、実際のスコア値・推薦理由文はダミーでよい)で行う。実際の配点・推薦理由の確定はStage C-2で行う

対象外:
- **設問文言・選択肢文言・実際の配点・推薦理由の確定稿**。すべてStage C-2(`feat-mobile-onboarding-team-quiz-content`、未作成)で扱う。要Ownerまたはラグビーに詳しいライターのレビュー
- **歴史・ライバル関係・注目選手などの診断専用コンテンツの新規作成**。作らない。結果画面は既存のチームページ・関連試合データへのリンクで代替する
- 選択肢ごとの生成画像
- 複雑なアニメーション演出
- AIによる自由回答判定
- 行動履歴(記事閲覧・フォロー等)による推薦の自動補正
- 12チーム以外への対応拡大
- 診断結果のSNSシェア画像生成
- 直接選択(Stage A)フローの変更

## データモデル変更 / API サーフェス

なし。

## UI サーフェス

- 既存のエディトリアル路線(紙・インク・赤アクセント最小限)を踏襲。診断画面は「新聞のパーソナリティ診断」的な体裁が方針と親和的
- 診断結果の提示は「あなたに最も合いそうなのは○○代表です」+ 他候補2件を淡々と紙面的に並べる。派手な演出は入れない
- 選択肢・結果画面のコンポーネントは、Stage Aのチーム選択チップ(`FavoritesEditor.tsx`パターン)と見た目を揃える(新規パターンを増やさない)

## 受け入れ条件

1. 5問(ダミー設問)に順に回答すると、疎なスコア加算(選択肢ごとに3〜5チームのみ加点)に基づいて固定12チーム中の上位1〜3チームが算出されることを確認するユニットテスト
2. 同点時のタイブレーク処理が決定的であることを確認するテスト
3. 「戻る」で前の設問に戻れる、「最初からやり直す」で回答がリセットされることを確認するテスト
4. 診断をスキップして直接選択(Stage A)へ移動できることを確認するテスト
5. 診断結果から選んだチームが`pendingFavoritesStore`に保存されることを確認するテスト(Stage Aの保存関数を呼んでいること)
6. 結果画面に、各チームのWeb版チームページまたは関連試合へのリンクが表示されることを確認するテスト(`Linking.openURL`が正しいURLで呼ばれること)
7. 対象外チームへの逃げ道(直接選択への導線)が結果画面に表示されることを確認するテスト
8. TypeScript strict・lint・test green
9. **Owner 目視**: 実機または iOS Simulator で診断UIの一連の流れ(ダミーデータ)を確認する。**この時点でチーム名・スコア・推薦理由文の正確性は確認対象外**(Stage C-2で確認する)

## 未解決の質問

- Stage C-1で使うダミー設問の具体的な文言(架空でよい)はCodexの裁量
- 結果画面からのリンク先を「Web版チームページ」「関連試合一覧」のどちらにするか(または両方出すか)はCodexの裁量。ネイティブ画面は無いため`Linking.openURL`での外部遷移が前提
- Stage C-2で確定させる実際の設問文言・選択肢・配点・推薦理由は、GPT提案にある5問構成案(プレースタイル/応援したいチーム像/雰囲気/好きな試合展開/応援で大事にすること)をたたき台に、Owner・ライターがレビューする
