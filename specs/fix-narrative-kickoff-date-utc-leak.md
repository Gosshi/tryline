# ナラティブ生成に kickoff_at が UTC のまま渡り、本文の日付が1日ずれる

## 背景

2026-08-21 03:47 JST、南アフリカ vs ニュージーランド第1テスト（match_id: `d6d5b1ab-58ec-44c8-a31d-54fadc0a662e`）の preview が QA に reject された。指摘の1つがこれ。

```
直近5試合の対戦相手・スコアや8月22日という日付は、提示された許可済み事実には含まれていません
```

生成された本文にこうある。

> エリス・パークで行われる**8月22日**の初戦は、近い攻撃数字に対し、南アフリカの失点抑制がわずかに上回る構図で始まる。

**この試合のキックオフは 2026-08-23 00:10 JST。** UTC では 2026-08-22 15:10 であり、**本文の日付は UTC の日付である。**

QA は「許可済み事実に含まれていない」という理由で指摘したが、実際には**日付そのものが誤っている**。指摘の理由は間違っているが、結果として実在するバグを1件拾った形になっている。

### 根本原因

`lib/llm/stages/assemble.ts:996` は DB の値をそのまま返す。

```ts
return {
  match: {
    id: match.id,
    kickoff_at: match.kickoff_at,   // UTC の timestamptz がそのまま
```

`lib/llm/prompts/generate-preview.ts:247` は、この assembled 全体を JSON 化してプロンプトへ入れる。

```ts
`試合データ: ${JSON.stringify(sanitizedAssembled)}`,
```

`lib/llm/prompts/generate-recap.ts:342` も同一の行を持つ。

つまり **LLM が見ているのは `"kickoff_at":"2026-08-22T15:10:00+00:00"` という UTC 文字列だけ**であり、日本時間へ変換する情報もその指示も存在しない。

`lib/llm/` 配下を `Asia/Tokyo` で grep しても 1 件もヒットしない。**LLM パイプラインには JST 変換が一切存在しない。**

一方 `lib/format/kickoff.ts` には UI 用の変換関数が既に4つある（`formatKickoffJst` / `formatKickoffJstDate` / `formatKickoffJstTime` / `formatKickoffJstCompact`）。**UI は正しく JST を表示しており、LLM だけが UTC を見ている。**

### 影響範囲

**JST キックオフが 00:00〜08:59 の試合すべてで、本文が日付に言及した場合に1日ずれる。**

対象は狭くない。`greatest-rivalry-2026` は全8試合が該当する。

| JST キックオフ | UTC 日付 | ずれ |
|---|---|---|
| 8/23 00:10（第1テスト） | 8/22 | あり |
| 8/26 02:10（ライオンズ戦） | 8/25 | あり |
| 8/30 00:10（第2テスト） | 8/29 | あり |
| 9/06 00:10（第3テスト） | 9/05 | あり |
| 9/13 06:00（第4テスト） | 9/12 | あり |

欧州リーグ（Six Nations / Premiership / URC / Top 14）も JST 早朝キックオフが大半であり、**公開済みコンテンツにも同じ誤りが混入している可能性が高い。** 監査が必要。

なお本文が日付に触れなければ表面化しないため、「全記事が誤っている」ことを意味しない。**触れた記事だけが誤る。**

## スコープ

対象:

- assembled の match に日本時間の表記を追加し、LLM に渡す
- preview / recap 両方の生成プロンプトに、日付は日本時間で書く旨の指示を追加する
- 公開済みコンテンツの誤日付を洗い出す読み取り専用の監査スクリプトを追加する

対象外:

- **`matches.kickoff_at` の保存形式。UTC のまま変更しない**
- UI 表示（`lib/format/kickoff.ts` 経由で既に正しい）
- 既存 `kickoff_at` フィールドの削除・改名（他の参照を壊す）
- **誤日付コンテンツの自動修正・自動再生成。** 監査結果を見て Owner が判断する
- QA プロンプト側の変更（別 spec `fix-qa-form-stats-individual-results.md`）
- 英語コンテンツの日付表記方針（現状 UTC 表記で実害の報告がないため、本 spec では ja を確実に直すことに絞る）

## データモデル変更

**なし。マイグレーション不要。** 既存の `matches.kickoff_at` から導出するだけ。

## API サーフェス

### 1. assembled への JST 表記の追加

`lib/llm/stages/assemble.ts` の戻り値 `match` に、日本時間の文字列フィールドを追加する。

- 値は `lib/format/kickoff.ts` の既存関数から得ること。**新しい日時整形ロジックを書かない**
- `formatKickoffJst` は `formatFromParts`（同ファイル 25-27 行）を通じて `2026-08-23 (日) 00:10 JST` 形式を返す。実装時に実際の出力を確認してから受け入れ条件の期待値を確定すること
- 既存の `kickoff_at` は**残す**。削除すると他の参照が壊れる

### 2. 生成プロンプトへの指示追加

`generate-preview.ts` と `generate-recap.ts` の双方に、以下の趣旨の指示を追加する。

- 日付・時刻に言及する場合は日本時間のフィールドを使うこと
- `kickoff_at` は UTC であり、これを日本時間として本文に書いてはならない

**既存の禁止事項ブロック（`PROHIBITIONS_BLOCK`）と同じ形式で追加すること。** 新しいブロック構造を発明しない。両ファイルで重複するため、`lib/llm/prompts/shared-prompt-blocks.ts` に置くのが既存の構成に沿う。

### 3. 監査スクリプト

`tools/` 配下に読み取り専用のスクリプトを追加する。既存の `tools/` スクリプトの起動方法（`node --env-file=.env.production.local tools/run-ts.cjs <script>`）に合わせること。

出力すべきもの:

- `match_content` の行のうち、対応する試合の JST キックオフ時刻が 00:00〜08:59 のもの
- そのうち `content_md` に「N月M日」形式の日付が含まれるもの
- 本文中の日付が JST 日付・UTC 日付のどちらと一致するか

**SELECT のみ。UPDATE / DELETE / DDL を含めてはならない。**

## UI サーフェス

なし。

## LLM 連携

段階4（ナラティブ生成）のプロンプトのみ。

**新規 LLM 呼び出しは追加しない。コスト増はプロンプトが数十トークン伸びる分のみで、実質ゼロ。** モデル・段数・出力スキーマは変更しない。モデル ID は直書きせず `lib/llm/models.ts` の定数を参照すること。

## 受け入れ条件

1. `AssembledContentInput` の `match` に日本時間表記のフィールドが存在する。
2. そのフィールドの値が `lib/format/kickoff.ts` の既存関数の出力と一致する。**独自の日時整形を実装していない**ことをテストで確認できる。
3. `kickoff_at` フィールドが引き続き存在し、値が UTC のまま変わっていない。
4. `kickoff_at` が `2026-08-22T15:10:00+00:00` のとき、追加フィールドが **8月23日**を示す。**UTC 日付である 8月22日を返さない。** この境界値をテストに含めること。
5. `buildPreviewPrompt` の出力に、日付を日本時間で書く旨の指示文字列が含まれる。
6. `buildRecapPrompt` の出力に、同じ指示文字列が含まれる。
7. 監査スクリプトが存在し、実行すると対象件数を出力する。**書き込み系 SQL を含まない**ことをコードレビューで確認できる。
8. 監査スクリプトが match `d6d5b1ab-58ec-44c8-a31d-54fadc0a662e` の preview を対象として検出する（`status` で絞る場合は draft も検証できるオプションを用意すること）。
9. `pnpm lint` / `pnpm tsc --noEmit` / `pnpm test` / `pnpm build` がすべて clean。
10. **コンテンツの再生成は実施しない。** 監査結果の提示までが本 spec の完了条件。

## 未解決の質問

1. **公開済みコンテンツをどう直すか。** 監査結果の件数次第で選択肢が変わる（少数なら手修正、多数なら再生成バッチ）。再生成する場合は `content-regen` スキルの「少件数の試し焼き→検品→全件」を必ず経ること（2026-06-12 の 297 件 draft 化事故の再発防止。QA 最低字数は `lib/llm/content-length.ts` を都度確認し、値を書き写さない）。件数が出てから Owner が判断する。

2. **英語コンテンツの日付表記。** 英語 preview / recap は日本のファン向けではないため、JST 固定が正しいとは限らない。現状 UTC のままで実害の報告がないため本 spec では触れないが、方針を決める価値はある。

3. **`kickoff_at` を LLM から隠すべきか。** 本 spec は JST フィールドを追加し指示で誘導する方式を取るが、UTC 文字列が JSON に残る以上、モデルがそちらを拾う可能性は残る。`sanitizeUnconfirmedProjectedLineups` と同様にプロンプト直前で UTC を落とす方式のほうが確実だが、他の用途で `kickoff_at` を参照している可能性があるため、まず追加＋指示で効果を測る。**再発したら隠す方式へ切り替える。**
