# 記事プロンプト B の改訂（B2）と、B1 との比較

## 背景

記事プロンプトの A/B 比較（`specs/feat-content-prompt-ab-experiment.md`、結果は `tmp/prompt-ab/2026-09-24T12-01-00-107Z/`）では、**B が 4 組中 4 組で選ばれた**（GPT-6 の名前を伏せた評価 `gpt6-review.md`。対応表との照合は Claude Code）。Claude Code の事実照合でも、B の誤りは 0 件、A は 3 本で計 5 件（予想スコア、根拠のない因果・心理、区間のトライ数の誤り、漢字の推測）だった。

一方で、GPT-6 は B を「このまま本番に入れることは勧めない」とし、次の弱点を挙げた（`gpt6-review.md` の 3 章）。

1. 「問い」が段落の途中で別の問いに変わる。原因の問いを立ててから「断定できない」と答える。
2. 比較範囲の断り書き（「予測ではない」「相手が異なる」）が何度も繰り返され、理解が進まない。
3. 最大リード・逆転直前の点差・連続得点区間の点差が混ざる。
4. **レビューの有料部分（3 つ目の見出しから先）が短い**（695 字、818 字。A は 1,930 字、1,515 字）。しかも無料部分で読んだ経過をもう一度たどっている。
5. 戦術ポイントの数値の誤りを確かめずに使う危険がある（4 試合中 4 件の誤り。直し方は `specs/fix-content-qa-false-positives.md` の 4）。

加えて、Claude Code の照合では、B の本文が「提供された直近 5 試合」「確定メンバーは示されていない」と、システム内部のデータの有無を本文で説明していた。

Owner の決定（2026-09-24）: **レビューは 3 節のまま**にする。有料部分のターニングポイントを記事の分析の中心に据え、分量は字数のノルマではなく役割で確保する。

## スコープ

**対象**
1. B のプロンプトの文言を B2 に改訂する（`lib/llm/prompts/variant-b/` の 3 ファイル）。
2. A/B スクリプト（`scripts/ab-content-prompts.ts`）の `run` に 2 つの指定を足す。
   - `--variants`: 生成する版を選ぶ。
   - `--pair-with`: 前回の実行の B の本文と、今回の B2 の本文を、名前を伏せて並べる。

**対象外**
- A のプロンプト、QA、ガード、抽出。
- B の本番適用（B2 の評価の結果を見て、別の spec にする）。

## API サーフェス

### 1. B2 の文言

- `PROMPT_VERSION`: `preview-b@0.2.0`、`recap-b@0.2.0`。
- 付録の文言を正とする。B1 のビルダーは残さない（B1 の本文は前回の実行の出力として残っている）。
- データブロックの組み立て（`buildVariantBDataBlocks` と `buildRecapDataBlocks`）と、`buildMatchPhaseFacts` は変えない。

### 2. `run --variants`

- `--variants A,B`（既定）、`--variants B`、`--variants A` を受け付ける。
- 1 つだけを指定した場合、`blind/` と `blind-key.json` は作らない（`--pair-with` と一緒に使う場合を除く）。

### 3. `run --pair-with <前回の実行のフォルダ>`

- `--variants B` と一緒のときだけ使える。それ以外の組み合わせは例外にする。
- 前回のフォルダの `ledger.json` と `blind-key.json` から、各 fixture の B の本文（`blind/<match_id>-X.md` または `-Y.md`）を見つける。
- 今回の B2 の本文と前回の B の本文を、fixture ごとに無作為に X と Y に割り当て、今回のフォルダの `blind/` に書き出す。対応表は `blind-key.json` に `{ "X": "B2", "Y": "B1" }` の形で書く。
- 前回のフォルダに、その fixture の B の本文がなければ、その fixture は並べずに警告を出す。
- `review-sheet.md` と `summary.md` は前回と同じ形で作る。`summary.md` の QA の欄は今回の B2 の分だけを載せ、「前回の B1 とは QA のコードが異なる可能性があるので、点数は比べない」と注記する。

## LLM 連携

- 段 3（本文）の B の文言だけを変える。
- 比較の実行（Claude Code が行う）: 前回と同じ 4 つの固定入力（`tmp/prompt-ab/fixtures/`）で、B2 だけを 4 本生成する。**入力は固定し直さない**（B1 と B2 の違いをプロンプトの違いだけにするため）。
- 費用: 4 本で約 $0.2（前回の B の 4 本の実績は $0.172）。上限 $1。実行前に Owner の承認を得る。

## 受け入れ条件

1. B2 のプロンプトに、付録の追加文言（共通の【問いと段落】【時間と点差】、レビューの【有料部分の役割】）が含まれることを確かめるテストがある（プレビューとレビュー、データの揃い方の全分岐）。
2. B2 のプロンプトに `1,200～1,600字` が含まれないことを確かめるテストがある。B1 で確かめていた「含まれない」文字列（`2,000字`、`最低3名` など）の検査は残す。
3. A の結合プロンプトのスナップショットが変わらない（既存のテストが通る）。
4. `run --variants B` で、LLM のモックが B だけ 1 回ずつ呼ばれ、A は呼ばれないことを確かめるテストがある。
5. `run --variants B --pair-with <dir>` のテスト（LLM はモック、前回のフォルダはテスト用に作る）で次を確かめる:
   - `blind/` に fixture ごとの X と Y ができる。
   - 片方が前回の B の本文と同じ内容である。
   - `blind-key.json` の対応が正しい。
   - 前回の B の本文がない fixture は並べられず、警告が出る。
6. `--pair-with` を `--variants A,B` と一緒に指定すると例外になる。
7. `pnpm lint`、`pnpm typecheck`、`pnpm test` が通る。**3 つとも実行して、結果を完了報告に含める。**

## 評価の手順（Claude Code が行う）

1. `run --fixtures <前回の 4 つ> --variants B --pair-with tmp/prompt-ab/2026-09-24T12-01-00-107Z` を実行する。
2. Claude Code が B2 の 4 本を固定入力と照合する（`fact-check.md`）。
3. GPT-6 に、B1 と B2 を名前を伏せて比べてもらう。観点は前回の 6 つに、「有料部分の役割と量」と「断り書きの繰り返し」を明示して足す。
4. **B2 を本番の候補にする基準:**
   - B2 に新しい重大な事実誤りが 0 件。
   - 4 組中 3 組以上で B2 が選ばれる。
   - レビュー 2 本で、有料部分が本文の半分以上を占める。
   - 基準を満たさなければ、B2 の弱点を直して同じ手順を繰り返す。

## 付録: B2 の文言（正）

改行位置は自由。文言は変えないこと。**B1 から変えた箇所には、行頭に【追加】【変更】と書いてあるが、これは説明のための印なので、プロンプトには入れない。**

### 共通指示（`variant-b/shared.ts`）

B1 の `COMMON_B_PROMPT` を基に、次のように変える。

**【使える根拠】の変更と追加**

- 【変更】「・戦術ポイントは論点の候補です。元の事実で確認できない主張は採用しません。」を次に置き換える。
  ```
  ・戦術ポイントは論点の候補で、誤りを含むことがあります。数値・勝敗・試合数は必ず試合データで確かめ、食い違う場合は試合データの値を使います。確かめられない論点は使いません。
  ```
- 【追加】「・直近の収録試合の結果を〜」の直後に、次を足す。
  ```
  ・試合数は実際に収録された数で書きます。項目名に last_5 とあるだけで「直近5試合」と呼びません。
  ```

**【人物と引用】への追加**

- 【追加】末尾に次を足す。
  ```
  ・英字しか入力にない選手名に漢字を当てません。表記辞書にない選手はカタカナで書き、姓名の順は入力のままにします。
  ・選手名を増やすために、チーム全体の評価や発言を特定の選手の功績へ割り振りません。
  ```

**【編集】の置き換え**

- 【変更】B1 の【編集】の中身を、次の 3 つのブロックに置き換える（B1 の「事実を列挙するだけで終えず〜」「一つの事実を別の節で再掲する場合は〜」の 2 行はここに統合する。残りの行は【編集】として残す）。
  ```
  【問いと段落】
  ・中心の問いは一つに固定します。核心の節で短い答えを示し、後の節はその答えの根拠を示します。途中で別の「問いは」「なぜ」に置き換えません。
  ・原因を示す観測がない場合は、原因の問いを立ててから「断定できない」と答えるのではなく、記録で答えられる比較の問いに最初から絞ります。
  ・比較範囲の断り（対象期間、相手の違い、予測ではないこと）は、その比較を初めて示す箇所で一度だけ書きます。同じ断りを結論まで繰り返しません。
  ・各段落は、新しい根拠、比較の結果、観戦や振り返りでの意味のいずれかを一つ加えます。どれも加えない段落は書きません。

  【時間と点差】
  ・期間を伴う記述では、その期間の開始直前と終了時のスコアを確かめます。
  ・最大リード、逆転直前の点差、ある連続得点区間の点差は別のものとして書き分けます。
  ・区間のトライ数・得点は、その区間の得点イベントだけから数えます。試合全体の数と混ぜません。
  ・最終スコアしかない過去の試合について、終盤の接戦、逃げ切り、リードの推移を作りません。
  ・2つの値の差や合計を書く場合は、入力の値で計算を確かめます。

  【編集】
  ・本文で、システムや入力データの存在に触れません（「提供された」「データでは示されていない」「確定メンバーは示されていない」のような書き方をしません）。書けないことは説明せず、書かずにおきます。
  ・答えられない原因、次戦相手、来季の見通しを埋めません。
  ・材料が足りない場合も、創作や反復で字数を埋めません。
  ・段落は、どの試合にも当てはまる枠組み（得点力の比較、スコアの形容、「AとBの対決は」、「一発勝負」）ではなく、この試合だけの瞬間・決定・文脈から書き始めます。
  ・最初の見出し直後は通常の段落です。箇条書きや引用ブロックだけにしません。
  ・指定された節を「# 」の見出しで出力し、別の記事タイトルを先頭に追加しません。強調記号やコードブロックは本文に使いません。
  ```

B1 の `COMMON_B_PROMPT` のそれ以外の部分（冒頭の役割、優先順位、【使える根拠】の他の行、【人物と引用】の他の行）は変えない。
