# レビュー生成に全得点時点の累計スコアを渡す

## 背景

2026-08-17、8/15 の日本 vs オーストラリア第2戦のレビュー再生成が QA で reject された（事実根拠 1/5）。**イベントデータは正しく復旧済み**で、汚染は解消していた。それでも本文のスコア計算が破綻していた。

### QA の指摘（実測）

> 39分のスコアを「17-19」としており、本文後段の「19-17」「21-17」と整合していません。
>
> 「前半は日本が34分に14-17とリードし、3点差で折り返した」は誤りで、ハーフタイム時点ではオーストラリアが21-17でリードしています。
>
> 「3点差を4点差へ変えたことで、日本は後半の最初の得点で再逆転できる状況ではなくなった」は論理的に誤りです。21-17から日本がトライを挙げれば22-21で再逆転できます。

### 実データとの照合

`match_events` から home（オーストラリア）基準で累計するとこうなる。

| 分 | 得点 | home–away |
|---|---|---|
| 5 | 日本 try | 0–5 |
| 7–8 | 豪州 try+G | 7–5 |
| 17–18 | 豪州 try+G | 14–5 |
| 26–27 | 日本 try+G | 14–12 |
| 34 | 日本 try | **14–17**（日本リード） |
| 39–40 | 豪州 try+G | **21–17** |
| 51 以降 | 豪州 5 トライ | 56–17 |

> **2026-08-17 訂正。** 初版は「39 分の 7 点を 2 点として扱った」「19 という数値はどの時点にも存在しない」と書いたが**誤り**。Codex の指摘で判明した。イベントは 39 分 try と 40 分 conversion に分かれており、**各イベント直後の累計は 39 分 19–17、40 分 21–17** である。19 は実在する。以下は訂正後の分析。

**本文の誤りは 2 種類ある。どちらも算術そのものではない。**

**1. 表記順が記事内で揺れている。** 39 分時点は home 基準で `19–17`（豪州 19・日本 17）。本文はこれを「17-19」と書き、後段では「19-17」「21-17」と書いた。**同じ時点を 2 通りの並びで書いている。** QA が「整合していません」と指摘したのはこの点である。

**2. ハーフタイムを誤認している。** 本文の「34分に14-17とリード」は**正しい**（この時点で日本がリード）。しかし続けて「3点差で折り返した」と書いた。**実際の前半終了時は 21–17 で豪州リード**であり、39–40 分の得点を見落として 34 分を折り返し地点と誤認している。

その結果、「3点差を4点差へ変えた…再逆転できる状況ではなくなった」という論理的に誤った記述（21-17 なら 1 トライで 22-21 と再逆転できる）まで派生した。

### 構造的な原因

`lib/llm/prompts/generate-recap.ts:164-203` の `scoreTimelineBlock` が LLM に渡すのは以下だけである。

- 前半終了時スコア（`ht_home` / `ht_away`）
- **リードが入れ替わった時点**のスコア（`lead_changes`）
- 勝利を決めた得点（`winning_score`）

**各得点時点の累計スコアは渡っていない。** そのため LLM は「5 分に日本がトライ → 7 分に豪州がトライ…」というイベント列から、**自分で足し算して途中経過を組み立てる**必要がある。今回はその算術を誤った。

さらに、スコアは**常に「ホーム — アウェイ」の順**で渡される（`generate-recap.ts:175`）。この試合は home が豪州なので `Australia 21 — Japan 17` となるが、日本代表戦の記事は自然と日本を主語に書く。**本文が「17-19」「19-17」と揺れているのは、主語を入れ替えるたびに数字の並びを組み替え、その過程で計算を誤ったため**とみられる。

**アウェイチームが記事の主役になる試合で起きる問題**であり、日本代表のアウェイ戦では再発する。**11 月の欧州遠征 3 戦（ウェールズ・イングランド・スコットランド）はすべてアウェイ**である。

### 必要なデータは既に計算されている

`lib/llm/stages/assemble.ts:177-183` の `computeScoreTimeline` 内に、**全得点時点の累計を保持する `scoringSnapshots` が既に存在する。**

```ts
const scoringSnapshots: Array<{
  event: AssembledContentInput["match_events"][number];
  home: number;
  away: number;
  leaderBefore: "home" | "away" | "draw";
  leaderAfter: "home" | "away" | "draw";
}> = [];
```

しかし `ScoreTimeline` 型（`lib/llm/types.ts:42-59`）に含まれておらず、**関数内で使われた後に捨てられている。** 新たに計算する必要はなく、**既にあるものを型に載せてプロンプトへ渡すだけ**で解決する。

## スコープ

対象:
- `lib/llm/types.ts` — `ScoreTimeline` に全得点時点の累計を持つフィールドを追加
- `lib/llm/stages/assemble.ts` — `computeScoreTimeline` が `scoringSnapshots` 相当を返すようにする
- `lib/llm/prompts/generate-recap.ts` — `scoreTimelineBlock` で全得点時点の累計を出力し、**LLM に算術をさせない**旨を明示
- 上記に対応するテスト

対象外:
- **`generate-preview.ts`**（プレビューは試合前なので得点経過が存在しない）
- `lead_changes` / `winning_score` / `ht_home` / `ht_away` の**既存フィールドの削除・変更**（追加のみ）
- スコアの表記順（ホーム–アウェイ）を変えること。**表記順は変えず、累計を渡すことで計算ミスを防ぐ**
- `match_events` の取り込み・整合性（`fix-live-ingest-event-key-collision` の範囲。マージ済み）
- QA ステージ・`fabrication-guard.ts` の変更

## データモデル変更

**DB の変更なし。** `AssembledContentInput` 内の型のみ拡張する。

`ScoreTimeline` に以下を追加する（フィールド名は Codex の判断でよい）:

```ts
score_progression: Array<{
  minute: number;
  home: number;        // その得点直後の累計（ホーム）
  away: number;        // その得点直後の累計（アウェイ）
  team: "home" | "away";
  type: string;        // try / conversion / penalty_goal 等
  player: string | null;
}>;
```

得点の算出は既存の `pointsForEvent`（`assemble.ts` 内）をそのまま使う。**新しい計算式を書き起こさないこと。**

## API サーフェス

**新規ルートなし。** 内部の型とプロンプト文字列のみ変更する。

## UI サーフェス

**変更なし。**

## LLM 連携

パイプライン **3 段階目（ナラティブ生成）**のプロンプトに渡す情報を増やす。

**新規の LLM 呼び出しは増えない。** プロンプトが数百トークン長くなるが、**リトライが減る分でむしろコストは下がる見込み**（今回は reject により 3 回の生成が無駄になっている）。

モデル ID は直書きせず `lib/llm/models.ts` を参照すること。

## 受け入れ条件

### データ

1. `computeScoreTimeline` の戻り値に、**得点が入ったすべての時点**の累計スコアが含まれる
2. 各要素に「分・その時点の home 累計・away 累計・得点したチーム・イベント種別」が含まれる
3. 得点にならないイベント（`substitution` / `yellow_card` 等）は含まれない
4. 累計の算出に既存の `pointsForEvent` を使っている（**新しい計算式を書かない**）
5. **ペナルティトライが 7 点で計算される**（`type: "try"` ＋ `is_penalty_try`。5 点にしてはならない）
6. 既存の `ht_home` / `ht_away` / `lead_changes` / `winning_score` / `final_home` / `final_away` が従来どおりの値を返す（回帰なし）
7. イベントが 0 件の試合では従来どおり `null` を返す

### プロンプト

8. `scoreTimelineBlock` が全得点時点の累計を出力する
9. 出力に**「本文で使うスコアはこの表の値をそのまま使い、自分で加算しないこと」に相当する明示的な指示**が含まれる
10. スコアの表記が「ホーム — アウェイ」の順であることが**明示されている**（どちらが先か分かるよう、表内でチーム名を併記する）
11. 既存の `lead_changes` / `winning_score` の出力は残す（重複してよい。**リード変化は分析の骨格として引き続き有用**）
12. `PROMPT_VERSION` が上がっている

### テスト

13. 日本 vs オーストラリア第2戦と同じ得点経過（5/7/8/17/18/26/27/34/39/40/51/52/58/60/73/74/75/76/81/82 分）を入力したとき、**イベントごとの累計が正しく出る**ことのテスト。**トライとコンバージョンは別イベントなので、それぞれの直後の累計を検証する**:
    - 34 分（日本 try）: **14–17**
    - 39 分（豪州 try）: **19–17**
    - 40 分（豪州 conversion）: **21–17**

    （初版は「39 分時点が 21–17」と書いていたが誤り。try と conversion を合算した値だった）
14. ペナルティトライを含む入力で 7 点として累計されることのテスト
15. 得点にならないイベントが混ざっても累計に影響しないことのテスト
16. `pnpm test` と型チェックが通る

### 段階実行（本番反映時）

17. **全件再生成をしない。** まず**アウェイチームが主役になる試合 1 件**（例: 8/15 日本 vs オーストラリア第2戦、`f01f68e2-bdd6-47c8-8910-0ea37a382b0a`）で recap を再生成し、Owner が以下を目視検品する:
    - 前半終了時が 21-17（豪州リード）と正しく書かれている
    - 途中経過のスコアがすべて実際の累計と一致する
    - QA verdict が `publish` に到達している
18. 検品通過後に、他の試合へ広げるかを Owner が判断する。Codex は 1 件目の結果を報告して止まること

## 未解決の質問

1. **今回の reject には、スコア計算とは別の指摘も含まれていた。**「前戦の『8月8日』『オーストラリアが35-32で勝利』といった情報は、提示された sourced_facts および試合データに含まれていません」。第1戦の情報が入力に無いのに本文に書かれており、**結果的に事実と合っているが根拠がない**（捏造にあたる）。本 spec の対象外とするが、**連戦シリーズでは前戦の情報を入力に含めるべきか**は別途検討が必要
2. 「選手別得点統計が match_events と矛盾しています」という指摘も出ていた。`fix-qa-player-stat-script-mismatch` 系の既存ガードによるものとみられるが、本 spec の修正後も残るかは再生成して確認する
3. スコアの表記順そのもの（常にホーム先）を、記事の主役チーム基準に変える案もある。**本 spec では採用しない**（表記順を動的にすると別の混乱を生む）。累計を渡すことで計算ミスが消えるかを先に確認する
