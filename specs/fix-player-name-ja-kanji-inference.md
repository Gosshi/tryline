# 選手名バックフィルがローマ字から漢字を推測する

## 背景

`fix-player-name-ja-coverage.md`（PR #720）で追加した `tools/backfill-player-name-ja.ts` を、2026-08-23 に本番で試し焼き（`--limit=20`、DB 非書き込み）した。

**外国籍選手の読みは狙いどおりだった。**

| 元の `name` | 生成された `name_ja` |
|---|---|
| Romain Taofifénua | ロマン・タオフィフェヌア |
| Théo Attissogbé | テオ・アティソグベ |
| Duarte Torgal | ドゥアルテ・トルガル |
| Darcy Rae | ダーシー・レイ |
| Francois Cros | フランソワ・クロ |

アフリカーンス語・フランス語・ポルトガル語の考慮が効いている。**この部分は変更しない。**

### 問題1: ローマ字から漢字を推測している

| 元の `name` | 生成された `name_ja` |
|---|---|
| **Yoshimitsu Yasue** | **安江祥光** |
| **AsaeliAi Valu** | **アサエリ愛・ヴァル** |

**ローマ字から漢字は一意に決まらない。** 「Yoshimitsu」の漢字は祥光・義光・吉光・良光など無数にあり、モデルが選んだ1つに根拠はない。

**これは捏造である。** しかも `players.name_ja` に書き込むと固定され、以後すべての記事に使われ続ける。カタカナの揺れより深刻な劣化になる。

なお日本代表11名の漢字表記は `feat-preview-player-kanji-glossary.md`（PR #600）で**検証済みのデータからバックフィル**している。**漢字は確定できる情報源から入れる**のが既定の方針であり、LLM の推測はこれに反する。

`AsaeliAi Valu` は元データも壊れている（正しくは `Asaeli Ai Valu`）。壊れた入力をそのまま漢字化している。

### 問題2: すでに日本語の選手にも LLM を呼んでいる

候補選択（`tools/backfill-player-name-ja.ts:138-143`）は `name_ja` が空かどうかしか見ていない。

```ts
.from("players")
.select("id, name, name_ja, team:teams!players_team_id_fkey(country)")
.or("name_ja.is.null,name_ja.eq.")
```

**`name` が既に日本語の選手が除外されていない。**

本番実測（2026-08-23）。

| 区分 | 人数 |
|---|---|
| `name` が既に日本語 | **646**（うち漢字 364 / カタカナのみ 282） |
| ローマ字で `name_ja` 未設定 | 1,799 |
| 合計 | 2,456 |

試し焼きでも `ハニテリ・ヴァイレア`（三菱重工相模原ダイナボアーズ）と `ディック・ウィルソン`（トヨタヴェルブリッツ）が対象に入り、**同じ文字列がそのまま返ってきた**。無害だが呼び出しの26%が無駄であり、さらに**漢字を持つ364人は問題1の危険に晒される**。

### 国籍で判定してはいけない

「日本人選手を除外する」を国籍やチームで判定する方式は破綻する。

- マイケル・リーチは日本代表だが名前はローマ字
- `Asaeli Ai Valu` はトンガ系の日本代表
- `Yoshimitsu Yasue` は `players.team_id` が null で国が引けない
- リーグワンには外国籍選手が多数いる

**名前や所属から国籍を推し量る heuristic を作らないこと。**

## スコープ

対象:

- `name` が既に日本語の選手を候補から除外する
- 生成結果がカタカナ以外を含む場合にスキップする

対象外:

- **外国籍選手の読みの生成ロジック。** 試し焼きで妥当性を確認済み。**触らない**
- **日本人選手の漢字表記を入れること。** 確定できる情報源が必要で、本 spec の範囲外
- 壊れた `name`（`AsaeliAi Valu` 等）の修正。**別途データ品質の問題**
- 重複した選手行の統合
- 全件バックフィルの実行

## データモデル変更

**なし。**

## API サーフェス

### 1. 候補選択の絞り込み（`tools/backfill-player-name-ja.ts:138-143`）

`name` が日本語文字（ひらがな・カタカナ・漢字）を含む選手を候補から外す。

**646人が対象外になる。** 呼び出しが減り、漢字を持つ364人に触れる危険も消える。

### 2. 出力の文字種による採否（`parseGeneratedPlayerNames`、同 `:81-120`）

**本 spec の中核。**

生成された `name_ja` が**カタカナ・長音符・中黒・空白のみ**で構成される場合だけ採用し、**ひらがな・漢字・ラテン文字を含む場合はスキップする**（その選手の `name_ja` は空のまま残す）。

**モデルが漢字を出したこと自体が「日本人名を推測している」というシグナルである。** それをそのまま検出条件に使う。国籍データも heuristic も要らない。

判定の期待値:

| 生成結果 | 判定 |
|---|---|
| ロマン・タオフィフェヌア | 採用 |
| テオ・アティソグベ | 採用 |
| 安江祥光 | **スキップ**（漢字） |
| アサエリ愛・ヴァル | **スキップ**（漢字） |

**実装上の注意。** 現在 `parseGeneratedPlayerNames` の末尾に `generated.length !== candidates.length` の件数一致チェックがある。スキップを導入すると件数が合わなくなるため、**この検査の扱いを見直すこと。** 「モデルが返さなかった」と「文字種で弾いた」は区別できる必要がある。前者は従来どおりエラー、後者は正常なスキップとして扱う。

### 3. スキップの可視化

試し焼きの出力で、**何人がどの理由でスキップされたか**が分かること。Owner が検品するときに「漢字が出たので弾いた人数」を把握できる必要がある。

## UI サーフェス

なし。

## LLM 連携

**新規の LLM 呼び出しは追加しない。** むしろ候補が646人減るぶん**呼び出しが減る**。プロンプトは変更しない（外国籍選手の読みは既に妥当なため）。モデル ID は直書きせず `lib/llm/models.ts` の `MODELS.FAST` を参照すること。

## 受け入れ条件

1. `name` に日本語文字（ひらがな・カタカナ・漢字）を含む選手が候補に含まれない。
2. 生成結果が `安江祥光` のとき、その選手はスキップされ `name_ja` が更新されない。
3. 生成結果が `アサエリ愛・ヴァル` のとき、同じくスキップされる。
4. 生成結果が `ロマン・タオフィフェヌア` / `テオ・アティソグベ` のとき、採用される。
5. 中黒・長音符を含むカタカナ名が誤ってスキップされない。
6. モデルが候補の一部を返さなかった場合は、従来どおりエラーになる（**文字種スキップと区別できている**）。
7. 試し焼きの出力に、スキップされた人数と理由が表示される。
8. 既存 `name_ja` を上書きしない挙動が維持されている（PR #720 の結果）。
9. べき等性が維持されている。
10. 外国籍選手向けの生成プロンプトが変更されていない。
11. `pnpm lint` / `pnpm tsc --noEmit` / `pnpm test` / `pnpm build` がすべて clean。
12. **全件バックフィルは実施しない。**

## 未解決の質問

1. **日本人選手の漢字表記をどう入れるか。** 本 spec ではスキップして空のまま残す。現状（記事ごとにカタカナが変わる）から悪化はしない。**確定できる情報源**（JRFU・リーグワン公式等）からのバックフィルが本筋だが、経路の確保が別途必要。

2. **壊れた `name` が他にもあるか。** `AsaeliAi Valu` のようにスペースが欠落した行が他にどれだけあるか未調査。取り込み経路の問題であり、**選手名の表記より先に直すべき可能性がある。**

3. **カタカナのみ282人の扱い。** `name` が既にカタカナの選手（リーグワン等）は候補から外れるが、**その表記をそのまま `name_ja` へ複製すべきか**は判断が要る。複製すればグロッサリに載り、記事の表記が安定する。**本 spec では扱わないが、安価に効く可能性がある。**
