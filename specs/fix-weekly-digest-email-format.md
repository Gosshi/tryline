# 週次メールが Markdown を生表示し、チーム名が英語で、内容が薄い

## 背景

**2026-08-31 21:39 JST、週次ダイジェストのメールが初めて実配信された。** PR #734（`fix-weekly-digest-cron-method.md`）で GET/POST 不一致を直して以来はじめてで、`project_retention_surfaces_delivery` に記録した「再訪の受け皿3つが全て配信ゼロ」のうち1つが動き出した。

**しかし届いたメールに3つの問題がある。**

### 1. Markdown が生のまま表示される

実際に届いたメールの本文（抜粋）:

```
# 【今週の海外ラグビーまとめ】南アフリカがニュージーランドを撃破…

## グレイテスト・ライバルリー・ツアー オールブラックス 南アフリカ遠征

### South Africa 33–26 New Zealand

→ [試合レビュー（日本語）](https://www.trylinerugby.com/matches/12d74f1b-…)

---
```

`#` `##` `###` `[text](url)` `---` が**すべて記号のまま見えている**。

**原因は経路の取り違えである。**

```
SYSTEM_PROMPT（route.ts:34）
  「note.com への投稿原稿を生成してください」
  「出力形式: Markdown形式（# タイトル, ## 見出し, [text](url) リンク）」
        ↓
   同じ1つの出力を2経路へ
        ├→ Discord に「note 原稿（コピペ用）」として投稿（:228）  ← Markdown が正しい
        └→ メールへ text として送信（:237）                    ← Markdown が壊れる
```

`lib/newsletter.ts` は **`text`（プレーンテキスト）しか持たない**（`:10` の型定義、`:121` の送信）。`html` フィールドが無い。

**購読者が受け取る最初のメールがこれである。**

### 2. チーム名が英語

`South Africa 33–26 New Zealand` / `Argentina 21–27 Australia`。

**大会名は日本語なのにチーム名だけ英語**という不整合が起きている。原因はクエリにある（`route.ts:183-185`）。

```
home_team:teams!… ( name )          ← name のみ
away_team:teams!… ( name )          ← name のみ
competition:competitions!… ( family, name_ja )   ← name_ja を取っている
```

**`teams.name_ja` は91チームすべてに入っている**（`project_seo_katakana_gap`、2026-08-10 実測）。取っていないだけである。

### 3. 内容がスコアの言い換えで終わっている

```
南アフリカがニュージーランドを33-26で下しました。
ラグビー界を代表するライバル同士の一戦は、7点差の熱戦となりました。
```

**2文目が1文目を言い換えているだけ。** `feedback_note_content_density` の「数字は1文で終わらせず、その数字が何を意味するかを続ける」に反する。

**材料は DB にあるが、生成器に渡っていない。** `buildUserPrompt`（`:99-105`）が渡すのは試合ごとのスコア・チーム名・大会名だけで、**`match_events` / `match_sourced_facts` / `match_content` を一切参照していない**。

同じ週末の試合について、DB には次があった。

| データ | 実測 |
|---|---|
| `match_events`（南ア×NZ） | 17件（コリシの38分トライ、コルビの7本のキック等） |
| `match_sourced_facts`（recap） | 8件（デュトイの100キャップ、入場者数56,589人、コリシ・サベアの試合後コメント） |
| `match_content`（recap） | 公開済み・2,605字 |

**いずれも使われていない。**

### D017 との関係（本 spec の起点）

このプロンプトは「**note.com への投稿原稿**を生成してください」と指示している。しかし **note の週次B型は D017（2026-08-15）で停止済み**である。

`project_growth_channel_decision` に未完了として記録がある。

> **routine「note週次まとめドラフト」の停止が必要**

**停止漏れが、初回配信で実体として現れた。** D017 の停止理由は「note が悪いのではなく X のリーチ不足で母数が無い」であり、note referral は2ヶ月連続で外部ユーザー0（2026-08-31 実測）。

**Owner 判断（2026-09-01）: note 原稿の生成をやめ、この生成器をメール専用にする。** これにより Markdown を出力する理由がなくなり、問題1が構造的に消える。

## スコープ

対象:
- `app/api/cron/weekly-digest/route.ts` の `SYSTEM_PROMPT` を**メール本文向け**に書き換える
- 同ルートの Discord への「note 原稿」投稿を**やめる**
- 同ルートのクエリに `teams.name_ja` を追加し、`buildUserPrompt` で日本語チーム名を渡す
- `buildUserPrompt` が渡す試合データの拡充

対象外:
- **`lib/newsletter.ts` の HTML 対応。** メール向けに生成すれば Markdown が出なくなるため不要。**HTML 化は行わない**
- **メールの購読・配信・レート制限の仕組み**（`feat-email-capture-newsletter.md` / `lib/newsletter-rate-limit.ts`）
- **cron のスケジュール**（月曜 21:00 JST = 12:00 UTC のまま）
- **対象試合の選定ロジック**（先週末土日・終了済み・リーグワン除外）。`feat-weekly-digest-cron.md` のまま
- フッター・配信停止リンク（`getEmailFooter`）
- **note への再進出**。D017 を覆さない
- iOS Push / Web Push

## 修正内容

### 1. Discord への note 原稿投稿をやめる

`postToDiscord` による「📋 note 原稿（コピペ用）」の投稿（`:228`）を削除する。

**`DISCORD_WEBHOOK_WEEKLY_DIGEST` の扱いは実装時に判断してよい**が、以下のどちらかであること。

- 環境変数ごと使わなくなるなら、参照を残さない
- 配信結果の通知に転用するなら、**note 原稿ではないことが明確な文面**にする

**「念のため残す」で note 原稿を送り続けないこと。** D017 に反する。

### 2. プロンプトをメール本文向けに書き換える

現行は「note.com への投稿原稿」「Markdown形式（`#` `##` `###` `**太字**` `[text](url)`）」と指示している。

**メールはプレーンテキストで送られる。** 次を満たすこと。

- **Markdown の記法を出力させない。** `#` による見出し、`[text](url)` リンク、`**太字**`、`---` を使わせない
- **URL は裸で書く。** `→ https://…` のように、そのままクリックできる形にする
- 見出しが必要なら、記号に頼らない表現（空行・全角の区切り等）にする
- タイトル行は残す（メールの件名は `lib/newsletter.ts:120` で固定なので、本文冒頭の見出しは内容の要約として機能する）

**「Markdown を使うな」と書くだけでは不十分である。** LLM は指示に反して記法を出すことがあるので、**出力後に検証する**こと（後述）。

### 3. 日本語チーム名を渡す

クエリに `name_ja` を追加する。

```
home_team:teams!matches_home_team_id_fkey ( name, name_ja )
away_team:teams!matches_away_team_id_fkey ( name, name_ja )
```

`buildUserPrompt` では **`name_ja` があればそれを使い、無ければ `name` にフォールバック**する。大会名が `competition?.name_ja ?? "大会名未設定"` としている流儀に揃える。

**`name_ja` は91チームすべてに入っているが、新規チームでは null になりうる。** フォールバックを省略しないこと。

### 4. 試合データを拡充する

`buildUserPrompt` に、試合ごとの以下を追加する。

- **`match_events`**: 分・種別・得点者・チーム。得点経過が分かる
- **`match_sourced_facts`**（`content_type = 'recap'`）: 試合後コメント・記録・入場者数など

**`match_content`（recap 本文）は渡さないこと。** 設計不変条件「スクレイプした生テキストは再配信しない」と同じ理由で、**生成済み記事の再利用は重複コンテンツを生む**。事実データから書かせる。

**捏造対策は現行の制約を維持する。**

> スコア・選手名・開催地は提供データのみ使う（推測・捏造厳禁）

拡充したデータについても同じ制約が効くよう、プロンプトに明記すること。

### 5. 内容の密度

「スコアの言い換えで終わらせない」ことを制約に加える。

- 数字を出したら、**その数字が何を意味するかを続ける**
- 試合ごとに、得点経過または試合後の事実から**1点以上の具体**を入れる

## LLM 連携

**段階は増やさない。** 既存の1回の生成呼び出しのまま、入力データとプロンプトを変える。

入力が増えるためトークン数は増加する。**週1回・試合数は通常2〜10件**なので影響は限定的だが、**変更前後の概算トークン数を PR 本文に書くこと**。

## 受け入れ条件

1. Discord への「note 原稿（コピペ用）」投稿が行われない
2. `SYSTEM_PROMPT` から Markdown 記法の指示（`#` 見出し・`[text](url)`・`**太字**`）が消えている
3. プロンプトに**メール本文であること**が明示されている
4. **生成結果に Markdown 記法が含まれないことを検証する仕組みがある。** 少なくとも行頭の `#`、`[…](…)` 形式のリンク、`---` の区切りを検出できること
5. 検証に引っかかった場合の挙動が定義されている（再生成・記法の除去・エラーのいずれか。**黙って配信しないこと**）
6. クエリが `teams.name_ja` を取得している
7. `buildUserPrompt` が `name_ja` を優先し、**null のときに `name` へフォールバックする**
8. `buildUserPrompt` に `match_events` が含まれる
9. `buildUserPrompt` に `match_sourced_facts`（`content_type='recap'`）が含まれる
10. **`match_content` の本文を渡していない**
11. 捏造禁止の制約が、拡充したデータにも及ぶことがプロンプトに明記されている
12. 「スコアの言い換えで終わらせない」制約がプロンプトにある
13. cron のスケジュールに差分が無い
14. 対象試合の選定ロジックに差分が無い
15. `lib/newsletter.ts` に差分が無い
16. `lib/newsletter-rate-limit.ts` に差分が無い
17. **サンプル出力（実データ or 固定データ）が PR 本文に貼られ、Markdown 記法が無いことが目視で確認できる**
18. 変更前後の概算トークン数が PR 本文にある
19. `pnpm lint` / `pnpm tsc --noEmit` / `pnpm test` / `pnpm build` がすべて clean

## 効果の測定方法

**次回配信（2026-09-07 21:00 JST）で Owner が実際に受信し、以下を確認する。**

- Markdown 記法が本文に無い
- チーム名が日本語
- 各試合にスコア以外の具体が1点以上ある
- リンクがクリックできる

**開封率・クリック率は `feat-newsletter-funnel-instrumentation.md`（PR #735）の計測に従う。** 本 spec では判定に含めない（購読者数が少なく統計にならないため）。

## 未解決の質問

- **`DISCORD_WEBHOOK_WEEKLY_DIGEST` の今後。** note 原稿をやめると用途が無くなる。配信結果の通知に転用するか、環境変数ごと廃止するかは Owner 判断
- **メールの HTML 化。** 本 spec ではプレーンテキストのまま整える。将来 HTML にする場合、`lib/newsletter.ts` に `html` を足し、Markdown → HTML の変換を入れることになる。**購読者数が増えてから判断する**
- **件名の固定。** `lib/newsletter.ts:120` で「【Tryline】今週の海外ラグビーまとめ」に固定されている。毎週同じ件名は開封率に不利な可能性があるが、実測が無いため本 spec では触らない
- **試合が0件の週。** 現行は Discord に何も送らない仕様（`feat-weekly-digest-cron.md`）。メールも送らないのか、別文面を送るのかは未定義。**閑散期に無音になる**
