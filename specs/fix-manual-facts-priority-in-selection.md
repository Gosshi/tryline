# 手動入力の事実を生成に優先して渡す

## 背景

**Owner が調査して入れた事実24件のうち、生成に渡ったのは1件だけだった。**

2026-09-07 の日本×カナダで実測した結果である。

```
lib/llm/sourced-facts/fetch.ts:383-384
.order("fetched_at", { ascending: false })
.limit(MAX_STORED_FACTS)   // = 8
```

**新しい8件しか渡らない。** そして `fetch-sourced-facts?force=true` は自動取得を毎回取り直すため、**自動側の `fetched_at` が実行時刻に更新され、手動を押し出す。**

| 順位 | 種別 | `fetched_at` |
|---|---|---|
| 1〜6 | 自動 | 09-07 06:44（再生成時に取り直し） |
| 7 | 自動 | 09-07 04:25 |
| 8 | **手動** | 09-06 11:51 |
| **9〜24** | **手動16件** | **落ちる** |

**手動入力は一度入れたら `fetched_at` が動かない**（自動再取得の削除対象から除外されているため）。一方**自動は再生成のたびに最新化される。** **再生成するほど手動が押し出される構造になっている。**

### 落ちた内容

エディー・ジョーンズのコメント、稲場巧の初トライの本人談、**公式 Player of the Match が確認できなかったという記録**、モール／スクラム／ラインアウトの文脈、テストマッチ連敗を4で止めた事実。

**`docs/chatgpt-prompts/` の運用で「自動で取れない層を優先して集めよ」と指示している、まさにその層が落ちている。**

## スコープ

対象:
- `loadSourcedFactsForMatch`（`lib/llm/sourced-facts/fetch.ts:370`）の**選択順序**
- あわせて、**allowlist フィルタを上限適用より前に移す**（後述）

対象外:
- **`MAX_STORED_FACTS` の値の変更。** 8 のまま
- 自動取得（`fetchSourcedFactsForMatch`）の変更
- 手動入力の経路（Discord）の変更
- プロンプトテンプレートの変更
- `supabase/`

## 影響範囲

**`loadSourcedFactsForMatch` は `lib/llm/stages/assemble.ts:965` の1箇所から呼ばれ、プレビュー・レビューの両方・全大会に効く。**

**すべての生成の入力が変わる。** 慎重に扱うこと。

## 1. 手動を優先して選ぶ

**選択の順序を次のとおりにすること。**

1. **`metadata.entry_method === "manual"` の事実を先に取る**（`fetched_at` の降順）
2. 枠が余ったら自動取得の事実で埋める（`fetched_at` の降順）
3. 合計で `MAX_STORED_FACTS` 件

**手動が8件以上ある場合、自動は1件も渡らない。** これは意図した挙動である。**Owner が調査して入れたものを、自動取得より優先する。**

**`isManualSourcedFact`（同ファイル `:72`）を判定に使うこと。** 判定条件を新しく書かない。

## 2. allowlist フィルタを上限より前に適用する

**現状はフィルタが上限適用の後にある。**

```
.limit(MAX_STORED_FACTS)   ← 先に8件に切る
...
const allowedRows = rows.filter(...)   ← そのあと除外
```

**除外された分だけ枠が空のまま生成に渡っている。** ログの `Excluded N non-allowlisted cached fact(s)` が出ている試合では、実際には 8 − N 件しか渡っていない。

**フィルタを先に適用し、そのうえで上限まで取ること。** 8枠が実際に8件で埋まるようになる。

**これは意図的な変更である。** プロンプトに渡る事実が増える試合があるが、**もともと設計が意図していた件数（8）に届くようにするだけ**である。

## 実装方法

**DB 側で `metadata->>entry_method` を並び替えに使うより、必要十分な件数を取得して JS で並べ替えるほうが単純である。**

- 1試合あたりの事実は実測で最大24件程度
- `confidence` の絞り込み（`high` / `medium`）は現行どおり DB 側で行う

**ただし方法は問わない。** 上の条件を満たせばよい。

## LLM 連携

**プロンプトに渡る事実の中身と件数が変わる。** モデル・テンプレートは変更しない。

**プロンプト長が増える試合がある。** 上限は 8 件のままなので増加は限定的だが、**QA の字数条件と干渉しないことを確認すること。** 過去にプロンプトの字数予算と QA の最低字数が矛盾し、297件が draft 化して本番から消えた事故がある（`project_regen_length_incident`）。

## 受け入れ条件

1. **手動の事実が自動より先に選ばれる**
2. 手動どうしの順序が `fetched_at` の降順である
3. 自動どうしの順序が `fetched_at` の降順である
4. **手動が `MAX_STORED_FACTS` 件以上あるとき、自動が1件も含まれない**
5. 手動が0件のとき、**現行と同じ結果になる**（自動のみ・`fetched_at` 降順）
6. 合計件数が `MAX_STORED_FACTS` を超えない
7. **`MAX_STORED_FACTS` の値が 8 のままである**
8. **allowlist フィルタが上限適用より前に行われている**
9. 除外が発生した試合で、**8枠が自動取得の事実で埋まる**
10. `confidence` の絞り込み（`high` / `medium`）が現行どおり
11. `content_type` の絞り込み（対象 + `shared`）が現行どおり
12. **`isManualSourcedFact` を判定に使っている**（新しい判定を書いていない）
13. 除外件数のログ（`Excluded N non-allowlisted cached fact(s)`）が引き続き出る
14. `fetchSourcedFactsForMatch` に差分が無い
15. `lib/llm/stages/assemble.ts` に差分が無い
16. `supabase/` に差分が無い
17. テストが次を覆っている:
    - 手動3件＋自動10件 → 手動3件が先、自動5件で合計8件
    - 手動10件 → 手動8件のみ、自動は0件
    - 手動0件 → **現行と同じ結果**（回帰テスト）
    - allowlist 外の自動が混ざる → 除外され、枠が別の事実で埋まる
    - allowlist 外でも手動なら渡る（既存の例外を維持）
18. `pnpm lint` / `pnpm tsc --noEmit` / `pnpm test` / `pnpm build` がすべて clean

## 検証方法

**本番で 2026-09-05 の日本×カナダのレビューを再生成し、手動入力の事実が本文に反映されることを確認する。**

現在この試合には**手動24件・自動7件**が入っている。修正後は**手動8件が渡る**はずである。

確認するのは次の2点。

1. `cron-post-match-recap-refresh` を 2026-09-05 指定で回す
2. **本文にエディー・ジョーンズのコメントか、モール／スクラム／ラインアウトの文脈のいずれかが入る**

**マージ後、デプロイが READY になってから実行すること。**

## 未解決の質問

- **手動が多い試合で自動の事実が完全に締め出される。** 本 spec ではそれを許容する設計にしているが、公式記録（反則数・出場記録）が落ちる可能性がある。**運用してから、枠を分ける（例: 手動5＋自動3）必要があるか判断する**
- **`MAX_STORED_FACTS = 8` が適切か。** 本 spec では変更しない。増やす場合はプロンプト長・コスト・QA 字数条件への影響を先に測る必要がある
