# 試合ページ ビジュアル刷新（feat-match-page-redesign）

## 背景

現状の試合詳細ページ `/matches/[id]` は「全面的にグレーの角丸カードを縦積み」した構成で、視覚的な階層も個性もなく、テンプレ感が強い（Owner 評価）。Tryline の価値は LLM 生成の日本語プレビュー/レビューにあるが、現在の UI ではそれが「のっぺりしたカードの中のテキスト」に埋もれ、掴みも回遊も弱い。

本仕様書は **既存コンポーネントの再スタイルによるビジュアル刷新** を対象とする。データモデル・パイプライン・クエリの作り直しは行わない。採用する視覚方向は `docs/design/mock-1-soft-v3.html`（案1「やわらかモダン」v3）を基準ビジュアルとする。

**基準モック / 参照:**
- 採用: `docs/design/mock-1-soft-v3.html`（レビュー・本文ありの A レイアウト）
- 比較: `docs/design/mock-1-soft-v2.html`（本文なし・要約のみ）、`docs/design/mock-2-graphic.html`（不採用＝広告感）、`docs/design/mock-3-premium.html`（不採用＝訴求弱）
- 関連: `specs/p1-match-content-display.md`（本文表示の既存仕様）、`specs/p1-match-events-ingestion.md`（events スキーマ）、`specs/p3-recap-require-events.md`・`specs/fix-content-fabrication.md`（捏造ガード）

## データモデル変更

**なし。** 既存テーブル（`match_content`・`match_events`・`standings` 系・`matches`）と RLS をそのまま使用する。

## API サーフェス

新規 HTTP API・新規クエリの追加なし。既存の読み取りを流用する:

- `lib/db/queries/match-content.ts` … `getPublishedContentForMatch(matchId)`（`preview` / `recap` の `content_md_ja`）
- `lib/db/queries/match-events.ts` … 要点（キーモーメント）の根拠データ（`minute` / `type` / `metadata.player_name`）
- `lib/db/queries/standings.ts` … 「順位への影響」テーブル
- `lib/db/queries/matches.ts` … スコア・日時・会場・ステータス

既存の `Promise.all` による並列 fetch 構成を維持する。クエリ署名は変更しない。

### 引用ブロック（本文中）

- 本文 `content_md_ja` 内の **Markdown `blockquote`（`> …`）を引用ブロックとしてスタイル**する（モックの `.pull`＝薄赤背景の強調ボックス）
- レンダリングは既存方針どおり **素朴な Markdown のみ**（`rehype-raw` 不使用、XSS 防止を維持）
- 引用は本文の一部であり、**新しい構造化フィールド・新カラムを追加しない**

### 要点キーモーメントの主役選定（決定的ロジック・決定）

要点の主役カードは 1 つ。`match_events` のみから**決定的に**選ぶ（解釈を含めない）。既存 `match-events` クエリ結果に対する UI 側の導出関数として実装し、単体テスト可能にする（新データ・新クエリ不要）。

- **基本ルール**: events を時系列に走らせてランニングスコアを再構成し、**最終的な勝者がそれ以降一度もリードを譲らなかった最後の得点**（lead-clinching score）を主役とする。
- **ラベルは中立**: 「リードを広げた得点」「突き放した得点」等。**「勝敗を分けた瞬間」「分岐点」のような解釈断定は使わない**。表示可能なのは `minute`・`type`・`metadata.player_name`・スコア推移のみ。**局面語（ラインアウト/モール/スクラム等）は使わない**。
- **エッジケース**:
  1. 主役得点の `minute` が null → 分を出さずに表示（捏造しない）
  2. 一度もリードを譲らない圧勝 → 「初めて 2 スコア差（8 点超）に広げた得点」を主役にする
  3. トライ無し（PG のみ）→ PG イベントで成立
  4. 引き分け → 主役カードは非表示（チップのみ表示）
  5. **再構成したランニングスコアが最終スコアと一致しない（events 欠損）→ 主役カードを出さない**（`fix-score-event-integrity-check` / `fix-derived-stats-event-integrity-gate` の整合ゲートと同思想）
- **小チップ 2 つ**も events 由来に限定（例: 前半の最大リード＝導出、最初のシンビン＝`yellow_card` イベント。該当が無ければ省略）。

## LLM 連携

本 PR のパイプライン変更は **プロンプト 1 行のみ**。それ以外の段階・モデル・スキーマには触れない。

### 引用（pull quote）= 本文抜粋に限定（案①）

- `lib/llm/prompts/generate-recap.ts`（および preview 側プロンプト）に、**「本文中、最も重要だと判断した一文を 1 つだけ Markdown の `>` 引用にする」** 旨を 1 行追加する
- 引用は本文に実在する一文であり、QA（段階 4・事実グラウンディング）を**そのまま継承**する。引用専用の事実検証は追加不要
- **禁止**: events に存在しないプレー局面語（ラインアウト/モール/スクラム等を起点と断定する記述）、および「分岐点」「初めて勝ち方を手にした」のような新規の解釈断定を引用で新たに作らないこと（本文の事実水準を超えない）

### 要点（キーモーメント）= データ由来に限定

- **レビュー（試合後）**: `match_events` 由来の **得点事実のみ**で構成する。表現できるのは「`minute` 分・`type`（トライ/コンバージョン/PG/DG）・`metadata.player_name`・スコア推移」まで。
  - 例（可）: 「63分 ◯◯のトライで 23–16 に」「サモア 64分 シンビン（`yellow_card`）」
  - 例（不可）: 「ラインアウト・モールでトライ」「この試合の分岐点」← events に局面情報・分岐点判定は存在しない
  - `match_events` が空の試合は要点ブロックを**非表示**（recap 自体が events 必須＝`p3-recap-require-events` と整合）
- **プレビュー（試合前）**: 要点ブロックは **非表示**（決定・2026-06-23 修正）。events が無く、段階 2 の戦術ポイントは**公開データ（`match_content` 等）に保存されておらず既存クエリで取得できない**ため。`新規クエリ・データ変更ゼロ` を守るべく非表示とする。プレビューはスコアヒーロー＋見出しカード＋本文で構成。将来、戦術ポイントを永続化する別仕様が入れば再検討する

### 整合性

本制約は `fix-content-fabrication.md`・`p3-recap-require-events.md` の方針（スコアからの展開推測を事実として書かない）に整合する。UI 側で events 由来データと本文を併置する際、**本文に無い数値・局面を UI のラベルで新造しない**こと。

## 決定事項（2026-06-23）

着手前に Owner が決定済み:

1. **デザイントークン統合 = A案（サイト全体刷新）**: 既存 shadcn HSL トークンを新パレットに書き換え、サイト全体に適用。他サーフェスの視覚回帰是正と CWV（フォント）対策を含む。トークン/見た目の変更はインデックス（SEO）に影響しない（HTML/本文/URL は不変）。
2. **プレビュー時の要点ブロックは非表示**（決定・2026-06-23 修正）。段階 2 戦術ポイントは公開データ未保存で既存クエリ取得不可のため、`新規クエリ禁止` と両立させるべく非表示。要点は recap（events 由来）でのみ表示。戦術ポイント永続化は別仕様に切り出す。
3. **本文折りたたみ「続きを読む」は使ってよいが、全文を初期 DOM に残す**（SEO 上有利）。
4. **得点グラフ（`score-graph.tsx`）は残す**（再スタイルして本文の下に配置）。
5. **要点キーモーメントの主役は lead-clinching score の決定的ロジック**で選ぶ（上記「要点キーモーメントの主役選定」節）。
6. **試合終了後もプレビューは消さず、recap の下に折りたたみ（`<details>`・既定は閉じ）で残す**（決定・2026-06-23 修正）。全文は初期 DOM に含める（SEO）。ただし `<meta description>`／構造化データの主ソースは**レビュー優先**を維持し、終了後にプレビューが上書きしないこと。
