# 選手の解決を日本語表記でも行う

## 背景

**日本代表戦の得点経過が、選手を1件も解決できずに投入を止められている。**

2026-09-07 に JRFU の得点経過18件の解析は成功した（単調性・合計・見出しすべて通過）が、**`unresolved_players_all_skipped: 1` で投入されなかった。**

原因は `resolvePlayerId`（`lib/ingestion/events.ts:94`）である。

```ts
.eq("team_id", params.teamId)
.ilike("name", `%${params.playerName}%`)
```

**`players.name`（英語表記）だけを見ている。** JRFU が返すのは `岡部崇人`・`ベン・ガンター` という日本語表記なので、一致しない。

### 実測（2026-09-07）

| | |
|---|---|
| 日本の選手 | 81人。うち **`name_ja` を持つのは11人** |
| カナダの選手 | 43人。**`name_ja` は0人** |

`name_ja` の格納形式は **`岡部 崇人`（姓名の間に空白あり）**。JRFU は **`岡部崇人`（空白なし）**。

**空白の有無だけで一致しない。** `ilike '%岡部崇人%'` は `岡部 崇人` にマッチしない。

```
name_ja で JRFU 表記を検索した結果:
  岡部崇人         → 0件
  原田衛           → 0件
  ベン・ガンター    → 0件
```

## スコープ

対象:
- `resolvePlayerId` に**日本語表記による解決**を追加する

対象外:
- **既存の英語名による解決の変更。** `ilike("name", ...)` の挙動をそのまま残す
- `name_ja` のバックフィル（別の課題）
- JRFU 側のパーサ
- 曖昧一致時の方針変更（後述）

## 既存の挙動を壊さないこと

**`resolvePlayerId` は Wikipedia 由来のイベント取り込みでも使われている。** `upsertMatchEvents` を経由するすべての経路が影響を受ける。

**英語名による解決を先に試し、一致しなかった場合にのみ日本語表記を試すこと。** 既存の一致結果が変わってはいけない。

## 曖昧なときは null を返すこと（既存の方針を維持）

現行は `data.length === 1` のときだけ ID を返し、**0件でも2件以上でも null** を返す。

**この方針を日本語表記の解決にも適用すること。** 複数の選手が一致したら null を返す。

## 空白を無視して比較すること

**`name_ja` と入力の両方から空白を取り除いてから比較すること。**

- 半角空白・全角空白の両方を除去する
- 実データの `name_ja` は `岡部 崇人`（全角空白）である

**部分一致ではなく完全一致にすること。** 日本語の氏名は短く、部分一致では別人に当たる危険がある（例: `原田` が複数人いる場合）。

## 実装方法

**DB 側で空白を除去する式を書くより、チームの選手を取得して照合するほうが単純である。**

- チームの選手数は最大でも100人程度（実測: 日本81人・カナダ43人）
- `team_id` で絞れば1クエリで済む

**ただし方法は問わない。** 上の条件を満たせばよい。

## 期待される効果と限界

**2026-09-05 の日本×カナダで、日本側の主要選手が解決できるようになる。**

`name_ja` を持つ11人には、岡部崇人・原田衛・下川甲嗣・竹内柊平・齋藤直人など、この試合の得点者が含まれる。

**カナダ側は `name_ja` が0人なので、引き続き解決できない。** これは想定内である。`match_events.player_id` は nullable であり、**部分的な未解決は許容される。**

**`unresolved_players_all_skipped` のガードを抜けることが目的である。** 全件未解決という異常状態を脱すればよい。

## 受け入れ条件

1. **英語名（`players.name`）による解決が先に試される**
2. **英語名で一致した場合の結果が現行と同一である**
3. 英語名で一致しなかった場合にのみ、日本語表記（`players.name_ja`）による解決が試される
4. **`name_ja` と入力の両方から半角空白・全角空白が除去されて比較される**
5. **比較が完全一致である**（部分一致ではない）
6. **一致が1件のときだけ ID を返す。** 0件および2件以上では null
7. `name_ja` が null の選手が候補に含まれない
8. `team_id` で絞り込まれている
9. **`upsertMatchEvents` の呼び出し側に差分が無い**
10. `lib/scrapers/` 配下に差分が無い
11. `supabase/` に差分が無い（マイグレーションなし）
12. テストが次を覆っている:
    - 英語名で一致 → 現行どおり解決（**回帰テスト**）
    - 英語名で不一致・`name_ja` で一致（空白あり `岡部 崇人` ← 入力 `岡部崇人`）→ 解決
    - `name_ja` で2件一致 → null
    - `name_ja` が null の選手しかいない → null
    - 半角空白・全角空白の両方
13. `pnpm lint` / `pnpm tsc --noEmit` / `pnpm test` / `pnpm build` がすべて clean

## 検証方法

**本番で 2026-09-05 の日本×カナダのイベント投入が通ることを確認する。**

現在の状態（2026-09-07 時点）。

| | |
|---|---|
| `matches` | `finished` / `57-12` |
| `match_events` | **0件** |
| `match_content` recap/ja | **`draft`**（誤った本文が残っている） |
| 直前の実行 | `unresolved_players_all_skipped: 1` |

**マージ後、デプロイが READY になってから実行すること。**

確認するのは次の3点。

1. `unresolved_players_all_skipped` が **0** になり、`match_events` が18件入る
2. **日本側の得点者に `player_id` が入っている**（カナダ側は null でよい）
3. `cron-post-match-recap-refresh` を 2026-09-05 指定で回し、**レビューの前半スコアが 31–7** と書かれる

**3が満たされなければ `draft` のまま止めること。**

## 未解決の質問

- **`name_ja` のカバレッジが低い。** 日本81人中11人、カナダ0人。**本 spec はこれを改善しない。** 選手名の日本語表記のバックフィルは別課題（`project_player_name_ja_backfill`: 全2456人中23人）
- **`name_ja` を完全一致にする一方、英語名は部分一致のままである。** 一貫していないが、**英語名の挙動を変えると既存のイベント取り込みに影響するため本 spec では触らない**
