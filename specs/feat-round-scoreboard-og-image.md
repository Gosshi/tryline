# ラウンド全結果スコアボードのOG画像を自動生成する

## 背景

2026-07-08 の集客分析（Fable/Codex）で、X投稿のインプレッション向上策として「静的インフォグラフィック画像」（順位表・ラウンド全結果のスコアボード）が両者一致で推奨された。LLM不要・限界費用ゼロで増やせる施策として評価が高い。

現状、この種の画像は `x-post` スキルの「データ画像の作り方」に記載された**完全手動のプロセス**（スクラッチパッドにHTML作成 → `python3 -m http.server` でローカル配信 → Playwright MCP でスクリーンショット → `sips` でクロップ）で、Owner が週2〜3本ペースで都度作っている。

一方、既存の `/api/og/route.tsx` には試合の OGP 画像生成基盤（`type=competition`・`type=result` の分岐、`@vercel/og` の `ImageResponse` を使用）が既にあり、単一試合のスコアカードは自動生成できている。**複数試合をまとめた「大会1ラウンド分の全結果」画像は存在せず**、この部分だけ手作業が残っている。

本specは、既存の `/api/og` 基盤を拡張し、この手作業を自動化する。

## スコープ

対象:
- `app/api/og/route.tsx` に新しい `type=round-scoreboard` 分岐を追加し、指定した大会・ラウンドの全試合結果（スコアのみ）を1枚の画像にまとめて生成する
- `lib/seo/og-image.ts` に、この新しい画像タイプ用の呼び出しヘルパー（例: `createRoundScoreboardOgImage`）を追加する
- 画像のデータソースは `matches.home_score` / `away_score` **のみ**を使う（`x-post` スキルの既定方針を踏襲。イベント集計〈トライ王ランキング等〉は、イベント汚染事故の教訓により対象外）
- Owner が特定の大会・ラウンドを指定してこの画像URLを取得できる仕組み（管理用エンドポイントまたはスクリプト。実装方法はCodexの裁量）

対象外:
- 順位表（standings）画像の自動生成（本specはスコアボードのみ。順位表画像は別途、内容が固まってから spec 化する）
- X への自動投稿（`fix-disable-x-auto-post.md` により自動投稿は停止済み。本specは画像生成のみで、投稿はOwnerが手動で行う既存運用を変更しない）
- `match_events` 由来の統計（トライ数・カード等）を使った画像（対象外、スコアのみ）

## データモデル変更

なし。

## API サーフェス

`app/api/og/route.tsx` の既存 `GET` ハンドラに `type=round-scoreboard` 分岐を追加。クエリパラメータ例: `?type=round-scoreboard&competition_id=<uuid>&round=<number>`（既存の `competition`/`result` タイプのパラメータ命名規則に倣う）。

## 実装詳細

### 1. 画像レイアウト

`x-post` スキルの「データ画像の作り方」に記載された既存の手動デザイン方針を踏襲する:
- 大会名・ラウンド番号を見出しに
- 各試合を1行（ホームチーム・スコア・アウェイチーム）で縦に並べる
- 勝者は色＋太字＋アクセント色のティックバーで示す（数字だけでなく形でも状態を示す）
- 日本語フォントはWebフォント読み込み不可の `@vercel/og` 制約を踏まえ、`route.tsx` 内の既存フォント指定パターンに合わせる

### 2. データ取得

指定した `competition_id` + `round` に紐づく `matches`（`home_score`/`away_score`が両方 not null の finished 試合のみ）を取得し、画像に埋め込む。

### 3. 既存パターンの再利用

`app/api/og/route.tsx` の `type=result`（169行目付近）の背景グラデーション・フォント指定等のスタイル定数をそのまま流用し、新規デザインをゼロから作らない。

## LLM 連携

なし。

## 受け入れ条件

1. `/api/og?type=round-scoreboard&competition_id=<uuid>&round=<number>` にアクセスすると、該当ラウンドの全試合結果（スコアのみ）を1枚にまとめた1200×630（または投稿用に適したサイズ）の画像が返る
2. 対象試合が0件（未終了・データ無し）の場合、エラーにならず適切なフォールバック（空表示または404）を返す
3. 生成される画像が `matches.home_score`/`away_score` 以外のデータ（`match_events` 由来の集計等）を一切使わない
4. `pnpm tsc --noEmit` / `pnpm lint` / `pnpm test` / `pnpm build` が通る
5. 実装後、`x-post` スキルの「データ画像の作り方」セクションに、この自動生成URLを使う新しい手順を追記できる状態になっている（スキル自体の更新は本spec完了後にOwnerまたは別途対応）

## 未解決の質問

- 画像サイズ（1200×630のOGP標準比率か、X投稿に最適な正方形・縦長比率か）はOwnerの好みによる。実装時に選択肢を提示するか、まずOGP標準比率で作り、後で調整可能な設計にしてよい
- Owner がこの画像URLをどう取得するか（管理画面のUIか、スクリプト実行で都度URLを組み立てるだけで十分か）は、運用の手間を最小化する方向でCodexの裁量に委ねる。迷う場合は質問として提示してほしい
