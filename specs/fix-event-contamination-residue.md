# 得点イベント汚染の残り（6 試合）の除去と、検知・取り込みの穴をふさぐ

## 背景

2026-09-24 の人名監査の調査中に、**別の試合の得点イベントがコピーされたまま残っている試合が 6 つ**あることを Claude Code が確認した（本番 DB の読み取りで確認）。

| 書き込み（UTC） | 本来の持ち主（スコアとイベント合計が一致） | コピーが入った試合（スコアと合わない） |
|---|---|---|
| 2026-07-12 06:54:40〜55 | ニュージーランド 34-32 フランス（`e13e388d`、18 件） | アルゼンチン 38-47 スコットランド（`42bebc1f`）、南アフリカ 45-21 イングランド（`b5b2af27`）、フィジー 24-39 ウェールズ（`8504834e`）、オーストラリア 31-33 アイルランド（`59513a57`）、日本 27-10 イタリア（`f56e9ee9`）。いずれも 18 件、合計 34-32 |
| 2026-09-06 10:12:32〜38 | 日本 32-35 オーストラリア（`2c276057`、19 件） | オーストラリア 56-17 日本（`f01f68e2`）。19 件、合計 32-35 |

- **どれも、分・種別の並びが持ち主と完全に一致**し、チームの割り当てだけが試合ごとに付け替えられている。コピー側の選手 ID は、ほぼすべて空（0〜2 件）。
- **原因:** 書き込みの時刻に、定期実行「Cron — Fill Event Gaps」が動いていた（7/12 06:54:30 開始、9/6 10:12:03 開始。`gh run list` で確認）。
  - 定期実行の入口 `app/api/cron/fill-event-gaps/route.ts:72-83` の `extractEventHtml` は、`wikipedia_event_id` が無いときや、ページ内に見つからないときに、**ページ全体の HTML** を返す。
  - それを `parseMatchEventsFromVeventHtml` に渡すため、同じページの別の試合のイベントが入った。
  - 手動実行用の `scripts/fill-event-gaps.ts:177-191` はこの問題を直してある（`null` を返し、`findEventBlockByTeams` で探し直す、#410・#412）。定期実行の入口にだけ直しが入っていない。
- **すでに入っている対策（今回の範囲外）**
  - 書き込み時のスコア照合（`lib/ingestion/event-integrity.ts`、2026-09-07 `38259c7`）で、同じ汚染は今は弾かれる。2 回の汚染はどちらもこの照合より前。
  - 画面の表示（`components/match-events-section.tsx`、2026-09-06 `21d6d2b`）は、スコアと合わないイベントを隠し、「得点経過は確認中です」と出す。**今は誤ったイベントは表示されていない。** 誤った表示が出ていたのは、Nations Championship の 5 試合で 7/12〜9/6、`f01f68e2` で 9/6 の数時間。
  - 記事生成の整合ゲートは、スコアと合わない試合の生成を止める。
- **残っている穴**
  1. **汚染した行が消されていない。** 6 試合の試合ページは「確認中」のままで、正しいイベントを取り直す段取りにも進めない。
  2. **重複の検知が、コピーの一部を拾えない。** `lib/data-integrity/contaminated-events.ts:54` の並びは `type|minute|player_id` なので、選手 ID のある持ち主と、ID が空のコピーは別物になる。2026-09-20 の週次監査（`cron-audit-data-integrity`）の出力では、`8504834e` の重複は「2 試合」とだけ出ていて（ID が空のコピー同士）、持ち主と、ID が 2 件あるコピー（`59513a57`、`b5b2af27`）は同じ組として出ていない。
  3. **定期実行の入口は、今もページ全体を解析に渡す。** 書き込み時の照合が最後の安全網として働くが、入口そのものも手動スクリプトと同じ動きにしておく。

## スコープ

**対象**
1. 重複の検知に、選手 ID を使わない並び（分と種別）での比較を足す。汚染と判定するのは「同じ並びの組の中で、イベント合計が自分のスコアと合わない試合」だけにする。
2. `scripts/cleanup-contaminated-events.ts` を、この判定で動くようにする（削除は、今までどおり `--confirm-owner-approved` のときだけ）。
3. 定期実行の入口の `extractEventHtml` を、手動スクリプトと同じ動き（見つからなければ取り込まない。チーム名と日付で 1 つに絞れたときだけ使う）にする。関数は共通化する。
4. 週次のデータ整合監査が、同じ判定で汚染を報告する。

**対象外**
- 6 試合の正しいイベントの取り直し。削除のあと、別の運用手順で行う（「マージ後の作業」を参照）。
- スコアとイベント合計が数点だけずれている試合（2026-09-24 時点で 155 試合。多くはコンバージョンの欠けなどの部分的な欠落）。別の問題として扱う。
- 公開済みのレビュー本文の見直し。Nations Championship の 5 試合のレビューは 7/4〜7/8 の生成で、7/12 の汚染より前だが、7 月初めの別の汚染事故（#479）と時期が重なる。取り直しのあとに本文を照合する。
- 画面の表示と書き込み時の照合（対策済み）。

## API サーフェス

### 1. 検知（`lib/data-integrity/contaminated-events.ts`）

- 新しい関数 `buildStructuralEventSignature(events)`: 選手 ID とチームを使わず、`type|minute` をソートして連結したハッシュ。`minute` が null のイベントを含む試合は対象にしない（並びが決まらないため）。
- 新しい関数 `findStructuralContamination(matches)`:
  - 入力は、試合ごとのイベント（`type`、`minute`、`team_id`）と、スコア（`home_score`、`away_score`）、ホームとアウェイのチーム ID。
  - 構造の並びが同じで、**イベントが 8 件以上**の試合の組を作る（件数の少ない試合の偶然の一致を避けるため、既存の 4 件より厳しくする）。
  - 組の中で、イベント合計（既存の点数の数え方。ペナルティトライは 7 点）が自分のスコアと一致する試合を「持ち主」、一致しない試合を「汚染」とする。
  - 持ち主がいない組（全員が不一致）も、全員を汚染として返す。
  - 戻り値: `{ signature, owners: matchId[], contaminated: matchId[], eventCount }[]`。
- 既存の `findContaminatedEventGroups` と `buildEventSignature` は残す（既存の呼び出し元を壊さない）。

### 2. 片付けのスクリプト（`scripts/cleanup-contaminated-events.ts`）

- 既存の判定に加えて、`findStructuralContamination` の `contaminated` を削除の対象にする。**`owners` の試合のイベントは、どちらの判定でも削除しない。**
- 既定は dry-run。削除の対象を試合ごとに一覧で出す（試合、スコア、イベント合計、件数、持ち主の試合）。
- `--confirm-owner-approved` のときだけ削除する。削除の前に、対象の試合のイベントを JSON で `tmp/contaminated-events-backup/<ISO 時刻>/` に書き出す。
- 公開済みのレビューがある試合は、今までどおり一覧に印を付ける（`hasPublishedRecap`）。

### 3. 定期実行の入口（`app/api/cron/fill-event-gaps/route.ts`）

- `scripts/fill-event-gaps.ts` の `extractEventHtml`（`null` を返す版）と `findEventBlockByTeams` を `lib/ingestion/`（例: `lib/ingestion/wikipedia-event-block.ts`）に移し、スクリプトと定期実行の入口の両方から使う。
- 定期実行の入口では、次のようにする。
  - `wikipedia_event_id` のブロックが見つかれば、それを使う。
  - 見つからなければ、`findEventBlockByTeams` でチーム名と日付から 1 つに絞れたときだけ使う。
  - どちらでもなければ、その試合は取り込まずに次へ進む。応答に「スキップした試合と理由」を足す。
- **ページ全体を解析に渡す経路を、どこにも残さない。**

### 4. 週次のデータ整合監査

- `cron-audit-data-integrity`（`/api/cron/audit-data-integrity`）が使う `lib/data-integrity/audit.ts` の重複検知で、`findStructuralContamination` の結果も報告する。
- 報告の形: 汚染と判定した試合ごとに、持ち主の試合の ID と、公開済みのレビューがあるかどうか。

## 受け入れ条件

1. **構造の並びで汚染を見つける。**
   - 前提: 持ち主（イベント 18 件、選手 ID あり、合計がスコアと一致）と、同じ分・種別の並びで、選手 ID が空、チームの割り当てが違い、合計がスコアと合わない試合を 2 つ。
   - 期待: 1 つの組として返り、`owners` が持ち主の 1 試合、`contaminated` が残りの 2 試合。
   - 確認方法: 並びに選手 ID を含めると、このテストが落ちること。
2. イベントが 7 件の試合同士は、並びが同じでも組にしない。
3. **スコアと一致する試合は、並びが同じでも汚染にしない**（`owners` に入る）。
4. `minute` が null のイベントを含む試合は、構造の並びの比較に入らない。
5. **片付けのスクリプト:**
   - dry-run では何も削除しない。
   - `--confirm-owner-approved` では `contaminated` の試合のイベントだけを削除し、削除の前にバックアップの JSON を書く。
   - `owners` の試合のイベントは削除しない。
   - いずれも Supabase のクライアントをモックにして確かめる。
6. **定期実行の入口:**
   - `wikipedia_event_id` が無く、ページに試合のブロックが 2 つある HTML では、チーム名と日付で一致する 1 つだけを解析する。
   - 一致するものが無ければ `upsertMatchEvents` を呼ばず、応答のスキップの一覧に理由付きで載る。
   - 確認方法: 見つからないときにページ全体を返す実装に戻すと、このテストが落ちること。
7. 週次監査の出力に、構造の並びで見つけた汚染が含まれる（モックの DB で確かめる）。
8. `pnpm lint`、`pnpm typecheck`、`pnpm test` が通る。**3 つとも実行して、結果を完了報告に含める。**

## マージ後の作業

9. **Claude Code:** 片付けのスクリプトを dry-run で実行し、削除の対象が次の 6 試合だけであることを確かめて、Owner に一覧を示す。
   - 対象: `42bebc1f`、`b5b2af27`、`8504834e`、`59513a57`、`f56e9ee9`、`f01f68e2`
   - 持ち主の `e13e388d` と `2c276057` が対象に入っていないこと。
   - 対象が 6 試合より多い場合は、削除に進まず内容を報告する。
10. **Owner:** 一覧を確認して、`--confirm-owner-approved` で実行する（削除を伴うので、Claude Code は実行しない）。
11. **正しいイベントの取り直し:** 6 試合について、取り直しの方法を別に決める。
    - Nations Championship 第 1 節の 5 試合は、`scripts/backfill-nations-championship-match-events.ts`（既存）を使う想定。
    - オーストラリア 56-17 日本は、JRFU の取り込み（#778）を使う想定。
    - 取り込みは書き込みを伴うので、Owner か Codex が行う。
12. **Claude Code:** 取り直したあと、Nations Championship の 5 試合の公開済みレビューの本文を、正しいイベントと照合する。
