# QA に直近5試合の個別スコアが渡らず、DB 実測どおりの記述が事実根拠で減点される

## 背景

2026-08-21 03:47 JST、南アフリカ vs ニュージーランド第1テスト（match_id: `d6d5b1ab-58ec-44c8-a31d-54fadc0a662e`）の preview が QA に reject された。事実根拠は 3/5 で、指摘がこれ。

```
直近5試合の対戦相手・スコアや8月22日という日付は、提示された許可済み事実には含まれていません
```

**本文が挙げた 10 件のスコアを本番 DB で全件照合したところ、すべて完全に一致した。**

**捏造ではない。QA の過検出である。**（同じ指摘に含まれる「8月22日」のほうは実際に誤りだが、原因も対処も別で、`fix-narrative-kickoff-date-utc-leak.md` が扱う。）

### 前身 spec との関係

`fix-qa-prompt-missing-form-and-match-metadata.md`（2026-08-08、commit `4727c15` で実装済み）が、まさに同種の過検出を直している。同 spec の背景には、同じ大会の別試合で「入力データにない直近5試合の戦績・平均得点、大会名、会場情報を断定しています」と指摘された事例が記録されている。

**その修正で QA に渡るようになったのは集計値だけである。** `lib/llm/prompts/qa-content.ts:13-18`

```ts
export type TeamFormStats = {
  avg_points_against_last_5?: number | null;
  avg_points_for_last_5?: number | null;
  record_last_5?: string | null;
  win_rate_last_5: number | null;
};
```

`formStatsBlock`（同 185-192 行）も、この 4 つを JSON 化して出すだけ。

```ts
const formStatsBlock =
  Object.keys(formStats).length === 0
    ? ""
    : [
        "## form_stats grounding",
        "以下は直近の試合データから機械的に算出された実数値です。本文がこれらの直近フォーム（戦績・平均得点）に言及している場合、入力データに基づく正当な記述として扱い factual_grounding を下げないこと。",
        JSON.stringify(formStats),
      ].join("\n");
```

**「平均45.4点」は検証できるが、「ウェールズに43-0」は検証できない。** 個別の対戦相手名とスコアが QA の入力に存在しないためである。

### 生成側は個別スコアを持っている

`generate-preview.ts:158` のデータスパース指示にこうある。

```
- recent_form の直近5試合スコアから攻撃力・守備力・連勝/連敗ストリークを読み取り本文に反映すること
```

**生成側は `recent_form` で個別スコアを見ており、そう書くよう指示までされている。QA だけが集計値しか見ていない。**

前身 spec が指摘した「生成側は持っているが判定側からは見えない」という非対称が、**一段深いレイヤーで残っている。** 前身 spec の受け入れ条件 5 は「値の出どころが生成側と同一であることをテストで担保する」と定めていたが、担保されたのは集計値についてのみだった。

### 影響範囲

**直近フォームを個別スコアで語る記事はすべて対象になる。** そしてそれは `dataSparseBlock` が明示的に推奨している書き方である。ラインアップが未確定な preview ほどこの書き方に寄るため、**良い記事ほど落ちやすい構造**が前身 spec の指摘どおり残っている。

## スコープ

対象:

- `QaMatchContext` に直近5試合の個別結果（対戦相手・スコア・ホーム/アウェー）を追加する
- それを QA 判定プロンプトのブロックとして出力する
- `lib/llm/pipeline.ts` の QA 呼び出しで、**生成側と同一の出どころから**配線する

対象外:

- 既存の集計値（`win_rate_last_5` / `avg_points_*` / `record_last_5`）の削除・改名。前身 spec の結果を維持する
- プログラム側ガード（`containsUnsupportedStatistic`）の判定ロジック変更。`fix-qa-win-rate-false-positive.md` と `fix-qa-team-stats-new-fields-unsupported.md` の結果を維持する
- 採点ルーブリックの閾値変更
- sourced_facts 0 件時の指示文（`qa-content.ts:111-114`）。**この指示自体は正しい**
- 生成プロンプトの変更
- 日付の UTC ずれ（`fix-narrative-kickoff-date-utc-leak.md`）
- sourced_facts の反映密度（`fix-preview-sourced-facts-underuse.md`）
- h2h（直近対戦成績）の QA への配線。**本文が h2h に言及して落ちた実例がまだ無いため、憶測で広げない**

## API サーフェス

### 1. `QaMatchContext` の拡張（`lib/llm/prompts/qa-content.ts`）

直近5試合の個別結果を保持するフィールドを追加する。

**フィールド名と構造は、`assemble` ステージの `recent_form` が既に持っている形に揃えること。** 新しい名前を発明せず、実装時に `lib/llm/stages/assemble.ts` の該当型を実読してから決める。前身 spec の API サーフェス節も同じ指示を出している。

最低限、判定に必要なのは以下。

- 対戦相手のチーム名（本文と同じ日本語表記であること。英語名だと照合できない）
- 自チームの得点と相手の得点
- ホーム / アウェーの別

### 2. 判定プロンプトへのブロック追加

`formStatsBlock` と**同じ形式**で追加する。既存ブロックの文面を踏襲すること。

- 「本文がこれらの個別試合結果（対戦相手・スコア）に言及している場合、入力データに基づく正当な記述として扱い factual_grounding を下げないこと」
- 値が空のときはブロックを出力しない（既存ブロックと同じ挙動）

**既存の `formStatsBlock` は残す。** 集計値と個別結果は別の記述を裏づけるため、どちらも必要。

### 3. 配線（`lib/llm/pipeline.ts`）

QA 呼び出しの `matchContext` 構築箇所で、拡張したフィールドを渡す。

**値の出どころは生成側と同一にすること。** 生成プロンプトが参照している `assembled.recent_form` をそのまま QA にも渡す。QA 用に DB を引き直すと、前身 spec と本 spec が二度直した「生成側と判定側が別の入力を見る」構造がまた再発する。

### 4. `PROMPT_VERSION`

`qa-content.ts:11` の `PROMPT_VERSION`（現在 `qa@2.6.0`）を上げること。

## 未解決の質問

1. **QA の issues に字数の矛盾が出ている。** 今回の通知には「本文は1500字以上で、字数要件を満たしています」と「本文が目標字数の下限未満です」が同一リストに並んでいた。実測 1,468 字なので前者が誤りである。

   `lib/llm/stages/qa.ts:485-486` は `measureContentLength(...) < lengthRequirement.min` で決定的に判定し、同 573-575 行のコメントは「プログラム側が字数の single source of truth」と明言している。**したがって判定自体は正しく、誤っているのは LLM が `issues` に書き足した文言のほう。**

   ただし Discord 通知に矛盾した2文が並ぶため、Owner のトリアージを妨げる（実際に「なんだろう」から調査が始まっている）。**LLM 由来の字数言及を `issues` から落とすのが妥当か、別 spec の候補。** 本 spec のスコープには含めない。

2. **対戦相手名の表記ゆれ。** 本文は `name_ja`（「ウェールズ」「ストーマーズ」）で書く。`recent_form` が英語名を保持している場合、QA が照合できず本 spec の効果が出ない。**実装時に `recent_form` の実データで日本語表記が入っていることを確認すること。** 入っていなければ、`japanese_name_glossary` と同じ経路で日本語名を解決する必要がある。

3. **前身 spec で個別スコアが漏れた理由。** 前身 spec は「平均得点は型にもガードにも判定プロンプトにも一切存在しない」と集計値の欠落を正確に特定したが、個別スコアには触れていない。同種の欠落が他のフィールド（h2h、順位表、ラインアップ）にも残っている可能性がある。**本 spec では憶測で広げないが、3 度目の同型事故が起きたら QA 入力と生成入力の差分を機械的に検出する仕組みを検討する価値がある。**
