# 記事の品質チェックの誤検知と、抽出の数値誤りを減らす

## 背景

記事プロンプトの A/B 比較（2026-09-24、`tmp/prompt-ab/2026-09-24T12-01-00-107Z/`）で、両方の版に共通する問題が見つかった。どれも本文の良し悪しとは関係なく、**正しい記事を作り直しに回す**、または**本文に誤りを持ち込む**。

直近 30 日の QA による作り直し率は、プレビュー 41%、レビュー 35%（`docs/chatgpt-prompts/gpt6-content-prompt-audit-2026-09-24.md` の 3.2）。作り直しは 1 回あたり $0.04〜0.055 と 30〜40 秒かかる。URC の開幕で、9/25 から週末ごとの記事数が増える。

公開済み記事の人名監査（2026-09-24、`tmp/entity-audit/entity-grounding-audit-2026-09-24T12-19-59-707Z.json`）でも 115 本が検出されたが、出典付きの事実に載っている選手（例: 9/5 のモンペリエ 対 ポーのプレビューの「ビリー・ヴニポラ」）も含まれており、3 と同じ種類の誤検知が混ざっている。

## スコープ

**対象**
1. QA に `h2h_last_5` と `kickoff_at_jst` を根拠として渡す。
2. 選手別の得点を照合するガードで、蹴った選手名が記録されていないチームのキックの本数・合計得点を比べない。
3. 人名照合で根拠なしになった表記を、もう一度だけ狭い問いで照合し直す。
4. `key_stats` に、コードで数えた勝敗数・連続の回数・試合数を足し、抽出プロンプトには自分で数えたり計算したりせずにその値を使うよう指示する。

**対象外**
- QA の採点基準（ルーブリック）の見直し。GPT-6 監査の 4.3 で提案されたもの。
- 他のガード（試合時間、未裏付け統計、ゼロ矛盾、ポジション語）の誤検知。GPT-6 監査の 4.1・4.2。
- 本文プロンプト（A と B）の文言。
- 公開済み記事の修正。

## API サーフェス

### 1. QA に渡す根拠（`lib/llm/prompts/qa-content.ts`、`lib/llm/pipeline.ts`）

- `QA_GENERATION_FIELD_DISPOSITIONS` の `h2h_last_5` を `"grounded"` にする。`QA_GROUNDING_CONTEXT_FIELDS` と `QaMatchContext` に `h2h_last_5` を足す。
- `buildQaContentPrompt` に `h2h_last_5` の grounding ブロックを足す。文言は `recent_form` のブロック（`:409-411`）と同じ形にする。
  - 「以下は両チームの直近の直接対戦の結果です。本文がこれらの日付・スコア・会場に言及している場合、入力データに基づく正当な記述として扱い factual_grounding を下げないこと。」
- `match_metadata` に `kickoff_at_jst` を足す。
  - 文言: 「本文がこれらの大会名・会場・日本時間のキックオフ日時に言及している場合、〜」
- `pipeline.ts` の QA の `matchContext` に、`usable.h2h_last_5` と `usable.match.kickoff_at_jst` を渡す。
- `qa@2.11.0` → `qa@2.12.0`

### 2. 選手別の得点ガード（`lib/llm/stages/qa.ts:434-456`）

- 照合の前に、チームごとに「キックの蹴った選手名が分かるか」を判定する。
  - `match_events` のうち、そのチームの `conversion`・`penalty_goal`・`penalty`・`drop_goal` に `player_name` が空のものが 1 件でもあれば、そのチームは「キッカー不明」とする。
- 照合する選手がキッカー不明のチームに属する場合、`conversions`・`penaltyGoals`・`totalPoints` は比べない。`tries` だけを比べる。
- 選手がどちらのチームに属するかは、`match_events` 上の、その選手のイベントのチームで決める。どのイベントにも出てこない選手（照合できない選手）の扱いは、今までどおり不一致とする。
- キッカーが分かっているチームの選手の比較は、今までどおりにする。

### 3. 人名照合のやり直し（`lib/llm/stages/verify-entities.ts`）

- `verifyNarrativeEntities` の 1 回目の結果で `ungroundedSurfaces` が 1 件以上ある場合、その表記だけを対象に**もう 1 回だけ**照合する。
  - プロンプト（`lib/llm/prompts/verify-entities.ts` に新しい関数を足す）は次の内容にする。
    - 対象の表記の一覧と、許可済み人物の一覧、sourced_facts を渡す。
    - 「各表記が、許可済み人物の誰かを日本語で書いたものかを判定する。カタカナ表記では、中点・ハイフン・スペースの有無、長音、ヴ／ブ、ティ／チなどの表記の揺れは同じ人物として扱う。判定できないものは null にする」
    - 出力は 1 回目と同じ JSON の形。
  - 2 回目で許可済み人物（または sourced_facts）に対応付けられた表記は、`ungroundedSurfaces` から外す。対応付けの判定は、1 回目と同じコードの条件（`parseEntityVerificationResponse` の許可集合・事実との照合）を通す。**LLM が名前を返しただけでは許可しない。**
  - 2 回目の呼び出しに失敗したら（例外、JSON 不正）、1 回目の結果をそのまま使う。**失敗を「許可」に倒さない。**
- 費用: 2 回目は根拠なしの表記がある記事だけで発生し、入力は短い（表記と許可リストと事実だけ）。1 回あたり $0.001 未満の見込み（gpt-5.6-luna）。
- `entity-verification@1.1.0` → `entity-verification@1.2.0`

### 4. `key_stats` の追加項目と抽出の指示（`lib/llm/stages/assemble.ts`、`lib/llm/types.ts`、`lib/llm/prompts/extract-tactical-points.ts`）

- `key_stats.home` と `key_stats.away` に次を足す。どれも `recent_form` から**コードで数える**。
  - `games_counted: number`（`recent_form` の試合数。最大 5）
  - `wins: number`、`losses: number`、`draws: number`
  - `current_streak: { result: "win" | "loss" | "draw"; count: number } | null`（最新の試合から数えて、同じ結果が何試合続いているか。試合がなければ null）
- 抽出プロンプトの `【禁止事項】` の後に、次のブロックを足す。
  ```
  【数値の扱い】
  - 勝敗数・連勝連敗・試合数は key_stats の wins / losses / draws / current_streak / games_counted の値をそのまま使う。recent_form から数え直さない。
  - 「直近5試合」と書けるのは games_counted が 5 のときだけ。5 未満なら「直近◯試合」と実際の数を書く。
  - 2 つの値の差・合計・比率を自分で計算して書かない。key_stats にある値だけを並べる。
  ```
- `extract@2.4.0` → `extract@2.5.0`
- 本文プロンプト（A）にも `key_stats` の JSON が入るので、項目の追加で A の結合プロンプトが変わる。A/B で保存した A のプロンプト（`tests/llm/__snapshots__/content-prompt-a-baseline.test.ts.snap`）を更新し、差分が `key_stats` の追加項目だけであることを PR 本文で示す。本文プロンプトの文言は変えないので、`preview@3.15.1` と `recap@4.21.0` はパッチ版を上げる（`preview@3.15.2`、`recap@4.21.1`）。

## LLM 連携

- 段 2（抽出）: プロンプトに数値の扱いを追加し、入力に項目を追加する。
- 段 4（QA・人名照合）: QA の根拠を 2 つ追加する。人名照合は、根拠なしの表記があるときだけ 2 回目を呼ぶ。
- モデルは変えない。

## 受け入れ条件

1. **QA が直近の対戦成績とキックオフ時刻を受け取る。**
   - `buildQaContentPrompt` の出力に、`h2h_last_5` の grounding ブロックと `kickoff_at_jst` が含まれることを確かめるテストがある。
   - `getQaGroundingCoverageGaps()` が空であること（既存のテストの形を保つ）。
2. **キッカー不明のチームでは、キックの本数を比べない。**
   - 前提: ホームのコンバージョンのイベントの `player_name` がすべて空で、ホームの選手 `Test Kicker` にトライ 1 本がある。
   - 本文から読み取った主張が `{playerName:"Test Kicker", tries:1, conversions:1, totalPoints:7}` のとき、ガードが発火しない。
   - 同じ前提で `{playerName:"Test Kicker", tries:2}` は発火する（トライの誤りは今までどおり捕まえる）。
   - キッカーが分かっているチームで、`conversions` を誤って主張した場合は発火する。
   - 確認方法: キッカー不明の判定を外すと、1 つ目のテストが落ちること。
3. **人名照合のやり直し。**
   - 1 回目で `{surface:"イザイア・アームストロングラヴラ", matched_entity:null}`、2 回目で `matched_entity:"Isaiah Armstrong-Ravula"`（許可済み人物）を返すモックで、最終の `ungroundedSurfaces` が空になる。
   - 2 回目が許可集合にない名前（例: `"Unknown Player"`）を返した場合は、根拠なしのまま残る。
   - 2 回目が例外を投げた場合は、1 回目の `ungroundedSurfaces` がそのまま返る。
   - 1 回目で根拠なしが 0 件なら、2 回目は呼ばれない。
   - 確認方法: 2 回目の結果をコードの条件を通さずに信じる実装にすると、2 つ目のテストが落ちること。
4. **key_stats の追加項目。**
   - `recent_form` が「勝・負・勝・勝・分」（新しい順）のとき: `wins:3, losses:1, draws:1, games_counted:5, current_streak:{result:"win", count:1}`。
   - 2 試合だけのとき: `games_counted:2`。
   - 試合がないとき: `games_counted:0`、`current_streak:null`。
   - 抽出プロンプトの出力に `【数値の扱い】` のブロックが含まれる。
5. A のプロンプトのスナップショットの差分が `key_stats` の追加項目だけで、テストが通る。
6. `pnpm lint`、`pnpm typecheck`、`pnpm test` が通る。**3 つとも実行して、結果を完了報告に含める。**

## マージ後の確認（Claude Code が行う）

7. A/B 比較の 4 つの入力を、新しいコードで固定し直し（抽出をやり直す。費用 $0.01 未満）、抽出の戦術ポイントに 4 件の誤りが再発しないかを見る。
8. 公開済みの記事の人名監査を、7〜9 月の検出分（27 本）に絞ってやり直し、誤検知がどれだけ減るかを見る（監査ツールに対象を絞る指定がなければ、そのための小さな変更を別に依頼する）。
9. マージ後 1 週間の QA による作り直し率を、直近 30 日（プレビュー 41%、レビュー 35%）と比べる。URC 開幕で記事の種類が変わるので、参考値として扱う。

## 未解決の質問

なし。姓だけの表記（例: 「ポラード」）の扱いは 1 回目の照合の既存の指示のままとし、2 回目では広げない（同じ姓の選手が両チームにいると取り違えが起こりうるため）。
