# プレビューの「核心」がデータの3分岐で機械的に決まり、その試合の見どころが書けない

## 背景

2026-08-21、南アフリカ vs ニュージーランド第1テストのプレビューを同じ素材で4回生成した。**4回とも冒頭が「5連勝」で始まった。**

```
18:45  5連勝中で直近5試合の平均得失点差も南アフリカが+33.0点…初戦で土をつけられるか
22:06  5連勝で平均得点45.4点・平均失点12.4点の南アフリカに、同じく5連勝で…
23:30  直近5試合をともに5連勝し平均45点超を記録する…
23:44  5連勝で直近5試合の平均得失点差が南アフリカ+33点…
```

**モデルの選択ではない。プロンプトがそう指定している。**

### 根本原因: `selectCorePattern` の3分岐

`lib/llm/prompts/generate-preview.ts:43-66`

```ts
function selectCorePattern(assembled: AssembledContentInput): CorePatternType {
  const phase = assembled.match_phase;
  if (phase === "playoff_final" || ... ) return "context";

  const homeStreak = assembled.key_stats.home.result_streak;
  const awayStreak = assembled.key_stats.away.result_streak;
  if (homeStreak === "winning" || homeStreak === "losing" ||
      awayStreak === "winning" || awayStreak === "losing") {
    return "form";
  }

  return "numeric";
}
```

両チームが5連勝中 → `result_streak === "winning"` → **「フォーム型」が確定する。**

そのとき出力される指示（同 `:80-84`）。

```
【フォーム型で書くこと】連勝/連敗ストリークや直近の状態変化を軸にする
例: 「5連勝中のBullsに、プレーオフ圏ギリギリのMunsterが土をつけられるか——フォームの差は数字ほど大きいか」
```

**18:45 版は例文の「土をつけられるか」をそのまま使っている。** 例文が模倣されている。

### この試合で「両者が連勝中」は最も平凡な事実だった

同じ試合の sourced_facts には以下が入っていた。**どれも本文の核心にならなかった。**

- 主将シヤ・コリシがハムストリング負傷で欠場、ピーター＝ステフ・デュトイが主将
- **その穴に入るポール・デ・ヴィリアスは、ニュージーランド戦が自身初のテスト出場**
- ニュージーランドはツアー中に4人を負傷で帰国させ、ベンチを3人入れ替えた
- **シリーズが引き分けなら、磁力で結合するトロフィーの2つの半分を両国で分け合う**
- ハンドレ・ポラードが試合登録23人から外れた

**3分岐に「チーム状況・ニュース型」が無いため、これらが核心になる余地が構造上存在しない。**

### 影響範囲は広い

`selectCorePattern` はデータで決定的に決まる。**連勝・連敗はごく普通に発生するため、多数のプレビューが同じ型で始まる。**

2026-06 の監査で「『得点力』冒頭が37%」という数字が出ている（`fix-recap-opening-variety.md` の背景）。症状は違うが、**プロンプトが冒頭の型を固定していることによる単調さ**という点で同根である。

### 過去2回の対処との違い（重要）

recap 側では同種の単調さに2度取り組んでいる。

| spec | やったこと | 結果 |
|---|---|---|
| `fix-recap-opening-variety.md` | 特定フレーズ（「得点力の差が注目」等）を `PROHIBITIONS_BLOCK` へ追加 | **モデルが別の紋切り型へ乗り換えて再発** |
| `fix-recap-opening-variety-v2.md` | フレーズではなく**冒頭文の構造**を禁止 | 実装済み |

v2 の背景にこう明記されている。

> 現行の対処法は「特定の禁止フレーズをリストに追加する」という対症療法であり、モデルが禁止されていない別の紋切り型フレーズに乗り換えるだけで再発する

**本 spec は禁止を足す方向では解かない。** 問題は禁じ方ではなく、**プロンプトが積極的に「これを軸にせよ」と指定していること**にある。禁止句・構造禁止をいくら足しても、指定された軸が変わらなければ冒頭は変わらない。

## スコープ

対象:

- 核心の問いを、その試合の入力（特に sourced_facts）から立てさせる
- 素材が乏しいときだけ既存の3パターンへ落とす
- プロンプト内の例文が模倣される問題への対処

対象外:

- **recap（`generate-recap.ts`）。** `fix-recap-opening-variety-v2.md` の結果を維持する。preview で方式が固まってから検討する
- 英語 preview
- セクション構成・各セクションの字数配分
- `lib/llm/content-length.ts`
- `PROHIBITIONS_BLOCK` への禁止句追加（**上記のとおり、この方向は既に2回失敗している**）
- 既存記事の再生成（マージ後に別途判断）
- QA の採点ルーブリック変更

## データモデル変更

**なし。マイグレーション不要。**

## API サーフェス

### 1. 核心の導出（`generate-preview.ts` の `buildCoreQuestionBlock`、43-108行）

sourced_facts に**その試合固有の出来事**（主将の欠場、初出場、大量の負傷離脱、シリーズの決着方式など）がある場合、**それを核心の候補として提示し、モデルに最も重要なものを選ばせる。**

- 3分岐（`context` / `form` / `numeric`）は**残す**が、**sourced_facts が乏しい場合のフォールバック**として位置づける
- 「連勝中である」だけを理由に `form` を強制しない
- 核心は **sourced_facts または DB 入力に根拠を持つこと**。根拠のない問いを立てさせない（捏造ガードとの整合）

**「ニュース型」という第4の分岐を機械的に選ばせる形にしないこと。** それでは分岐が3つから4つに増えるだけで、同じ問題が起きる。**選択の主体をモデル側へ移すことが要件。**

### 2. 例文の扱い

現行は各パターンに具体例を1つ与えており、**実際に模倣されている**（18:45 版の「土をつけられるか」）。

例文を残すか外すかは判断してよいが、**例文の言い回しがそのまま出力に現れない**ようにすること。手段は問わない（複数例を並べる、抽象化する、外す、等）。

### 3. `PROMPT_VERSION`

`generate-preview.ts` の `PROMPT_VERSION` を上げること。**現在値はコードを実読して確認する**（ローカルが古い可能性があるため、値をこの spec から書き写さない）。

## UI サーフェス

なし。

## LLM 連携

段階4（ナラティブ生成）のプロンプトのみ。

**新規 LLM 呼び出しを追加しない。** sourced_facts は既にプロンプトへ渡っている。コスト増はプロンプトが数行伸びる分のみ。モデル ID は直書きせず `lib/llm/models.ts` を参照すること。

## 受け入れ条件

1. `sourced_facts` が0件のとき、`buildGeneratePreviewPrompt` の出力に従来どおり3分岐のいずれかの指示が現れる。**修正前の挙動を固定する回帰テストを置くこと。**
2. 両チームが `result_streak: "winning"` かつ sourced_facts に主将の欠場を含む場合、出力が**「フォーム型で書くこと」だけを指定する状態になっていない**。
3. 同条件で、核心の候補として sourced_facts 由来の材料を参照する指示が含まれる。
4. 核心の問いが入力に根拠を持つことを要求する指示が含まれる。
5. プロンプト出力に、現行の例文（「5連勝中のBullsに、プレーオフ圏ギリギリのMunsterが土をつけられるか」等）がそのままの形では含まれない。
6. `match_phase` がプレーオフ系のとき、大会文脈を軸にする指示が引き続き出る（**この分岐は妥当なので壊さない**）。
7. `contentType: "recap"` のプロンプト出力が本変更の前後で一致する。
8. `preview` / `language: "en"` の出力が本変更の前後で一致する。
9. `PROMPT_VERSION` が上がっている。
10. `pnpm lint` / `pnpm tsc --noEmit` / `pnpm test` / `pnpm build` がすべて clean。
11. **既存記事の再生成は実施しない。** Codex の作業はコードとテストまで。

## 未解決の質問

1. **モデルに選ばせると出力の分散が増える。** 今日は同じ素材で4回生成し、字数1,451〜1,944字、情報密度2〜5と大きくばらついた。核心の選択まで委ねると分散はさらに広がりうる。**通知（`feat-content-notification-diagnostics.md`）と回帰検知が入った状態なので、悪化は検知できる。** 数週間運用して、分散が許容範囲かを判断する。

2. **「その試合固有の出来事」を機械的に定義できるか。** 本 spec は sourced_facts の内容判断をモデルに委ねている。「主将の欠場は重要、控えの入れ替えは些末」といった重み付けは決定的には書けない。**ここを機械化しようとすると、また3分岐と同じ硬直に戻る。**

3. **recap への展開。** recap は結果が確定しているため核心の立て方が異なる。`fix-recap-opening-variety-v2.md` が構造禁止で対処済みであり、**同じ改修をそのまま持ち込まないこと。** preview の運用実績を見てから判断する。

4. **今日の4版が実例として使える。** 本 spec の効果検証には、同じ試合（match_id `d6d5b1ab-58ec-44c8-a31d-54fadc0a662e`）で再生成し、冒頭が「5連勝」以外になるかを見るのが最も直接的である。素材は36件揃っている。
