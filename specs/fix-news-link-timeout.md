# ニュースリンク収集が 504 でタイムアウトする

## 背景

`fix-news-link-feed-coverage.md`（PR #731）で取得件数を13件から56件に増やしたところ、**次の実行が 504 で失敗した**（2026-08-26）。

```
2026-08-26T08:05:08Z  実行開始
2026-08-26T08:06:09Z  curl: (22) The requested URL returned error: 504
```

**ちょうど60秒で打ち切られている。** ルートの設定は `app/api/cron/collect-news-links/route.ts:14` の `export const maxDuration = 60`。

### 部分的には成功していた

タイムアウト前に処理された分は保存されている。

| ドメイン | 取得 | 紐付け | 通知 |
|---|---:|---:|---:|
| rnz.co.nz | 12 | 1 | 1 |
| nzherald.co.nz | 11 | 5 | 5 |
| **stuff.co.nz** | **8** | 8 | 7 |

Stuff は34件あるはずが**8件で止まっている**。ここでタイムアウトした。

**PR #731 の修正自体は正しく効いている。** Stuff は8件中8件、NZ Herald は11件中5件が紐付いており、通称辞書は機能している（修正前は13件中1件）。

### 原因

`app/api/cron/collect-news-links/route.ts` は、取得した全リンクを**単一の `for` ループで直列処理**している。

```ts
const links = await fetchNewsLinks();
for (const link of links) {
  const match = matchNewsLink(link.title, candidates);
  // upsert → 該当すれば LLM 翻訳 → Discord 通知
}
```

該当した記事1件ごとに「**LLM 翻訳 → Discord 送信**」が直列で走るため、**該当件数に比例して実行時間が伸びる**。加えて `fetchNewsLinks` は RNZ の `Crawl-delay: 7` を守るため待機する。

取得が4.3倍になった結果、60秒を超えた。**上限を設ける仕組みが無い。**

## スコープ

対象:
- `app/api/cron/collect-news-links/route.ts` の `maxDuration`
- 1回の実行で処理する件数の上限
- 上限に達した場合の挙動とレスポンス

対象外:
- **`lib/news-links.ts` のパース・照合・翻訳ロジック**（PR #731 で正しく動いている）
- **設計の境界。** 記事本文の取得・保存・LLM への投入は引き続き行わない
- Discord 通知フォーマット（**後続 spec が `match_id: <uuid>` 行に依存**）
- `news_links` のスキーマ変更
- 翻訳・通知の並列化（**本 spec では行わない**。理由は後述）
- 通知頻度（cron のスケジュール）の変更
- 新規ドメインの追加

## 1. maxDuration を 300 に上げる

`ingest-standings`（`app/api/cron/ingest-standings/route.ts:10`）が既に `maxDuration = 300` を使っており、**このリポジトリに前例がある**。同じ値にする。

**ただしこれだけでは不十分。** 件数がさらに増えれば同じ問題が再発する。次の上限と併用すること。

## 2. 1回あたりの処理件数に上限を設ける

**通知する件数に上限を設け、超えた分は次回に回す。**

- 上限は定数として持ち、変更しやすくする。**初期値は20件**
- 上限は「**通知した件数**」で数える。取得やスキップは数えない（該当しない記事は LLM も Discord も使わないため、時間をほとんど消費しない）
- 上限に達したら**残りのリンクの処理を打ち切る**

**取りこぼしは起きない。** cron は1日4回走り、`source_url` が UNIQUE なので既処理分は重複しない。未処理分は次回に持ち越される。

### 打ち切り時も保存は行うか

**行わない。** 上限に達した時点でループを抜ける。

理由は、保存だけして通知しないと `notified_at` が null のまま残り、**次回の実行で「未通知」として再評価される必要がある**が、現行の実装は毎回フィードを取り直すため、フィードから消えた記事は永久に通知されなくなる。

上限で打ち切れば、その記事は次回のフィードにまだ載っている可能性が高く、そのとき処理される。**単純な方が壊れにくい。**

## 3. レスポンスに打ち切りを示す

現行のレスポンスは次の形。

```json
{"fetched":13,"matched":1,"notified":1,"status":"ok"}
```

**上限で打ち切ったことが分かるフィールドを足す**（例: `"truncated": true`）。これが無いと「56件取得したのに20件しか通知されない」状態を、正常なのか異常なのか判断できない。

## なぜ並列化しないのか

翻訳と通知を並列にすれば速くなるが、本 spec では行わない。

- **Discord にレート制限がある。** 並列に投げると 429 を受ける
- **OpenAI の並列度も考慮が要る**
- **定常運用では件数が少ない。** 今回の56件は初回に溜まっていたぶんで、以降は前回からの差分のみ。1日4回走るので1回あたり数件に収まるはず

**まず上限で確実に完走させ、実運用で本当に遅いと分かってから並列化を検討する。** 早すぎる最適化を避ける。

## 受け入れ条件

1. `maxDuration` が 300 になっている
2. 1回の実行で通知する件数に上限があり、**定数として定義されている**（初期値20）
3. 上限は「通知した件数」で数える。該当しなかった記事は上限を消費しない
4. 上限に達したらループを打ち切り、それ以降のリンクを保存も通知もしない
5. レスポンスに打ち切りを示すフィールドがある
6. 上限未満で完了した場合、そのフィールドが打ち切りを示さない
7. `source_url` の UNIQUE により、次回実行で既処理分が重複しない
8. **`lib/news-links.ts` に差分が無い**（パース・照合・翻訳は変更しない）
9. Discord 通知フォーマットが変わっていない（**末尾の `match_id: <uuid>` 行を含む**）
10. `news_links` のスキーマに差分が無い
11. 上限に達するケースと達しないケースの両方にテストがある
12. `pnpm lint` / `pnpm tsc --noEmit` / `pnpm test` / `pnpm build` がすべて clean

## 未解決の質問

- **上限20件が妥当か。** 実運用で「毎回 truncated になる」なら上限が低すぎるか、フィードが多すぎる。**数回動かしてから判断する**
- **通知が多すぎないか。** 今回の実測では31件中14件が該当した。この比率が続くと1日あたりの通知数が多くなり、Owner が無視するようになる恐れがある。**該当率が高すぎる場合、フィルタを厳しくする（例: 今後7日以内の試合に限る）ことを検討する**
- **初回の滞留分。** 現在 Stuff は34件中8件しか処理できていない。上限を入れても、cron が数回走れば追いつく。急ぐなら手動実行を繰り返せばよい
