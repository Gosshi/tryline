# feat-style-guard-gated-rollout

## 背景

`feat-style-guard-shadow-mode.md`（先行spec）で計測した「AI文体判定を導入した場合のretry/reject率」をOwnerが確認し、導入可と判断した後に着手する第二段階。GPT-5.6の追加調査（2026-07-20）に基づき、既存のretry機構にそのまま乗せるのではなく、以下の安全策を組み込んだ形で導入する。

**前提条件: `feat-style-guard-shadow-mode.md` の計測結果をOwnerが確認済みであること。** 計測結果を見ずに本specへ着手しないこと。

## スコープ

対象:
- `japanese_quality` の公開閾値について、いきなり `>= 4` を必須にするのではなく、暫定条件として **`japanese_quality >= 4` または（`japanese_quality = 3` かつ 決定的スタイル違反なし）** を採用する。QAモデルの3と4の判定は揺れがあるため、決定的ガードと組み合わせることで誤検知の影響を緩和する
- AI文体定型句検出・類似度チェック（`feat-style-guard-shadow-mode.md` で実装済みのロジックを流用）を、**事実違反とは別の独立したretry予算**として扱う。既存の事実違反（`factualHardBlock` 等）は現行通り最大2回のretryを許容するが、**スタイル違反のみの場合はretryを最大1回に制限**する
- retry時、次のナラティブ生成プロンプトに**具体的な違反箇所をフィードバックとして渡す**（例: 「前回は『浮き彫りになった』を2回使用」「最終段落に新しい事実がない」「直近記事と冒頭の書き出しが類似」等）。単に温度を変えて同じプロンプトを再実行するのではなく、修正すべき箇所を明示する
- スタイル違反のみでretryしても改善しない場合、draft化する（reject/削除ではなく、既存のfail-closedパターンに従いdraftとして保持する）
- 判定基準をhard gate / soft gateに分離する:
  - **hard gate**（即retry対象）: メタコメント混入、入力にない人名・数字、禁止された引用、過去記事とほぼ同一の冒頭、明白な定型句の過剰反復、日本語として破綻している
  - **soft gate**（合計点方式、1項目だけでは即retryしない）: 接続詞の軽微な多用、段落長が均一、見出しの類似、`japanese_quality` が3か4か微妙なケース

対象外:
- `feat-style-guard-shadow-mode.md` で実装した検出ロジック自体の再実装（既存のものを流用する）
- note記事への適用（noteは別途 `note-weekly` ワークフローの見直しとして検討する。本specの対象外）
- 英語コンテンツへの適用

## LLM 連携

- スタイル違反によるretryは最大1回に制限されるため、既存の事実違反retry予算（最大2回）と合わせても、1試合あたりの追加コストは限定的（最大で追加1回のナラティブ生成、`MODELS.NARRATIVE`）
- retryプロンプトへの違反フィードバック追加は、プロンプト長を増やすがLLM呼び出し回数自体は増やさない

## 受け入れ条件

1. `japanese_quality = 3` かつ決定的スタイル違反なしの場合、publish判定になることを確認するテストがある（暫定条件の一部）
2. `japanese_quality = 3` かつ決定的スタイル違反ありの場合、retry（最大1回）になることを確認するテストがある
3. スタイル違反のみでretryが1回発生した後、2回目も違反が解消しない場合、draft化される（事実違反の2回retry予算とは別枠で消費されること）ことを確認するテストがある
4. retry時のプロンプトに、前回の具体的な違反内容（検出された定型句・類似記事の情報等）が含まれることを確認するテストがある
5. hard gate項目（人名捏造・禁止引用等）は即retry対象のまま、既存の挙動が変わらないことを確認する回帰テストがある
6. `pnpm test` / `pnpm tsc --noEmit` / `pnpm lint` が通る
7. 本番デプロイ後、reject率・draft化率の変化をOwnerに報告する

## 未解決の質問

- soft gateの合計点方式の具体的な閾値（何点でretry対象にするか）は、`feat-style-guard-shadow-mode.md` の計測結果を見てOwnerが決定する
- `japanese_quality >= 4` を将来的に完全なhard gate（暫定条件を外す）に移行するタイミングは、本spec導入後の運用実績を見てOwnerが判断する
