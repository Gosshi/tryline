# ログインモーダル: メールアドレスが送信できない問題を修正

## 背景

2026-08-16、本番でログインできない状態が報告された。モーダルには「エラーが発生しました。」とだけ表示される。

**Supabase の `auth_logs` を実測したところ、原因が確定した。**

```
timestamp: 2026-08-16T02:52:03 〜 02:52:14
path:      /otp
status:    400
error:     400: Unable to validate email address: invalid format
件数:      12 秒間に 21 件以上
```

**Supabase がメールアドレスを「形式が不正」として拒否している。** 画面に入力されていたのは一般的な Gmail 形式の正常なアドレスであり、**実際に送信された値が入力欄の見た目と異なっている**ことを意味する。

### 該当コード

`components/auth-modal.tsx:26-33`

```ts
const [email, setEmail] = useState("");

async function submit() {
  const supabase = getSupabaseBrowserClient();
  const { error } = await supabase.auth.signInWithOtp({
    email,                                                   // ← trim していない
    options: { emailRedirectTo: `${location.origin}/auth/callback` },
  });

  setState(error ? "error" : "sent");                        // ← エラー内容を捨てている
}
```

### 問題は 4 つ重なっている

| # | 問題 | 影響 |
|---|---|---|
| 1 | `email` を trim せずそのまま送信 | **直接の原因。** スマホのオートフィルやコピー＆ペーストで前後に空白・改行が混入すると 400 になる |
| 2 | 送信前のクライアント側バリデーションがない | 不正な値がそのまま外部 API へ渡る |
| 3 | `error ? "error"` でエラー内容を捨てている | 「エラーが発生しました。」しか出ず、**Owner にもユーザーにも原因が分からない** |
| 4 | 送信中の二重送信防止がない | 12 秒で 21 件のリクエストが発生している |

**3 が今回の調査を最も妨げた。** Supabase は `invalid format` と明確に返しているのに、その情報を捨てて汎用メッセージに変換していた。画面を見ただけでは原因にたどり着けない。

### 実害

メールニュースレターは 2026-08-10 から本番稼働している。**登録した購読者がログインできない状態が続いていた可能性がある。** サイトの中核機能（AI チャット、お気に入り、Premium）はすべてログインの先にあるため、影響は限定的ではない。

### エラー表示の方針（重要）

**エラー内容を具体的に出す。ただし、アカウントの存在有無を漏らしてはならない。**

Supabase の `signInWithOtp` は、存在しないアドレスに対しても成功を返す設計（ユーザー列挙対策）。したがって:

- **表示してよい**: 「メールアドレスの形式が正しくありません」（入力の問題）、「時間をおいてお試しください」（レート制限）、「通信に失敗しました」（ネットワーク）
- **表示してはならない**: 「そのアドレスは登録されていません」「アカウントが見つかりません」等、**登録済みかどうかが判別できる文言**

エラー種別の判定は Supabase が返す `error` オブジェクト（`status` / `message` / `code`）から行う。**判定できない場合は従来どおり汎用メッセージにフォールバックする**（未知のエラーで画面が壊れないこと）。

なお `signInWithOAuth`（Google）側も現在は同じ汎用表示なので、同様に扱う。

## 受け入れ条件

### 入力値の正規化

1. 入力の前後に半角空白がある（`"  user@example.com  "`）場合、trim された値が `signInWithOtp` に渡る
2. 入力の前後に全角空白・改行・タブがある場合も同様に除去される
3. 入力欄の表示値そのものは変更しない、または trim 後の値に揃える（**どちらでもよいが、送信される値と画面の値が食い違わないこと**）

### 送信前バリデーション

4. 空文字（または空白のみ）で送信ボタンを押した場合、**API を呼ばず**にエラーメッセージを表示する
5. `@` を含まない等、明らかに形式が不正な値では **API を呼ばず**にエラーメッセージを表示する
6. バリデーションは過度に厳格にしない。**正常なアドレスを弾かないことを優先する**（`user+tag@example.co.jp` のようなプラス記号付き・複数ドットのアドレスが通ること）

### エラー表示

7. Supabase が形式エラー（400 `invalid format`）を返した場合、「メールアドレスの形式が正しくありません」に相当する**具体的なメッセージ**が表示される
8. レート制限（429）の場合、時間をおいて再試行する旨が表示される
9. 上記のいずれにも当てはまらないエラーでは、従来どおり汎用メッセージが表示され、**画面が壊れない**
10. **どのメッセージも、アカウントの登録有無を推測させる文言を含まない**
11. Google ログイン失敗時も、汎用ではなく可能な範囲で具体的なメッセージが出る

### 二重送信防止

12. 送信中は送信ボタンが無効化され、連続タップで複数回 API が呼ばれない
13. 送信が完了（成功・失敗いずれも）したらボタンは再び押せる状態に戻る

### 成功時の挙動

14. 送信に成功した場合の表示（`state === "sent"`）は現状から変えない

### テスト

15. `tests/components/auth-modal.test.tsx` に上記 1・4・5・7・12 に対応するケースが追加されている
16. `pnpm test` と型チェックが通る

### 本番確認（マージ後）

17. 本番のログインモーダルから実際にメールを送信し、**Supabase の `auth_logs` に 400 が出ないこと**を確認する。確認は Owner が行う

## 未解決の質問

1. **「ログインする」を押すと 404 になる**という事象が別途報告されているが、**本 spec では原因を特定できていない。** 調査した限り、PC 版（`user-menu.tsx:63`）もモバイル版（`mobile-header-menu.tsx:256`）もモーダルを開く `<button>` であり、リンクではないため 404 にならない。Magic Link 経由の可能性も、今回はメール送信自体が 400 で失敗しているため成立しない。→ **再現時の URL が判明してから別 spec で扱う。本 spec のスコープに含めない**
2. **モバイルアプリ側に同じ問題があるか未確認。** `tryline-mobile` の認証画面でも同様に trim していない可能性がある。Web 側の修正後に確認し、必要なら別 spec を起票する
3. 12 秒で 21 件というリクエスト数は、二重送信防止の欠如だけで説明できるか、それとも自動リトライが別に存在するか未確認。実装時に `getSupabaseBrowserClient` の設定を確認すること
