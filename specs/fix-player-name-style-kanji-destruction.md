# 出典が提供する漢字表記を強制的にカタカナ化し姓名を逆転させる問題

## 背景

2026-08-08 の日本 vs オーストラリア戦（match_id: `2c276057-bb3a-4617-a5b1-b7742e65f034`）で生成された recap は、**sourced_facts が漢字で提供している選手名をカタカナへ変換し、さらに姓名を逆転させた**。

| sourced_fact（`rugby-japan.jp`、confidence: high） | recap の出力 |
|---|---|
| 伊藤龍之介 | リュウノスケ・イトウ |
| 植田和磨 | カズマ・ウエダ |
| 松永拓朗 | 松永 拓朗（正しい） |

松永だけが漢字で残ったのは、`players.name_ja` に登録があり日本語表記グロッサリへ入ったためである。**グロッサリに無い選手は、正しい漢字が入力データに存在していても破棄される。**

2026-08-08 のプレビュー再生成では、外国籍選手にも同じ現象が起きた。

| 正しい表記 | 生成結果 |
|---|---|
| ディラン・ライリー | ライリー・ディラン |
| ワーナー・ディアンズ | ディアーンズ・ワーナー |
| リーチ マイケル | レイチ・マイケル |
| エイダン・ロス | ロス・エイダン |

この再生成は**採用を見送り、手動で修正した**。同種の手作業は 2026-08-08〜09 に3回発生している（プレビューの漢字化、選手名の誤り訂正、recap の漢字化）。

### 根本原因

`lib/llm/prompts/generate-recap.ts`（288-296行）と `lib/llm/prompts/generate-preview.ts`（207-215行）に**同一の `nameStyleInstruction`** がある。

```
"選手名は、日本語表記グロッサリにある場合は指定の漢字表記を必ず使うこと。グロッサリにない選手はカタカナで記載すること。アルファベット表記は禁止。",
"英語の人名はカタカナに変換し、姓名の間に中点（・）を入れること。",
"アポストロフィ、van/de などの小辞、複合姓は日本語として自然な読みを優先すること。",
"チーム名・大会名は日本語表記グロッサリまたは試合データ内の日本語名を使うこと。英語表記のまま出力しないこと。",
```

**問題は2つある。**

1. **「グロッサリにない選手はカタカナで記載すること」が無条件命令になっている。** 入力データ（`sourced_facts` / `match_events` / `projected_lineups`）に漢字表記が存在する場合の例外がない。結果として、正しいデータを持っているのに破棄する
2. **姓名の語順を保つ指示がない。** 「中点を入れる」としか言っておらず、元の順序を維持する要求がないため、モデルが自由に反転できる

なお `feat-preview-player-kanji-glossary.md`（PR #669、マージ済み）はグロッサリの**供給源**を `match_events` からロスターへ広げたもので、本件は**グロッサリに載っていない選手の表記規則**という別レイヤーである。PR #669 のおかげで松永拓朗は正しく出たが、`players.name_ja` は日本代表81名中11名しか埋まっておらず、大半の選手はグロッサリ外に留まる。

### 現状データでは大半がグロッサリ外

`players.name_ja` が入っているのは**日本代表11名のみ**（2026-08-08 実測、非日本代表は0名）。伊藤龍之介にいたっては `players` テーブル自体に存在しない。バックフィルが進むまでは、**入力データ中の漢字を尊重する経路が唯一の実効的な手段**になる。

## スコープ

対象:
- `nameStyleInstruction`（`generate-recap.ts` / `generate-preview.ts`）の修正
  - 入力データに漢字表記が存在する場合はそれを優先する
  - 姓名の語順を元の表記から変えない

対象外:
- 日本語表記グロッサリの構築ロジック（`feat-preview-player-kanji-glossary.md` の結果を維持する）
- `players.name_ja` のバックフィル（データ投入は別作業）
- league-one 分岐の文面（既存の別ルールがあり、本件の症状は non-league-one 側で発生している）
- チーム名・大会名の表記規則
- 既存 published 記事の遡及的な再生成（別途 Owner 判断）
- QA・採点ルーブリックの変更

## データモデル変更

**なし。マイグレーション不要。**

## API サーフェス

**なし。** プロンプト文字列の変更のみ。

## LLM 連携

パイプラインの narrative 生成段階のみ。モデル・段数・QA 基準は変更しない。`PROMPT_VERSION` は両ファイルとも上げること。

### 修正方針

`nameStyleInstruction` の優先順位を明示する形に書き換える。**優先順位は次のとおり。**

1. 日本語表記グロッサリにある選手 → 指定の漢字表記を必ず使う（既存どおり）
2. **グロッサリに無いが、入力データ（`sourced_facts` / `match_events` / `projected_lineups`）に日本語表記が含まれる選手 → その表記をそのまま使う。漢字をカタカナへ変換しない**（新規）
3. どちらにも日本語表記が無い選手 → 英語名をカタカナへ変換する（既存どおり）

加えて、**いずれの場合も姓名の語順を入力データの表記から変えないこと**を明示する。日本人選手を「名・姓」の順に並べ替えない。外国籍選手の「名・姓」を「姓・名」へ入れ替えない。

文面は実装時に既存の言い回しへ合わせること。新しい用語を発明しない。

## UI サーフェス

なし。

## 受け入れ条件

1. `generate-recap.ts` と `generate-preview.ts` の `nameStyleInstruction` に、入力データの日本語表記を優先する旨が含まれる。
2. 同 instruction に、姓名の語順を入力データから変えない旨が含まれる。
3. 両ファイルの `PROMPT_VERSION` が上がっている。
4. league-one 分岐の文面が変更されていない。
5. 日本語表記グロッサリの構築ロジック（`buildJapanesePlayerNameGlossary` および呼び出し側）が変更されていない。
6. **2つの instruction が同一内容であることを担保するテストがあること。** 現状は同じ文字列が2ファイルに重複しており、片方だけ更新される事故を防ぐ必要がある（共通定数への切り出しでもよい）。
7. `pnpm lint` / `pnpm tsc --noEmit` / `pnpm test` / `pnpm build` がすべて clean。

## 未解決の質問

1. **プロンプト変更の効果は実際に生成しないと確認できない。** 受け入れ条件はプロンプト文字列の検証までしか担保できず、モデルが指示に従うかは別問題である。マージ後に 8/8 の日本戦 recap を再生成し、伊藤龍之介・植田和磨が漢字で出るかを実測すること。**published は reject 時に温存される**（PR #589）ため、試行のリスクは低い。

2. **入力データ中に同一選手の表記ゆれがある場合の優先順位が未定義。** 8/8 の例では sourced_facts が「マキシファウルア」、JRFU の別記事が「ファウルア・マキシ」と異なる。どちらを採るかの規則は本 spec では定めていない。実装時に判断し、報告すること。

3. **語順維持を指示してもモデルが従わない可能性がある。** 従わない場合は、グロッサリを唯一の正とする方式（入力データから日本語表記を機械的に抽出してグロッサリへ入れる）へ切り替える必要がある。その場合は別 spec とする。

4. **`players` テーブルに存在しない選手がいる。** 伊藤龍之介は日本代表81名のロスターに含まれていない。本 spec は入力データ中の表記を尊重することで回避できるが、ロスターの鮮度自体は別課題として残る。
