# メールアドレス捕捉と週次ニュースレター配信

## 背景

2026-08-09〜10 の実測で、**Tryline には再訪を生む装置が実質的に存在しない**ことが確認できた。

| 指標 | 実測 |
|---|---:|
| 検索流入ユーザー | 135 |
| うち新規 | **131（97%）** |
| iCal 購読リクエスト（7日間） | **1** |
| push 購読者 | **0** |
| 登録ユーザー | 3 |

**月に約200人が訪れ、ほぼ全員が二度と戻らない。** 毎月ゼロから積み直している。

2026年11月の日本代表欧州遠征は、GSC にデータが存在する期間で**初のピークシーズン**になる。そこで来訪者を捕まえられなければ、同じことが繰り返される。

### なぜメールか

再訪装置は3つあり、うち2つは既に実装済みで機能していない。

| 装置 | 実装 | 実績 |
|---|---|---|
| push 通知 | 済（`app/api/push/{send,subscribe,unsubscribe}`） | 購読者0 |
| iCal 購読 | 済（`app/api/calendar/[feed]`、カレンダーと大会ハブに導線あり） | 7日で1リクエスト |
| **メール** | **なし** | — |

push は許可ダイアログの摩擦が大きく、iCal は日程しか運べない。**メールは摩擦が中程度で、任意の内容を運べる唯一の手段**である。

なお push と iCal がゼロなのは「壊れている」からとは限らない。**71セッションでは転換率を評価できない**（優秀な CTA でも2〜4件で、ゼロとの差はノイズ）。母数が増える11月に、3つ揃えて比較するのが正しい。

### 配信する中身は既に生成されている

`specs/feat-weekly-digest-cron.md`（実装済み）は、毎週月曜夜に先週末の試合結果を**LLM で日本語のまとめ原稿に自動生成**し、Discord webhook へ送信している。Owner がそれを note へ転記する運用。

**この原稿がそのままニュースレター本文になる。** 本 spec で新たに作るのは「捕捉」と「送信」の2脚だけであり、コンテンツ生成は不要。

## スコープ

対象:
- メールアドレスの登録フォームと保存
- ダブルオプトイン（確認メール）
- 配信停止
- 週次ダイジェストのメール送信
- 登録導線の設置

対象外:
- **ダイジェスト原稿の生成ロジック**（`feat-weekly-digest-cron.md` の実装をそのまま使う）
- Discord 送信の停止。**両方に送る**（Owner の note 転記フローは維持）
- push 通知・iCal の変更
- セグメント配信・パーソナライズ（大会別・チーム別の配信は将来の課題）
- HTML メールの凝ったデザイン。**プレーンに近い形で始める**
- 既存の Supabase Auth ユーザーへの自動登録。**別の同意が必要**

## データモデル変更

新規テーブル1件。マイグレーションが要る。

```
email_subscribers
  id
  email                 -- 一意
  status                -- 'pending' | 'confirmed' | 'unsubscribed'
  confirmation_token    -- 確認用。使用後は無効化
  confirmed_at
  unsubscribed_at
  source                -- 登録元ページ（計測用）
  created_at
```

**RLS を必ず有効化すること。** 匿名ユーザーが他人のメールアドレスを読めてはならない。書き込みはサーバー経由に限定する。

2026-07-26 に `weekly_news_items` で RLS 無効のまま本番投入した事故があるため、**本番適用後に RLS 状態を直接確認すること**。

## API サーフェス

### 1. 登録

`POST /api/newsletter/subscribe`

- メールアドレスの形式検証
- 既に `confirmed` なら成功として扱う（存在を漏らさない）
- `pending` で保存し、確認メールを送る
- **レート制限を必ず入れる。** 無制限だと他人のアドレスへの嫌がらせに使える

### 2. 確認（ダブルオプトイン）

`GET /api/newsletter/confirm?token=…`

- トークンを検証し `confirmed` にする
- トークンは使い捨て。有効期限を設ける
- 完了後は結果を伝えるページへ遷移させる

### 3. 配信停止

`GET /api/newsletter/unsubscribe?token=…`

- **全メールのフッターに必ず入れる**（法令要件）
- ログイン不要・1クリックで完了すること

### 4. 送信

既存の週次ダイジェスト cron に、メール送信を追加する。

- 宛先は `status='confirmed'` のみ
- **Discord 送信は維持する**（既存フローを壊さない）
- 送信失敗は握り潰さず件数をログに残す
- 送信結果（成功・失敗件数）を運用通知へ出す

## UI サーフェス

### 登録フォームの設置場所

実測のエンゲージメントに基づいて置く。

| ページ | 1セッション滞在 | 設置 |
|---|---:|---|
| `/calendar` | 120秒 | **置く** |
| 大会ハブ `/c/[competition]/[season]` | 107秒 | **置く** |
| トップ `/` | 36秒 | 置く |
| 試合ページ `/matches/[id]` | **3.6秒** | **置かない** |

**試合ページには置かない。** 3.6秒で離脱するページに置いても登録されず、記事の読み心地を損なうだけ。

既存の iCal 購読ボックス（`app/calendar/page.tsx` 181-199行、`app/c/[competition]/[season]/page.tsx` 584行付近）の近くに、同じ見た目で並べるのが自然。

### 文面

「何が届くか」「頻度」を明示すること。**「登録」だけのボタンは登録されない。**

例: 「週に1回、週末の試合結果を日本語でまとめて送ります」

## LLM 連携

なし。本文は既存の週次ダイジェストを使う。**新規の LLM 呼び出しは発生しない。**

## 法令要件（特定電子メール法）

日本国内向けの配信となるため、以下は必須。

- **オプトインの取得**。ダブルオプトインで同意の記録を残す
- **送信者の表示**。メール本文に送信者名・連絡先を記載
- **配信停止の手段**。全メールに1クリックの停止リンク
- 同意の取得日時を保存すること（`confirmed_at`）

## 受け入れ条件

1. `email_subscribers` テーブルが作成され、**RLS が有効**である。匿名ロールから読み取れない。
2. 登録 → 確認メール → 確認リンク → `confirmed` の一連が動作する。
3. 未確認（`pending`）のアドレスには配信されない。
4. 配信停止リンクが1クリックで機能し、以後配信されない。
5. 全メールに送信者情報と配信停止リンクが含まれる。
6. 登録エンドポイントにレート制限がある。
7. **既存の Discord 送信が壊れていない。** 週次ダイジェストは Discord とメールの両方へ送られる。
8. 送信の成功・失敗件数がログに残る。**失敗を握り潰さない。**
9. 登録フォームが `/calendar`・大会ハブ・トップに設置され、**試合ページには無い**。
10. `pnpm lint` / `pnpm tsc --noEmit` / `pnpm test` / `pnpm build` がすべて clean。

## 未解決の質問

1. **送信サービスの選定。** Resend・SendGrid・Amazon SES 等。現在の規模（購読者0〜数十）では各社の無料枠に収まる見込みだが、**Owner の判断とアカウント作成が要る**。送信ドメインの認証（SPF/DKIM）も Owner 作業。

2. **送信元ドメイン。** `trylinerugby.com` から送るなら DNS 設定が要る。サブドメイン（`mail.` 等）を使うかも判断が要る。

3. **配信頻度と内容。** 現在の週次ダイジェストは月曜夜に先週末の結果をまとめる形。**11月の日本代表戦は水〜土に散る**ため、週次だけで足りるか検討の余地がある。試合前日の通知を出すなら別途設計が要る。

4. **既存の登録ユーザー3人をどうするか。** Supabase Auth のアカウントとニュースレターは別の同意である。**自動で登録してはならない。** 案内を出すかは Owner 判断。

5. **11月に間に合うか。** 送信サービスの選定・ドメイン認証・実装・テストで、Owner 作業が複数回挟まる。**9月中の着手が望ましい。**
