# Top 14 の未来日程が1節先までしか見えない問題

## 背景

`/calendar` は説明文で **「月曜 00:00 JST から翌月曜 00:00 JST までの試合を、全大会横断で曜日ごとにまとめています」** と明示している（`app/calendar/page.tsx`）。カレンダーは前後8週まで移動できる（`MAX_WEEK_OFFSET = 8`、`lib/format/week.ts`）。

しかし **Top 14 は 2026-09-14 以降のどの週にも1試合も出ない。**

### 本番 DB の実測（2026-08-31）

| 大会 | 2026-09-01 以降の取り込み済み試合 | 初戦 | 最終 |
|---|---|---|---|
| urc / 2026-27 | 144 | 2026-09-25 | 2027-05-15 |
| premiership / 2026-27 | 90 | 2026-09-25 | 2027-06-03 |
| **top-14 / 2026-27** | **14** | 2026-09-05 | **2026-09-13** |

週別:

| JST 週 | 総試合数 | 内訳 |
|---|---|---|
| 2026-08-31 | 9 | **top-14: 6** ほか |
| 2026-09-07 | 10 | **top-14: 7** ほか |
| 2026-09-14 | **1** | **top-14: 1** のみ |
| 2026-09-21 以降 | 13〜14 | urc + premiership のみ。**top-14: 0** |

### これは「取り込み漏れ」ではない。設計どおりの結果である

`lib/ingestion/sources/top14-lnr-live.ts`:

```ts
const TOP14_LNR_SEASON = "2026-27";                 // :10
export const MAX_TOP14_LNR_ROUNDS_PER_INGEST = 3;   // :12
// getDefaultTop14LnrRoundSlugs() は現在節 ±1 節を返す（:25-42）
```

**この節単位の制限は Owner が意図的に設けたものである（2026-08-29）。取得する節数（3）は変えない。変えるのは窓の位置だけである（2026-09-01 承認）。**

> フランスには法律上 sui generis データベース権がある。CGU に主張が無くても「実質的な部分の抽出」は制限され得るため、**Owner 判断で節単位に絞っている**（1回3節上限・節間3秒待機）。**全26節の一括取得はしない。**

したがって **「フルシーズンをバックフィルする」は本 spec の解ではない。** その判断は既に下されている。

**Codex はこの制約を緩める実装をしてはならない。**

### 結果として起きていること

1. **時間が経てば試合は貯まる。** ライブ取り込みが毎週 ±1節を入れるため、シーズン終盤には182試合が揃う
2. **しかし未来は常に1節先までしか見えない。** カレンダーが8週先まで移動できるのに、Top 14 は約1週先で途切れる
3. **URC とプレミアシップは全シーズン分が入っている**ため、**Top 14 だけが欠けた状態**が並んで見える。「全大会横断」という記述と食い違う
4. **欠落が無言である。** ユーザーには「その週に Top 14 の試合が無い」のか「まだ取り込んでいない」のか区別できない

### 付随して見つかった潜在バグ

`scripts/backfill-top14-regular-season.ts`:

```ts
const SUPPORTED_SEASONS = new Set(["2024-25", "2025-26"]);   // :45
// :85  if (!SUPPORTED_SEASONS.has(season)) → エラー終了
```

**現行シーズン 2026-27 が許可リストに無い。** 同じ「シーズン」を表す定数が2箇所にあり、片方だけ更新された。

| 場所 | 値 | 更新状況 |
|---|---|---|
| `lib/ingestion/sources/top14-lnr-live.ts:10` | `"2026-27"` | 新シーズンに更新済み |
| `scripts/backfill-top14-regular-season.ts:45` | `{"2024-25", "2025-26"}` | **未更新** |

**このスクリプトを今すぐ実行するわけではない**（上記の Owner 判断があるため）。しかし**将来 Owner が過去シーズンの補完等で使いたくなったとき、現行シーズンだけ使えない**状態は潜在バグである。`SUPPORTED_SEASONS` はリポジトリ内でこのスクリプト固有（走査で確認済み）。

> **2026-09-01 分割**: 本 spec の「未取得の可視化」部分は、判定方法が実データで機能しなかったため **`specs/fix-schedule-coverage-notice-by-rounds.md` へ切り出した**（PR #750 レビューで判明）。本 spec に残るのは**取得窓の前方シフトとシーズン定数の是正**のみ。受け入れ条件の8〜14・18〜20 は移管済みで、本 spec では判定しない。

## UI サーフェス

### 「まだ取り込んでいない」を無言にしない

現在、Top 14 が載らない週は「その週に Top 14 が無い」のと見分けがつかない。

**取り込み済みの最終キックオフより先の週を表示しているとき、その旨を伝える。**

- `/calendar` で、**表示中の週より後にも開催があるが未取得の大会**がある場合、一覧の近くに注記を出す
- 文面の要件: **推測や言い訳ではなく事実だけを書く。** 「Top 14 の日程は開催が近づいてから掲載されます」に相当する内容
- 大会ハブ `/c/top-14/2026-27` にも同等の注記を出す
- **注記は該当する大会がある週にだけ出す。** 常時表示にしない

**判定方法は Codex が設計してよい**が、次を満たすこと:

- 大会名をハードコードしない（Top 14 固有の分岐を書かない）。将来ほかの大会が同じ状態になっても機能すること
- 追加のクエリを増やす場合は、`/calendar` の既存のクエリ本数を大きく増やさない（現状は `getMatchesInRange` + `getStandingPositionLookupForCompetitions` + `getSpoilerGuardEnabledForUser`）

### 表示しないもの

- **試合の件数や日程を推測して埋めない。** 「あと N 試合あります」のような未取得データに基づく数値を出さない

## 受け入れ条件

### シーズン定数の是正

1. `scripts/backfill-top14-regular-season.ts` の `SUPPORTED_SEASONS` が**ハードコードされた `Set` ではなくなっている**。`lib/ingestion/sources/top14-lnr-live.ts` の `TOP14_LNR_SEASON` を単一の出所として参照するか、同等に「現行シーズンが自動的に含まれる」形になっている
2. `--season=2026-27` が**受け付けられる**（実行はしない。`--dry-run` で許可されることの確認まで）
3. 過去シーズン（`2024-25` / `2025-26`）が**引き続き受け付けられる**
4. 不正な書式（`1999-00`、`abc`）は従来どおり拒否される
5. **`MAX_TOP14_LNR_ROUNDS_PER_INGEST` の値が `3` のまま**
6. `lib/scrapers/top14-lnr-results.ts` に差分が無い

### 取得窓の前方シフト（2026-09-01 Owner 承認）

6a. `getDefaultTop14LnrRoundSlugs()` が **現在節・+1・+2 の3節**を返す（従来は 現在節-1・現在節・+1）
6b. **返す節数が3であることは変わらない。** 1回の実行で4節以上を取らない
6c. 現在節が **j25 のとき j25・j26 の2節**、**j26 のとき j26 の1節**を返す（`> 26` を生成しない。既存の `1..26` クランプを維持する）
6d. 現在節が **j1 のとき j1・j2・j3** を返す（下限側で `j0` 等を生成しない）
6e. **既存データが壊れないこと。** 直前節（現在節-1）を取得しなくなるが、`upsert` であって `delete` ではないため、既に DB にある確定済みスコアは残る。**これを実際に確認して PR 本文に書く**
6f. 節間の待機（3秒）が**変わっていない**
7. シーズン定数の共有化に**ユニットテストを追加する**（現行シーズンが通る / 過去2シーズンが通る / 不正な書式が拒否される）

### 未取得の可視化

8. `/calendar?week=2026-10-26` に、Top 14 の日程が未取得である旨の注記が表示される
9. `/calendar?week=2026-09-07`（Top 14 が7試合入っている週）には**注記が出ない**
10. `/c/top-14/2026-27` に同等の注記が表示される
11. `/c/urc/2026-27`（全シーズン取り込み済み）には**注記が出ない**
12. 注記の判定に**大会名・family のハードコードが無い**（`top-14` という文字列で分岐していない）
13. 注記に**未取得の試合数・日程の推測値が含まれていない**
14. `/calendar` の「全大会横断」という説明文が**削除・改変されていない**

### 共通

15. `/calendar` のデータ取得クエリ本数が、変更前後で**2本以上増えていない**
16. `pnpm lint` / `pnpm tsc --noEmit` / `pnpm test` / `pnpm build` がすべて clean
17. **本番へのデータ投入を伴わない。** `--confirm-owner-approved` を実行しない

### デザイン品質

18. 注記は `app/globals.css` の既存トークンのみを使う。新しい色・角丸・影を導入しない
19. 注記が試合一覧より目立たないこと。**主役は試合であって注記ではない**
20. **Owner による目視確認を要する。** 注記の文面が、言い訳がましくなく事実として読めるかは機械的に判定できない

## 判定方法（効果測定）

本 spec は**データを増やさない**ため、流入・滞在の指標は動かない見込み。

| 確認 | 方法 | 期待 |
|---|---|---|
| 無言の欠落が解消したか | `/calendar?week=2026-10-26` を目視 | 注記が出る |
| 誤検知が無いか | Top 14 が入っている週・URC ハブを目視 | 注記が出ない |
| 潜在バグの解消 | `--season=2026-27 --dry-run` | 許可される |
| 定数の腐りが再発しないか | シーズンを1つ進めたユニットテスト | 通る |

**数値指標は設定しない。** 本 spec の目的は「嘘をつかないこと」であり、指標の改善ではない。

## 未解決の質問

**1**: ~~Top 14 の未来日程をどこまで見せるか~~ → **決着（Owner 承認、2026-09-01）。案B（取得窓を前方にずらす）を採用する。**

| 案 | 内容 | 追加リクエスト | 判断 |
|---|---|---|---|
| A | 何も増やさず、未取得であることを表示する | 0 | **併用する**（窓の外は依然として未取得のため） |
| **B（採用）** | 取得窓を「現在節 ±1」から「現在節・+1・+2」へ**前方にずらす** | **0**（3節のまま） | **採用。** 追加リクエストがゼロで、sui generis の判断に抵触しない |
| C | 未来節を1日あたり数節ずつ、時間をかけて埋める | 累計26節分 | **不採用。** 総量は一括取得と同じで、分散させても「実質的な部分の抽出」の懸念は変わらない |

**A と B は併用する。** B で未来が約1節ぶん多く見えるようになるが、それでも8週先までは埋まらないため、A の「未取得である」表示は引き続き必要。

**検証が必要な点**: 直前節（現在節 -1）を取得しなくなることで、**確定済みスコアの再取得を失う**。確定後にスコアが訂正されるケース（誤記修正・不戦勝の裁定など）を拾えなくなる。実害は小さい見込みだが、**Codex は直前節のデータが既に DB にある状態で窓をずらしても既存データが消えない・壊れないことを確認すること**（upsert であって delete ではないこと）。

**2: 「未取得」の判定基準をどう置くか。** 「その大会の取り込み済み最終キックオフより後の週か」で判定するのが素直だが、**シーズンが実際に終了した大会**（例: 5月に終わる URC を6月の週で見る）でも同じ条件が成立してしまう。競技のシーズン終了日を持っていないため区別できない。**Codex は誤検知の具体例を PR 本文に列挙すること。** 誤検知が多いようなら、判定を「その大会に未来の試合が1件でもあるか」等へ緩める

**3: 2027-28 シーズンで `TOP14_LNR_SEASON` の手動更新を忘れないか。** 受け入れ条件1で許可リストの直書きは解消するが、この定数自体は手で更新するまま残る。`feat-data-integrity-weekly-audit.md` の枠組みで検知する案があるが、本 spec のスコープ外とした
