# 日本代表戦の得点経過を JRFU から補完する

## 背景

**スコアだけ埋めてもレビューは生成されない。**

2026-09-06 に `feat-jrfu-result-fallback`（PR #776）をマージし、日本×カナダのスコアは JRFU の日程ページから `57-12` / `finished` になった。**しかしレビューは生成されなかった。**

原因は PR #770 で入ったゲートである。

```
lib/llm/pipeline.ts:248-258
if (contentType === "recap" && assembled.eventIntegrity?.reason === "events_unavailable") {
  return { status: "skipped" };
}
```

**`match_events` が0件の試合は、レビューを生成しない。** イベントが無いまま書かせると LLM が得点経過を推測して捏造するため（`project_content_fabrication`）、**このゲートは意図どおり働いている。**

`feat-jrfu-result-fallback` は受け入れ条件16で「`match_events` に書き込んでいない」と定めた。**スコアとイベントの両方が必要だった。**

### 取得元は確認済み

**JRFU の試合ページに得点経過がある**（2026-09-06 に `https://www.rugby-japan.jp/match/29975` で確認）。

```
5'   5 - 0   岡部崇人      → /player/510741
6'   5 - 0   松永拓朗      → /player/510763
15'  10 - 0  原田衛        → /player/510754
```

**分数・累計スコア・選手名・選手 ID が揃っている。** 日程ページの各試合が `/match/<id>` にリンクしている。

## スコープ

対象:
- JRFU の試合ページから**得点経過**を取り出し、`match_events` に投入する
- 対象は**日本代表戦のうち、スコアがあってイベントが0件のもの**に限る

対象外:
- **`feat-jrfu-result-fallback`（スコア補完）の変更。** そのまま残す
- **`lib/llm/pipeline.ts` のゲートの変更。** ゲートは正しい
- `lib/scrapers/jrfu-match-broadcasts.ts` の変更
- Wikipedia 由来のイベント取り込みの変更
- 交代・カード。**JRFU の得点経過に載っているものだけを扱う**
- 日本代表以外の試合

## www を付けること

**`rugby-japan.jp`（www なし）は証明書が期限切れでアクセスできない**（2026-09-06 実測）。

**日程ページの `href` は www なしで出てくる。** 既存の `normalizeUrl`（`lib/scrapers/jrfu-match-broadcasts.ts`）が `https://www.rugby-japan.jp/schedule/` を base に正規化しているため現状は正しく動いているが、**新しいコードで href をそのまま使うと失敗する。**

## 既存イベントがある試合に触らないこと

既存の `upsertMatchEvents`（`lib/ingestion/events.ts:59`）は、**対象試合のイベントを全削除してから挿入する。**

```
.from("match_events").delete().eq("match_id", params.matchId)
```

**したがって「既存があれば触らない」は upsert の外側で判定すること。** 呼ぶ前に件数を数え、**0件でなければ対象から外す。**

Wikipedia から入った正しいイベントを、解析ミスで消す事故を防ぐため。

## 投入前にスコアと突き合わせること（最重要）

**イベントから計算した合計が `matches.home_score` / `away_score` と一致しない場合、投入してはいけない。**

得点の重みは `try` 5点 / `conversion` 2点 / `penalty_goal` 3点 / `drop_goal` 3点。

**一致しなければ何も投入せず、期待値と実際値をログに残してスキップする。**

**これが無いと事態は悪化する。** 誤ったイベントを入れると `eventIntegrity` が通ってしまい、**間違った得点経過でレビューが生成される。** イベントが無くて生成されないより悪い。

**ペナルティトライの扱いに注意すること。** 過去に5点として扱うバグがあった（`project_event_contamination`）。JRFU の表記を確認し、**判別できなければその試合をスキップする。**

## 得点種別の判定は実 HTML から決めること

**得点種別（`try` / `conversion` / `penalty_goal` / `drop_goal`）をどう判別するかは、実際の HTML を見て決めること。**

確認時点では「視覚的な指標で区別される」ことしか分かっていない。**クラス名・アイコン・テキストのいずれで判別するかを実物で確定し、spec ではなく実装とテストで固定する。**

**推測で決めないこと。** 手作りのフィクスチャは実データで壊れる（`feedback_scraper_test_fixture_realism`）。**実ページの HTML をフィクスチャに使う。**

## 選手の解決

**既存の `resolvePlayerId({ playerName, teamId })` を使うこと**（`lib/ingestion/events.ts` が使っている関数）。

**選手が解決できなくても投入は続けること。** `match_events.player_id` は nullable である。**解決できなかった選手名はログに残す。**

JRFU のページには `/player/<id>` のリンクがあるが、**その ID を `players` に紐づける仕組みは現在存在しない。** 本 spec では**名前による解決に留める。** ID の活用は別途。

## リクエスト数

- 日程ページ: **1回**
- 試合ページ: **対象試合ぶんのみ**

**1回あたりの最大試合数を定数で定義すること。推奨5。** 対象は「スコアありでイベント0件の日本代表戦」なので通常は0〜1件である。

**`fetchWithPolicy` を使うこと。** `rugby-japan.jp` は許可ドメインで、D026 の例外は適用されない。

## 実行結果の可視化

レスポンスに次を含める。

- イベントを投入した試合数
- **スコア不一致でスキップした試合数**（期待値と実際値もログに）
- 既存イベントありでスキップした試合数
- 解決できなかった選手名の件数

**0件が正常な状態である。**

## 受け入れ条件

1. JRFU の試合ページから**分数・得点種別・選手名・チーム**を取り出すパーサが新設されている
2. 対象が「**日本代表戦 かつ スコアあり かつ `match_events` 0件**」に限られている
3. **`match_events` が1件以上ある試合を対象にしない**（`upsertMatchEvents` を呼ぶ前に判定している）
4. **イベント合計とスコアが一致しない場合、1件も投入せずスキップし、期待値と実際値がログに出る**
5. 得点の重みが `try` 5 / `conversion` 2 / `penalty_goal` 3 / `drop_goal` 3 で計算されている
6. **ペナルティトライが5点として扱われていない**（判別できない場合はその試合をスキップ）
7. 得点種別の判別が**実 HTML の構造**に基づいている
8. **試合ページの URL に `www` が付いている**
9. `fetchWithPolicy` を使っている
10. 日程ページの取得が1回、試合ページの取得が対象試合ぶんのみ
11. **1回あたりの最大試合数が定数として定義されている**
12. 既存の `resolvePlayerId` を使っている
13. **選手が解決できなくても投入が続き、解決できなかった名前がログに出る**
14. `feat-jrfu-result-fallback` のスコア補完の**後**に走る
15. レスポンスに**投入試合数・スコア不一致スキップ数・既存イベントありスキップ数・未解決選手数**が含まれる
16. **`lib/llm/pipeline.ts` に差分が無い**
17. **`lib/scrapers/jrfu-match-broadcasts.ts` に差分が無い**
18. `lib/ingestion/jrfu-result-fallback.ts` のスコア補完ロジックに**振る舞いの変更が無い**
19. `supabase/` に差分が無い
20. パーサのテストが**実ページの HTML**をフィクスチャにしている
21. テストが次を覆っている: 全種別の得点 / スコア一致 → 投入 / **スコア不一致 → 投入しない** / 既存イベントあり → 触らない / 選手未解決でも投入継続 / 上限超過
22. `pnpm lint` / `pnpm tsc --noEmit` / `pnpm test` / `pnpm build` がすべて clean

## 検証方法

**本番で 2026-09-05 の日本×カナダの `match_events` が埋まり、その次の `ingest-live-competitions` でレビューが生成されることを確認する。**

この試合は本 spec の起点であり、**現在 `finished` / `57-12` / events 0件 / レビュー未生成**という状態で止まっている。

**マージ後、デプロイが READY になってから実行すること。** 2026-09-06 に、マージ3分後に実行して古いデプロイに着弾させた失敗がある。

## 未解決の質問

- **分数の計時規則が媒体で違う。** JRFU は原田衛のトライを `15'`、Americas Rugby News は `14分` としている。**JRFU（主催者）を正とする方針で書いているが、Discord から手動入力した事実の分数と本文で食い違う可能性がある**
- **`/player/<id>` を `players` に紐づけるか。** 名前による解決には限界があるが、ID を保持する仕組みが現在無い。**本 spec では扱わない**
- **カード（イエロー／レッド）が JRFU の得点経過に載っているか未確認。** 載っているなら別途取り込む価値がある（`match_events` に該当 type が存在しないという既知の欠落を埋められる）
