# Discord で事実を入れたら、公開済みのプレビューをその場で作り直す

## 背景

2026-09-26（土）、日曜キックオフの 3 試合（セール 対 ブリストル 1:30、ポー 対 ラ・ロシェル 4:00、オーストラリア 対 南アフリカ 18:30。いずれも日本時間）のプレビューが **20:05（日本時間）に作られて公開された**。Owner が ChatGPT の調べ物（20:00 実行）を Discord で入れたのはその後で、**3 本とも事実が入らないまま公開された**。

**原因（設計のずれ）:**
- プレビューは「キックオフの日（日本時間）の前日 15:00」を過ぎ、かつキックオフまで 24 時間以内になった最初の Live Pipeline で作られる（`lib/cron/preview-window.ts`、`lib/cron/content-windows.ts` の `previewCandidateUpperBound`、D030）。
- ChatGPT の調べ物は、2026-09-25 に 12:00 から 20:00 に移した（Top 14 のフランスの記事を拾うため。ChatGPT のスケジュールタスクは上限で増やせない）。**設計上、事実は常に生成より後に届く。** これまで間に合っていたのは、GitHub の定期実行が深夜まで遅れていたため（直近 2 週の Top 14 は 0:30〜1:10 に生成）。
- 生成の時刻を 22:00 以降にずらすだけでは解決しない。日曜の対象には日本時間の未明にキックオフする欧州の土曜夜の試合があり（セール戦 1:30、ポー戦 4:00）、22:00 以降の次の Live Pipeline（予定は 3:00 JST、実際は遅れがち）では間に合わない試合が出る。
- 生成後に入れた手動の事実を反映する自動の経路は無い（`memory: project_preview_manual_facts_after_generation`）。反映には手動の再生成（`Manual — Preview Regeneration`）が要る。

**方針:** 前日 15:00 の生成は今のまま残し（調べ物をしなかった試合にも必ずプレビューができるように）、**Discord で事実を入れたとき、その試合の日本語プレビューがすでにあれば、その場で作り直す**。まだ無ければ何もしない（その後の通常の生成で事実が使われる）。これで GitHub の定期実行の遅れにも、調べ物の時刻にも左右されない。

## スコープ

**対象**
- `/調査事実を追加` の保存（`app/api/discord/interactions/route.ts` の `processResearchFactEntry`）のあとに、次の条件をすべて満たすときだけ、その試合の日本語プレビューを作り直す。
  1. 保存した事実の `content_type` が `preview`（キックオフ前）
  2. この送信で、新しく保存された事実が 1 件以上ある（重複だけなら作り直さない）
  3. その試合の日本語プレビュー（`match_content`、`content_type = "preview"`、`language = "ja"`、`status` が `published` または `draft`）がある
- 作り直しの結果を、Discord の返信に書き足す。

**対象外**
- レビュー（`recap`）の作り直し（レビューは調べ物の締め切り 20:30 を待ってから生成する仕組みがすでにある）。
- 英語のプレビュー。
- 前日 15:00 の生成の時刻（変えない）。
- ChatGPT の調べ物の時刻（20:00 のまま）。

## API サーフェス

### `app/api/discord/interactions/route.ts`

- `processResearchFactEntry` で保存したあと（今の `after()` の中）、上の 3 条件を満たせば `generateMatchContent(matchId, "preview", "ja")`（`lib/llm/pipeline.ts`）を呼ぶ。
  - 既存の生成と同じ処理なので、公開中のプレビューを守る仕組み（新しい版が QA で下書きになったら、公開中の版を残す）はそのまま効く。
  - Web 検索は、#893 により手動の事実がある試合では行われない。
- このルートの `maxDuration` を、生成が収まる長さにする（`export const maxDuration = 300`。今の値が短ければ）。
- 生成の前に、Discord に「保存しました。プレビューを作り直しています…」と途中経過を返す（今の返信の編集で）。生成が終わったら、結果を書き足して返信を更新する。
  - 例: `プレビューを作り直しました（公開）` / `プレビューを作り直しましたが、QA で不合格のため公開中の版を残しました` / `プレビューの作り直しに失敗しました: <理由>`
- 生成が例外を投げても、事実の保存は取り消さない（保存と作り直しは別の処理として扱う）。

### 同じ試合に続けて送った場合

- 1 試合につき、作り直しは送信のたびに 1 回。同じ試合に短時間で 2 回送った場合は 2 回作り直す（Owner は 1 試合につき 1 回送る運用なので、これ以上の制御は入れない）。

## LLM 連携

- 段 1〜4（通常の生成）を 1 回。費用は 1 本あたり約 $0.05（本文 $0.042、検査 $0.004。直近 14 日の実績）。
- 見込み: 調べ物をした試合のうち、入れる前にプレビューができていた試合の数だけ増える。週末 18 試合すべてが対象でも約 $1。

## 受け入れ条件

1. 次の条件で `generateMatchContent(matchId, "preview", "ja")` が 1 回呼ばれる（モック）: キックオフ前の試合、新しく保存した事実が 1 件、日本語プレビュー（`published`）がある。
2. 次のどれかなら呼ばれない（それぞれテスト）:
   - 日本語プレビューがまだ無い
   - この送信で新しく保存した事実が 0 件（すべて重複）
   - キックオフ後の試合（`content_type = "recap"`）
3. 生成の結果（公開・公開中の版を残した・失敗）が、それぞれ Discord の返信に書き足される。
4. 生成が例外を投げても、事実の保存は成功のままで、返信に失敗の理由が載る。
5. 確認方法: 条件 3（日本語プレビューがある）の判定を外すと、2 の 1 つ目のテストが落ちること。
6. `pnpm lint`、`pnpm typecheck`、`pnpm test` が通る。**3 つとも実行して、結果を完了報告に含める。**
