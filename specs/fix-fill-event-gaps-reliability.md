# イベント補完が時間切れで完走せず、失敗と成功を正しく報告しない問題

## 背景

2026-08-08 の日本 vs オーストラリア戦で、試合終了から recap 公開まで約14時間を要した。スコア投入は `feat-lipovitan-challenge-cup-live-ingestion.md`（PR #671）で自動化されたが、**得点イベントの取り込みは依然として手作業に依存している**。

`app/api/cron/fill-event-gaps/route.ts` を実測した結果、複数の独立した問題が重なっていることが判明した。

### 問題1: `maxDuration = 60` に対して処理が重すぎる

ルートは `maxDuration = 60`（13行目）を明示している。一方で処理は次のとおり。

- `CRON_BATCH_SIZE = 25` 件を対象にする
- 1件ごとに `fetchWithPolicy` で Wikipedia を取得
- 1件ごとに `await sleep(1_500)`（レート制限遵守のため必要）

**待機だけで 25 × 1.5秒 = 37.5秒**を消費する。取得と解析を加えると60秒を超え、504 で打ち切られる。

2026-08-08〜09 に2回実行し、いずれも 504 で終了した。GitHub Actions は `curl -f` の失敗により**ワークフロー全体を failure と報告**した。

### 問題2: 失敗と報告されたが、実際には成功していた

2回目の実行は 504 を返したが、**サーバ側の処理は継続し、日本戦の19イベントが正しく登録されていた**（合計32-35でスコアと一致）。

つまり現状は次の状態にある。

- **成功しても failure と報告される**ため、結果を DB で直接確認しない限り分からない
- どこまで処理できたかが記録されない
- ワークフローのログに件数が残らない

これは「静かに失敗する」の裏返しで、**静かに成功している**。どちらも同じく運用上の判断を誤らせる。

### 問題3: `match_events` 全行を毎回取得している

ギャップ判定のために、次のクエリを実行している。

```ts
const { data: eventedRows } = await client
  .from("match_events")
  .select("match_id");
```

**フィルタが無い。** 2026-08-09 時点で `matches` の `finished` は1,034件あり、イベントを持つ試合の総イベント数は1万行を優に超える。これを毎回すべて読み出し、アプリケーション側で `Set` を作って突き合わせている。

DB 側で「イベントを持たない finished 試合」を直接絞れば、この転送は不要になる。

### 問題4: ローカルスクリプトには並び順が無い

`scripts/fill-event-gaps.ts` の `loadGapMatches`（332-356行）は `.eq("status","finished").limit(limit)` のみで、**`ORDER BY` を持たない**。既定 `--limit=50` は1,034件から任意の50件を抜き取るため、28件のギャップを拾える確率は低い。実際 `--limit=50` では「Found 0 matches」となり、`--limit=1100` で初めて22件が検出された。

ルート側は `.order("kickoff_at", { ascending: false })` を持つため、**直近の試合は対象に入る**。スクリプトとルートで挙動が異なる。

### 既に存在する仕組み

ルートは **`matchIds` をリクエストボディで受け付ける**（最大40件、25-27行目）。狙い撃ちの経路は実装済みで、`matchIds` 指定時は `CRON_BATCH_SIZE` の制限も外れる。

**GitHub Actions のワークフローがこれを使っていないだけである。**

## スコープ

対象:
- ギャップ判定を DB 側で行い、`match_events` 全行の取得をやめる
- 60秒以内に完走する構成にする（バッチサイズ・`maxDuration` のいずれか、または組み合わせ）
- 処理結果（対象件数・成功件数・失敗件数）をワークフローのログに残す
- タイムアウト時に成功を失敗と誤報告しない
- `scripts/fill-event-gaps.ts` の `loadGapMatches` に並び順とギャップ絞り込みを入れる
- ワークフローから特定試合を狙い撃ちできるようにする（ルートの `matchIds` は実装済み）

対象外:
- **解析の失敗そのもの**。`no unique event block found`（リーグワン6件・URC5件）と `event totals exceed final score`（SRP6件等）は別課題であり、本 spec では扱わない。**後者はスコアと合わないイベントの登録を防ぐ正常な動作**であり、無効化してはならない
- `parseMatchEventsFromVeventHtml` の ja.wikipedia 対応
- `lib/ingestion/sources/wikipedia-lipovitan-challenge-cup.ts` の `rawHtml` 対応（live ingest 経路でのイベント取得。別 spec）
- レート制限（`sleep(1_500)`）の短縮。robots.txt 遵守方針を守る
- cron の実行頻度の変更

## データモデル変更

**なし。マイグレーション不要。**

## API サーフェス

### 1. ギャップ判定を DB 側へ

`match_events` 全行の取得をやめ、**イベントを持たない `finished` 試合**を DB 側で絞り込む。

Supabase クライアントでの実現方法は実装時に判断すること（`match_events` への left join と null 判定、あるいは既存の他クエリで使っている手法に合わせる）。**アプリケーション側で全件を突き合わせる現在の方式は廃する。**

### 2. 60秒以内に完走させる

`maxDuration = 60` を維持したまま完走させるか、`maxDuration` を延ばすかを実装時に判断する。判断材料として、**1件あたり最低1.5秒の待機が必須**である点を考慮すること。

バッチサイズを下げる場合、1回の実行で処理しきれないギャップが翌回へ持ち越される。**その場合でも、古いギャップが永久に処理されない状態を作らないこと**（現在の `kickoff_at` 降順のみだと、直近の試合が常に優先され、古いギャップに到達しない）。

### 3. 結果の報告

レスポンスは既に `{ errors, filled, gaps }` を返している。ワークフロー側でこれを**ログへ出力**し、`filled` と `gaps` が要約行に残るようにすること。

タイムアウトした場合に、**ワークフローが失敗と報告しつつサーバ側は完了している**状態を解消する。方法は実装時に判断してよい（処理を確実に時間内へ収める、あるいはタイムアウトを許容して結果を別途確認する等）。

### 4. 狙い撃ち

ワークフローに `workflow_dispatch` の入力を追加し、`matchIds` を渡せるようにする。`cron-post-match-recap-refresh.yml` の `from` / `to` 入力が既存の参考例になる。

### 5. スクリプトの是正

`scripts/fill-event-gaps.ts` の `loadGapMatches` に、ルート側と同等の並び順とギャップ絞り込みを入れる。`--limit` の既定値が実質的に機能していない現状を解消する。

## 受け入れ条件

1. `match_events` 全行を取得するクエリが存在しない。ギャップ判定が DB 側で行われている。
2. 既定の実行が 60 秒以内に完了する（またはタイムアウトしない構成になっている）。
3. ワークフローのログに、対象件数・成功件数・失敗件数が残る。
4. 処理が成功したのにワークフローが失敗と報告する状態が解消されている。
5. ワークフローから `matchIds` を指定して特定試合だけを処理できる。
6. `scripts/fill-event-gaps.ts` の `loadGapMatches` に並び順があり、ギャップを DB 側で絞り込んでいる。`--limit=50` で既存のギャップが検出される。
7. **スコア不一致によるスキップ（`event totals exceed final score`）が引き続き機能する。** 誤ったイベントを登録しないガードを弱めていないことをテストで担保する。
8. 古いギャップが永久に未処理のまま残らない（優先順位の設計を報告すること）。
9. `pnpm lint` / `pnpm tsc --noEmit` / `pnpm test` / `pnpm build` がすべて clean。

## 未解決の質問

1. **`maxDuration` を延ばすか、バッチを小さくするか。** 1件1.5秒の待機が必須のため、60秒では実質35件程度が上限になる。現在のギャップは28件なので一度に処理できる範囲だが、将来増えたときの設計が要る。

2. **live ingest 経路でイベントを取れるようにする方が本筋かもしれない。** `lib/ingestion/live-ingest.ts` は `statusChangedToFinished` の試合に対しイベント解析を行うが、`rawHtml` が空だとスキップする（314-317行）。リポビタンのアダプタは既存スクレイパーの型に HTML が無いため空文字を渡している。ここを埋めれば試合終了と同時にイベントが入り、`fill-event-gaps` は復旧手段に徹することができる。本 spec の対象外だが、**8/15 の第2戦に間に合わせたいのはむしろこちら**である可能性がある。

3. **解析失敗22件中21件の内訳は別途対応が要る。** `no unique event block found` と `event totals exceed final score` はそれぞれ原因が異なる。前者はシーズンページから該当試合ブロックを特定できない問題、後者はガードの正常動作である。本 spec を実施しても、これらは解消しない。
