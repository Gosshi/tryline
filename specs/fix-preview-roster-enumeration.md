# プレビューがラインアップを羅列し、考察の紙面を潰している

## 背景

2026-08-21、南アフリカ vs ニュージーランド第1テストのプレビュー（QA 情報密度 **5/5**、published）に、以下のセクションが含まれていた。

> ## 前方の密度と9番・10番の選択が攻撃の輪郭を決める
> 南アフリカは1番オックス・ンチェ、2番マルコム・マークス、3番ウィルコ・ラウを先発させ、4番エベン・エツベト、5番ルアン・ノーチェが続く。後方には9番グラント・ウィリアムズ、10番サーシャ・ファインバーグ＝ムンゴメズル、12番ダミアン・デアレンデ、13番ジェシー・クリエル、14番チェスリン・コルビ、15番ダミアン・ヴィレムセが並ぶ。ベンチには16番ヤン＝ヘンドリク・ウェッセルズ、22番コーバス・ライナッハ、23番マニー・リボックが控える構成だ。
>
> 一方のニュージーランドは、1番イーサン・デ・グルート、2番コーディー・テイラー、3番タイレル・ローマックスを前列に置き、4番ジョシュ・ロードと5番ファビアン・ホランドを先発させる。（以下略）

**約25名の名前と背番号の列挙で、記事1,944字のうち約500字（およそ4分の1）を占める。**

問題は3つある。

**1. 同じページに同じ情報の表がある。** `components/match-lineups-section.tsx` が試合ページでラインアップを描画している（`app/matches/[id]/page.tsx` から使用）。**本文はすぐ上の表を散文で言い直しているだけで、情報量はゼロ。**

**2. 見出しの約束を本文が果たしていない。** 見出しは「9番・10番の選択が攻撃の輪郭を決める」だが、本文は誰が出るかを並べただけ。9番・10番の考察は別のセクションにある。

**3. QA が満点を付けた。** 情報密度 5/5。指標が「facts が含まれているか」を測っており、「解釈が加わっているか」を測っていない。

このセクションで唯一情報があったのは、**ホランドがトゥイプロトゥに代わる唯一の変更**という一文だけである。そこには起用変更の意味がある。残りは表を読めば分かる。

### 根本原因1: 人数のノルマが課されている

`lib/llm/prompts/generate-preview.ts:181-190`

```ts
const lineupUsageBlock = hasLineups
  ? [
      "【ラインアップ実名活用】projected_lineups に存在する選手名は積極的に本文へ登場させること。",
      "- projected_lineups.home から最低3名、projected_lineups.away から最低3名の実名を本文に含めること。",
      "- キーポジション（9番、10番、11番・14番・15番、主将、2番など）を優先し、先発選手は「先発」として扱うこと。",
      ...
      "- 対面ポジションまたは役割が近い選手同士の実名マッチアップを最低1つ描くこと。",
    ].join("\n")
```

**「最低3名」は人数の下限であり、羅列で満たせる。** 理由を求めているのは「実名マッチアップを最低1つ」の1行だけで、しかも下限が1つしかない。

### 根本原因2: 量の要求が二重になっている

`fix-preview-sourced-facts-underuse.md`（PR #709、2026-08-21 マージ）が `sourcedFactsBlock` をこう変更した。

```
本文の趣旨に沿うものはできるだけ多く反映すること。
```

**これは正しい修正だったが、`lineupUsageBlock` の人数ノルマと重なって「量を出せ」という圧力が二重になった。** #709 以前のプレビューは統計比較だけで薄かった。#709 以後は材料を並べるようになった。**どちらも解釈が無い点では同じ。**

### 根本原因3: 文言による禁止が効いていない

`lib/llm/prompts/qa-content.ts:125` には既にこう書かれている。

```
単なる列挙や不自然なこじつけは反映として数えないこと。
```

**この指示は存在し、#709 で preview にも適用されている。それでも情報密度 5/5 が付いた。**

**プロンプトへ文言を足すだけでは直らないことが実証されている。** 本 spec は決定的な判定を導入する。

## スコープ

対象:

- `lineupUsageBlock` の人数ノルマを、根拠を伴う言及の要求へ置き換える
- 羅列を決定的に検出するガードを追加する
- QA の情報密度ルーブリックで、根拠を伴わない実名列挙を加点対象から外す

対象外:

- **`components/match-lineups-section.tsx` の変更。** 表はこのままでよい。問題は本文が重複していること
- **選手名への言及そのものの禁止。** 根拠を伴う言及は増やしたい
- recap（試合後）。試合後は得点者への言及が自然に根拠を伴うため、同じ問題が起きているか未確認。**先に preview で方式を確立する**
- `sourcedFactsBlock` の「できるだけ多く反映」の撤回。#709 の結果は維持する
- 字数下限の変更（`lib/llm/content-length.ts` に触らない）
- 英語 preview
- 既存記事の再生成（マージ後に `content-regen` の手順で別途判断）

## データモデル変更

**なし。マイグレーション不要。**

## API サーフェス

### 1. 羅列の決定的検出（`lib/content/fabrication-guard.ts`）

同ファイルには決定的ガードが4つある（`containsUnsupportedStatistic` / `containsContradictedZeroStatClaim` / `hasConfirmedSourcedFactLineup` / `containsUngroundedPlayerReference`）。**同じ形式で追加すること。**

検出の考え方:

- 本文を文単位（`。`）に分割する
- 1文の中に「背番号＋選手名」のペアが**3つ以上**現れる文を**列挙文**とみなす
- 列挙文の合計文字数が本文全体に占める割合を算出する
- 割合が閾値を超えたら検出とする

**閾値は実装者が決めてよいが、以下2つを必ず満たすこと。**

- 本 spec 背景に引用したセクションを含む本文（1,944字中およそ500字が列挙）が**検出される**
- 「2名の実名＋それぞれの起用理由」で構成された段落が**検出されない**

**PR 本文に、選んだ閾値とその根拠、および上記2ケースの実測値を書くこと。**

背番号の表記ゆれ（`9番` / `九番` / `No.9`）は、実データで確認してから対応範囲を決めること。**現行の生成物に現れる表記だけを対象にすれば足りる。**

### 2. 生成プロンプトの変更（`generate-preview.ts:181-190`）

`lineupUsageBlock` から**人数の下限を削除**し、根拠を伴う言及を要求する形へ置き換える。

盛り込むべき趣旨:

- **ラインアップの羅列を禁止する。** 先発一覧は試合ページに表として掲載されており、本文で繰り返す価値がない
- 選手名に言及する場合は、**その選手固有の根拠を必ず添える**こと（前戦の実績、負傷・復帰、起用変更の意味、対面との関係など）
- 根拠を書けない選手には言及しない

**「最低3名」を「最低N名」に置き換えるだけにしないこと。** 人数の下限がある限り羅列で満たされる。

既存の以下は**維持する**。

- `is_starter` による先発・リザーブの区別
- `projected_lineups` / `match_events` に無い選手名・役職・外部文脈を創作しない禁止
- 片側だけにラインアップがある場合の片側限定ルール

`PROMPT_VERSION`（`generate-preview.ts:19`）を上げること。

### 3. QA ルーブリック（`qa-content.ts`）

情報密度の採点で、**根拠を伴わない実名列挙を加点対象から外す**旨を明示する。

既存の「単なる列挙や不自然なこじつけは反映として数えないこと」（`qa-content.ts:125`）は**残したうえで**、実名の列挙に対して具体的に述べる。

`PROMPT_VERSION`（`qa-content.ts:11`）を上げること。

**ただし本 spec の主眼は 1 の決定的ガードである。** ルーブリックの文言だけに依存しないこと（それが効かなかったのが背景）。

## UI サーフェス

なし。

## LLM 連携

段階4（ナラティブ生成）と段階5（QA）のプロンプト、および生成後の決定的ガード。

**新規 LLM 呼び出しを追加しない。** ガードはプログラム側で動く。

**ただしガードが発火すると再生成が走るため、間接的に LLM 呼び出しが増える可能性がある。** 閾値を厳しくしすぎると再生成が頻発する。実装時に既存の retry 上限（`lib/llm/stages/qa.ts`）を確認し、**無限に再生成しないことを確かめること。** モデル ID は直書きせず `lib/llm/models.ts` を参照すること。

## 受け入れ条件

1. 羅列検出の関数が `lib/content/fabrication-guard.ts` に存在し、既存4関数と同じ形式で export されている。
2. 本 spec 背景に引用したセクションを含む本文が**検出される**。この本文を丸ごとテストフィクスチャに含めること。
3. 「2名の実名＋それぞれの起用理由」で構成された段落が**検出されない**。
4. 選手名を一切含まない本文が検出されない。
5. `buildGeneratePreviewPrompt` の出力から「最低3名」という人数下限の記述が消えている。**修正前は存在することを固定するテストを置くこと。**
6. 同出力に、羅列の禁止と根拠を伴う言及の要求が含まれる。
7. `is_starter` による先発・リザーブ区別の指示が維持されている。
8. `projected_lineups`・`match_events` に無い選手名を創作しない禁止が維持されている。
9. 片側だけにラインアップがある場合の片側限定ルールが維持されている。
10. `generate-preview.ts` と `qa-content.ts` の `PROMPT_VERSION` が上がっている。
11. `contentType: "recap"` のプロンプト出力が本変更の前後で一致する。
12. `contentType: "preview"` / `language: "en"` の出力が本変更の前後で一致する。
13. ガード発火時に再生成が無限ループしない（既存の retry 上限に従う）ことをテストで確認できる。
14. `pnpm lint` / `pnpm tsc --noEmit` / `pnpm test` / `pnpm build` がすべて clean。
15. **既存記事の再生成は実施しない。** Codex の作業はコードとテストまで。

## 未解決の質問

1. **既存記事をどうするか。** 同じ羅列は他のプレビューにも存在する可能性が高い。マージ後に件数を調べ、再生成するかを Owner が判断する。再生成する場合は `content-regen` スキルの「少件数の試し焼き→検品→全件」を必ず経ること（2026-06-12 の 297 件 draft 化事故の再発防止）。**本 spec のガードは、その調査にそのまま使える。**

2. **recap にも同じ問題があるか。** 試合後は得点者への言及が自然に根拠（得点した事実）を伴うため、preview ほど深刻でない可能性がある。**未調査。** preview で方式が固まってから確認する。

3. **「根拠を伴う」を機械的に判定できるか。** 本 spec は「羅列の検出」だけを決定的にし、根拠の有無は QA に委ねている。羅列を潰しても「◯◯が先発する。彼は good player だ」のような空虚な根拠付けに逃げる可能性は残る。**通知（`feat-content-notification-diagnostics.md`）が入ってから、実際の生成物で観察して判断する。**

4. **`lineupUsageBlock` は `feat-lineup-aware-previews.md` が導入したもの。** 人数ノルマにはラインアップを確実に使わせる意図があったはずで、下限を外すと逆に選手名がまったく出ない記事に戻る恐れがある。**その兆候が出たら、下限ではなく「根拠付き言及の最低数」という形で戻すこと。**
