# sourced_facts が再取得のたびに重複を蓄積し、密度指標の母数を壊す

## 背景

2026-08-21〜23、南アフリカ vs ニュージーランド第1テスト（match_id: `d6d5b1ab-58ec-44c8-a31d-54fadc0a662e`）で `fetch-sourced-facts` を `force=true` で複数回実行した結果、件数がこう推移した。

```
7 → 15 → 23 → 31 → 36 → 43
```

**しかし増えているのは件数だけで、情報は増えていない。** 36件時点で内容を数えたところ、**実質は14種類程度**だった。

| 内容 | 件数 |
|---|---|
| コリシ欠場・デュ・トワ主将 | **4件** |
| ホランドがトゥイプロトゥに代わる唯一の変更 | **4件** |
| ファインバーグ＝ムンゴメズル先発・リボックはベンチ・ポラード除外 | 3件 |
| マッケンジー/ジョーダン/ロイガードのフィットネステスト通過 | 3件 |
| 先発一覧 | 3件 |
| シリーズ第1テストである | 3件 |
| スコット・バレット背中手術で遠征欠場 | 2件 |

**4件はすべて同じ `rugby.com.au` から、4通りの言い回しで入っていた。**

```
南アフリカ主将シヤ・コリシはハムストリングの回復過程にあり、この試合は欠場する。先発ではピーター＝ステフ・デュトイが主将を務める。
南アフリカはピーター＝ステフ・デュトイを主将に起用する。シヤ・コリシはハムストリングの回復にさらに時間を充てるため、この試合では主将を務めない。
南アフリカはピーター＝ステフ・デュトイが主将を務める。通常の主将シヤ・コリシはハムストリングの負傷から完全に回復するため、追加の時間を与えられた。
南アフリカはピーター＝ステフ・デュトイを主将に指名した。正主将シヤ・コリシはハムストリング負傷から完全に回復するため、さらに時間を与えられている。
```

### 根本原因

重複排除は2箇所にあるが、**どちらも文字列の完全一致でしか効かない。**

**1. DB の一意制約**（`supabase/migrations/20260606010000_create_match_sourced_facts.sql:14`）

```sql
unique (match_id, fact)
```

**2. バッチ内 dedup**（`lib/llm/sourced-facts/allowlist.ts:334`）

```ts
const key = `${item.fact.toLowerCase()}|${item.source_domain}`;
```

`fetch-sourced-facts` は毎回 LLM で記事から事実を抽出し直す。**抽出は非決定的で、同じ記事から同じ事実を取っても毎回違う日本語になる。** 1文字でも違えば別の行として `upsert`（`lib/llm/sourced-facts/fetch.ts:528`）される。

**つまり `force=true` で再取得するたびに、言い換えが1セット追加される。**

### 何が壊れるか

**1. 密度指標の母数が膨らむ**

`fix-preview-sourced-facts-underuse.md`（PR #709）で導入した基準が `qa-content.ts` にある。

> 本文の趣旨に沿う sourced_facts のおおむね7割以上を自分の日本語で反映している

**実質14種類の情報が36件として数えられるため、すべて書いても7割に届かない。** 達成不能に近い基準になっている。2026-08-21 の再生成で情報密度が 2/5 に落ちた一因はここにある可能性が高い。

**2. プロンプトのトークンを食う**

36件で概ね3,000〜4,000字。さらに `fix-preview-core-question-derivation.md`（PR #716）のレビューで、核心ブロックにも同じ JSON を埋め込む実装が上がり、**二重埋め込みで最大8回同じ事実が現れる**状態になりかけた（差し戻して解消済み）。

**3. 重複した事実が過剰に重み付けされる**

「最も特徴づける出来事を選べ」と指示しても、**重複の多い事実ほどプロンプト内で目立つ。** 選択の歪みになる。

### 副次的に判明した制約の穴

`unique (match_id, fact)` に **`content_type` が含まれていない。** preview 用と recap 用で同一文字列の事実が発生した場合、片方が他方を上書きする。実害はまだ観測していないが、**設計として誤っている**（インデックスのほうは `(match_id, content_type, confidence)` と content_type を含んでおり、非対称）。

## スコープ

対象:

- 再取得時に同一ソースからの旧抽出が蓄積しない仕組み
- `unique (match_id, fact)` に `content_type` を含める
- 既存の重複行の棚卸し（**調査のみ。削除は Owner 判断**）

対象外:

- **埋め込みベクトルによる意味的類似判定の導入。** 新しいインフラとコストを伴う。まず構造で解く
- allowlist・取得元の変更
- 抽出プロンプトの変更（**非決定性は前提として受け入れる**）
- 密度基準「7割」の変更。**母数が正しくなれば基準は妥当**
- **既存重複行の削除そのもの。** 件数を出すまでが本 spec
- 既存記事の再生成

## データモデル変更

**マイグレーションが必要。**

- `unique (match_id, fact)` → `content_type` を含む形へ変更

**`feedback_migration_before_merge` の原則に従い、マージ前に本番へ適用すること。** 既存データに `content_type` 違いの同一 `fact` があると制約変更が失敗しうるため、**適用前に重複の有無を確認すること。**

## API サーフェス

### 1. 再取得時の置き換え（`lib/llm/sourced-facts/fetch.ts:526-531`）

現在は無条件 `upsert` で追記される。**同一の `(match_id, content_type, source_domain)` について再取得したとき、旧抽出が残らない形にすること。**

推奨する考え方は「**あるソースからの最新の抽出が、そのソースからの前回の抽出を置き換える**」である。これなら意味的類似の判定が不要で、他ドメインの事実も失わない。

**実装方式は判断してよいが、以下を満たすこと。**

- 背景に挙げたコリシ欠場4件（すべて `rugby.com.au`）が、再取得後に**1件へ収束する**
- **別ドメインの事実が消えない**（`springboks.rugby` / `therugbypaper.co.uk` の事実が `rugby.com.au` の再取得で失われない）
- 再取得で**取得できなかった場合に、既存の事実を全部失わない**（0件を取得した場合に全消しにならないこと）

最後の条件は重要である。`fix-recap-sourced-facts-zero-result-retry.md` が扱ったとおり、**取得が0件になるケースは実際に起きる**。

### 2. 一意制約の変更

`content_type` を含める。既存の `(match_id, content_type, confidence)` インデックスと整合させる。

### 3. 重複の棚卸しスクリプト

`tools/` に読み取り専用のスクリプトを追加し、既存データの重複規模を出す。

- 試合ごとの `content_type` 別の件数
- 同一 `(match_id, content_type, source_domain)` に何件あるか
- 件数が多い上位の試合

**SELECT のみ。削除しない。** 起動方法は既存の `tools/` に合わせる（`node --env-file=.env.production.local tools/run-ts.cjs <script>`）。

## UI サーフェス

なし。

## LLM 連携

**新規 LLM 呼び出しを追加しない。** 抽出の回数自体は変わらないが、**プロンプトへ乗る件数が減るためトークンは減る。** モデル ID は直書きせず `lib/llm/models.ts` を参照すること。

## 受け入れ条件

1. 同一の `(match_id, content_type, source_domain)` で2回続けて取得したとき、**2回目の結果が1回目を置き換え、件数が累積しない**。
2. 背景のコリシ欠場4件に相当するケース（同一ドメイン・異なる言い回し・同一事実）が、再取得後に1件へ収束することをテストで確認できる。
3. **別ドメインの事実が、あるドメインの再取得で失われない。**
4. **取得結果が0件のとき、既存の事実が全消しにならない。**
5. `unique` 制約に `content_type` が含まれている。
6. マイグレーションが存在し、**本番適用手順が PR 本文に書かれている**。
7. 棚卸しスクリプトが存在し、SELECT のみで動作する。**書き込み系 SQL を含まない**ことをコードレビューで確認できる。
8. 棚卸しスクリプトが、既存データの重複件数を出力する。
9. `pnpm lint` / `pnpm tsc --noEmit` / `pnpm test` / `pnpm build` がすべて clean。
10. **既存重複行の削除と記事の再生成は実施しない。**

## 未解決の質問

1. **既存の重複をどうするか。** 棚卸しの結果次第。削除する場合は `DELETE` を伴うため **Owner 自身または Codex が実行する**（Claude Code は実行しない）。削除後に密度スコアがどう動くかを観測する価値がある。

2. **「置き換え」で本当に良いか。** 同じソースでも、時間が経てば新しい事実が加わる（例: 試合前は「スキャン検査を受ける」、後日「欠場が確定」）。置き換えると**古い事実が消える**が、それは通常望ましい。ただし**試合をまたいで有効な事実**（シリーズの決着方式など）が消える可能性はある。実運用で観察する。

3. **密度基準「7割」の再評価。** 母数が正しくなった後、7割が妥当かを見直す価値がある。**本 spec では変更しない**（母数が壊れている状態で閾値をいじると、原因の切り分けができなくなる）。
