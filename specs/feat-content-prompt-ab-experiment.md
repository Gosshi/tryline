# 記事生成プロンプトの A/B 比較（現行 A と書き換え B、4 試合 8 本）

## 背景

- Owner の要望（2026-09-24）: レビューは密度と戦術を濃いまま保ち、「事実の羅列感」を減らして、過去の試合や分析による独自性を出したい。
- 同じ日に行った試し焼き（GPT-6 と現行 terra の比較）で、効き目が大きいのは**モデルではなくプロンプトの構造**だと分かった。
- 2 本の監査が、指示同士の食い違いと水増しの圧力を具体的に挙げている。
  - `docs/content-prompt-audit-2026-09-24.md`（GPT-6。事実の裏付けと QA ガード）
  - `docs/prompt-structure-audit-2026-09-24.md`（Claude Code。指示文の書き方）
  - 主な指摘:
    - レビューの字数指示が 2,000 字なのに、QA の下限は 1,200 字
    - プロンプトの前に付く冒頭指示（250〜350 字）が、本体の字数と食い違う
    - 「好調」を禁じる一方で使えと指示している
    - キックの分母を禁じる一方で「4/5」を勧めている
    - 分からない原因・次戦の相手・来季の見通しを必須にしている
    - 人数・項目数のノルマがある
    - 読者が試合ページの表で既に見ている得点経過を、本文でなぞらせている
- 書き換えを本番に入れる前に、**同じモデル・同じ入力・同じ QA** で現行 A と書き換え B を比べ、B の方が良いかを確かめる。本番の記事は 1 本も変えない。

## スコープ

**対象**
1. B 版のプロンプトビルダーを新設する（プレビュー・レビューの本文、日本語のみ）。
2. `generateMatchContent` に試し焼き専用のオプションを 3 つ足す。
   - `promptVariant`: A か B を選ぶ。
   - `frozenInput`: 固定した入力を使い、集約と抽出を飛ばす。
   - `trialFirstAttemptOnly`: 初回の出力だけを評価する。
3. 比較用スクリプト `scripts/ab-content-prompts.ts`（`freeze` と `run` の 2 段）と、そのテスト。

**対象外**（別の spec にする）
- GPT-6 監査の P1 にあたる安全面の修正。具体的には、表記辞書の選手が人名照合の対象から外れる経路（`lib/content/allowed-entities.ts:128` → `lib/llm/stages/verify-entities.ts:116`）、未確定メンバーが抽出・加筆の経路から流れ込むこと、抽出で PG 数を反則傾向として使うこと。
  - A/B は非公開で、両方の版が**同じ固定入力・同じ抽出結果**を使うので、この実験の比較には影響しない。
  - ただし **B を本番に入れる前に、これらを直す必要がある**。
- QA の採点基準（`qa-content.ts`）とコード側ガード（`qa.ts`）の変更。両方の版を現行の `qa@2.11.0` で採点し、記録するだけにする。
- 英語版、抽出プロンプト、人名照合プロンプトの変更。
- H2H・順位の時点管理など、入力材料の変更。
- 既存記事の再生成と、B の本番適用（結果を見て Owner が判断する）。

## API サーフェス

### 1. `generateMatchContent`（`lib/llm/pipeline.ts:210`）のオプション追加

```ts
options: {
  models?: ContentModelOverrides;
  persist?: boolean;
  comparisonQaModel?: string;
  promptVariant?: "A" | "B";            // 既定は "A"
  frozenInput?: {
    assembled: AssembledContentInput;
    tacticalPoints: TacticalPoint[];
  };
  trialFirstAttemptOnly?: boolean;      // 既定は false
}
```

- `frozenInput` を指定したときは、段 1（`assembleMatchContentInput`）と段 2（`extractTacticalPoints`）を呼ばず、渡された値を使う。
  - 段 1 のあとにあるレビューの整合性チェック（`eventIntegrity` の mismatch と events_unavailable による skip）は、固定された `assembled` に対してそのまま実行する。
- `trialFirstAttemptOnly: true` のときの動き:
  - 本文の生成は 1 回だけ。`NARRATIVE_GENERATION_ATTEMPTS` のループを 1 回で抜ける。
  - 人名照合と QA は通常どおり実行し、判定（verdict）をそのまま結果に入れる。
  - 字数不足の加筆（`reviseNarrativeLength`）も、作り直しもしない。
- `promptVariant`、`frozenInput`、`trialFirstAttemptOnly` のどれかを指定したときは、`persist !== false` なら**例外を投げる**。本番の経路からは使えないようにする。
- `promptVariant` を省略した場合と `"A"` を指定した場合は、現行とまったく同じ結合プロンプトになること（受け入れ条件 1）。

### 2. `PipelineTrialDetails` に追加する項目

```ts
promptSha256: string;        // 実際にモデルへ渡した結合プロンプト全体のハッシュ
prompt: string;              // 結合プロンプト全文（台帳とレビュー用）
inputSha256: string;         // frozenInput（assembled＋tacticalPoints）のハッシュ
```

`generateNarrative`（`lib/llm/stages/generate-narrative.ts:50`）の戻り値に、組み立てたプロンプト文字列 `prompt` を足して受け渡す。

### 4. `scripts/ab-content-prompts.ts`

実行方法は `node --env-file=.env.production.local tools/run-ts.cjs scripts/ab-content-prompts.ts <sub> ...`（本番スクリプトの実行方法の決まりどおり）。

**`freeze --matches <id,...> --content-type preview|recap [--out <dir>]`**
- 各試合について `assembleMatchContentInput(matchId, "ja", contentType)` を実行し、続けて `extractTacticalPoints(assembled)` を 1 回だけ実行する（現行の `MODELS.FAST`）。
- 次の場合は、その試合を**失敗扱いにしてファイルを書かない**:
  - プレビューで、試合の `status` が `scheduled` でない、または `home_score` / `away_score` が null でない（試合後の入力がプレビューに混ざるのを防ぐ）。
  - レビューで、match_events が 0 件、または `eventIntegrity.status === "mismatch"`。
- 出力は `tmp/prompt-ab/fixtures/<matchId>-<contentType>.json`（`tmp/` は gitignore 済み）。中身:
  - `assembled`、`tacticalPoints`、`inputSha256`
  - `frozenAt`（ISO）、`gitSha`（`git rev-parse HEAD`）
  - 抽出の `PROMPT_VERSION`、抽出に使ったモデル ID と費用
- 同じファイルが既にあれば上書きしない（`--force` がある場合だけ上書き）。

**`run --fixtures <file,...> [--max-usd 2] [--dry-run]`**
- 各 fixture について、`promptVariant` の A と B で 1 本ずつ `generateMatchContent(matchId, contentType, "ja", { persist: false, frozenInput, promptVariant, trialFirstAttemptOnly: true })` を呼ぶ。A と B の順番は fixture ごとに無作為にする（乱数の種を台帳に残す）。
- モデル: 本文・QA・人名照合とも現行の `MODELS` のまま（上書きしない）。`comparisonQaModel` は使わない。
- 費用の上限:
  - 各呼び出しの前に「使った額＋1 本あたりの見込み額」が `--max-usd`（既定 2）を超えるなら、そこで止める。
  - 見込み額は既存の `getRecentAverageArticleCost`（`scripts/trial-content-models.ts`）を流用する。
  - `--dry-run` は LLM を呼ばず、組み合わせの一覧と見込み額だけを出す。
- 出力先は `tmp/prompt-ab/<ISO 時刻>/`:
  - `ledger.json`: 1 本ごとに次を記録する。
    - matchId、contentType、variant、promptVersion、promptSha256、inputSha256、各段のモデル ID
    - QA の点数・判定・issues、人名ゲートの結果（通過したか、根拠のない表記）
    - 本文の字数、`splitRecapForPaywall`（`lib/match-content/markdown.ts:123`）で分けた**無料部分と有料部分の字数**（レビューのみ）
    - 費用と所要時間、`gitSha`、乱数の種
  - `prompts/<matchId>-<variant>.txt`: 結合プロンプトの全文。
  - `blind/<matchId>-X.md`、`blind/<matchId>-Y.md`: 本文だけを置く。版名・版番号・QA 結果は入れない。X と Y のどちらが A かは fixture ごとに無作為に決める。
  - `blind-key.json`: X と Y の対応表。`blind/` とは別の場所に置く。
  - `review-sheet.md`: 付録 B の評価表のひな形（試合ごとに X と Y の欄）。
  - `summary.md`: 版別の QA 平均点、判定、字数、費用の表。**Owner が評価を終えるまで、A と B は名前を伏せて X/Y と表示する**（`--reveal` を付けた場合だけ A と B で表示する）。

**採用の目安**（予備判定であって、統計的な証明ではない）:

- 4 組中 3 組以上で Owner が B を選ぶ。

41% の作り直し率が下がったという結論は、この 8 本からは出さない。

## 受け入れ条件

1. **A は本番と変わらない。**
   - 変更前の main で、固定した fixture 入力（テスト用に作ったもの）について `buildJapaneseNarrativePrompt` が返す結合プロンプトを、プレビューとレビュー（データの揃い方 3 通り）の計 4 通りで保存する。
   - 変更後に `promptVariant` を省略した場合と `"A"` を指定した場合の出力が、保存した文字列と**完全に一致する**テストを置く。
   - 確認方法: A の分岐に 1 文字足すとテストが落ちること。
2. `promptVariant`、`frozenInput`、`trialFirstAttemptOnly` のどれかを `persist` 未指定（true 扱い）と一緒に渡すと例外になるテストがある。
3. `frozenInput` を渡したとき、`assembleMatchContentInput` と `extractTacticalPoints` が**呼ばれない**ことをモックで確かめるテストがある。
4. `trialFirstAttemptOnly: true` のとき、本文生成が 1 回だけで、`reviseNarrativeLength` が呼ばれないことを確かめるテストがある（QA が retry と判定する条件にして確かめる）。
5. B の結合プロンプトに、次の文字列が**含まれない**ことを確かめるテストがある（プレビューとレビューの両方、データの揃い方の全分岐）:
   - `2,000字`
   - `250〜350`
   - `最低3名`
   - `最低3種類`
   - `最低1つ`
   - `好調（0.8`
   - `ゴール4/5`
   - `来シーズン`
   - `正確な最終スコアである`（プレビューのみ）
   - `【絶対禁止表現`
   - 確認方法: 付録 A の文言にこのどれかを混ぜると落ちること。
6. B の結合プロンプトに、次が**含まれる**ことを確かめるテストがある。
   - `KICKOFF_TIMEZONE_INSTRUCTION` と `MATCH_DURATION_INSTRUCTION` の全文
   - 日本語表記グロッサリのブロック（グロッサリが空でない入力で）
   - `試合データ:` に続く、サニタイズ済みの入力 JSON
   - 戦術ポイントの JSON
   - レビューでは、match_events とスコア推移の値
   - 未確定ラインアップの選手名が B のプロンプトに**出ない**こと（`sanitizeUnconfirmedProjectedLineups` が効いていること）
7. レビューの B は、見出しとして `# この試合の核心`、`# 試合全体像`、`# ターニングポイント` をこの順に指示する。見出し名は `qa.ts:567`、`lib/match-content/description.ts:32` の文字列と一致させる（テストで一致を確かめる）。
8. `freeze` は、試合後のプレビュー（status が scheduled でない、またはスコアがある）と、イベント 0 件またはスコア不一致のレビューを拒否し、ファイルを書かない（テストあり）。
9. `run` のテストでは LLM をモックにして、次を確かめる:
   - fixture 1 件につき A と B が 1 本ずつ作られる。
   - `blind/` のファイルに版名・版番号・QA の点数が含まれない。
   - `blind-key.json` の対応が `ledger.json` と一致する。
   - 見込み額が上限を超える場合は、LLM を 1 回も呼ばずに止まる。
10. `pnpm lint`、`pnpm typecheck`、`pnpm test` が通る。**3 つとも実行して、結果を完了報告に含める。**

## 付録 A: B 版の文言（正）

> 出典は GPT-6 監査の 5.1〜5.3。そこに Claude Code 監査の F14（読者が試合ページで既に見ている情報）を足し、キックの書き方は安全側（成功本数のみ）に統一した。改行位置は自由。文言は変えないこと。

### A-1. 共通指示（`variant-b/shared.ts`）

```text
あなたはTrylineの日本語編集担当です。渡された試合の根拠から、読者が試合を見る・振り返る際に役立つ、一つの問いと一つの発見をまとめます。現地取材、映像確認、関係者への取材を行ったように書かないでください。

優先順位は、事実と人物の裏付け、引用・権利の制約、記事構成、文体の順です。字数や見栄えのために上位の条件を破ってはいけません。

【使える根拠】
・この指示に続けて渡される試合データ、sourced_facts、派生スタッツ、チームスタッツ、順位表、戦術ポイントだけを使います。あなたが事前に知っている選手の経歴・所属・役割・統計は使いません。
・戦術ポイントは論点の候補です。元の事実で確認できない主張は採用しません。
・数値には対象チーム・選手、指標、期間を対応させます。欠損値を0と扱いません。反則数のデータがないチームについて、反則の多い少ないや規律を断定しません。
・直近の収録試合の結果を、今季全体や同一大会の成績と読み替えません。
・PG成功数は反則数ではありません。キックは成功本数だけを書き、試投数・成功率・分数表記は使いません。
・時系列や数値の差だけでは、原因、戦術の仕組み、心理、能力は証明できません。記録上の変化は説明できますが、原因には原因を支える観測が必要です。
・日時と順位は対象時点を確認します。試合後の情報を試合前の事情にしません。

【人物と引用】
・人名は、確定メンバー、得点イベント、sourced_factsに出てくる人物だけを使います。表記辞書への掲載だけでは使用許可になりません。
・欠場報道は欠場の根拠であり、出場や他選手の先発を推定する根拠ではありません。
・人名の人数ノルマはありません。根拠のない役割・評価・発言を付けません。
・生テキストの転載はせず自分の日本語で説明します。直接引用は原則避け、必要な場合も15語以内、同一ソースから複数回引用しません。自分の要約を選手や監督の発言のように見せてはいけません。

【編集】
・事実を列挙するだけで終えず、「この対比から何が分かるか」を一段だけ説明します。例えば得点区間の違いは説明できますが、それだけで守備崩壊とは呼べません。
・一つの事実を別の節で再掲する場合は、新しい比較に不可欠な最小限にします。
・答えられない原因、次戦相手、来季の見通しを埋めません。

```

### A-3. レビュー固有（`generate-recap-b.ts`）

```text
終了した試合のレビューを書いてください。読者は海外ラグビーを日本語で追うファンで、この記事は試合ページに載ります。同じページに得点経過の表（時刻・得点者・種別）と最終スコアが既にあるため、本文の役割は、表では分からないこと（流れが変わった理由として言える範囲、両チームの差、次に何を見るべきか）を伝えることです。表の内容を順番に書き起こしません。

# ターニングポイント

全体は1,200～1,600字を目安とします。最終節を分析の中心にしますが、節ごとの最低字数は設けません。根拠と構成上の必要があれば目安を超えても構いません。材料が足りない場合は、創作や反復で字数を埋めません。出力は日本語のマークダウン本文だけです。
```
