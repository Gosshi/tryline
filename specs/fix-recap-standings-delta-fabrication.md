# recap が「試合前の順位」を捏造する問題

## 背景

2026-09-21、Top 14 の j3 にイベントが入った直後に生成した recap 2 本が、
どちらも `factual_grounding: 2` で reject され draft 止まりになった。

QA の指摘:

```
入力データにない試合日時、シーズン、順位、勝ち点などの情報が含まれています。
```

本文の該当箇所（RC Vannes v Stade Toulousain）:

> 試合前の順位表ではトゥールーズが1試合を終えて勝ち点1の10位、ヴァンヌが勝ち点0の13位だった。

**試合経過の記述は完全に正確だった。** 3分ラファージュのPG、21分ブティエのドロップゴール等、
`match_events` と 1 件も食い違わない。壊れているのは順位の枠組みだけである。

### 原因

プロンプトが**入力に存在しない値を要求している**。

| 箇所 | 指示 |
|---|---|
| `lib/llm/prompts/generate-recap.ts:52` | 「大会内での位置づけ（大会名・シーズン・**順位表への影響**、…）」 |
| 同 `:94` `:101` | データスパース時のセクション「# 大会文脈と**順位への影響**」450-550字 |
| 同 `:243` | 「スコアと**順位変動**のみを記述し、試合展開の描写は行わないこと」 |
| 同 `:245` | 「competition_standings の**順位変動（この試合結果による上昇/下降）を必ず計算**して記述すること」 |

一方 `loadCompetitionStandings`（`lib/llm/stages/assemble.ts:514-545`）が渡すのは
**現在の順位表スナップショット1枚だけ**で、position / total_points 等の現在値しか持たない。

「この試合による変動」は before と after の差分だが、**before が入力に存在しない**。
モデルは必ず書けと指示されているので、before を作り出す。これが捏造の発生源。

Vannes 戦は `match_events` が 17 件あるため**データスパースではなく**、
`:52` の bullet（`:122` で使用）が効いている経路である。

### なぜ今まで出なかったか

退行ではない。**Top 14 は 2026-09-21 まで j3 のイベントが 0 件で、recap 自体が作られなかった**
（`specs/fix-top14-lnr-drop-goal-and-per-match-isolation.md`）。
イベントの壁が取れて初めてこの欠陥が露出した。

順位表の保有状況（2026-09-21 実測）:

| 大会 | competition_standings 行数 |
|---|---:|
| top-14-2026-27 | 14 |
| urc-2026-27 | 16 |
| premiership-2026-27 | 10 |
| pnc-2026 | **0** |

**PNC は順位表を持たないため、同日の PNC recap 2本は `factual_grounding: 5` で published だった。**
順位表を持つリーグ戦（Top 14 / URC / プレミアシップ）で今後も同じことが起きる。

## 実装方針

### 原則（この spec の本体）

**プロンプトが値の記述を要求してよいのは、その値が組み立て済み入力に実在する場合だけ。
実在しない値を求める指示は、条件付きで出さないか、そもそも書かない。**

今回は「差分」を要求しているのに入力が「現在値」しか持たない。
差分を要求するのをやめ、**現在値として言えることだけを言わせる**。

### 1. 非スパース経路（`:52`）

`buildMatchContextBullet` の戻り値から「順位表への影響」を落とし、
**現在の順位表スナップショットとして言えること**に置き換える。

要求してよい例: 「この試合を終えた時点で◯位」「勝ち点◯」
要求してはいけない例: 「試合前は◯位だった」「◯位から◯位へ上がった」「順位を上げた/下げた」

### 2. データスパース経路（`:243` / `:245`）

「順位変動（この試合結果による上昇/下降）を必ず計算して記述すること」を、
現在値の記述に置き換える。**「必ず計算」を残さない。**

### 3. セクション名（`:94` `:101`）

「# 大会文脈と順位への影響」は「影響＝差分」を含意するため、
差分を求めない名前に改める。字数目標（450-550字）は維持する。

**セクション名は出力の見出しとしてそのまま本文に出る。**
`:103` に「上記5つの見出し以外は絶対に追加してはならない」という制約があり、
見出し名を変える場合は同じ配列内の記述と整合させること。

### 4. 禁止の明示

順位表ブロックの近傍に、**試合前の順位・勝ち点を書いてはならない**ことを明示する。
既存の禁止文（`:341` 「入力にない統計・スコア・負傷・欠場・発言・選手名を推測・創作してはならない」）
に「順位・勝ち点・試合前の順位」を加える形でもよい。

`:341` の列挙に順位が無かったことが、今回モデルを素通りさせた一因である。

## 受け入れ条件

### プロンプト

1. `buildGenerateRecapPrompt` が返す文字列に、**差分を要求する語が含まれない**。
   具体的に、`/順位変動|順位表への影響|上昇\/下降|試合前の順位/` のいずれにもマッチしない。
   これを非スパース入力・データスパース入力の**両方**で検証する。
2. 同文字列に、**試合前の順位・勝ち点を書いてはならない旨の禁止文が含まれる**。
3. データスパース経路のセクション見出しリストと字数目標リストで、
   同じ見出し名が使われている（`:94` 側と `:101` 側の不一致が無い）。
4. 出力セクションは 5 つのままで、増減していない。

### 回帰

5. **見出し名を変える場合、以下の既存 assert が必ず落ちるので同時に更新する**
   （2026-09-21 に実測で特定済み）。

   - `tests/llm/prompts/generate-recap.test.ts:254` — `expect(prompt).toContain("# 大会文脈と順位への影響")`
   - `tests/llm/prompts/generate-recap.test.ts:255` — `expect(prompt).not.toContain("# 大会文脈と順位への影響（450-550字）")`

   他に漏れが無いか `grep -rn "大会文脈\|順位" tests/` で再確認し、
   更新した箇所を PR 本文に列挙すること。
   なお `tests/llm/prompts/generate-preview.test.ts` の「大会文脈」系 assert は
   preview 用プロンプトのもので本変更とは無関係。触らないこと。
6. `pnpm vitest run tests/llm` が全緑。

### 検証手順

7. AC 1 と AC 2 のテストを**修正前のコードに対して実行して落ちること**を確認してから修正する。
   AC 1 の正規表現は修正前の `generate-recap.ts` の `:52` / `:243` / `:245` の
   3 箇所にマッチする（2026-09-21 実測）。落ちなければテストが対象のプロンプトを
   見ていないので書き直す。
8. `pnpm tsc --noEmit` と `pnpm lint` が通る。
9. PR を出す前に `gh pr checks` で CI の緑を確認する（main では CI が走らないため）。

## デプロイ後の運用手順

実装には含めない。

1. draft の 2 本（RC Vannes v Stade Toulousain / Union Bordeaux Bègles v Stade Français）を再生成
2. `factual_grounding` が 3 以上へ改善するか確認する。**改善しなければこの spec の想定が外れている**ので、
   本文のどこが指摘されたかを見て原因を取り直す
3. 残る Top 14 5 試合の recap を生成する

## 未解決の質問

1. **順位変動を本当に書きたいなら、試合前の順位表が要る。**
   `competition_standings` は現在値のみを保持し履歴が無い。
   書きたい場合はラウンドごとのスナップショットを持つ設計変更が必要で、
   これは本 spec のスコープ外。Owner の判断事項。
   本 spec は「書かせない」側に倒している。

2. **`factual_grounding: 3` で publish される閾値の是非**（`lib/llm/stages/qa.ts:384`）。
   2026-09-21 に Sharks v Benetton（5/10 の URC）が
   「順位表、勝ち点、キックオフ時刻…を断定しています」と指摘されながら
   `factual_grounding: 3` で published を通った。本 spec では触らない。

3. QA は「試合日時、シーズン」も指摘している。Vannes 戦の本文中の
   「2026年9月20日4時開始」は JST として正しい値だったが、
   その値が入力のどのフィールド由来かは未確認。順位の修正後に同じ指摘が残るなら、
   運用手順 2 で判明する。
