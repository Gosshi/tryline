# レビュー本文が「データが無い」ことを読者に報告する問題を修正

対象リポジトリ: **tryline のみ**（生成プロンプトは web 側にのみ存在）。

## 背景

2026-08-16、日本 vs オーストラリア第2戦のレビュー（`recap@4.16.0`）に以下の一文が公開された。

> オーストラリアの次の対戦相手と日程は、入力データには示されていない。そのため具体的な対戦構図は確定できない

同じ記事にもう 1 件ある。

> 順位表は入力データにないため大会順位への直接の影響は判定できない

**読者にとって何の情報にもならない。**「システムに渡されたデータの範囲」という内部事情を、記事の読者に向けて説明している。プレビュー側には既に「『情報が少ない』『選手不明』等の逃げ表現は一切禁止。手元のデータで書き切ること」という指示が `generate-preview.ts` の `dataSparseBlock` にあるが、**recap 側には同等の指示がない。**

### 本番実測: 8/9 以降に集中している

`match_content`（published / ja / recap、841 本）を「入力データ」「確定できない」「判定できない」「断定できない」「データにない」「記載がない」で検索した結果:

| 生成日 | recap 数 | 逃げ表現あり | prompt_version |
|---|---:|---:|---|
| 2026-08-16 | 1 | **1** | recap@4.16.0 |
| 2026-08-11 | 1 | **1** | recap@4.15.0 |
| 2026-08-10 | 1 | **1** | recap@4.15.0 |
| 2026-08-09 | 1 | **1** | recap@4.14.0 |
| 2026-07-20 | 3 | 0 | recap@**4.14.0** |
| 2026-07-19 | 3 | 0 | recap@4.13.1 |
| 2026-07-13 | 7 | 0 | recap@4.13.1 |
| 2026-07-12 以前 | 6 | 0 | recap@4.11〜4.13.0 |

**8/9 以降は 4 本中 4 本（100%）、7/20 以前は 20 本中 0 本。**

### 原因はプロンプト改版ではない

`recap@4.14.0` は 7/20（0 件）と 8/9（1 件）の両方で使われている。**プロンプトのバージョン差では説明できない。**

**違いは大会の性質にある。**

| 期間 | 大会 | 順位表 |
|---|---|---|
| 8/9〜8/16 の 4 本 | `lipovitan-challenge-cup-2026` / `greatest-rivalry-2026` | **なし**（テストマッチ・ツアー） |
| 7/20 以前の 20 本 | `nations-championship-2026` 等 | あり |

実際の文面が「順位表は入力データにないため〜」であることとも一致する。**順位表や次戦などのデータが存在しない大会で、LLM がその不在を本文に書いてしまっている。**

### なぜ今後も起きるか

順位表を持たない大会は今後も続く。

- `greatest-rivalry-2026`: 2026-09-12 まで（南アフリカ代表との 4 テスト＋クラブ戦）
- 日本代表の 11 月欧州遠征、各国のツアー・テストマッチ全般

**放置すれば、最も注目される試合ほどこの表現が出る。** 実際、8/9 と 8/16 の 2 本はいずれも日本代表戦だった。

## スコープ

対象:
- `lib/llm/prompts/generate-recap.ts` — 存在しないデータの不在を本文に書かせない指示の追加
- `tests/llm/prompts/generate-recap.test.ts` — 上記の指示が出力されることのテスト

対象外:
- **`generate-preview.ts` の変更**（既に同等の指示がある）
- **`assemble` への次戦データ・順位表データの追加**。「データを渡せば書ける」という方向の修正は本 spec では行わない（未解決の質問 1 参照）
- QA ステージ・`fabrication-guard.ts` の変更。**逃げ表現は捏造ではない**ので、決定的ガードの対象にはしない
- 既に published となっている 4 本の再生成（段階実行は受け入れ条件に含めるが、一括再生成はしない）
- 順位表を持たない大会の判定ロジックそのもの

## データモデル変更

**なし。**

## API サーフェス

**新規ルートなし。** プロンプト文字列のみ変更する。

`PROMPT_VERSION` は上げること（`generate-recap.ts` の定数）。ただし**バージョンを上げても既存コンテンツは自動再生成されない**（`prompt_version` は `pipeline.ts:733` で記録されるだけで、再生成のトリガーではない）。この点を PR 本文に誤って書かないこと。

## UI サーフェス

**変更なし。** 生成される本文の内容が変わるのみ。

## LLM 連携

パイプライン **3 段階目（ナラティブ生成）**のプロンプトを変更する。

**新規の LLM 呼び出しは増えない。追加コストはゼロ。**

モデル ID は直書きせず `lib/llm/models.ts` の定数を参照すること。

## 受け入れ条件

### プロンプト

1. `buildGenerateRecapPrompt` の出力に、**入力データの不在に言及することを禁じる指示**が含まれている
2. その指示は、少なくとも以下を禁止対象として明示している: 「入力データ」「提供されたデータ」等のシステム内部を指す語、「確定できない」「判定できない」「断定できない」「示されていない」といった、データ不足を理由に結論を保留する表現
3. **「書けないなら、その話題に触れない」**という方針が指示に明記されている（不在を述べるのではなく、記述対象から外す）
4. 既存の禁止事項・構成指示・字数指示と矛盾しない（特に、字数を満たすために不在の説明で埋める余地を残さないこと）
5. `PROMPT_VERSION` が上がっている

### 保持すべき挙動

6. **事実の限界を述べること自体は禁止しない。** 「得点記録だけからは個々の守備対応を断定することはできない」のような、**取材・観戦の限界に触れる記述は許容される**。禁止するのは「入力データにない」というシステム内部の事情の開示である。この線引きが指示から読み取れること
7. データが十分にある試合の出力が、従来と同じ構成・品質で生成される（回帰なし）

### テスト

8. `tests/llm/prompts/generate-recap.test.ts` に、上記 1〜3 の指示文が出力に含まれることのテストが追加されている
9. `pnpm test` と型チェックが通る

### 段階実行（本番反映時）

10. **全件再生成をしない。** まず**順位表を持たない大会の試合 1 件**（`greatest-rivalry-2026` または `lipovitan-challenge-cup-2026`）で recap を再生成し、以下を Owner が目視検品する:
    - 「入力データ」「判定できない」等の表現が消えている
    - 順位表や次戦に触れないことで、記事が不自然に短くなっていない
    - 字数が `lib/llm/content-length.ts` の下限を満たしている（**値をここに書き写さず、実装時に同ファイルを確認すること**）
11. 検品通過後、残り 3 本を再生成するかを Owner が判断する。Codex は 1 件目の結果を報告して止まること

## 未解決の質問

1. **本 spec は「不在を書かせない」だけで、「次戦を書けるようにする」ことはしない。** 後者には `assemble` へ次戦データを渡す改修が必要だが、**その前にデータの正しさを確認する必要がある**。実測では DB 上のオーストラリアの次戦は 2026-11-08（イングランド戦）だが、第2戦の sourced_facts には「8/29 のアルゼンチン遠征」への言及がある。**8 月末〜9 月のオーストラリア戦が DB に存在しない可能性があり、そのまま次戦データを渡すと誤った情報を書く。** 調査は別途行う
2. 「順位表を持たない大会」を構造的に判定して、そもそも順位表セクションを要求しない設計にすべきか。本 spec ではプロンプトの禁止指示だけで対処するが、根本的には `competition` の性質に応じて構成指示を変えるほうが正しい可能性がある。効果を見てから判断する
3. 同種の表現が英語版 recap（`recap@x.x.x-en`）にも出るか未確認。英語側の実データが乏しいため本 spec では対象外とするが、日本語側の修正後に確認する価値がある
