# リフレッシュワークフローの失敗可視化と並列化

## 背景

2026-09-05 に本番で2つの問題が同時に表面化しました。

### 1. 全部失敗しても緑になる

OpenAI のクレジットが尽き、`cron-weekend-preview-refresh` の8試合すべてが `fetch-sourced-facts` で HTTP 500 になりました。

```
Weekend preview refresh summary: targets=8 success=0 failure=8
```

**それでも GitHub Actions の実行結果は `success` でした。**

ループは `set -uo pipefail` の下で失敗を数えるだけで、**失敗件数を終了コードに反映していません**（`.github/workflows/cron-weekend-preview-refresh.yml` / `cron-post-match-recap-refresh.yml`）。

**前日の定期実行も `success=4 failure=5` で緑でした。** つまり**半分失敗した状態が丸1日、誰にも通知されずに続きました。** 週末の直前に生成が止まっていたことに、Owner は手動実行するまで気づけませんでした。

### 2. 直列ループが 9/25 に破綻する

クレジット復旧後の再実行の実測です。

| | |
|---|---|
| 8試合 | **16分35秒** |
| 1試合あたり | **約2.1分** |

ループは1試合ずつ `fetch-sourced-facts` → `generate-content` を叩くだけで、**並列化されていません。** `timeout-minutes` は **30** です。

**2026-09-25 に URC 144試合とプレミアシップ90試合が開幕すると、対象は週20〜30試合になります。**

**2.1分 × 25試合 = 約52分。30分の枠に収まりません。** 途中で打ち切られ、後半の試合は生成されないまま緑で終わります。**問題1と重なると、誰も気づきません。**

## スコープ

対象:
- `.github/workflows/cron-weekend-preview-refresh.yml`
- `.github/workflows/cron-post-match-recap-refresh.yml`

対象外:
- **アプリケーションコード全般。** `app/api/cron/` 配下と `lib/` に差分を作らない
- **スケジュールの変更**（木21:05 / 金21:05 / 月09:05）
- **対象試合の決め方**（カレンダー API の呼び方・日付範囲・`status` フィルタ）
- 生成の中身（プロンプト・モデル・QA）

## 実装順の依存

**`specs/feat-tuesday-recap-refresh.md` を先に実装してください。** そちらが `cron-post-match-recap-refresh.yml` に火曜のスケジュールと分岐を足すので、**後から本 spec を当てるほうが衝突しません。**

## 1. 失敗を終了コードに反映する

**`failure` が1件でもあれば、ステップを失敗させてください。**

サマリ行（`... summary: targets=N success=N failure=N`）は**現行の文言のまま残してください。** ログを目で追う手順を変えないためです。

**成功件数が0で対象件数が0でない場合も、当然失敗になります。**

**対象が0件のときは成功で終わってください。** 火曜のレビュー再生成は「手動入力が無ければ0件」が正常です（`feat-tuesday-recap-refresh.md`）。

## 2. 分割して並列実行する

**GitHub Actions の matrix で試合を分割してください。**

```
ジョブ1: 対象試合を解決し、チャンクに分けて出力
   ↓
ジョブ2: matrix でチャンクごとに並列実行（既存のループをそのまま使う）
   ↓
ジョブ3: 全チャンクの結果を集計し、失敗があれば失敗させる
```

### チャンクの大きさと並列度

**どちらも定数として YAML に書いてください。**

- **1チャンクあたりの試合数**: 推奨 5
- **同時実行数（`max-parallel`）**: 推奨 3

**並列度を上げすぎないでください。** 同時に走る `generate-content` が増えると OpenAI のレート制限に当たります。**3並列 × 5試合で、25試合なら2巡・約21分**の想定です。

### 上限

**1回あたりの最大試合数を定数で定義し、超えたら先頭だけ処理してログに残してください。**

推奨値は 40。**日付範囲の指定を誤ったときに残高を焼き切らないためのガードです。** 2026-09-05 にクレジットが尽きた実績があります。

## コストは減りません（重要）

**並列化は所要時間を縮めるだけで、LLM の呼び出し回数は変わりません。**

対象が週8試合から25試合に増えれば、**LLM コストはそのまま3倍になります。** 本 spec はそれを解決しません。

**残高の監視は運用で行ってください。** 生成が止まったときに真っ先に疑うべきは残高です。

## データモデル変更

なし。

## API サーフェス

なし。**エンドポイントの呼び方（パス・パラメータ・順序）を変えないでください。**

`fetch-sourced-facts?match_id=..&content_type=..&force=true` → `generate-content` の順序は、**事実を集め直してから記事を作るという依存**そのものです。逆にすると入力した事実が反映されません。

## UI サーフェス

なし。

## LLM 連携

**ワークフロー自体は LLM を呼びません。** 呼び出しは既存のエンドポイントの中で起きます。**回数は変わりません。**

## 受け入れ条件

1. **`failure` が1件以上のとき、ワークフローの実行結果が失敗になる**
2. **対象0件のときは成功で終わる**
3. サマリ行の文言が現行のまま残っている（`targets=` / `success=` / `failure=`）
4. 対象試合の解決方法に差分が無い（カレンダー API の呼び方・日付範囲・`status` フィルタ）
5. **スケジュール（cron 式）に差分が無い**
6. `workflow_dispatch` の `from` / `to` が従来どおり動く
7. 試合が matrix で分割され、チャンクごとに並列実行される
8. **1チャンクの試合数と `max-parallel` が定数として YAML に書かれている**
9. **1回あたりの最大試合数が定数として定義され、超過分は処理されずログに残る**
10. 失敗したチャンクがあれば、集計ジョブが失敗する
11. **どの試合が失敗したかがログから特定できる**（現行の `WARN: ... match_id=...` を維持）
12. `fetch-sourced-facts` → `generate-content` の順序と引数に差分が無い
13. **`fetch-sourced-facts` が失敗した試合で `generate-content` を呼ばない**（現行の挙動）
14. `app/` と `lib/` に差分が無い
15. 両方のワークフローに同じ変更が入っている
16. `feat-tuesday-recap-refresh.md` の火曜の分岐が壊れていない（**先に実装されている前提**）

## 検証方法

**実際に走らせて確かめてください。** YAML は静的解析だけでは壊れているか分かりません。

1. `workflow_dispatch` で**試合が3件以上入る日付範囲**を指定して実行し、matrix が分割されることを確認する
2. **対象0件の日付範囲**で実行し、成功で終わることを確認する
3. PR 本文に**両方の実行 URL と所要時間**を貼る

**LLM を呼ぶので、検証の実行は Owner の承認を得てから行ってください。**

## 未解決の質問

- **チャンク5・並列3が妥当か。** OpenAI のレート制限の実際の上限を測っていない。**9/25 以前に、25試合規模で1度試す必要がある**
- **土曜キックオフの試合が木・金の2回リフレッシュされている。** 25試合規模では無視できない重複だが、金曜のメンバー発表を拾う価値もある。**本 spec では変更しない**
