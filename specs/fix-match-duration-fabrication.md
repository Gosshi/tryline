# 記事が「90分」と書く。ラグビーは80分である

## 背景

2026-08-21、南アフリカ vs ニュージーランド第1テストのプレビューが **QA を通過して published になった本文**にこうあった。

> 互いの先発構成にどこまで圧力をかけられるかを測る**90分**となる

**ラグビーユニオンの試合は80分である。** Owner が公開前に気づき、手作業で `match_content.content_md` を UPDATE して修正した。

**これは初めてではない。** `project_lineup_preview_timing_gap` の記録に、2026-08-13 の日本代表戦プレビューで同じ誤りがあったと残っている。

> 「90分の主導権」＝ラグビーは80分

**2回とも QA を通過している。** 情報密度・事実根拠・戦術的深さ・日本語品質のいずれの観点でも検出されなかった。

### なぜ検出されないか

**1. 決定的なガードが存在しない**

`lib/content/fabrication-guard.ts` の export は以下がすべてである。

```
UNSUPPORTED_STATISTIC_ISSUE / UNGROUNDED_PLAYER_REFERENCE_ISSUE /
UNGROUNDED_ENTITY_ISSUE / WINNER_MISMATCH_ISSUE /
PLAYER_STAT_MISMATCH_ISSUE / CONTRADICTED_ZERO_STAT_CLAIM_ISSUE /
ROSTER_ENUMERATION_ISSUE

containsUnsupportedStatistic / containsContradictedZeroStatClaim /
hasConfirmedSourcedFactLineup / containsRosterEnumeration /
containsUngroundedPlayerReference
```

**競技の基本ルールに関するガードが1つも無い。**

**2. プロンプトにも書かれていない**

`lib/` 全体を `80分` で grep すると **0件**。**正しい試合時間がどこにも明示されていない。** モデルはサッカーの一般知識に引きずられている。

**3. 既存ガードの守備範囲外**

`containsUnsupportedStatistic` は「データに存在しない統計値」を対象にする。「90分」は統計値ではなく**競技の前提**なので、入力データと突き合わせても検出できない。

**4. 入力データそのものが 90 を渡している（2026-08-25 追記）**

上記1〜3は「モデルがサッカーの一般知識に引きずられている」という前提に立っているが、**それだけではない。実際には `match_events` に不正な `minute` 値が入っており、モデルはそれを忠実に読んでいる。**

Western Force vs Waratahs（2025-05-24、recap 公開済み）の `match_events`:

| minute | type | team |
|---:|---|---|
| 75 | penalty_goal | Waratahs |
| **90** | **try** | Waratahs |
| null | drop_goal | Waratahs |

生成された本文は「**90分のドロップゴール**でワラターズが逆転勝利」。90分のトライと分不明のドロップゴールを混同しているが、**90 という数字自体はデータ由来**である。

**この経路はプロンプト対策だけでは塞がらない。** `shared-prompt-blocks.ts` に「80分である」と書いても、入力に `minute: 90` があれば同じ誤りが再発しうる。

`match_events.minute > 80` の実測分布（2026-08-25、全 126 件 / 91 試合）:

| minute | 件数 | 評価 |
|---|---:|---|
| 81〜85 | 119 | **正常。** 80分ホーン後にプレーが継続して得点が入るのはラグビーでは普通 |
| 86〜87 | 3 | 要確認 |
| 90 | 1 | **異常。** 本件の原因 |
| 96・100 | 2 | ノックアウトの延長（10+10分）なら正当。「未解決の質問2」の想定どおり |
| **471** | 1 | **明らかなゴミ値** |

**`minute > 80` を一律に弾いてはいけない。** 81〜85 を無効化すると正当な得点が消える。

**本 spec のスコープは広げない。** データ側の是正は別 spec とする。ただし出力ガード（本 spec の対象）を設計する際、**「入力データが不正な分数を渡してくる場合がある」ことを前提に置くこと。** 本文に現れた分数がラグビーとして成立しない値であれば、それが入力データ由来であっても検出対象とする。「入力に存在するから正しい」という扱いにしない。

### なぜ重要か

**ラグビーメディアとして最も出してはいけない類の誤り**である。統計の細部が1つ違うのとは意味が異なり、**書き手が競技を知らないことを一行で露呈する。**

Tryline の立ち位置は「海外ラグビーが日本語で分かる」ことであり、**読者はラグビーを知っている。** 90分と書いた瞬間に信頼を失う。

## スコープ

対象:

- 本文中の試合時間の誤りを決定的に検出するガード
- 生成プロンプトに正しい試合時間を明示する

対象外:

- **競技ルール全般の網羅的な検証。** 試合時間に絞る。範囲を広げると `selectCorePattern` と同じ硬直に陥る（`fix-preview-core-question-derivation.md` 参照）
- QA の採点ルーブリック・閾値の変更
- 既存記事の一括点検・修正（**別途調査。下記「未解決の質問」参照**）
- セブンズ（7人制）への対応。**Tryline は15人制のみを扱う**
- 英語コンテンツ（`preview@2.0.0-en` の別経路。**まず日本語で方式を確立する**）

## API サーフェス

### 1. 決定的ガード（`lib/content/fabrication-guard.ts`）

既存5関数と**同じ形式**で追加する。issue 定数も既存6つと同じ形で定義する。

検出の考え方:

- 本文に**試合時間として** `90分` が現れたら検出
- 「90分」は他の文脈でも出うる（引用、比較、比喩）。**ただしラグビー記事において試合時間以外で90分に言及する場面は実質存在しない**ため、まず単純な検出で始めてよい
- 表記ゆれ（`90分間` / `九十分`）は**実データに現れる形だけ**対応する。現行の生成物を確認してから決めること

**過検出を恐れて緩めすぎないこと。** 2回とも公開直前まで気づかれなかった。多少の誤検出は再生成で吸収できるが、**見逃しは記事に残る。**

### 2. 生成プロンプトへの明示

`lib/llm/prompts/shared-prompt-blocks.ts` に、**ラグビーユニオンの試合は80分（40分ハーフ）である**旨を追加する。既存の `PROHIBITIONS_BLOCK` / `KICKOFF_TIMEZONE_INSTRUCTION` と同じ形式にすること。

preview / recap の双方に効く場所へ置く。両ファイルで重複させない。

**ただしプロンプトへの追記は補助である。** `fix-recap-opening-variety-v2.md` が記録しているとおり、**文言を足すだけでは再発する**。主軸は1のガード。

### 3. retry の扱い

ガードが発火すると再生成が走る。**既存の retry 上限（`lib/llm/stages/qa.ts`）に従い、無限に再生成しないことを確認すること。**

## 受け入れ条件

1. 試合時間の誤りを検出する関数が `lib/content/fabrication-guard.ts` に存在し、既存5関数と同じ形式で export されている。
2. issue 定数が既存6つと同じ形式で定義されている。
3. **本 spec 背景の実文**「互いの先発構成にどこまで圧力をかけられるかを測る90分となる」が**検出される**。この文をテストフィクスチャに含めること。
4. 「80分」を含む正しい本文が**検出されない**。
5. 試合時間に言及しない本文が検出されない。
6. `buildGeneratePreviewPrompt` と `buildGenerateRecapPrompt` の双方の出力に、80分である旨の記述が含まれる。
7. 同じ記述が両ファイルで重複定義されていない（共有ブロックに置かれている）。
8. ガード発火時に既存の retry 上限を超えて再生成し続けないことをテストで確認できる。
9. `contentType: "recap"` の既存出力が、6の追加を除いて変わっていない。
10. `preview` / `language: "en"` の出力が変わっていない。
11. `pnpm lint` / `pnpm tsc --noEmit` / `pnpm test` / `pnpm build` がすべて clean。
12. **既存記事の点検・修正は実施しない。**

## 未解決の質問

1. ~~**既存の公開記事に同じ誤りが残っていないか。**~~ → **2026-08-25 に本番 `match_content` を調査し、回答済み。**

   背景に記した2件は Owner が**公開前に**気づいて手修正したもの。それとは別に、**現在も公開中（`status = 'published'`）の記事に4件残っている。**

   | キックオフ | 試合 | 種別 | 該当表現 |
   |---|---|---|---|
   | 2026-08-25 | Lions vs New Zealand | preview | 見出し「遠征の連続性と新主将の運用が映す**90分**」 |
   | 2026-08-07 | Stormers vs New Zealand | preview | 「**90分**の評価を決める」 |
   | 2025-09-27 | Zebre Parma vs Edinburgh | recap | 「判断力が光った**90分間**だった」 |
   | 2025-05-24 | Western Force vs Waratahs | recap | 「**90分**のドロップゴールで…逆転勝利」 |

   調査方法: `match_content` を `content_md like '%90分%'` で抽出し `matches` / `teams` と join、`status` と `content_type` を確認。

   **この4件が意味すること:**

   - **表記ゆれ `90分間` は実データに存在する。** 「実データに現れる形だけ対応する」という上記の指示に従い、`90分` と `90分間` の両方を検出対象に含めること（`九十分` は0件のため対象外でよい）
   - **preview と recap の両方で発生している。** どちらか一方だけにガードを入れるのでは不十分
   - 「90分のドロップゴール」は語法の誤りではなく、**存在しない時間の得点を報じる事実の捏造**である。過検出を恐れて緩めない根拠として扱ってよい
   - **本 spec のスコープは変わらない。** 受け入れ条件12「既存記事の点検・修正は実施しない」は維持する。既存4件の修正は Owner が別途判断する

   なお 2026-08-25 の1件は調査時点で**公開中**だった。Owner への申し送り事項。

2. **延長戦をどう扱うか。** ノックアウト戦では20分の延長がある。「100分」等が正当に現れうる。**現行の対象大会に延長のある試合が含まれるかを確認してから、除外規則が必要か判断すること。** 過剰に作り込まない。

3. **他の競技ルールにも同種の誤りがないか。** トライ5点・コンバージョン2点・ペナルティゴール3点・ドロップゴール3点といった基本は、`fix-penalty-try-scoring`（ペナルティトライ5点バグ）で一度事故が起きている。**本 spec では広げないが、同じ形のガードを足せる構造にしておくこと。**
