# feat-mobile-onboarding-team-picker: 初回起動時のお気に入りチーム選択(v1: 直接選択のみ)

対象リポジトリ: **tryline-mobile** のみ(クライアント側完結。データモデル・BFF 変更なし)。**2段階の1段目(UI・ローカル保存)**。ホーム反映・ログイン同期は後続spec `feat-mobile-onboarding-favorites-sync` で対応する。

## 背景

現状、お気に入りチームは設定タブからログイン後にしか登録できない(`FavoritesEditor.tsx` は `!me` の場合「ログインが必要です」を表示するだけ)。初回起動時にチームへの愛着を作れず、通知（`notifyPrematch`）などログイン後価値の実感が遅れる。2026-07-23 の監査（GPT）で「オンボーディングから『自分の週面』へ」として優先度1で提案された。

当初案(2026-07-23 Owner発案)は「直接選択」と「5問プレースタイル診断」の2入口だったが、診断側は top12 チームの選定基準・設問文言・チーム紹介文の紋切り型表現リスクがあり Owner レビュー待ちで着手できずにいた。GPTの再提案(2026-07-23)を踏まえ、**v1は直接選択のみに絞る**。理由:
- 既存の `FavoritesEditor.tsx` が実装済みの手法(主要大会上位8件の順位表からチーム名を重複排除して選択肢にする)をそのまま流用でき、新規コンテンツ制作(top12選定・タグ・設問文言)が一切不要になる
- 「選んで終わり」ではなく、選択直後にホームの表示が変わるところまでを含めることで、ログイン前から価値を体感できる(GPT提案: 「選んだ直後にホームの並びが変わるところまでをオンボーディング体験に含めるべき」)

5問診断は将来の別specで、直接選択フローへの追加入口として検討する(本specでは対象外)。

**分割の経緯**: 初回実装依頼時、初回ルーティング・ローカル保存・認証同期・ホーム反映を1本のPRに詰め込んだ結果、スコープが大きすぎて着手すらされなかった(調査のみで停止)。本specはUIとローカル保存のみに絞り、ホーム画面連携とログイン時同期は独立した後続spec `feat-mobile-onboarding-favorites-sync` に分離する。

## スコープ

対象:
1. **初回起動判定＋オンボーディング画面の追加**(`app/_layout.tsx` から `expo-router` の Stack にオンボーディングルートを追加。初回のみ表示、以降はスキップ)
2. **チーム選択UI**: `FavoritesEditor.tsx` と同じロジック(主要大会上位8件の順位表からチーム名を重複排除して収集)を再利用し、最大 `MAX_FAVORITES`(3)件まで直接選択させる。共通化(例: `src/settings/useTeamChoices.ts` 相当のフック抽出)を推奨するが、重複実装でも可
3. **選択結果のローカル永続化**: `expo-secure-store` に一時保存する(`seenStore.ts` と同じ方式、新規ファイル `src/onboarding/pendingFavoritesStore.ts` 目安)。保存・取得・クリアの関数を用意する(後続specがこれを利用する)
4. **完了画面**: チーム選択の直後に、選んだチームに基づく具体的な中身(直近の試合、読める記事)を1〜2件見せてから、通知・ログインを任意で案内する(完了必須にしない)。試合・記事データは既存の`calendar`クエリから取得してよい
5. **スキップ可能性**: 「あとで選ぶ」で通過、以降再表示しない

対象外(やらないことを明示):
- **ホーム画面のログイン前パーソナライズ・ログイン成立時の同期**。後続spec `feat-mobile-onboarding-favorites-sync` で対応する。本specでは`pendingFavoritesStore`にデータを保存するところまでで完結する
- **5問のプレースタイル診断フロー**。将来、直接選択に迷うユーザー向けの追加入口として別specで検討する
- **代表/クラブの事前フィルタ選択**。チームデータ(`V1TeamSummary`)に国代表/クラブを区別するフィールドが存在しないため、v1では全チームを一つのリストから選ぶ。将来API側で区分フィールドが追加されれば検討する
- お気に入り上限(`MAX_FAVORITES`)の変更
- BFF・データモデルの変更
- ダークモード対応
- 既存 `FavoritesEditor`(設定タブ)のログイン後編集フローの変更(そのまま維持。オンボーディングは初回の入り口を追加するだけ)

## データモデル変更

なし。

## UI サーフェス

- チーム選択肢の取得方法は `FavoritesEditor.tsx` のロジック(`useQueries` で主要大会上位8件の standings を取得し、`team_short_code` で重複排除)をそのまま流用する
- 選択チップの見た目は `FavoritesEditor.tsx` の `Button`(`selected` 時 `✓ {name}`)パターンを踏襲する(新規パターンを増やさない)
- 完了画面: 選択したチームが登場する直近の試合(`calendar` データから抽出)と、読める記事(`has_preview`/`has_recap` が true のもの)を1〜2件表示してから、通知・ログイン導線を提示する。エディトリアル路線(紙・インク・赤アクセント最小限)を踏襲し、派手な演出は入れない
- スキップ導線(「あとで選ぶ」)を必ず用意する

## 受け入れ条件

1. 初回起動時のみオンボーディングが表示され、2回目以降の起動ではスキップされることを確認するテスト
2. チーム選択で `MAX_FAVORITES` 件まで選択できることを確認するテスト
3. 選択した内容が `expo-secure-store` にローカル保存されることを確認するテスト(`pendingFavoritesStore`の保存・取得・クリア関数のユニットテスト)
4. 完了画面に選択したチームの直近試合・記事が表示されることを確認するテスト(該当データがある場合)
5. オンボーディングは「あとで選ぶ」でスキップ可能。スキップ後もアプリの他機能は通常どおり使えることを確認するテスト
6. TypeScript strict・lint・test green
7. **Owner 目視**: 実機または iOS Simulator でオンボーディングのチーム選択〜完了画面までの流れを確認する

## 未解決の質問

- 5問診断フローは将来の別specで検討する。直接選択フローへどう合流させるか(入口の並べ方等)はその時点で判断する
- 代表/クラブの事前フィルタは、チームデータに区分フィールドが追加された場合に将来検討する
