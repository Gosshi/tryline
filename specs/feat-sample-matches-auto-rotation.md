# 無料サンプル試合を直近の好試合へ自動的にローテーションする

## 背景

2026-07-10、Codex（新モデル）による集客・収益化分析の両方で指摘された課題。

`lib/sample-matches.ts` の `SAMPLE_MATCH_IDS`（8件のハードコードされたUUID配列）を確認したところ、全8件が**2026年5月15日〜31日**のkickoffで、本日（2026-07-10）時点で1ヶ月以上前の試合のみだった。これらはホームページの無料サンプルレビュー・料金ページ等でPremium未加入ユーザーに見せる「品質の見本」だが、古いサンプルは「今も動いているサービス」という印象を弱める。

## スコープ

対象:
- `lib/sample-matches.ts` のハードコードされた `SAMPLE_MATCH_IDS` 配列を、直近の終了試合から自動的に候補を選ぶロジックに置き換える
- 選定基準（実装時にCodexが具体化してよいが、以下を満たすこと）:
  - 直近30〜60日以内に終了した試合を優先する
  - レビュー（recap）が公開済み（`match_content` に `content_type='recap'` かつ published）であること
  - 複数の大会からバランスよく選ぶ（1大会に偏らせない）
  - 件数は現行と同じ8件程度を維持する
- 選定結果は毎回DBクエリで動的に決めるのではなく、日次または週次のcronで再計算し、キャッシュ/固定リストとして保持する設計にしてよい（既存の他のcronパターン、例: `app/api/cron/` 配下を参考にする）

対象外:
- サンプル試合の選定に「好試合かどうか」を判定するLLM評価（点差・接戦度・注目度等の機械的な指標のみで選定し、LLMによる主観的な「面白さ」判定は行わない。コスト増加を避けるため）
- 個々のサンプル試合の表示UI自体の変更（`lib/sample-matches.ts` の中身の選定ロジックのみが対象）

## データモデル変更

サンプル試合の選定結果を保持する必要がある場合、軽量なテーブル（例: `sample_matches` に `match_id`・`selected_at`）を追加するか、既存の設定用テーブルがあれば流用する。実装時にCodexが判断してよい。

## API サーフェス

なし（既存のサンプル試合取得関数のインターフェースは維持する）。

## 受け入れ条件

1. `lib/sample-matches.ts` のサンプル試合が、ハードコードされた固定UUIDではなく、直近30〜60日以内の終了試合から動的または定期再計算で選ばれる仕組みになっている
2. 選定された試合は全てレビュー（recap）が公開済みである
3. 複数の大会から選ばれており、1大会に偏っていない
4. 既存のホームページ・料金ページでのサンプル試合表示に回帰がない（表示件数・レイアウトが変わらない）
5. `pnpm tsc --noEmit` / `pnpm lint` / `pnpm test` / `pnpm build` が通る
6. 本番デプロイ・cron設定はOwner承認後に別途行う

## 未解決の質問

- 選定を日次/週次cronで再計算するか、ページ表示時に動的にクエリするかはCodexの判断に委ねる（後者の方がシンプルだが、毎リクエストでのDB負荷が気になる場合は前者を選んでよい）
