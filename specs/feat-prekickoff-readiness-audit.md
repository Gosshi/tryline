# キックオフ前にプレビューの準備状況を点検して通知する

## 背景

2026-08-21、南アフリカ vs ニュージーランド第1テスト（8/23 00:10 JST）で以下が同時に起きていた。**いずれも Owner が偶然気づくまで誰にも検知されなかった。**

1. **ラインアップは 8/20 に発表済みで、allowlist 内の Wikipedia に先発15人が載っていた**にもかかわらず、`match_lineups` は 0 件だった。手動で `manual-ingest-lineups` を実行するまで、実名なしのプレビューが公開される直前だった
2. プレビューは 03:47 に生成されたが QA に却下され、**draft のまま放置されていた**（キックオフまで20時間）

さらに、`cron-weekend-preview-refresh.yml` の対象範囲には構造的な穴がある。

| run | cron 式 | 対象範囲 | カバーする曜日 |
|---|---|---|---|
| 木 21:05 JST | `5 12 * * 4` | 当日〜+2日 | 木・金・土 |
| 金 21:05 JST | `5 12 * * 5` | 翌日〜+2日 | 土・日 |

**土曜は2回試行されるが、日曜は金曜の1回きり。水曜キックオフはどちらの窓にも入らず0回。**

`greatest-rivalry-2026` は JST キックオフが深夜のため日付が繰り上がり、**テスト4戦（8/23・8/30・9/06・9/13）が全部「日曜」= 1回きりの枠**に入る。ツアー戦のシャークス戦（8/12 水）とライオンズ戦（8/26 水）は**自動では一度も生成されない**。

窓を広げる修正は別途あり得るが、**どう広げても「走ったが失敗した」ケースは残る。** 必要なのは、生成の成否にかかわらず**キックオフ前に準備状況を点検して報告する独立した経路**である。

## スコープ

対象:

- キックオフ前の試合について準備状況を点検し、欠落があれば Discord へ通知する cron を追加する

対象外:

- **`cron-weekend-preview-refresh.yml` の対象範囲の変更。** 窓の穴を直すかは別の判断で、本 spec は検知に徹する
- **自動修復。** 取り込みや再生成を本 cron から実行しない。通知のみ
- 読者向けプッシュ通知（`send-prematch-notifications` は別系統。触らない）
- recap（試合後）の点検。preview に絞る
- 英語コンテンツの点検

## データモデル変更

**なし。マイグレーション不要。**

## API サーフェス

### 1. 点検ルート（新規）

`app/api/cron/` 配下に読み取り専用のルートを追加する。既存 cron ルートの認可パターン（`assertCronAuthorized`、`lib/cron/auth`）と応答形式（`apiSuccess` / `apiError`、`lib/api/v1/response`）を踏襲すること。

対象試合の抽出は **`getMatchesInRange(startIso, endIso)`（`lib/db/queries/matches`）を使う。** `app/api/cron/send-prematch-notifications/route.ts:21-27` が同じ関数を使っており、そこが参考実装になる。

点検する条件（**すべて決定的。LLM を使わない**）:

| 判定 | 条件 |
|---|---|
| プレビュー未公開 | `match_content` に `content_type='preview'` / `language='ja'` / `status='published'` の行が無い |
| プレビューが draft 滞留 | draft はあるが published が無い |
| ラインアップ未取り込み | `match_lineups` が 0 件、かつ `matches.external_ids.wikipedia_url` が設定済み（＝取り込める見込みがある） |
| sourced_facts 0件 | `match_sourced_facts` に `content_type='preview'` の行が無い |

**「ラインアップ未取り込み」は `wikipedia_url` が設定済みのときだけ報告すること。** 未設定の試合は取り込みようがなく、報告しても行動につながらない。

### 2. 通知

`lib/llm/notify.ts` に新しい通知関数を追加し、既存の `postOpsAlert` を使う。**新しい送信経路を作らない。**

- 欠落が1件も無ければ**通知しない**（静かな日は静かにする。毎日「異常なし」が届くと読まれなくなる）
- 各行に対戦カードの日本語表記とキックオフ JST を含める（`teams.name_ja` と `lib/format/kickoff.ts`）
- Discord の 2,000 字上限（`notify.ts:12`）を超える場合に備え、件数サマリを先頭に置くこと

### 3. スケジュール

GitHub Actions のワークフローを追加する。既存の `cron-*.yml` の構成を踏襲すること。

**発火タイミングは、気づいてから手を打てる余裕がある時刻にすること。** キックオフ直前に通知しても行動できない。実装時に既存 cron の JST 換算（`5 12 * * 4` = 木 21:05 JST 等）を確認し、1日1回で日曜・水曜キックオフの両方を拾える時刻を選ぶこと。**選んだ時刻とその理由を PR 本文に書くこと。**

## UI サーフェス

なし。

## LLM 連携

**なし。LLM 呼び出しを一切追加しない。** すべて DB クエリで決定的に判定する。コスト増はゼロ。

## 受け入れ条件

1. 新しい cron ルートが `assertCronAuthorized` で保護され、未認可のとき 401 を返す。
2. 対象試合の抽出に `getMatchesInRange` を使っている。**独自の範囲クエリを実装していない**ことをコードレビューで確認できる。
3. published な ja プレビューが存在する試合は、報告に含まれない。
4. draft のみ存在する試合が「draft 滞留」として報告される。
5. `match_lineups` が 0 件かつ `external_ids.wikipedia_url` が設定済みの試合が「ラインアップ未取り込み」として報告される。
6. `match_lineups` が 0 件でも `wikipedia_url` が未設定の試合は、ラインアップの欠落として報告されない。
7. preview 用 `match_sourced_facts` が 0 件の試合が報告される。
8. 欠落が 0 件のとき、`postOpsAlert` が呼ばれない。**これを固定するテストを置くこと。**
9. 報告の各行に対戦カードの日本語表記とキックオフ JST が含まれ、JST は `lib/format/kickoff.ts` の出力と一致する。
10. ルートが **SELECT のみ**で、書き込みを行わない。
11. ワークフローが追加され、`workflow_dispatch` でも起動できる。
12. `pnpm lint` / `pnpm tsc --noEmit` / `pnpm test` / `pnpm build` がすべて clean。
13. **本番へ通知を送るテストを書かない。** `postOpsAlert` はモックする。

## 未解決の質問

1. **点検する時間窓をどれだけ手前に取るか。** キックオフ 24 時間前だと `cron-weekend-preview-refresh` の金曜 run（日曜キックオフの約27時間前）より後になり、生成の失敗を拾える。48 時間前まで広げると水曜キックオフも拾えるが、まだ生成予定の試合まで「欠落」と報告してしまう。**実装時に既存 cron のスケジュールと突き合わせて決め、根拠を PR 本文に書くこと。**

2. **`cron-weekend-preview-refresh` の窓の穴自体を直すか。** 本 spec は検知に徹するが、水曜キックオフが自動生成されないのは検知だけでは解決しない。別 spec の候補。

3. **recap への拡張。** 試合後の recap にも同種の欠落はあり得るが、preview ほど時間的な切迫がないため本 spec では扱わない。運用が安定してから判断する。
