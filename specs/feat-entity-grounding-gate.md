## 背景

2026-07-04、Nations Championship 2026 開幕日（日本 vs イタリア、`match_id = f56e9ee9-14be-49e3-b47d-c51a29c07593`）のプレビュー生成で、同日中に3回連続で選手名捏造が発生した。都度対応（決定的コードガード追加 → `hasLineups`判定の是正 → 生JSONダンプのサニタイズ）を重ねたが、最終的に**入力データを一切与えなくても、LLMが事前学習で獲得した実在選手の知識（parametric knowledge）を使い、「今日この試合に出場している」という未確認の断定を生成する**ことを実証で確認した（当該試合の `projected_lineups`・`match_events`・`sourced_facts` が全て空/未確定であるにもかかわらず、実在するイタリア代表SH・SO、日本代表FLの3選手名が役割付きで生成された。プロンプトに渡る生データからは当該選手名が一切含まれないことをコードレベルで直接検証済み）。

**根本原因の再定義**（設計文書§1）: これは prompt injection ではなく、data-to-text 生成における **faithfulness（入力忠実性）の破れ＝parametric knowledge leakage**。「入力から危険データを隠す」対策には原理的な限界があり、際限のない正規表現の追加（もぐら叩き）では解決しない。**防ぎたい対象（学習済み知識）は入力空間に存在しないため入力側では制御できないが、出てはいけないもの（許可リスト外の人名）は出力空間で完全に定義できる**。よって検証は生成後の出力側で行う。

## LLM 連携

- **新規ステージ**: `verifyNarrativeEntities`。モデルは `MODELS.FAST`（`gpt-4o-mini`）、`temperature: 0`、`createTextResponse` の `jsonMode: true` を使用（既存インフラそのまま流用）
- プロンプトの仕事は**抽出と対応付けのみ**（「良い記事か」は判定させない）:
  1. 本文中の人物への言及（フルネーム・姓のみ・カタカナ表記すべて）を全件列挙
  2. 各言及について、許可リストのどのエントリに対応するかを返す。対応しなければ `null`
  3. カタカナ⇔英語の表記ゆれ（長音・中点・姓名順・姓のみ言及）は同一人物として対応付けてよいと明示する
- 出力スキーマ（例）:
  ```json
  { "mentions": [ { "surface": "本文中の表記", "matched_entity": "許可リスト内の名前 or null" } ] }
  ```
- **判定は常にコード側の決定的ロジック**（LLMは分類器、判定はプログラム、という既存 `containsUnsupportedStatistic` と同じ役割分担）。`matched_entity: null` が1件でもあれば `UNGROUNDED_ENTITY_ISSUE` を issues に追加し `factual_grounding: 1` に強制
- **fail-closed 必須**: 照合ステージ自体がAPIエラー等で失敗した場合、素通し（publish許可）にしてはならない。照合不能＝ publish しない扱いとする
- 許可済みエンティティ集合の収集元（`buildAllowedPersonEntities(assembled)`）:
  - `projected_lineups.home / away` — **confirmed側のみ**（`hasConfirmedEntry` 相当の判定。フォールバック選手は含めない。ここを誤ると許可リストに歴代選手プール全員が入り、ゲートが無意味化する。`fix-projected-lineup-fallback-fabrication` の教訓そのもの）
  - `match_events[].player_name`
  - `sourced_facts`（原文テキストをそのまま照合コンテキストとして渡す。事前の人名抽出はしない）
  - **集合が空になり得ることは仕様**（データスパース試合）。空の場合、いかなる人名も定義上違反になる
- retry時のフィードバック: 違反 surface を再生成プロンプトに明示注入する（例: 「前回の出力には入力データに存在しない人名（〇〇、△△）が含まれていた。これらを含め、入力データにない人名は一切書かないこと。」）。盲目的な再生成よりretry成功率を上げる狙い
- 並行実行: `verifyNarrativeEntities` と既存QAの評価呼び出しは独立したAPI呼び出しのため `Promise.all` で並行実行しレイテンシ増を抑える。両方の結果が揃ってから `applyDeterministicQaGuards`（同期関数）で合流させる
- コスト試算: 照合1回あたり入力約3-4Kトークン・出力約100-300トークンで `gpt-4o-mini` 単価から**$0.001未満**。retry込みで1試合最大$0.002程度。既存のナラティブ生成コスト（1試合数セント）に対して誤差
