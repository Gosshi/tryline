# 調査由来の事実を Discord から入力する

## 背景

**Owner が ChatGPT で調べた事実を Tryline に入れる経路が無い。**

`feat-discord-fact-entry.md`（PR #738 / #739）で作った入力経路は、**通知メッセージを長押しして開く**方式で、`news_links` に一致する行が無ければ拒否する（`app/api/discord/interactions/route.ts:232-241, 257-260`）。

調査由来の事実には対応する通知メッセージが無いため、**現状は入力できない。**

### なぜ調査由来の事実が必要か

`project_news_link_pipeline` のとおり、自動取得できるドメインは12件に限られる。rugbypass・planetrugby・espn・bbc 等は**利用規約が AI システムの訓練・開発目的を明示禁止**しているため allowlist から外している。

**しかし Owner が ChatGPT で調べるのは、この制約の外側にある。**

- **Tryline は何もクロールしない**
- Owner が消費者向け製品を使って調べるだけ
- 得られるのは事実であり、**事実に著作権は無い**

同時に、現在 Owner が抱えている2つの負担が解消する。

| 現在の負担 | 実測 |
|---|---|
| Discord 通知が多い | **1日13〜25件**（2026-08-26〜09-02） |
| 記事が英語で読むのがつらい | Owner 申告 |

**1回の調査依頼で済むため、通知を読む負担も英語の負担も減る。**

### ChatGPT が読めるサイトは限られる（2026-09-04 実測）

参考情報として記録する。**本 spec の設計はこれに依存しない**が、運用上の期待値として重要。

| サイト | ChatGPT 系クローラ |
|---|---|
| `rnz.co.nz` | ❌ `ChatGPT-User: Disallow: /`（`anthropic-ai` も同様） |
| `stuff.co.nz` | ❌ `GPTBot` / `ChatGPT-User` / `OAI-SearchBot` すべて `Disallow: /` |
| `nzherald.co.nz` | ✅ 許可（OpenAI 用の節はあるが `Disallow: /` は無い） |

**ChatGPT の検索結果は、これら以外の媒体からも来る。** どこから来た事実かは出典 URL で判断する。

### 過去2回の失敗と、それを潰す方法

**「LLM に記事を探させる」はこのプロジェクトで2回失敗している。**

`x-post` スキルに構造的な禁止として記録がある。

> 2026-07-27 に「今週のニュース」draft 2件が**捏造（URL が 404）**と判明して収集停止、2026-07-29 に RUGBY DESK 案を同じリスクで見送っている。**2件とも原因は「LLM に記事を探させたこと」**

**2回とも失敗の形は同じ「出典 URL が 404」だった。** これは機械的に潰せる。

**保存前に出典 URL へ HTTP リクエストを投げ、200 でなければ拒否する。** 1リクエストで、記録されている失敗モードが両方消える。

**ただし限界がある。** URL が 200 でも、その記事がその事実を書いている保証は無い。**潰せるのは「存在しない URL」だけ**で、内容の正しさは Owner の目視に依存する。この限界は受け入れる。

### 「allowlist バイパス」の再整理

`feat-discord-fact-entry.md` は `news_links` 照合を必須とし、その理由をこう書いた。

> 任意のメッセージに `match_id` と URL を書くだけで allowlist 外ドメインの手動入力を登録できる抜け道を防ぐため

**この整理は誤っていた。** allowlist は「**Tryline が自動取得してよいか**」の基準であって、「**Owner が調べた事実を入れてよいか**」の基準ではない。両者を混同していた。

Owner 以外は Discord のユーザー ID で拒否されるため、**悪用ではなく誤操作の防止**が実際の論点である。誤操作は、コンテキストメニュー（任意のメッセージに実行しうる）ではなく**明示的なコマンド**にすることで防ぐ。

**既存の通知経由の入力は変更しない。** そちらは `news_links` 照合を維持する。

## スコープ

対象:
- Discord のスラッシュコマンド新設（調査由来の事実入力）
- 出典 URL の存在検証
- `match_sourced_facts` への保存

対象外:
- **既存のコンテキストメニュー経由の入力の変更**。`news_links` 照合はそのまま維持する
- **`lib/llm/sourced-facts/allowlist.ts` の変更**
- **自動取得経路の変更。** `fetchSourcedFactsForMatch` は従来どおり allowlist を厳格に適用する
- `lib/news-links.ts` の変更
- Discord 通知の頻度・件数（別途）
- 入力した事実の編集・削除機能
- 記事の再生成トリガー（`content-regen` の手順で別途）
- ChatGPT 側のプロンプト設計（Owner の運用）

## 入力の流れ

```
① Owner が ChatGPT に調査を依頼し、事実と出典 URL を得る

② Discord でスラッシュコマンドを実行

③ モーダルが開く
   - 試合（必須・選択式）
   - 事実（必須・複数行・**1行1件**）
   - 出典 URL（必須・1行）
   - 確度（任意・既定 medium）

④ 送信
   → 出典 URL に HTTP リクエスト（**1送信につき1回だけ**）
   → 200 以外なら拒否し、理由を返す
   → 200 なら、**1行を1件として match_sourced_facts に複数行保存**
   → 保存件数・重複でスキップした件数を Owner に返す
```

**1送信で複数の事実を入れられることが要件です。** 実運用の規模で確かめた結果、1送信=1事実では回りません。

| 単位 | 2026-09-06 の週末（9試合）で必要な送信回数 |
|---|---:|
| 1送信 = 1事実 | **約36回** |
| **1送信 = 1試合＋1出典 URL＋複数事実** | **約12回** |

**9/25 に URC 144試合とプレミアシップ90試合が開幕すると、前者は確実に破綻します。**

ChatGPT の出力は「試合ごとに事実が数件、出典は1〜2個」という形になるため、**この単位が実際のデータ形状と一致します。**

## 試合の選び方

**UUID を手入力させない。** モーダルの選択肢として提示する。

- 候補は**キックオフが前後2週間以内**の試合とする
- 表示は「MM/DD ホーム × アウェイ」のように**日本語チーム名**で（`teams.name_ja` を優先し、無ければ `name`）
- **選択肢は最大25件**（Discord の String Select の上限）。超える場合はキックオフが近い順に切る

### オートコンプリート（type 4）は使わない

Discord のスラッシュコマンドにはオートコンプリートがあるが、**現在のルートは interaction type 4 を処理していない**（扱っているのは 1 / 2 / 5）。

**モーダル内の String Select で代替する。** 前後2週間の試合は25件に収まる見込みで、実装量も少ない。

## モーダルの構造（既知の罠）

**`fix-discord-modal-required-placement.md`（PR #744 で確定）の形に従うこと。** 同じ失敗を繰り返さないための必須事項。

- **モーダル内のコンポーネントは Label（type 18）で包む。** Action Row（type 1）に入れると Discord が payload を破棄する
- **`required` は Label ではなく、包まれる側（Text Input / Select）に付ける。** Label のフィールドは `type` / `id?` / `label` / `description?` / `component` のみ
- Select に `min_values` / `max_values` を付けない。任意であることは `required: false` が表す

**症状の見分け方**: サーバーが 200 を返しているのに Discord が「アプリケーションは時間内に応答しませんでした」と出す場合、遅延ではなく **payload 不正**である。

## 3秒制限とタイムアウト（最重要）

**モーダルを開く応答は defer できない。** 試合候補の取得は1クエリで済ませること。

**送信後の処理は defer すること。** 出典 URL への HTTP リクエストが入るため、3秒を超える可能性が高い。

```
モーダル送信を受信
  → 即座に defer（type 5）を返す
  → URL 検証 → 保存
  → 結果を後から送る
```

**defer せずに HTTP リクエストを挟むと、成功していてもタイムアウト表示になる。**

## 出典 URL の検証

**保存前に必ず検証する。** これが本 spec の中核。

- `http` / `https` のみ許可する
- **HEAD を試し、405 等で拒否されたら GET にフォールバックする**（HEAD を受け付けないサイトがある）
- **リダイレクトは追い、最終的に 200 であれば合格**とする
- **短いタイムアウト**を設ける（定数で持つ）
- 200 以外・タイムアウト・接続失敗は**すべて拒否**し、Owner に理由が分かる応答を返す

### 本文を読まないこと

**存在確認のみを行い、レスポンスボディを読まない。**

これは「Tryline が記事本文を取得して LLM に渡さない」という `project_news_link_pipeline` の設計根拠を保つために必要である。**リンクチェッカーと同じ振る舞いに留める。**

### robots.txt の扱い

`lib/scrapers/fetcher.ts` の `fetchWithPolicy` は robots.txt を強制する。**これを使うと、robots で AI ボットを拒否している媒体の URL が検証段階で弾かれる。**

**本 spec では `fetchWithPolicy` を使わず、素の fetch で存在確認のみ行う。** 根拠は次のとおり。

- **本文を1バイトも読まない**ため、クロール（収集・蓄積）にあたらない
- Owner の明示的な操作を起点とする**1回限り**のリクエストである
- 目的は「これから記事に載せる出典リンクが生きているか」の確認であり、リンクチェッカーと同種である

**Owner が 2026-09-04 に承認済み。`docs/decisions.md` の D026 に記録した。**

**この例外はこの検証処理に限る。** `lib/scrapers/` 配下の取得経路と `fetchSourcedFactsForMatch` の自動取得は、従来どおり robots.txt と allowlist を厳格に適用する。

## 事実の分割と書式

### 分割の規則

- **改行で分割し、1行を1件とする**
- **空行と、前後の空白のみの行は捨てる**
- 各行は前後の空白を除去して保存する
- 行頭の箇条書き記号（`-` `*` `・` および全角中黒）が付いていたら**除去する**。ChatGPT の出力をそのまま貼れるようにするため
- **1件も残らなければ拒否する**（空白だけの送信を保存しない）

### 長さの上限

**1件あたりの最大文字数を定数として定義し、超える行は拒否する。推奨値は 300 文字。**

Discord の Text Input の上限（4000）をそのまま使わないでください。**既存の自動取得 fact は実測で 40〜110 文字**なので、300 文字あれば十分な余裕があります。

これは実害への対処です。**2026-08-30 の手動入力テストで、66行の会話体の論評が1件の事実として保存されました。**

> 「SpringboksがSpringboksらしさを取り戻して…」「方向性そのものが否定される内容ではなさそうです」

**`match_sourced_facts` は生成パイプラインが事実として読む場所なので、このまま記事本文に意見が混ざります。** 既存の自動取得 fact は1件1文・主語と数字が明確で、形式が違いすぎます。

**上限を超えた行は、どの行が長すぎるか分かる形で拒否してください。**

### 書き方のルールは UI に出す

**次の文言をモーダルの「事実」フィールドの説明（Label の `description`）に出してください。**

```
1行に1件・300字以内。主語と数字を明示し、意見や推測は書かない。
```

**「1件1文」とは書かないでください。** 既存の自動取得 fact は1〜2文のものが多く、実装と食い違います。

**Label の `description` は表示のためのフィールドで、`required` とは別物です。** Label が持てるのは `type` / `id?` / `label` / `description?` / `component` だけなので、ここに入れます。

**意見が混ざっていないことはコードで判定できません。** UI に出して Owner が守る運用にします。

## 保存する内容

| カラム | 値 |
|---|---|
| `match_id` | モーダルで選択された試合 |
| `content_type` | **キックオフ時刻から決定**（前なら `preview`、後なら `recap`） |
| `fact` | **分割後の1行**（行ごとに1レコード） |
| `fact_ja` | **`fact` と同じ値** |
| `source_url` | モーダルの入力（検証済み・**リダイレクト後の最終 URL でなく入力値**を保存する） |
| `source_domain` | `source_url` のホスト名 |
| `confidence` | モーダルの選択（既定 `medium`）。**同一送信の全件で同じ値** |
| `model_version` | `manual` |
| `metadata` | **`entry_method` は `"manual"` を必ず含める**（後述）＋ 経路が判別できる値 |

### `entry_method` は必ず `"manual"` にすること

**読み取り時の allowlist 例外（`lib/llm/sourced-facts/fetch.ts:400`）と、自動再取得からの削除保護（同 `:109`）は、いずれも `metadata.entry_method === "manual"` を条件にしている。**

別の値にすると、**保存できても記事生成時に無言で捨てられる**か、**次の自動取得で消える**。

**経路の区別は別のキー**（例: `entry_path`）で持つこと。`entry_method` を変えてはいけない。

## 受け入れ条件

1. スラッシュコマンドが新設され、既存のコンテキストメニューコマンドと共存する
2. **既存のコンテキストメニュー経由の入力に差分が無い**（`news_links` 照合が維持されている）
3. モーダルに「試合」「事実」「出典 URL」「確度」の4項目がある
3-a. **「事実」が複数行入力で、Label の `description` に書き方のルールが表示されている**
4. 試合が**選択式**で、UUID の手入力を要求しない
5. 候補がキックオフ前後2週間以内に限定され、**25件を超えない**
6. 試合名が**日本語**で表示される（`name_ja` 優先・null なら `name` にフォールバック）
7. **モーダルのコンポーネントが Label（type 18）で包まれ、`required` が包まれる側に付いている**
8. Select に `min_values` / `max_values` が無い
9. **モーダル送信の応答が defer されている**
10. 出典 URL が `http` / `https` 以外なら拒否される
11. **HEAD が拒否された場合に GET へフォールバックする**
12. **リダイレクトを追い、最終的に 200 なら合格**する
13. **200 以外・タイムアウト・接続失敗のいずれでも1件も保存されず、理由が分かる応答が返る**
13-a. **HTTP リクエストは1送信につき1回だけ**（事実の件数に比例して増えない）
14. タイムアウトが**定数として定義されている**
15. **レスポンスボディを読んでいない**
16. **`fetchWithPolicy` を使っていない**（素の fetch で存在確認のみ）。この例外は D026 で承認済みで、**この検証処理の外へ広げていない**
17. 保存された行の `metadata.entry_method` が **`"manual"`**
18. 経路を区別できる値が `metadata` に入っている（`entry_method` 以外のキーで）
19. `model_version` が `manual`、`fact` と `fact_ja` が同値
20. `content_type` がキックオフ時刻から決まる
21. `source_url` が**入力値**で保存される（リダイレクト後の URL ではない）
22. 保存された事実が `loadSourcedFactsForMatch` から返る（allowlist 外ドメインでも）
23. **自動取得経路で allowlist が従来どおり厳格に効く**（緩んでいないことをテストで証明する）
24. **自動再取得で削除されない**
25. 同じ `fact` を再投入しても重複行を作らない（一意制約 `match_id, content_type, fact`）
25-a. **改行で分割され、1行が1レコードとして保存される**
25-b. **空行・空白のみの行が捨てられ、行頭の箇条書き記号（`-` `*` `・` 全角中黒）が除去される**
25-c. **有効な行が1件も無ければ拒否される**
25-d. **1件あたりの最大文字数が定数として定義され、超える行は「どの行か分かる形で」拒否される**
25-e. **応答に保存件数と重複スキップ件数が含まれる**
25-f. **同一送信の全レコードが同じ `source_url` / `source_domain` / `confidence` / `content_type` を持つ**
26. Owner 以外の Discord ユーザー ID からの実行が拒否される
27. `lib/llm/sourced-facts/allowlist.ts` と `lib/news-links.ts` に差分が無い
28. `lib/scrapers/fetcher.ts` に差分が無い
29. URL 検証の各分岐（200 / 404 / タイムアウト / 不正スキーム / HEAD 拒否→GET 成功）にテストがある
29-a. **事実の分割にテストがある**（複数行→複数レコード / 空行の除去 / 箇条書き記号の除去 / 全行が空 → 拒否 / 上限超過 → 拒否 / 一部が既存と重複 → 残りは保存されスキップ件数が返る）
30. `pnpm lint` / `pnpm tsc --noEmit` / `pnpm test` / `pnpm build` がすべて clean

## Owner 側の作業（デプロイ後）

**コマンドの登録が必要。** サーバー限定エンドポイントを使えば即時反映される。

```
POST https://discord.com/api/v10/applications/{application_id}/guilds/{guild_id}/commands
```

**スラッシュコマンド（type 1）の名前の規則は、実装時に公式ドキュメントで確認すること。** メッセージコマンド（type 3）とは制約が異なる。名前は実装が照合する定数と**完全一致**させる必要がある。

## 未解決の質問

- **内容の正しさは検証できない。** URL が 200 でも記事がその事実を書いている保証は無い。数字・引用・負傷の詳細は Owner が出典を確認する運用が要る
- **既存の通知経由の入力との使い分け。** 通知から入れられる事実は通知経由が自然だが、両方の経路が使える状態になる。統合するかは運用してから判断する
- **候補の窓（前後2週間）が妥当か。** 狭いと過去の試合に事実を足せない。運用してから調整する
