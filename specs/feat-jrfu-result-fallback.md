# 日本代表戦の結果を JRFU から補完する

## 背景

**2026-09-05 の日本×カナダは、試合終了から28時間経ってもレビューが生成されなかった。**

| 時刻（JST） | 状態 |
|---|---|
| 2026-09-05 16:40 | 試合終了 |
| 2026-09-05 19:11 | `ingest-live-competitions` 実行。`matches_updated: 4` だが**スコアは入らず** |
| 2026-09-06 20:42 | **まだ `status=scheduled` / score=null / `match_events` 0件 / レビュー未生成** |

**原因は取り込み元にある。** `lipovitan-challenge-cup-2026` の結果は ja.wikipedia の大会ページから取っているが、**そこがまだ「- - 前半-」で未記入だった**（2026-09-06 に WebFetch で確認）。

`lib/cron/orchestrate.ts` のレビュー生成は `status = "finished"` の試合しか対象にしないため、**結果が入らない限り記事は永久に作られない。** 手動で入力した事実12件も待機したままになる。

### 一方、公式には出ている

**`https://www.rugby-japan.jp/schedule/` に 57–12 が掲載されている**（2026-09-06 確認）。日本代表の全試合が日付・対戦相手・スコア・会場つきで並ぶ**単一の安定した URL** である。

**この URL は既に `lib/scrapers/jrfu-match-broadcasts.ts` が放送情報の取り込みで使っている。** ただし現行のパーサが取り出すのは `matchUrls` と `year` だけで、**スコアは見ていない**（`parseJrfuScheduleHtml`）。

### 試合ごとのハードコードは繰り返さない

同じ問題は過去にもあり、**JRFU の記事 URL を1本ずつ埋め込む形で回避されている。**

```
lib/scrapers/wikipedia-lipovitan-challenge-cup-results.ts:27
const JAPAN_FIJI_JRFU_URL = "https://www.rugby-japan.jp/news/54073";
```

**記事 ID は予測できないため、この方式では日本代表戦ごとに PR が必要になる。** 日程ページを使えば1本で足りる。

## スコープ

対象:
- JRFU の日程ページから**日本代表戦の結果（スコア）**を取り出すスクレイパーの新設
- それを `ingestAllLiveCompetitions` の**補完パス**として組み込む

対象外:
- **既存の Wikipedia ソースの変更。** 取得・解析・優先順位を変えない
- **`lib/scrapers/jrfu-match-broadcasts.ts` の変更。** 放送情報の取り込みを壊さない
- `JAPAN_FIJI_JRFU_URL` の削除。**動いているものは残す**
- `match_events` の取り込み。**スコアと `status` だけを扱う**
- 日本代表以外の試合。JRFU の日程ページには載らない
- ワークフローの変更。既存の cron の中で走らせる

## 既存の結果を上書きしない

**補完に限る。** 次の条件を**すべて**満たす試合だけを更新する。

- `matches.status` が `"finished"` **でない**
- `home_score` と `away_score` が**どちらも null**
- JRFU 側にスコアが**両方**入っている

**すでに結果が入っている試合には触らない。** Wikipedia から入った正しい結果を、解析ミスで壊す事故を防ぐため。

**JRFU と Wikipedia でスコアが食い違う場合の解決は本 spec の対象外。** そのときは何もせず、ログに残すだけにする。

## チーム名の対応表を明示すること

**JRFU の日程ページは日本語表記である**（例: `リポビタンDチャレンジカップ2026　カナダ代表戦`）。

**対戦相手を文字列操作で導出しないこと。** 明示的な対応表（日本語表記 → `teams.slug`）を定数として持つ。

これは過去の事故の再発防止である。Top 14 の取り込みで、**分割できないスラッグを分割して対戦チームを求めようとし、機能しないコードが数か月放置された**（`resolveTop14TeamsFromLnrSlug`、PR #742 で `TOP14_TEAM_SLUG_BY_LNR_NAME` の明示表に置き換え）。

**対応表に無い相手は、更新せずログに残してスキップする。** 推測で埋めない。

## 日付を主キーにしないこと（2026-09-06 訂正）

**JRFU の日程ページは現地時間で表示している。** ページ内に2箇所、次の注記がある。

> ※試合日時は現地時間を表示しています

実例として、対アイルランド戦は `07.11 (Sat) 20:10` / McDonald Jones Stadium と、**オーストラリアの現地時刻**で表示されている。

**したがって日付を JST として扱うことはできない。** 会場のタイムゾーンをページから知る手段もない。

**当初この spec は「JST で突合する」と規定していたが、これは誤りだった。** Codex が実装前にフィクスチャで気づいて停止した。

### 採用する突合の規則

**会場のタイムゾーンを推定しないこと。** 次の方法で突合する。

1. 対戦相手を**明示的な対応表**で `teams.slug` に解決する（後述）
2. その相手と日本の試合のうち、**JRFU が示す日付から前後2日以内**にキックオフするものを候補とする
3. **候補がちょうど1件のときだけ更新する**
4. **候補が2件以上あるとき、または0件のときは更新せず、ログに残す**

**前後2日にしているのは、現地時刻と UTC の差が最大でも1日のずれしか生まないためである。** 同一シリーズの連戦は7日以上離れており（2026年の日本×オーストラリアは 8/8 と 8/15）、この窓で取り違えることはない。

**候補が複数出たら必ずスキップすること。** 曖昧なまま更新して間違った試合にスコアを入れる事故を防ぐ。

**この方式ならタイムゾーンの知識が一切不要になる。** 会場が国内でも海外でも同じ規則で動く。

## robots.txt は守ること

**`fetchWithPolicy`（`lib/scrapers/fetcher.ts`）を使うこと。** `rugby-japan.jp` は許可ドメインであり、**D026 の例外はここには適用されない。** D026 は Discord の出典 URL 存在確認に限った例外である。

**リクエストは1回だけ。** 日程ページ1枚に全試合が載っているため、試合ごとに取りに行く必要はない。

## データモデル変更

なし。`matches.status` / `home_score` / `away_score` を更新するだけ。

## API サーフェス

なし。**新しいエンドポイントを作らない。**

既存の `POST /api/cron/ingest-live-competitions` の処理の中で、Wikipedia 由来の各ソースを回した**後**に補完パスとして走らせる。

## UI サーフェス

なし。

## LLM 連携

**なし。** スクレイピングと DB 更新のみ。

## 実行結果の可視化

**補完した件数をレスポンスに含めること。** 既存の各大会の `counts` と並ぶ形で、次を返す。

- 更新した試合数
- 対応表に無い相手でスキップした数（相手の表記もログに出す）
- 既に結果があってスキップした数

**0件が正常な状態である。** Wikipedia が先に更新されていれば補完は不要。

## 受け入れ条件

1. JRFU の日程ページから**日付・対戦相手・スコア**を取り出すパーサが新設されている
2. **`lib/scrapers/jrfu-match-broadcasts.ts` に差分が無い**
3. **`lib/scrapers/wikipedia-lipovitan-challenge-cup-results.ts` に差分が無い**（`JAPAN_FIJI_JRFU_URL` を含めて残す）
4. `fetchWithPolicy` を使っている（素の fetch を使っていない）
5. **リクエストは1回だけ**（試合数に比例しない）
6. 対戦相手が**明示的な対応表**（日本語表記 → `teams.slug`）で解決されている
7. **対応表に無い相手はスキップし、その表記がログに出る**
8. **会場のタイムゾーンを推定していない**（JST 固定でも、会場名からの推定でもない）
8-a. 突合が「**対戦相手＋JRFU の日付から前後2日以内**」で行われている
8-b. **候補が2件以上、または0件のときは更新せず、ログに残る**
9. **`status` が `"finished"` の試合を更新しない**
10. **`home_score` / `away_score` のどちらかが入っている試合を更新しない**
11. JRFU 側にスコアが片方しか無い試合を更新しない
12. 更新時に `status` を `"finished"` にし、スコアを両方入れる
13. `ingestAllLiveCompetitions` の**既存ソースの後**に走る
14. 既存ソースの失敗がこの補完を止めない（逆も同様）
15. レスポンスに**更新数・対応表なしスキップ数・既存結果スキップ数**が含まれる
16. `match_events` に書き込んでいない
17. `supabase/` に差分が無い（マイグレーションなし）
18. パーサのテストが**実際の HTML 構造**に基づいている（手作りの最小 HTML でない）
19. テストが次を覆っている: スコアあり / スコアなし（未実施の試合）/ 対応表に無い相手 / **海外開催で JRFU の日付が DB のキックオフ日と1日ずれるケース** / **同一相手との連戦（候補が窓内に1件だけ入ること）** / **候補が2件以上のときスキップすること** / 既に `finished` の試合を触らない
20. `pnpm lint` / `pnpm tsc --noEmit` / `pnpm test` / `pnpm build` がすべて clean

## 検証方法

**本番で 2026-09-05 の日本×カナダが `finished` / 57–12 になることを確認する。**

この試合は本 spec の起点であり、**Wikipedia が更新されない限り他の経路では埋まらない。** マージ後、次の `ingest-live-competitions` で更新されることを DB で確認する。

**先に Wikipedia が更新されてしまった場合は、受け入れ条件9・10により本パスは何もしない。** その場合はパーサの単体テストで代替する。

## 未解決の質問

- **対応表の初期エントリをどこまで入れるか。** 2026年の日本代表戦に出てくる相手（カナダ・オーストラリア・フィジー・アメリカ等）に絞るか、主要国を先に入れるか。**運用しながら足す前提で、最小から始めるのが妥当と考える**
- **Wikipedia とスコアが食い違ったときの扱い。** 本 spec では何もしないが、どちらを正とするかは別途決める必要がある
- **前後2日の窓が適切か。** 現時点の日程では問題ないが、同一相手と3日以内に2試合行う日程なら候補が2件になりスキップされる。**更新されないだけで誤りは起きない**ので、実際に起きてから対処する
