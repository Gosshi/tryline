# fix-public-page-auth-decoupling

## 背景

GPT-5.6による性能調査（2026-07-20）と実コード確認で判明: 匿名ユーザーがトップページを開くだけで、Supabase Authへのネットワーク往復が最低2箇所で発生している。

- `components/site-header.tsx:14` — `SiteHeader`（ルートレイアウトに配置、全ページ共通）が `getUser()` を無条件に呼び、ログイン済みなら追加で `getUserProfile()` / `getSpoilerGuardEnabledForUser()` も呼ぶ
- `app/page.tsx:112` — トップページ自身が独立して再度 `getUser()` を呼ぶ

`lib/auth/server.ts` の `getSupabaseServerClientWithAuth()`（`getUser()` 等の内部実装）は `next/headers` の `cookies()` を使用しており、これは Next.js の Dynamic API。ルートレイアウトに含まれる `SiteHeader` がこれを呼ぶことで、**サイト全ページが強制的に dynamic レンダリングになっている**と推測される（`[[project_site_performance]]` の TTFB 1.7〜3秒・CDN常時MISSと符合）。

## スコープ

対象:
- ログイン状態・お気に入りチーム・スポイラー設定・プレミアムバッジ等、ユーザー個別の状態表示を、ページ本体のサーバーレンダリングから分離する
- `SiteHeader` は静的な骨格（ロゴ・ナビリンク・大会ドロップダウン）のみをRSCでレンダリングし、ユーザー個別部分（ログインボタン/ユーザーメニュー切り替え、プレミアムバッジ）は独立したクライアントコンポーネントが自身でセッション状態を取得する構成に変更する
- `app/page.tsx:112-113` の `getUser()` / `getUserProfile()` 呼び出しも、ページ本体のデータ取得から分離する（お気に入りチーム優先表示など個別化が必要な部分のみ、分離後のクライアント側取得結果に基づいて動的に描画する）
- セッション状態の取得方法は実装時の裁量とするが、次のいずれかを想定: (a) 軽量なAPIルート（例 `/api/auth/session`）をクライアントから叩く、(b) Supabaseのブラウザクライアントで `getSession()` をクライアント側実行する

対象外:
- `middleware.ts` の変更（別spec `fix-middleware-auth-scope.md` で対応）
- ログイン・ログアウトのUXフロー自体の変更
- 認証必須ページ（マイページ等）の扱い変更。これらは元々個別化が前提のため、本specの対象外（従来通りサーバー側で認証確認してよい）

## データモデル変更

なし。

## API サーフェス

セッション状態取得用の軽量エンドポイントを新設する場合、レスポンスは既存の `getUser()` / `getUserProfile()` / `isProfilePremium()` が返す情報（ログイン有無・表示名・プレミアム状態）を最小限に絞ったJSONとする。既存のCookie/RLSの認可境界は変更しない。

## UI サーフェス

- ヘッダーの見た目・配置は変更しない。ログイン状態切り替え部分だけ、初回描画時に一瞬「未ログイン相当」の骨格が見え、その後クライアント側でユーザー状態に更新される形になってよい（レイアウトシフトが起きないよう、両状態で同じ高さ・同じ枠のプレースホルダーを用意すること）
- お気に入りチームの優先表示（トップページ）も同様に、初回は非個別化の一覧、クライアント側取得後に優先並び替えが反映される形でよい

## 受け入れ条件

1. 匿名ユーザー（Supabase認証Cookieなし）がトップページにアクセスした際、サーバーサイドで `getUser()` / `getUserProfile()` 等の認証APIが呼ばれないことを確認するテスト、またはE2E/統合テストがある
2. ログイン済みユーザーがトップページにアクセスした際、ログイン状態・プレミアムバッジ・お気に入りチームが最終的に正しく表示されることを確認するテストがある
3. `SiteHeader` の静的骨格部分がサーバーコンポーネントとして認証呼び出しなしでレンダリングされることを確認するテストがある
4. レイアウトシフト（CLS悪化）が起きないこと（プレースホルダーと実データ表示後で要素サイズが一致することを目視またはテストで確認）
5. `pnpm test` / `pnpm tsc --noEmit` / `pnpm lint` / `pnpm build` が通る
6. 変更後、匿名ユーザーのトップページTTFBが改善傾向にあることを本番デプロイ後に `curl` 等で確認する（数値目標は定めないが、施策前後の比較値をOwnerに報告すること）

## 未解決の質問

- セッション取得の実装方式（軽量APIルート vs クライアント側Supabase SDK直接呼び出し）はCodexの裁量とするが、実装前にどちらが本プロジェクトの既存パターン（`lib/db/public-server.ts` 等）と整合するか確認すること
- Next.js 15のPartial Prerendering（PPR）が本プロジェクトで有効化可能か・望ましいかは未検討。今回はPPRに依存しない実装とする
