# Codex 実装レビュー

コードは書き直さない。問題点を指摘し、Owner が Codex にフィードバックする。

## 手順

1. **差分を把握**: `git diff main...HEAD` または対象 PR（`gh pr diff <番号>`）。
2. **spec と照合**: 対応する `specs/<name>.md` の受け入れ条件を 1 項目ずつ確認。スコープ対象外の実装が紛れていないかも見る。
3. **テスト確認**: 受け入れ条件に対するテストがあるか。`pnpm test` の結果（Owner または CI の出力）を確認。

## Tryline 固有チェックリスト

- [ ] **設計不変条件**: match_id 中心 / LLM 生成物は試合単位キャッシュ（ユーザー単位は違反）/ スクレイプ生テキストの再配信なし / 4段階パイプライン維持
- [ ] **プロンプトインジェクション**: スクレイプしたテキストや DB 由来テキストをプロンプトに埋める箇所で、指示とデータの分離ができているか
- [ ] **RLS の穴**: 新テーブル・新クエリで RLS ポリシーの有無。`lib/db/public-server.ts`（anon）と `lib/db/server.ts`（service role）の使い分けが正しいか
- [ ] **robots.txt / レート制限**: `lib/scrapers/` に触る変更は parser 使用・キャッシュ・レート制限を確認
- [ ] **LLM コスト**: ループ内呼び出し、キャッシュ迂回、モデル ID の直書き（`lib/llm/models.ts` を経由すべき）がないか
- [ ] **統計捏造ガード**: sourced facts にない数値・固有名詞を LLM が補完できる余地を作っていないか（#344 のガードを弱めていないか）
- [ ] **秘密情報**: ハードコードされたキー・`.env` 読み出しの露出がないか

## 出力形式

CRITICAL（マージ前必須修正）/ HIGH（修正推奨）/ MEDIUM / LOW に分類し、各指摘に「Codex に伝えるフィードバック文」を添える。問題なしなら受け入れ条件ごとの照合結果を表で示す。
