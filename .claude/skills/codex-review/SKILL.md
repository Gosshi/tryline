# Codex 実装レビュー

コードは書き直さない。問題点を指摘し、Owner が Codex にフィードバックする。

## 手順

1. **差分を把握**: ローカル未コミット/ステージ済み差分は `git status` + `git diff`（+ `git diff --staged`）、ブランチ・PR は `git diff main...HEAD` または `gh pr diff <番号>`。レビュー対象がどちらかを確認してから選ぶ。
2. **spec の現在性を確認**: 対応する `specs/<name>.md` 自体が古くないか、`git log --oneline -- specs/<name>.md` と `docs/decisions.md` で確認してから権威ある文書として扱う。
3. **spec と照合**: 受け入れ条件を 1 項目ずつ確認。スコープ対象外の実装が紛れていないかも見る。
4. **テスト・品質確認**: 受け入れ条件に対するテストがあるか。`pnpm lint` / `pnpm tsc --noEmit` / `pnpm test` / `pnpm build` の結果（自分で実行するか、Owner/CI の出力）を確認。
5. **ビジュアル成果物の確認**: UI/画像/動画等の目視評価を伴う変更は、実スクリーンショットや生成物そのものを見て確認する（差分のコードだけで判断しない。CSS背景・画像レイヤーは特に、2026-07-07 の2連続不可視バグの教訓）。

## Tryline 固有チェックリスト

- [ ] **設計不変条件**: match_id 中心 / LLM 生成物は試合単位キャッシュ（ユーザー単位は違反）/ スクレイプ生テキストの再配信なし / 4段階パイプライン維持
- [ ] **プロンプトインジェクション**: スクレイプしたテキストや DB 由来テキストをプロンプトに埋める箇所で、指示とデータの分離ができているか
- [ ] **プロンプトの自己矛盾**: LLMへの指示文中に、互いに反する2つのルールが並んでいないか（`verify-entities.ts` で実際に起きた事故と同型）
- [ ] **RLS の穴**: 新テーブル・新クエリで RLS ポリシーの有無。`lib/db/public-server.ts`（anon）と `lib/db/server.ts`（service role）の使い分けが正しいか
- [ ] **robots.txt / レート制限**: `lib/scrapers/` に触る変更は parser 使用・キャッシュ・レート制限を確認
- [ ] **LLM コスト**: ループ内呼び出し、キャッシュ迂回、モデル ID の直書き（`lib/llm/models.ts` を経由すべき）がないか
- [ ] **統計捏造ガード**: sourced facts にない数値・固有名詞を LLM が補完できる余地を作っていないか（`specs/fix-content-fabrication.md` のガードを弱めていないか）
- [ ] **秘密情報**: ハードコードされたキー・`.env` 読み出しの露出がないか

## 出力形式

CRITICAL（マージ前必須修正）/ HIGH（修正推奨）/ MEDIUM / LOW に分類し、各指摘に「Codex に伝えるフィードバック文」を添える。問題なしなら受け入れ条件ごとの照合結果を表で示す。
