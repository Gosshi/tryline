# note 記事ドラフト

note（@tryline_rugbyjp）の記事ドラフトを作る。**公開するのは Owner。**

2026-07-13 に note 運用方針v1 を確定（`docs/decisions.md` D013）。「全試合を並べる週次まとめ」中心から、下記の3タイプ制へ移行した。

## 権威ドキュメント

- 運用 playbook: `docs/note-owned-media-playbook.md`（役割・カレンダー・計測の原本）
- タイトル案ストック: `docs/marketing-strategy-2026-07-06.md` §7.2（22本）
- 過去記事の例: `docs/notes/` 配下

## 0. Owner ブリーフ（執筆着手前に必須、A・B対象）

**2026-07-20 追加。** 従来は「Claude Codeが先に一通り書く→Ownerが読んで訂正する」という順序だったため、同じ記事に何度も訂正が入りやすかった（実例: 反則数の前提誤り、写真差し替え、試合外の事情の追加等）。これを防ぐため、**執筆に着手する前に**Ownerから以下3点を必ず受け取る（3〜5分想定。長文は不要）:

1. **論点（1つ）**: この記事で一番言いたいこと
2. **一次情報**: Owner自身が現地観戦・視聴で見た・感じたこと（DBやWebSearchでは出てこない情報）
3. **まだ分からないこと**: 断定を避けるべき点、検証待ちの点

この3点を軸にDB・sourced_facts・WebSearchでの裏取りを行い、初稿から一次情報を反映させる。ブリーフが無いまま「とりあえず書いて」と言われた場合は、上記3点を質問してから着手する（AskUserQuestionでもよい）。

C（月1エバーグリーン）は時間的切迫が無いため、この即時ブリーフは必須としない（従来通りテーマ確認から始めてよい）。

## 記事の型（3種）

### A. 日本代表戦翌日の単発深掘り（最優先）

- 日本代表戦ごと。試合終了後12〜18時間以内、**翌朝7〜10時公開**を暫定テスト
- 1記事1つの問い
- **A を出す週は B（週次）を出さない**（同日・同週の露出分散を避ける）
- タイトルの型: 「日本はなぜアイルランドに20–36で逆転負けしたのか——得点経過で見る3つの分岐点」/「20–26まで戻した日本が、最後に追いつけなかった理由」
- 見出し構成: 導入（最も強い事実と問い）→ 分岐点を2〜3見出し（各見出しに DB 由来の数字1つ以上）→ 次戦への含意 → CTA
- 主CTA: 当該試合の `/matches/[id]`（得点推移・詳細）
- データ: 当該試合の `match_events`（得点経過）・`match_content`（preview 予想との対比）

### B. テーマ型週次（最大週1。A を出す週は休止）

- 全試合網羅をやめ、**2〜3試合に絞って1つのテーマで貫く**（旧「全試合を各3〜4文」ルールは D013 で置換。「1行では情報量不足」という2026-07-06の教訓は「絞った試合を深く書く」形で継続）
- 週末ガイド型は木曜19時、振り返り型は日曜夜〜月曜朝を暫定テスト
- 全試合の記録は Tryline 本体（カレンダー・recap）が担当。note は「問い・背景・書き手の見方」を担当
- タイトルの型: 振り返り「73–8でも『イングランド完全復活』とは言い切れない——第2節に残った3つの問い」/ ガイド「今週末、1試合だけ見るなら？日本時間で選ぶ海外ラグビー3試合」
- 冒頭3行の型: 「今節で最も驚いたのは、勝敗そのものではなかった。/ 大差がついた試合にも、次節で再確認したい共通点がある。/ 今週は全結果ではなく、3つの問いだけを取り上げる。」
- 見出し構成: 導入（テーマの提示）→ 試合ごとに1論点 ×2〜3見出し → まとめ（次節の注目）→ CTA
- 主CTA: テーマに合わせて試合ページ / カレンダー / 大会ガイドのいずれか1つ
- データ: 対象試合の `matches`（スコア）・`competition_standings`（順位）・preview 予想との対比

### C. 月1エバーグリーン／独自データ企画（交互に実施）

- 火〜水曜午前目安（曜日より完成度優先）。Owner 工数は週次と別枠で最大3時間
- エバーグリーン候補: marketing-strategy §7.2 の案1・2 など。「RWC2027への道」連載は `rwc2027` スキルのバックログに従う
- 独自データ企画（「AIで904試合をレビューして見えたこと」等）は、**公開時点の実件数・対象期間・番狂わせ等の定義を本文に明記できる場合のみ**書く
- タイトルの型: 検索「海外ラグビー観戦のはじめ方——大会の選び方から日本時間との付き合い方まで」/ 企画「904試合のレビューから見えたこと——当たった予想、外れた予想、まだ分からないこと」（公開コピーで「AI」を前面に出さないブランド方針に合わせる）
- 冒頭3行の型（企画）: 「Trylineでは、海外ラグビーの試合レビューを継続して作ってきた。/ ただ、試合数が増えても『予想しやすい試合』ばかりではない。/ 今回は実データだけを使い、外れ方に共通点があるかを調べた。」
- 見出し構成: 前提・定義（対象期間・件数・方法）→ 本論3〜4見出し → 限界・分からないこと → CTA
- 主CTA: 大会ハブ / カレンダーなど記事テーマに一致するページ
- データ: `matches` / `match_content` の集計（集計クエリは `prod-investigation` の読み取り専用ルールで実行し、集計条件を本文に明記）

## 共通の書き方

- **タイトル**: 疑問・数字・固有名詞（日本代表・大会名・対戦相手）を含める。「今週のまとめ」「プレビュー」だけの弱いタイトルは禁止
- **冒頭3行**: 最も強い事実 → 残された問い → この記事で分かること。note はおすすめカード・タイムラインに冒頭が出るため、ここで読む理由を示す
  > 日本は58分、20–26まで戻した。
  > それでも残り22分で試合をひっくり返せなかった。
  > Trylineの得点経過から、分岐点を3つに絞って振り返る。
- **予想対比**: `match_content`（preview）の予想と recap「この試合の核心」を対比させる（従来手順を継続）。本文は要約・言い換えし、コピペしない
- **数字は展開する（2026-07-20追加）**: 新しい数字・事実を1つ足すごとに、単独の一言で終わらせず「その数字が何を意味するか」を続ける文を必ず書く。「反則は日本9・フランス10で僅差だった」で終わらせず、「では何が問題だったのか」を掘り下げて初めて密度が出る（詳細は `feedback_note_content_density` メモリ参照）
- **sourced_facts は必ずDBを直接確認する（2026-07-20追加）**: `match_content`（LLM生成のrecap本文）だけを見て「未検証」と判断しない。本文に採用するか迷う事実は `match_sourced_facts` テーブルを直接クエリしてから判断する（`prod-investigation` の読み取り専用ルールで）
- **試合後コメント・詳細スタッツはWebSearchで補強する（2026-07-20追加）**: DBのsourced_factsだけでは試合後コメント・反則数・タックル成功率等が不足しがちなので、WebSearchでの追加取材を前提にする。検索結果には無関係な話題（同時期の別スポーツイベント等）が混入することがあるため、ドメイン指定検索と内容の整合性確認をしてから本文に採用する
- **出典は文末にまとめる**: 単純な事実（誰がトライを決めたか等）に逐一 `(news.yahoo.co.jp)` 式の引用を本文中に挟まない。個別引用・スタッツの出典は「## 出典」セクションとして文末にまとめる
- **見出し画像**: 2つの選択肢を検討する。(1) Ownerが現地で撮影した写真がある場合は**それを優先**（一次情報としての説得力が生成画像より高い。使用前に他の観客の顔が判別できないか等を確認）。(2) 無い場合は `image-gen` スキルで生成する。**生成する場合は記事固有の具体的な絵にする**（汎用的なスクラム/ハイタッチ画像は「どの記事にも貼れる」ため避け、その記事の核心（例: 規律の話ならレフェリーのカード、番狂わせの話なら該当シーンを想起させる構図）に紐づけること。必須末尾制約・失敗パターン対策句は `image-gen` スキルに従う
- **note非対応の記法を使わない**: noteはMarkdownテーブルを表示できない。表にしたくなったら地の文か箇条書きに変換する
- **CTAは本文に直接組み込む**: ドラフト内に「## CTA」等の別セクションとしてメモするだけで終わらせず、実際に公開する本文（主CTAは記事の結び付近、フッター固定リンクは末尾）にリンクとして組み込んだ状態でドラフトを完成させる
- **ハッシュタグ**: 内容に即した**4〜5個**（`#ラグビー` `#海外ラグビー` ＋ `#日本代表`・大会名等）。チーム愛称タグを8〜10個並べる旧運用はしない。本文末尾に「推奨ハッシュタグ」として運用メモを残す（本文には含めない）
- **ドラフト保存**: `docs/notes/YYYY-MM-DD-<deep-dive|weekly|evergreen>.md`

## 送客導線（CTA 2段構成）

1. **主CTA 1本**: 記事内容に直接一致するページ（A→当該試合の得点推移・詳細ページ、B→テーマに合う試合/日程/大会ガイド、C→大会ハブ等）。**記事と無関係な過去試合を主CTAにしない**
2. **フッター固定**: 「今週の全試合日程（日本時間）は Tryline のカレンダーで」→ カレンダーページ

**Tryline ドメインへの全リンク**に `utm_source=note&utm_medium=referral` を付与（付与率100%。GA4 流入分離用）。既にクエリがある URL には `?` でなく `&` で連結する。**外部サイトへのリンク（JRFU 等の出典）には付けない**（GA4 で計測できず、外部に不要なパラメータを送るだけ）。

## データ取得（「DB 数字限定」を実行するための入口）

- 試合結果・スコア・得点経過・順位: `prod-investigation` スキルの読み取り専用ルールで Supabase から（`matches` / `match_events` / `competition_standings`）。またはサイトの `/calendar`・`/matches/[id]` から転記
- 予想対比の素材: `match_content`（`content_type='preview'`）の予想と recap「この試合の核心」
- 外部公式スタッツ: `sourced_facts` に取り込み済みのもののみ使用可。それ以外は本文に書かない

## 絶対ルール

- **recap 全文を転載しない**(要約＋送客のみ。重複コンテンツで両方沈む)
- **数値は Tryline DB で確認できるもののみ**(スコア・得点経過・順位)。外部公式スタッツは sourced_facts に取り込み済みのもの以外使わない(D013。捏造統計禁止ルールの拡張)。**例外**: Owner が一次情報として直接提供した出典（現地撮影の掲示情報、Owner自身が確認したニュース記事等）は、出典・確認方法を本文末尾「出典」に明記した上で使用可（sourced_facts未取り込みの場合も同様）。この例外はOwnerが明示的にソースを渡した場合のみで、Claude Code側の判断で勝手にsourced_facts外の数値を採用してはならない
- 直接引用は最小限・言い換え原則
- A と B を同日・同週に重ねない
- 「全データ分析」等と書きながら対象・方法を示さない表現をしない

## X 連動（公開チェックリスト）

`x-post` skill の「強い1本＋スレッド」原則と接続する。**責務分離: 親投稿の下書きは `x-post`、note URL を載せる返信は `x-reply` の扱い**（URL 付き reply 1日1〜2件ルールの枠内）。

**タイプ別の親投稿**（どのタイプでも単独の URL 告知投稿には戻さない）:

- **A**: 試合直後の X 親投稿（強い1本＋スレッド）に返信
- **B**: 対応する週末ガイド・結果分析の親投稿に返信
- **C**: 記事の最も強い結論を **URL なしの親投稿**として先に出し、その返信に note URL
- 適切な親投稿がない場合は、C 方式で親投稿を立ててから返信する

手順:

1. 親投稿を確認、なければ作成（上記タイプ別）
2. note 公開直後、親投稿への返信で「記事で新たに分かったこと＋URL」を投稿
3. 6〜12時間後、新しい図・別の論点がある場合のみ引用RT
4. 翌日に選択式質問投稿（①②③形式）で会話枠へ接続

チェック項目: note URL / UTM 確認 / 対応する X 親投稿 ID / スレッド返信実施 / 計測予定の記録（下記「計測と KPI」）

## 週の時間配分（Owner 実作業 75分。C は別枠最大3時間）

**2026-07-20更新**: 「0. Owner ブリーフ」を先頭に追加し、事後の事実確認・訂正往復を減らす配分に変更。

Owner ブリーフ（論点・一次情報・未確定事項）5分 / テーマ・使用データ確認 10分 / Owner の最終確認（ブリーフが反映されているか・事実誤認がないか）15分 / 画像・タグ・CTA・公開 10分 / X 連動 10分 / note 内交流 15分 / 数値記録 5分 / 予備 5分

## note 内交流（週15分・4週間テスト）

- 週2〜3回、ラグビーを書いている note クリエイターの記事を**読んでから**具体的なスキ・コメントをする
- 相互スキを目的にしない
- 4週間でフォロー・コメント・プロフィール言及の発生を測り、反応がなければ頻度を下げる（推薦アルゴリズムへの直接効果は未確認のため、関係構築テストとして扱う）

## 計測と KPI（最初の4週間は相対値で判定。予測値ではなく継続・中止の判定基準）

**記録タイミング**（測定時点と判定時点を一致させる）:

- 全記事: 公開 **24時間後・72時間後**（X 表示・URLクリック・note ビュー・referral）
- A / B: **7日後**のビューを追加記録
- C: **7日後＋30日後**を追加記録

**判定基準**:

- A（深掘り）: 直近5記事の **7日ビュー中央値の1.5倍**
- B（テーマ型週次）: 直近5本の B の **7日ビュー中央値以上**（B が5本未満の間は全記事の7日中央値で代用）。**2本連続で下回ったら頻度を下げる**
- C（月次）: 直近5本の C の **30日ビュー中央値の2倍**（C が5本未満の間は全記事の30日中央値で代用）、または UTM referral **3件以上**
- 全体: note referral **8 → 15セッション/28日**
- UTM 付与率 **100%**（Tryline ドメイン向けリンク）
