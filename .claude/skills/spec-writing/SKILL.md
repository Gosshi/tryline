# 仕様書作成（/specs）

Claude Code の主要成果物。アプリコードは書かず、Codex が迷わず実装できる仕様書を書く。

## 手順

1. **重複・矛盾チェック**: `ls specs/` で既存 specと照合。類似 spec があれば新規作成せず更新を提案する。
   - 命名規則: 新機能は `feat-<name>.md`、バグ修正は `fix-<name>.md`
2. **過去の判断を確認**: `docs/decisions.md` と `docs/architecture.md` を読む。
3. **ユーザーストーリーの確認**: 受け入れ条件が曖昧なら Owner に質問してから書く。
4. **CLAUDE.md のテンプレートに従う**: 背景 / スコープ / データモデル変更 / API サーフェス / UI サーフェス / LLM 連携 / 受け入れ条件 / 未解決の質問。

## 必須チェックリスト

- [ ] 設計不変条件に違反していないか（match_id 中心、試合単位キャッシュ、生テキスト再配信禁止、robots.txt 尊重、4段階パイプライン、15語超引用禁止、モバイルファースト PWA）
- [ ] LLM/TTS/画像生成/Web Search 等の呼び出しを増やす場合、**コスト見積もり**を明記（モデルIDは直書きせず `MODELS.FAST` / `MODELS.NARRATIVE` 等 `lib/llm/models.ts` の集中管理を参照。プロバイダは OpenAI 固定。動画・画像処理を伴う場合はローカル処理分も含めて算出する）
- [ ] コンテンツ再生成を伴う場合、「少件数の試し焼き→検品→全件」の段階実行を受け入れ条件に含める（2026-06 の 297 件 draft 化事故の再発防止。QA最低字数は `lib/llm/content-length.ts` を都度確認し値を書き写さない）
- [ ] 受け入れ条件は Codex が機械的に検証できる粒度（「〜が表示される」ではなく「〜のとき X が Y を返す」）
- [ ] スコープ対象外を明示する（MVP 機能膨張の防止）
- [ ] 統計・事実の LLM 補完（捏造）を許す余地がないか
- [ ] **ビジュアル/UI/画像/動画を含む spec は、デザイン品質の基準を受け入れ条件に含める**: 参照スタイル方向、使用トークン（サイト系なら `app/globals.css` の CSS変数）、避けるべき表現（テンプレ的な均一レイアウト、静止画の羅列に動きが一切ない構成等）を明記し、Owner による目視評価を受け入れ条件の1項目にする。機械的な受け入れ条件だけで完了とせず、定性的な品質判断が必要な旨を明示する
- [ ] specで参照するファイルパス・関数名・コマンドは、実際に存在するか `grep`/`ls` 等で確認してから書く（存在しない参照は Codex の実装を誤らせる）
- [ ] specが依存する既存 spec・decisions が現在も有効か、`git log --oneline -- <path>` や `docs/decisions.md` で確認する（古いゲート・閾値をそのまま引用しない）

## やらないこと

- 仕様書内にアプリコードの完全実装を書かない（参照すべき既存パターンのファイルパスを指す）
- 依頼されていない spec を勝手に作らない
