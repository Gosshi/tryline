# X 投稿ドラフト

@tryline_rugbyjp の自発ポストの下書きを作る。**投稿するのは Owner。自動投稿は停止済み**（`specs/fix-disable-x-auto-post.md`）で復活させない。

## X の位置づけ（2026-08-28 実測で確定）

**X は現時点で獲得チャネルではない。** GA4 実測（2026-07-31〜08-27 の28日）で X 起点の実流入は **t.co 8ユーザー**のみ。`x / social`（2ユーザー28セッション）と `x / profile`（2ユーザー16セッション）はセッション/ユーザー比が8〜14で Owner 自身の回遊とみられる（referral はユーザー数で見る。D017 の教訓）。同期間の検索流入は **113ユーザー**（bing 70 + google 30 + yahoo 9 + その他4、同期間 GA4）で **約14倍の開き**がある。サイト読者の **63% は Windows デスクトップ**（107/171ユーザー、同期間 GA4）で X の中心層（モバイル）と重なっていない。

この前提で、X の役割は次の3つに限定する:

1. **信頼の担保**: 検索で来た人が「実在する運営か」を確かめる場所。プロフィール・固定ポスト・週1以上の稼働が保てていれば足りる
2. **試合日の接点**: 実況タイムラインだけは X 層とラグビー関心が確実に重なる。投下はここ（型4、`x-reply` の実況参加）に集中する
3. **ニュースへの応答**: 型5・型7

**判断基準: 1投稿の作成に Owner+Claude 合計15分を超える手間をかける施策は、X 単独の期待効果では正当化しない**（成果物がサイト側でも使える場合のみ例外）。

検証方法: 28日ごとに GA4 `sessionSource=t.co` の**ユーザー数**を記録する。20ユーザー/28日を超えたらこの位置づけを見直す（現在値8）。

## 投稿の型（下記一覧にある型のみ。追加する場合はこの一覧に追記する）

1. **試合結果**: スコア＋一言（レビューの「この試合の核心」から要約。全文コピペしない）
2. **週末プレビュー**: 「今週末の海外ラグビー」— カレンダーページのデータから注目3〜5試合を JST 付きで。**画像は `/api/og?type=calendar` の生成画像をネイティブ画像として本文に添付する。これは必須で、リンクカードに任せてはいけない。**（2026-08-28 の実測で確定。旧記述の「週次投稿は毎回新規クロールされるためリンクカードでも通常問題ない」は**誤りだった**。`/calendar` は毎週同じ URL なので **X は再クロールせず前週のカードをそのまま出す**。実例: 8/28 の投稿で「8月17日 - 23日 JST / 1大会 1試合」という1週間前の画像が表示された。同時刻のページ側 og:image パラメータは `week_label=8月24日 - 30日 JST` / `match_count=3` / `competition_count=2` と正しく、原因は X 側のキャッシュだった）。**画像を添付すると X はリンクカードを描画しないため、URL を本文に置く例外運用（2026-08-09）と併用しても古いカードは出ない。** 画像の取得方法は下記「カレンダー OG 画像の取得手順」。URL（`/calendar`）の置き場所は既存の「ネイティブ投稿優先」ルールと 2026-08-09 の例外に従う

   なお画像は「その週全体」の件数を出すため、本文で週末2〜3試合に絞ると**画像の試合数と本文の試合数が食い違って見える**ことがある（例: 週の頭に終わった試合が画像の件数に含まれる）。役割が違うので原則そのままでよいが、差が大きいときは本文に一言添える
3. **note 連動**: note 記事は単独の URL 告知投稿をしない。**タイプ別の親投稿**（A=試合直後の強い1本 / B=週末ガイド・結果分析の親投稿（B型記事は D017 で停止済みのため事実上発生しない） / C=記事の最も強い結論を URL なしで先に親投稿として出す。適切な親投稿がなければ C 方式で立てる）への**返信**で「記事で新たに分かったこと＋URL」を投稿し、6〜12時間後に新しい図・別論点がある場合のみ引用RT、翌日に選択式質問投稿で会話へ接続。**責務分離: 親投稿の下書きは本スキル、URL を載せる返信は `x-reply` の扱い**（2026-07-13 D013。手順・チェックリストは `note-weekly` スキルの「X 連動」節が正）
4. **試合日ライブ**: キックオフ前後の速報・寸評（playbook X4。週末の注目試合に集中）
5. **引用リポスト**: 海外の公式発表・信頼できる現地報道に、日本語の付加価値を添えて引用RT（2026-07-13 に対象を日本代表絡みから海外ラグビー全般へ拡張）。優先順: (a) 各国代表・クラブ・大会の公式発表（メンバー発表・負傷・移籍・監督コメント）、(b) 試合直後の公式ハイライト・記録、(c) 信頼できる現地記者のニュース、(d) 日本人選手が所属する海外クラブの情報。**必ず「日本のファンにとってなぜ重要か」「次の試合にどう影響するか」を一言入れる**。1日1〜2件まで。禁止: 英文のほぼ全訳、「楽しみですね」等の感想だけの引用、出典不明の移籍情報の拡散、同じニュースの重複投稿。形は「日本語で要約＋Tryline の見方＋原投稿」（長文の直接引用はしない）
6. **データ画像**: 大会ラウンド完結時の「全結果スコアボード」を画像化して投稿。**大会ラウンド完結時に1本のイベント駆動。「週2〜3本」の量目標は 2026-08-28 に廃止**（2026-07-06 の開始以降、投稿単位の効果実測が一度も記録されないまま7週経過。レンダリング工程の手間に対し根拠のない量目標は作業だけを生む。量を増やすのは、次回 X アナリティクス CSV でデータ画像投稿と文字投稿のインプレッション中央値を比較してから）。作り方は下記「データ画像の作り方」参照。**週末結果まとめは固定シリーズ名「【週末の海外ラグビー】」を毎回タイトルに使う**（番組化・2026-07-13 追加。**フォロー転換への効果は 2026-08-28 時点で未実証**。t.co 実流入は前28日1→直近28日8ユーザーと動いたが、同期間に日本代表戦（8/8・8/15）があり番組化の効果とは切り分け不能。シリーズ名は一貫性のためコストゼロで維持するが、効果があるとは主張しない。判定は X アナリティクス CSV のフォロー発生と投稿タイプの突合で行う）。**ハッシュタグではなく本文中の記号（【】）で表記する**（2026-07-14 修正: 検索需要のない自作タグをハッシュタグ化しても発見に寄与しない。ハッシュタグを付ける場合は下記ハッシュタグ表の「週末結果データ画像」欄に従い `#海外ラグビー` を1個）

7. **ニュース＋データ考察**: 海外で報じられたニュースを、Tryline の DB 実データで検証・補強して投稿する（2026-08-08 追加）。詳細は下記「型7 の運用ルール」を参照。**翻訳ではなく検証**。reply 版は `x-reply` スキルの「海外ニュース要約＋Trylineデータ紐付け型」が正で、本型はその自発投稿版にあたる

## 型7「ニュース＋データ考察」の運用ルール（2026-08-08 追加）

翻訳だけなら既存の大手アカウント（@rugbykuronekoya 等）が速く上手い。Tryline の優位は**過去の試合データベース**にあり、ニュースを事実として受け取り数字で意味を与えるところで差がつく。この型は「訳す」のではなく「検証する」。

### 起点は必ず Owner（厳守）

- **Claude は記事を探しに行かない。** Owner が記事 URL または X 投稿を投げるところから始める
- **Owner の負担は「何のニュースか」の1行だけ**。記事を通読して要約する必要はない（例:「サヴェアが負傷らしい」「Xがトップ14に移籍」）。そこから先の裏取りは Claude が担当する:
  - **許可ドメインからの取得は Claude がやってよい**（`lib/llm/sourced-facts/allowlist.ts` に載っているもの。Wikipedia / rugby-japan.jp / therugbypaper.co.uk / onrugby.it / rugby.com.au / unitedrugby.com / league-one.jp / rugby-rp.com 等）。同じニュースは複数媒体が報じているため、禁止ドメインで読んだ話でも許可ドメイン側で裏が取れることが多い
  - **禁止ドメインの記事 URL は Claude が開かない**。その場合だけ Owner に事実の補足を頼む
  - X 投稿が元なら本文をそのまま貼ってもらう（Claude は X をクロールしない）
- 裏が取れない事実は書かない。「たぶんこう報じられている」で埋めない
- **ニュース収集の自動化はしない。** 2026-07-27 に「今週のニュース」draft 2件が捏造（URL が 404）と判明して収集停止、2026-07-29 に RUGBY DESK 案を同じリスクで見送っている。2件とも原因は「LLM に記事を探させたこと」。この失敗はここで構造的に塞ぐ
- X のページは Claude からクロールしない（`x-reply` と同じ理由。robots/レート制限）

### 著作権・規約の線引き（2026-08-07 の監査で確定）

- **アウトは2つだけ**: (1) 機械で取得して蓄積し繰り返し材料として使うこと、(2) 表現をそのまま移すこと（翻訳・長い引用）
- **リンクを貼るのは複製ではない**。公開 URL の参照であり、リンクカードの見出し・画像は媒体側が OG タグで自ら設定したもの
- **事実に著作権はない**。「X が負傷した」「Y が移籍した」を自分の言葉で書くのは自由
- **要約の density に注意**。読めば原文が不要になるほど網羅した要約は実質的な代替になる。事実を数点拾い、そこから自分の分析に進む形にする
- 15語超の直接引用をしない（Tryline の設計不変条件）
- **「大手メディアだから安全」は成り立たない**。2026-08-07 の監査で rugbypass.com / skysports.com / bbc.co.uk / espn.com / planetrugby.com はいずれも AI 利用・データマイニング禁止または GPTBot ブロックだった。World Rugby・イングランド協会・オールブラックス等の公式サイトも同様。**規模ではなく許諾で判断する**。機械取得の許可ドメインは `lib/llm/sourced-facts/allowlist.ts` が唯一の正

### 手順

1. Owner が記事 URL / X 投稿と要点を渡す
2. Claude が DB で裏を取る（`prod-investigation` の読み取り専用ルール）。使えるもの: 直近試合の得失点、H2H、`match_events` の得点経過、今後の日程
3. **ニュースの前提にある「仕組み」自体を検証する**。見出しの因果関係をそのまま採用しない（2026-07-21、ランキング変動のニュースで「得失点差も加味される」という前提が World Rugby 公式ルールと異なり、実際の主因も別チームの自滅だったという事故がある）
4. 下書き2案（トーン違い）を文字数付きで出す

### 形式

- **元が X 投稿なら引用RT**（元投稿の引用欄から読まれる経路が増え、リンクによる露出低下も受けない）
- **元が記事 URL だけなら本文完結**にし、URL は 1st reply に置く（本文にリンクを入れると露出が落ちる。@rugbykuronekoya が本文に URL を貼れるのはフォロワー15,930で露出が自力で足りるため。Tryline は露出がボトルネックなので同じ形は取れない）
- 文字数は既存ルールどおり200〜260字
- **必ず「日本のファンにとってなぜ重要か」「次の試合にどう影響するか」を入れる**（型5と共通）

### 頻度

週2〜3本。タイムライン配分の「海外ニュースの引用リポスト30%」の枠内で運用する。

## 投稿の原則（2026-07-13 確定、X運用方針v2）

07-13 の実測分析（`docs/marketing-strategy-2026-07-06.md` 2.3節）に基づく確定原則。個別ルールと矛盾する場合はこちらが優先。

- **1投稿=1メッセージ**。冒頭は日付・大会名でなく「最も驚く事実」から始める（例: 「73–8。5連敗中だったイングランドに何が起きた？」）。実測で日付始まりの同型連投はインプレッション最低帯だった
- **複数試合は分割連投しない**。最も強い結論の1本を立て、残りの試合はスレッド（自分への返信）でぶら下げる。リンクはスレッド2本目以降に置く（2026-07-05 の「3試合ずつ分割・各投稿リンク可」ルールを実測に基づき置き換え）
- **タイムライン配分**: 独自の試合分析・日程・結果 50% / 海外ニュースの引用リポスト 30% / reply・会話 20%
- **重心は日本代表＋その週の主要国際試合**。認知獲得フェーズでは日本代表戦のある週に集中投下し、他大会は入ってきた人に見せる奥行きとして扱う
- **立ち位置**: 「海外ラグビーのニュースが日本語で分かり、それが次の試合にどう影響するかまで分かる」。速報の速さでは勝負しない（速報量産をやらない方針は維持）
- 質問で締める場合は「どう思いましたか？」でなく選択式にする（例: 「日本が最も差を感じたのは？ ①接点 ②キック処理 ③規律」）

## 予想→答え合わせの連続性（2026-07-13 追加）

金曜プレビュー投稿（型2、H2H→キーマッチアップ→勝敗予想の3連ツリー）で立てた予想は、次の月曜まとめ投稿（型1 or 6）で必ず答え合わせをする。「金曜に予想した◯試合中◯試合的中」のように的中率を一言添える。的中率の積み上げが「続きものとして追う理由」を作り、フォローの動機になる。数字は実際の予想内容と結果から算出したものだけを使う（水増し・後付け解釈禁止）。

## カレンダー OG 画像の取得手順（型2で必須）

自作せず、**本番が実際に出している og:image をそのまま落とす**。ページ側のパラメータを使うので、週・件数・注目カードが必ず本番表示と一致する。

1. **本番ページから og:image の URL を取り出す**

   ```bash
   curl -s https://www.trylinerugby.com/calendar \
     | grep -oE '<meta property="og:image" content="[^"]+"' | head -1
   ```

   `week_label` / `match_count` / `competition_count` / `focus_*` が入っている。**この値が今週のものかを目視で確認する**（ここが古ければ X のキャッシュではなくページ側の問題）。

2. **その URL を PNG として保存する。** `--max-time` を長めに取る（**画像生成に1分以上かかることがある**。既定のタイムアウトでは落ちる）

   ```bash
   curl -s --max-time 100 -o <scratchpad>/calendar-og-<日付>.png "<og:image の URL>"
   ```

3. **必ず Read で開いて中身を見る。** 週の表記・件数・注目カードが今週のものか確認してから Owner に渡す（`feedback_screenshot_audit_caveat` と同じ理由で、生成できた＝正しいとは限らない）

4. `SendUserFile` で Owner に渡す。投稿は Owner が実施（自動投稿はしない）

## データ画像の作り方

- **対象**: 大会1ラウンド分の全試合結果（スコアのみ）。それ以外の切り口（トライ王ランキング等 `match_events` 集計）は、イベント汚染事故（`project_event_contamination` / `project_nc_data_pipeline` メモリ参照）が解消・検証されるまでは扱わない。**`matches.home_score` / `away_score` のみを使う**
- **データ取得**: `prod-investigation` スキルの作法で Supabase から SELECT のみ（例: 対象大会・直近ラウンドの `matches` を `teams` / `competitions` と JOIN）
- **デザイン**: `app/globals.css` の CSS 変数（`--color-paper` `--color-ink` `--color-ink-muted` `--color-rule` `--color-accent`）をそのまま使う。フォントは Web フォント読み込みができない前提で `"Hiragino Maru Gothic ProN", "BIZ UDPGothic", sans-serif` 等のシステム丸ゴシック代替を使う。勝者は色＋太字＋アクセント色のティックバーで示す（数字だけでなく形でも状態を示す）
- **レンダリング手順**:
  1. スクラッチパッドに単体 HTML を作成（`<meta charset="utf-8">` 必須、無いと日本語が文字化けする）
  2. `python3 -m http.server <port> --bind 127.0.0.1` でスクラッチパッドを配信（Artifact の CSP・`file://` 直読み不可のため）
  3. Playwright MCP（`browser_navigate` → `browser_resize` → `browser_take_screenshot(fullPage:true)`）でスクリーンショット。カード自体を固定サイズ（例 1080×1500）にして `.card` に `overflow:hidden` を付けている場合、内容がその高さに収まっているか要確認（CJK フォントは行送りが見込みより大きくなりやすく、フッターが欠ける事故が起きやすい）
  4. `sips -c <height> <width> in.png --out out.png` でカードサイズぴったりに中央クロップ
  5. Owner に画像を渡して検品→投稿は Owner が実施（自動投稿はしない）

## ルール

- **1日1〜3投稿まで**。連続大量投稿はしない（2026-05-23 の教訓）
- **投稿時刻は 9時台・12時台・17〜20時台（JST）を第一候補にする**（2026-08-28 追加）。サイト訪問の実測ピーク（GA4、2026-07-31〜08-27: 9時17・12時17・17時16・19時15・20時15ユーザー。深夜2〜8時は1〜8）に合わせた暫定ルール。読者の63%がデスクトップのため、始業前後・昼休み・終業後の PC 前時間帯を優先する。曜日は実測でほぼフラット（土32・日30・火19ユーザー）のため曜日ルールは設けない。**ただしこれは代理指標である。** 上の「X の位置づけ」節が述べるとおり X の閲覧層はサイト読者と重ならない可能性が高く、サイト訪問の時間帯を X の投稿時刻の根拠にするのは論理的に弱い。X 上の閲覧時間は直接計測できないため暫定でこれを使うが、次回 X アナリティクス CSV で投稿時刻帯別のインプレッション中央値を比較して確定する。試合日の実況・結果速報はキックオフ時刻優先でこの限りではない
- **文字数目安は200〜260字**（**この帯の優位は未実測の暫定値**。2026-08-28 時点で文字数帯別の比較は行われていない。次回 X アナリティクス CSV 取得時に 〜100 / 100〜200 / 200〜260 / 260字超 のインプレッション中央値で検証する）。短すぎる一言（100字未満）は情報量不足で読まれにくい。直近5試合の個別スコアを2〜3試合分具体的に列挙する等、実データを積み増して自然に文字数を伸ばす（水増しの言い回しで埋めない）。追加する数字は必ず生成済みプレビュー/レビューの根拠データ（DB実測）と一致するものだけを使う（2026-07-09 追加）
- **ネイティブ投稿優先**: 外部リンクは reach を下げる。URL は本文でなく 1st reply に置くか省略。リンク付き投稿は1日1回まで（playbook X3）
  - **例外（2026-08-09 追加・重要）**: **自分の投稿への1st replyが他アカウントから見えない状態では、URL を本文に入れる。** 2026-08-09、Owner が実際に確認したところ返信が他アカウントから不可視で、URL を1st replyに置くとクリックが発生しない状態だった。**露出の低下より導線の消失の方が損失が大きい。** 判断手順: 投稿前に返信の可視性が確認できていなければ本文に URL を入れる。可視性が確認できている場合のみ従来どおり1st replyに置く。**リンク付き投稿は1日1回までの制限は維持する**（本例外は配置の話であって本数の話ではない）
  - 複数試合を扱う場合も分割連投はせず「強い1本＋スレッド」形式にする（上記「投稿の原則」参照）。リンクはスレッド2本目以降に置く（2026-07-05 の分割・投稿ごとリンク可ルールは 2026-07-13 に廃止。実測で分割連投がインプレッション最低帯だったため）
- 数字は実データのみ（Supabase / サイト表示から転記。捏造統計禁止）
- **ハッシュタグは投稿タイプ別に判断する**（2026-07-14 実測に基づき更新。42投稿分析で「ハッシュタグのクリック数」は全件0だった。タグを標準装備にせず、今まさに検索されていると判断できる場面だけ使う）:

  |---|---|---|
  | 固定ポスト | **0** | プロフィール転換に集中。検索流入は狙わない |
  | 独自分析・試合結果 | 0〜1 | 検索される具体的なタグだけ（`#海外ラグビー` 等） |
  | 試合実況（ライブ） | 1〜2 | 公式・放送局が当日案内している実況タグを都度確認して使う（固定タグを推測で使わない） |
