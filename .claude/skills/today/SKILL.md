# /today — 朝の司令塔

Owner の目標状態は「**判断だけする**」。このスキルは毎朝1回起動され、23本のスキルのどれを使うか Owner が考えなくて済むようにする。**Owner はスキル名を覚えなくてよい。/today だけ覚えればよい。**

## 手順 1: 状況収集（すべて読み取り専用・可能な限り並列）

1. `date '+%Y-%m-%d (%a)'` — 曜日で分岐が変わる
2. `bash tools/ops/codex-queue.sh 21` — オープン PR・spec パイプラインの滞留
3. `git log --oneline -8 main` — 前回セッション以降の動き
4. `ls -t docs/notes/ | head -3` — 週次記録・ニュースダイジェストの鮮度
5. 月曜のみ: GA4 MCP で先週のセッション数・チャネル内訳（前週比）。取得失敗時は「取得失敗」と明記してスキップ

**取れなかった情報は「取得できず」と書いて先へ進む。止まらない。捏造しない。**

## 手順 2: 曜日別ルーチン

| 曜日 | 自動で確認すること | 承認キューに乗せる判断 |
|---|---|---|
| 月 | routine「note週次まとめドラフト」（月曜 7:00 JST 発火）の `draft:` PR を検品（note-weekly 規約: 捏造なし・転載なし・送客3点セット） | note を公開するか / 修正指示 |
| 月 | GA4 の数字クイックチェック（weekly-ops §3 の5分版） | 異変があれば growth-analysis で深掘りするか |
| 金 | routine「週末ニュースダイジェスト」（金曜 18:00 JST 発火）の `draft:` PR を検品（出典・確度ラベル必須） | ダイジェストをマージするか / reply ネタとして採用するか |
| 毎日 | codex-queue の「PR オープン（レビュー待ち）」 | codex-review → マージ可否 |
| 毎日 | X reply の候補（試合日・話題性から1〜3スレッド） | reply を投稿するか（下書きは x-reply に委譲） |
| 土日 | 当日の試合カード（試合日なら） | 結果ポストを仕込むか（x-post に委譲） |

routine の PR が期待日に存在しない場合は「routine が発火していない可能性。https://claude.ai/code/routines で確認を」と承認キューに乗せる。

## 手順 3: 出力形式（これ以外を出さない）

```markdown
## 本日の承認キュー（YYYY-MM-DD 曜日）

1. [判断] <Owner が決めること一文>
   背景: <一行> / 推奨: <推奨と理由一文> / 所要: <N分> / 実働: <委譲先スキル名 or 手動>
2. ...（最大5件。判断が5件を超える日は重要度順に切り、残りは「今日はやらないこと」へ）

## 今日はやらないこと
- <あえて触らないもの＋一言の理由>

## 数字メモ（月曜のみ）
- <実測値＋期間のみ。解釈は異変時だけ>
```

## 原則

- **判断項目だけを出す**。作業項目（下書き・調査・レビューの実働）はキューに乗せず、Owner の判断後に該当スキルで実行する
- 出力は 15 分で読み切れる分量。長い分析はしない（必要なら「深掘りは growth-analysis で」と誘導）
- 数字は実測のみ・期間明記（growth-analysis の出力規約と同じ）
- 週5時間・毎日10分の枠を超える提案をしない（weekly-ops と同じ制約）

## 権限境界

- このスキル自体は**読み取り専用**。投稿・マージ・publish・課金操作（regen 含む）・ファイル削除は、承認キューで Owner が判断した後に該当スキル経由で行う
- 本番 DB・GA4・GSC は読み取りのみ

## 委譲マップ（判断後の実働先）

| 判断 | 実働スキル |
|---|---|
| PR をマージする | `pr-merge` |
| PR を精査してから決める | `codex-review` / `tryline-spec-checker`(agent) |
| reply / ポストを出す | `x-reply` / `x-post` |
| note を公開する | `note-weekly`（最終検品）→ 公開は Owner |
| 数字を深掘りする | `growth-analysis` |
| データ異常を調べる | `prod-investigation` → spec 化は `spec-writing` |
| 新しい機能をやる | `spec-writing` → `codex-handoff` |
