# 記事生成プロンプトの構造監査（Claude Code、2026-09-24）

参照コミット: `46790cc`。作成: Claude Code（`/claude-api prompt-audit`）。
同日の GPT-6 監査（`docs/content-prompt-audit-2026-09-24.md`）は**事実の裏付け・QA ガード**を主に見ている。本書は**指示文そのものの書き方**（圧力語・矛盾・古い指示の残骸・ノルマ・例文の引きずり）を見る。重なる所は短くし、本書でしか出ない所見を優先した。

**この文書は提案だけ。** ファイルは変更していない。下の差分は Codex への spec の材料にする。

## 前提（Step 0）

- **範囲:** 次のファイルが範囲。
  - `lib/llm/prompts/` の 6 ファイル。
  - プロンプトを組み立てて呼び出すコード: `lib/llm/stages/generate-narrative.ts`、`lib/llm/openai.ts`、`lib/llm/models.ts`、`lib/llm/content-length.ts`。
  - 見出し文字列に依存するコード: `lib/llm/stages/qa.ts:567`、`lib/match-content/description.ts:32`、`lib/x/preview-thread.ts:25`。
  - 英語版のプロンプト（`generate-narrative.ts` の `buildEnglish*`）は対象外。
- **対象モデル:** OpenAI の `gpt-5.6-terra`（本文）と `gpt-5.6-luna`（抽出・QA・固有名詞照合）。いずれも `lib/llm/models.ts` で指定。GPT-6 は比較の候補。
  - 呼び出しは OpenAI Responses API で、Anthropic の SDK は使っていない。本書は Claude への移行を提案しない（プロバイダは OpenAI とする方針）。
- **確度の付け方:** 監査の手順書は Claude の文書を確度の根拠にしているが、今回のモデルは OpenAI なので、その根拠は使えない。代わりに次の基準にした。
  - **高:** 同じリポジトリ内で指示同士が食い違っていることを、コードで確かめられたもの。モデルの性質に関する主張ではない。
  - **中:** 最近の指示追従型モデル全般によく見られる傾向に基づくもの（例文の引きずり、ノルマによる水増しなど）。
  - **低:** 書き方の古さから推定しただけのもの。報告のみで、差分には入れない。

**影響が大きい 3 点:**

1. **字数の指示が 3 か所で食い違っている（F1・F2）。**
   - レビューのプロンプトは「全体で 2,000 字以上を必ず満たす」と 3 回書き、各セクションの字数目標も合計 2,000 字を超える。一方、QA の実際の下限は 1,200 字（`content-length.ts:26`）。
   - 経緯: `git blame` を見ると、この 2,000 字は QA 下限が 2,000 字だった時期に合わせた版（`76fe4873`、2026-06-12「align recap length targets with the 2000-char QA minimum」）。同じ 6/12 に Owner の判断で QA 下限だけ 1,200 字に下げられ、プロンプトはそのまま残った。
   - さらに、プロンプトの前に付け足される冒頭指示（`generate-narrative.ts:153-163`）が冒頭セクションを「250〜350 字」とし、プロンプト本体の「150〜250 字」（レビュー）・「200 字以内」（プレビュー）と食い違う。
   - Owner の言う「事実の羅列感」の直接の出どころは、この水増しの圧力。
2. **同じことについて逆の指示が出ている（F3〜F5）。** 「好調」を禁じる一方で、使うよう指示している箇所がある。キックの分母を禁じる一方で「ゴール 4/5」を勧めている。本文の引用（>）は 1 回必須なのに、字数不足を加筆するときの指示では禁止。モデルはどちらを守っても片方に違反する。
3. **読者が試合ページで既に見ている情報が、プロンプトに書かれていない（F14、`add`）。** 試合ページには得点経過の表（`components/match-events-section.tsx`）が載っている。それなのにプロンプトは「スコア推移を時系列で整理」を必須にしている。表と同じ内容を本文でなぞるのが、羅列感の構造的な原因。「読者は表を既に見ている」という文脈を 1 行足すことが、禁止表現を増やすより効く見込み。

## 検証の進め方（Step 7）

- **A/B 比較に組み込む。** 前回決めた「同じモデル（terra）・同じ入力で、現行 A と書き換え B を 4 試合 8 本」で行う。B 版は、本書の H1〜H14 と GPT-6 監査の P1（事実の裏付け側）を**別々のプロンプト版**にする。見た目の変更と安全側の変更の効果を分けて測るため。
- 見る指標は次の 5 つ:
  1. QA の作り直し率
  2. 裏付けと戦術の点数
  3. 表の内容をなぞった文の割合（得点イベントを時系列に書き起こした文を数える）
  4. 「得点力」で始まる冒頭の率
  5. 捏造ゲート・人名照合で落ちた件数
- 高確度の食い違い（F1〜F6）は、A/B を待たずに直してよい候補。どちらを守ってもどちらかに違反する状態なので、直さない理由がない。ただし F1・F2 は字数、F5 はガードに影響するので、Codex の spec に含めてテストで確かめる。
- この文書の段階では、有料の LLM 実行も、コード・データの変更もしていない。
