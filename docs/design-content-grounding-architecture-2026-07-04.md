# コンテンツ生成のグラウンディング・アーキテクチャ設計

作成: 2026-07-04（Nations Championship 開幕日インシデントの恒久対応）
ステータス: Owner レビュー待ち（承認後、フェーズ1を specs/ に切り出して Codex へ委譲）

---

## 0. TL;DR

- 今日の4回の対応はすべて「**入力空間**から危険データを隠す」か「**出力の正規表現**で症状を検出する」アプローチだった。試行4（入力ゼロでも学習済み知識から実在選手を捏造）が示した通り、入力遮断ではモデルのパラメトリック知識は消せない。正規表現は言い回しの無限のバリエーションに原理的に勝てない。
- 恒久解は軸足の移動: **出力空間での決定的なエンティティ照合**。生成された本文から人名を全部抽出し、入力データ由来の「許可済みエンティティ集合」と突合、1件でも不一致があれば機械的に reject/retry する。検出条件が「見出しキーワード＋ポジション語」ではなく「**人名である**」こと自体になるため、言い回しに依存しない。
- 抽出は `gpt-4o-mini` の専用軽量ステージで行う（1回 $0.001 未満、試合あたりコストへの影響は誤差）。判定はコード側の決定的ロジック。**LLM は分類器、判定はプログラム**という役割分担が肝。
- 今日作った `confirmed` シグナル・サニタイズ・QA ハードブロック配管（`isFactualGroundingHardBlock` → `resolveVerdict`）は無駄ではなく、**新ゲートがそのまま刺さる差し込み口**として全部活きる。捨てるものはない。
- 公開済みコンテンツの監査は必要かつ安価（全公開記事に同じ照合を回して数ドル）。恒久対応のデプロイ後に一括実行を推奨。

## 1. この問題のクラスは何か

### 1.1 分類

prompt injection ではない（敵対的入力が存在しない）。RAG のグラウンディング問題の一種だが、より正確には要約・データ→テキスト生成研究で言う **faithfulness（入力忠実性）の破れ**、その中でも **parametric knowledge leakage（パラメトリック知識の混入）** と呼ばれる現象。

- モデルは「入力にあること」と「事前学習で知っていること」を内部で区別していない。日本代表・イタリア代表は事前学習コーパスに大量に存在するため、入力が薄いほど学習済み知識が穴を埋めに来る。**今回のように著名な代表チーム同士の試合は、無名クラブの試合より捏造リスクが構造的に高い**。
- Garbisi / Marin / Labuschagne が「実在の著名選手」だったのは偶然ではなく、この現象の典型的な出方（もっともらしい実在エンティティを、未確認の文脈=今日の先発、に断定的に接続する）。
- 研究側の対応は FActScore / QAFactEval 系の「原子的事実に分解して入力と突合する」事後検証。フルの事実分解は高価だが、その**最も安価で歩留まりの良いサブセットが「固有エンティティ（人名）の存在照合」**であり、今回の事故クラスはちょうどそこに収まる。

### 1.2 既存パターンの適用可能性（このコスト帯で）

| パターン | 適用可能性 | 判定 |
|---|---|---|
| テキスト指示の強化（closed-book ペルソナ等） | 今日3回失敗した通り、確率を下げるだけで保証にならない | 補助のみ。単独では不採用 |
| constrained decoding（生成時にトークンを制約） | OpenAI API では任意の許可リストで自由文を制約する手段がない（logit_bias は人名に非現実的） | 不採用 |
| citation-forcing（全文に出典必須） | 記事の読み味を壊す。全事実への強制は過剰 | 不採用（sourced_facts では既に部分適用済み） |
| structured output ＋ 自己申告エンティティ列挙 | 追加コストゼロだが、捏造した同一モデルの自己申告は漏れ得る（申告漏れ＝すり抜け） | 単独では不十分。補助としては可 |
| **生成後の専用エンティティ照合パス（別モデル呼び出し）** | 抽出タスクは狭く客観的で `gpt-4o-mini` の得意領域。判定はコード側で決定的 | **採用（本設計の核）** |
| self-consistency（複数回生成して一致検証） | 生成コストが倍以上。この問題には過剰 | 不採用 |
| データ量に応じた構成の構造的分岐 | 既に `isDataSparse` として部分実装済み。単独では「自由文である限り」捏造を防げないことが今日証明された | 採用（第1層として維持）だが単独では不十分 |

### 1.3 核心の非対称性

今日の対応が全部もぐら叩きになった理由は一言で言える:

> **防ぎたい対象（学習済み知識）は入力空間に存在しないので、入力空間の操作では制御できない。一方、出てはいけないもの（許可リスト外の人名）は出力空間で完全に定義できる。**

だから検証は出力側でやる。入力側の対策（サニタイズ・プロンプト指示）は「捏造の発生確率を下げる」努力として残す価値はあるが、「捏造が公開されない」ことの保証は出力側ゲートだけが与えられる。

## 2. 解決アーキテクチャの選択肢とトレードオフ

### 案A: 構造化出力＋自己申告リスト照合

生成時に「本文で言及した人名を全て列挙せよ」フィールドを強制し、コードで許可リストと突合。

- 長所: 追加 API 呼び出しゼロ。実装が最小。
- 短所: **申告の網羅性を捏造した本人に依存する**。名前を書いたのに列挙しない漏れが原理的に防げない（今日の教訓「モデルのテキスト遵守を信用しない」に反する）。また現在の生成出力はプレーンな Markdown であり、構造化出力への変更は生成品質・文字数制御への影響が未知。
- 評価: 単独採用は不可。案Dの上に重ねる価値も薄い（Dが網羅するため）。

### 案B: データ量に応じたコンテンツ戦略の分岐（構造的制約）

確定ラインアップも試合イベントも無い試合では自由な物語生成をやめ、数値・順位・フォームだけの機械的な文章に切り替える。

- 長所: 捏造の「動機」を構造的に減らす。既に `isDataSparse` ＋データスパースモード指示として8割実装済み。
- 短所: **LLM が自由文を書く限り保証にならない**（今日の試行4はまさにデータスパース指示下で起きた）。完全にテンプレート化（LLM に人名を書く余地を与えない=穴埋め生成）すれば保証になるが、記事品質が大きく落ち、Tryline の価値提案（読み物としての解説）を毀損する。
- 評価: 第1層として維持する。ただし enforcement は別層に置く。

### 案C: プロンプトエンジニアリング強化

- 評価: 今日3回失敗。1行足すのは自由だが、設計上は**信頼ゼロの補助**として扱う。今後のインシデント対応で「プロンプトに禁止を書き足す」を再発防止策と呼ばないこと（このドキュメントの存在意義）。

### 案D: 生成後のエンティティ照合ゲート（推奨の核）

新しい専用ステージ。`gpt-4o-mini` に「本文」と「許可済みエンティティ集合」を渡し、**本文中の全人名を抽出し、各名前が許可リストのどれに対応するか（または対応しないか）**を構造化 JSON で返させる。コード側で「未対応の人名が1件でもあれば factual hard block」を決定的に判定。

- 長所:
  - 検出条件が「人名であること」自体なので、見出し・言い回し・セクション構成に依存しない。今日の試行1〜4の全パターンを1つのゲートで捕捉する。
  - **カタカナ問題を LLM 側で吸収できる**。本文は「アレッサンドロ・ガルビージ」、DB は「Alessandro Garbisi」。決定的な文字列照合では表記ゆれ（長音・中点・姓名順・姓のみ言及）で破綻するが、「このカタカナ名は許可リストのどのエントリに対応するか」は mini が確実にこなせる狭い照合タスク。**判定（不一致→reject）はコードが行う**ので、LLM の役割は分類に限定される。
  - 許可リストが空（データスパース試合）の場合、**いかなる人名も自動的に違反**になる。今日の事故クラスは定義上すり抜け不能。
  - 監督名・「主将」などへの拡張余地がある。
- 短所:
  - 生成1回あたり mini 呼び出しが1回増える（コスト試算は §4.6）。
  - 抽出漏れ（mini が人名を見落とす）の残存リスク。ただし「日本語文中の人名抽出」は NER の最も基本的なタスクで、見落としの範囲は現行の正規表現より圧倒的に狭い。既存の正規表現ガードを**ゼロコストの先行フィルタ**として残すことで二重化する。
- 評価: **採用**。コスト・堅牢性・実装複雑度のバランスが最良。

### 案E（追加検討）: 主軸にしないもの

- **事後リダクション（違反文を機械削除して公開）**: reject/retry より安いが、文脈が壊れた記事が出るリスク。品質はブランドの生命線なので不採用。retry 予算を使い切ったら draft 落ち（現行挙動）が正しい。
- **生成の2パス化（骨子→本文）**: 捏造抑制効果が不確実な割に生成コスト増。不採用。
- **回帰カナリアセット**: データスパース試合数件＋今日の実インシデント本文を固定の評価セットにし、プロンプト変更時に dry-run で捏造検出率を測る。これは案ではなく**運用プラクティス**として採用推奨（再生成インシデントの教訓「試し焼き必須」と同型）。

### 推奨構成: 三層防御

```
第1層（構造・入力側）  : データスパース分岐 ＋ 未確定lineupサニタイズ
                        → 捏造の「発生確率」を下げる（既存資産、保証はしない）
第2層（決定的先行検査）: containsUngroundedPlayerReference 等の正規表現
                        → ゼロコストで明白なケースを即検出（既存資産）
第3層（出力側ゲート）  : エンティティ照合ステージ（新規、案D）
                        → 「許可リスト外の人名が公開されない」ことの保証
```

第3層だけが「保証」を与える。第1・2層は第3層の retry 回数（＝コストと draft 落ち率）を減らすための存在、と役割を再定義する。

## 3. 今日の4回の対応は無駄だったか

無駄ではない。**全部が新アーキテクチャの前提部品**になる。

| 今日の成果物 | 新アーキテクチャでの役割 | 処遇 |
|---|---|---|
| `confirmed` シグナル（試行2） | **許可リスト構築の必須入力**。confirmed=false のフォールバック選手を許可リストに入れたら、ゲートが「歴代選手プール全員OK」になり無意味化する。今日これを直していなければ第3層は成立しなかった | 維持（土台） |
| `sanitizeUnconfirmedProjectedLineups`（試行3） | 第1層。捏造の発生確率を下げ retry 回数を節約。generate-recap 側の同型修正も同様 | 維持 |
| `containsUngroundedPlayerReference`（試行1） | 第2層。API 呼び出し前のゼロコスト先行フィルタ。**「これが検出の主役」という位置づけだけを剥奪**する | 維持（役割格下げ） |
| `isFactualGroundingHardBlock` / `resolveVerdict` の hard block 配管 | 第3層の違反が流れ込む**既存の enforcement 経路**。新ゲートは新しい issue 定数を1本追加してここに合流するだけで retry/reject/draft 落ちが全部動く | 維持（差し込み口） |
| `hasLineups` フラグ | データスパース判定の入力として継続 | 維持 |

つまり今日1日は「enforcement の配管工事と、許可リストを正しく定義するためのデータ整備」だったと再解釈できる。欠けていたのは検出器の頑健性だけで、それが第3層。

## 4. 推奨案の具体設計（フェーズ1、Codex 委譲可能な粒度）

### 4.1 新規: 許可エンティティ集合の構築

**ファイル**: `lib/content/allowed-entities.ts`（新規。`fabrication-guard.ts` と同じ層）

```
buildAllowedPersonEntities(assembled: AssembledContentInput): AllowedEntity[]
```

- 収集元（**これが唯一の真実**）:
  - `projected_lineups.home / away` — ただし confirmed 側のみ（`lib/llm/lineups.ts` の `hasConfirmedEntry` 相当の判定を再利用）。サニタイズ済み assembled を渡せば自然に満たされるが、関数側でも confirmed 判定を防御的に適用する
  - `match_events[].player_name`
  - `sourced_facts` — 事実文中の人名。フェーズ1では原文テキスト全体を照合用コンテキストとして渡す（人名の事前抽出はしない。§4.2 の照合プロンプトが原文参照で判断できる）
- 各エントリは `{ name, source: "lineup" | "event" }` のような形（sourced_facts は原文渡し）。
- **集合が空になり得る**ことが仕様（データスパース試合）。空のときゲートは「人名が1つでもあれば違反」として機能する。

### 4.2 新規: エンティティ照合ステージ

**ファイル**: `lib/llm/stages/verify-entities.ts`＋`lib/llm/prompts/verify-entities.ts`（新規）

```
verifyNarrativeEntities(options: {
  narrative: string;
  allowedEntities: AllowedEntity[];
  sourcedFacts: SourcedFactInput[];
}): Promise<EntityVerificationResult>
```

- モデル: `MODELS.FAST`（gpt-4o-mini）、`temperature: 0`、`jsonMode: true`（既存 `createTextResponse` をそのまま使用）。
- プロンプトの仕事は**抽出と対応付けのみ**。「良い記事か」を聞かない:
  1. 本文中の人物への言及（フルネーム・姓のみ・カタカナ表記すべて）を全件列挙
  2. 各言及について、許可リストのどのエントリに対応するかを返す。対応しなければ `null`
  3. カタカナ⇔英語の表記ゆれは同一人物として対応付けてよい、と明示
- 出力スキーマ（例）:
  ```json
  { "mentions": [ { "surface": "本文中の表記", "matched_entity": "許可リスト内の名前 or null" } ] }
  ```
- **判定はコード側**: `matched_entity: null` が1件でもあれば違反。違反 surface のリストを返す。
- チーム名は今フェーズでは対象外（許可リストに常に入るので実害が薄く、誤検知を避けるため人名に限定）。

### 4.3 変更: fabrication-guard / QA への合流

**ファイル**: `lib/content/fabrication-guard.ts`
- 新 issue 定数を追加: `UNGROUNDED_ENTITY_ISSUE = "入力データに存在しない人名を含む"`（既存2定数と並置）。

**ファイル**: `lib/llm/stages/qa.ts`
- `isFactualGroundingHardBlock` の判定対象に `UNGROUNDED_ENTITY_ISSUE` を追加（1行）。
- `applyDeterministicQaGuards` は同期関数なのでここに API 呼び出しは入れない。照合はパイプライン側で実行し、結果を `evaluateNarrativeQuality` の options 経由（例: `entityViolations: string[]`）で渡し、ガード内で issue 追加＋`factual_grounding: 1` に落とす（既存2ガードと同じ形）。

**ファイル**: `lib/llm/pipeline.ts`
- 生成ループ内で、ナラティブ生成後に `verifyNarrativeEntities` と QA 用の情報収集を**並行実行**（`Promise.all`）してレイテンシ増をほぼゼロにする（QA プロンプトに違反リストを渡す都合で直列が必要なら、mini 2連の直列でも数秒であり許容）。
- **リビジョン経路（revision QA 側）にも同じ照合を通すこと**。ここを忘れると修正パスがすり抜け穴になる（試行3の教訓: 経路は必ず全部塞ぐ）。
- retry 時のフィードバック: 違反 surface を再生成プロンプトに明示注入する。例:
  > 前回の出力には入力データに存在しない人名（アレッサンドロ・ガルビージ、レオナルド・マリン）が含まれていた。これらを含め、入力データにない人名は一切書かないこと。
  盲目的な再生成より retry 成功率が上がり、reject/draft 落ちを減らす。

### 4.4 プロンプト側の軽微な追随（信頼ゼロの補助）

- `lib/llm/prompts/shared-prompt-blocks.ts` の禁止ブロックに「あなたが事前知識として知っている選手情報（代表歴・所属・ポジション・主将などの役割）は、この試合の入力に存在しない限り使用禁止」を1項追加。効果は保証しないが retry 回数の節約にはなる。

### 4.5 受け入れ条件（specs 化する際の骨子）

1. 確定ラインアップ・イベント・sourced_facts がすべて空の試合で生成した preview に人名が1つでも含まれる場合、verdict が publish にならない（unit: 照合結果→verdict の決定的テスト、およびモック化した照合ステージでのパイプラインテスト）
2. 許可リスト内の選手（カタカナ表記）は違反にならない（表記ゆれケースをフィクスチャ化: 中点有無・長音・姓のみ言及）
3. リビジョン経路でも照合が実行される
4. 照合ステージの失敗（API エラー等）は **fail-closed**（照合できなければ publish しない。silent fallback で素通しにしない — 試行2の教訓: フォールバックは安全側に倒す）
5. 今日の実インシデント4件の本文をフィクスチャとして固定し、全件で違反が検出されること（回帰カナリア）
6. preview / recap の両パイプラインに適用されること

### 4.6 コスト試算

- 照合1回: 入力 ≈ 本文2,000字＋許可リスト ≈ 3–4K tokens、出力 ≈ 100–300 tokens
- gpt-4o-mini（$0.15/1M in, $0.60/1M out）→ **1回あたり $0.001 未満**
- retry 込みで1試合最大3回でも $0.002 程度。gpt-4o のナラティブ生成（1試合数セント）に対して誤差。コスト制約内。

## 5. フェーズ分け

### フェーズ1（即時）: エンティティ照合ゲート
§4 の全体。1 spec・1 PR 規模。これだけで今日の事故クラス（人名捏造）は全経路で公開不能になる。

### フェーズ2（ゲート稼働後）: 公開済みコンテンツの一括監査
- **監査すべきか → 推奨: する**。判断材料:
  - 同じ生成コード・同じプロンプトが全大会で稼働してきた以上、データスパース試合の公開済み preview に同種の捏造が存在する事前確率は高い（既知の未解決事項として「旧 preview 約20件＋sourced facts 0件時の補完捏造」も残っている）
  - 監査コストは1記事 $0.001 未満。公開済み全件でも数ドル。実装は照合ステージを再利用したバッチスクリプト1本（`tools/audit-entity-grounding.ts`、既存の `node --env-file=.env.production.local tools/run-ts.cjs` 実行の型）
  - 放置コストは「間違いを書かないこと」を差別化価値とするプロダクトにとって非対称に大きい（UI から "AI" 文言を外した判断とも整合: 敵は AI ではなく間違い）
- 注意点: 生成時点のデータと現在のデータは違う。生成後にラインアップが確定した試合では、当時捏造だった名前が現在の許可リストに載り得る（見逃し方向）。監査は「現在のデータで照合→違反はレビューして再生成 or 非公開」の運用でよく、厳密な生成時点再現は不要。
- 優先順位: preview（データが薄い状態で生成されがち）→ recap のイベント欠落大会（URC・SRP は既知のイベントギャップがあり相対リスク高）。

### フェーズ3（任意・後日）: 対象の拡張
- 人名以外へ: 監督名、役割断定（「主将」「ベテラン」）。**許可リスト内の実在選手に誤った役割を付ける捏造はフェーズ1では検出外**。ただしデータスパース試合では人名ごと弾かれるため、残存リスクは「確定ラインアップあり試合での役割誤り」に限定され、重大度は一段低い（MOM 推論問題と同系統として扱う）
- 回帰カナリアセットの CI 組み込み（プロンプト変更 PR で dry-run 生成＋照合を自動実行）

## 6. 決定事項として記録すべきこと（docs/decisions.md 向け）

1. 捏造対策の enforcement は出力空間のエンティティ照合を主とし、プロンプト指示・入力サニタイズは確率低減の補助と位置づける（テキスト指示の追加を単独で再発防止策と呼ばない）
2. LLM の役割は抽出・分類まで。publish/reject の判定は常に決定的コード（既存の `resolveVerdict` 主義の拡張）
3. ガード系ステージのフォールバックは fail-closed（照合不能なら publish しない）
