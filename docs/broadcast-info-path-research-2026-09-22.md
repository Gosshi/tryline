# 11月日本代表戦の放送情報：掲載経路の調査結果

調査日: 2026-09-22（JST）  
依頼: [放送情報をサイトに載せる経路の確定依頼](chatgpt-prompts/gpt6-broadcast-info-path-2026-09-22.md)  
用途: Owner の判断と Claude Code の仕様化に渡す調査報告。仕様書ではない。本番書き込み・実装・PR作成は行っていない。

## 結論

**推奨経路は「WOWOWに公開番組情報の商用案内利用を一度確認 → 公開一次情報の必要な事実だけを既存CLIでOwnerが登録 → 既存の試合ページに表示」の一本とする。** JRFUの空欄が埋まるまで待つことも、新しいWOWOWスクレイパーの開発も、掲載の前提にしない。

配信先の情報は存在する。WOWOWオンデマンドの3試合の個別URLと、ライブ配信開始予定時刻まで検索インデックス上の公式ページ情報で確認できた。一方、今回の取得環境では個別ページの直接表示が推奨ブラウザ案内になり、通常ブラウザによる確認も許可されなかった。**現在の画面での最終確認と本番登録後の表示確認は未完了**である。

Ownerは最終回答で「WOWOWアカウントを持っている」と訂正した。これを前提とする。公開情報の少数の事実を案内することは著作権上のリスクが低いと評価するが、会員規約の商用利用制限の適用は別問題である。**手動で読む、ログアウトする、AIに代読させる、というだけで規約上の問題が消えるとは判断しない。** 許諾または当該利用が制限対象外である旨の回答を得るまでは、この経路での本番掲載を保留する。

したがって、技術経路と掲載候補は具体化できたが、「障害がすべて解消し、今日確実に掲載できる」とは結論できない。残る確認と担当をC-2に限定して明示する。これは放送情報の掲載一般に許諾が必須という法的断定ではなく、今回求められた確実性と運用制約に合わせた推奨である。

### A-3. JRFUの試合ページにいつ追加されるか

**初掲載時刻を示す履歴は確認できず、「通常何日前」とは結論できない。** ニュース発表日と、`/match/<id>` の `div.broadcast` 更新日は別である。現在のページや検索クロール日から過去の初掲載日を逆算しない。

リポジトリ内には、[2026-08-14の実測を記した仕様書](../specs/fix-broadcast-service-mapping.md)で8/15豪州戦のWOWOW案内が既に存在したという記録がある。また[7/15の手動登録仕様書](../specs/feat-match-broadcasts.md)に7/18フランス戦の複数サービスが記載されている。これは「遅くとも前日／3日前には確認されていた」という観測であり、前日／3日前に追加された証拠ではない。

過去の厳密な追加日を確定するには、OwnerまたはClaude Codeが、保存済みページ・日次取得ログなどの「空欄だった最終観測」と「非空だった最初の観測」を比較する必要がある。本調査ではそうした履歴を得ていない。今回の掲載はこの不明点に依存させない。

## B. 法的判断と実務上の扱い

以下は公開資料に基づく一般的な日本法の整理であり、個別契約についての弁護士による法律意見ではない。

### B-1. 会員規約は非会員の自動取得を拘束するか

一般論として、サイトに規約へのリンクがあるだけで、あらゆる第三者に契約上の義務が当然に成立するわけではない。申込み・承諾や規約の組入れを検討する。定型約款では、定型取引の合意に加え、規約を契約内容にする合意または事前表示などが問題となる。クリック同意がないから必ず無効、無料サービスだから契約はない、という判断も誤り。[民法522条・548条の2](https://laws.e-gov.go.jp/law/129AC0000000089?occasion_date=20250401)、[経済産業省・オンライン契約の解釈整理](https://www.meti.go.jp/policy/it_policy/ec/20250212003-1.pdf)。

[WOWOW WEB会員規約](https://www.wowow.co.jp/guidance/webmem/)は登録・アカウント保有者を定義し、14条1項の義務主体もアカウント保有者としている。一方、WEBサービスの定義は広く、17条2項も私的利用・再掲載を制限する。したがって:

- 非会員が同意なく公開ページを読むという仮定では、この会員規約だけを根拠に当然に拘束されるとは考えにくい。ただし別規約・画面上の合意等は別途確認が必要。
- 実際のOwnerは会員である。会員というだけで全公開ページの閲覧が一律禁止になるとは断定できないが、商用メディアへの利用が14条・17条の対象外だとも確定できない。ログアウトしても既に成立した契約関係が消えるわけではない。
- `robots.txt` の許可は契約・著作権の許諾ではない。依頼書の「非会員規約は存在しない」という不在証明も、全導線を監査した結論としては採用しない。

本経路では自動取得を採用しない。それでも会員の商用利用という論点は残るので、C-1の限定した確認で解消する。

### B-2. 放送予定は自由に再掲載できるか

チャンネル名・日時・カードという個々の事実そのものには、通常、思想感情を創作的に表現した著作物としての保護は及ばない。事実の伝達にすぎない雑報・時事報道についても著作権法10条2項の整理がある。ただし「日程表だから丸ごと自由」ではない。[文化庁・令和8年度著作権テキスト](https://www.bunka.go.jp/seisaku/chosakuken/seidokaisetsu/pdf/94383901_01.pdf)、[著作権法](https://laws.e-gov.go.jp/law/345AC0000000048)。

素材の選択・配列に創作性があれば編集著作物（12条）、情報の選択・体系的構成に創作性があればデータベースの著作物（12条の2）の問題になる。番組説明文、写真、ロゴ、表のデザインも事実そのものとは区別する。**自分の試合一覧に必要な数項目を独自形式で記載することと、他社の番組表・データベースの表現や構成を再利用することは同じではない。** 同じ文化庁資料を参照。

また、著作権が及ばない事実でも、有効に成立した利用契約による制限までなくなるわけではない。今回の落としどころは、事実のみ・少数試合・独自表示・公式リンク・確認記録とし、会員契約の扱いを別に確認すること。

### B-3. Trylineへの掲載自体のリスク

| 論点 | 本件での評価 | 実務上の対応 |
|---|---|---|
| 少数の事実を独自表示する著作権リスク | 低いと評価。ただしゼロの保証ではない | 説明文・写真・ロゴ・表組みはコピーしない |
| 会員規約違反 | 適用範囲が未確定。掲載一般の著作権問題より本件では優先して確認すべき | WOWOWに具体的な利用態様を示し、回答を保存 |
| 大量取得・アクセス負荷・取得制限回避 | 本経路では行わない | 新規クローラー、裏API、会員限定ページの取得を作らない |
| 日時やテレビ／配信の誤案内 | 現実的な運用リスク | アクセス時刻・配信開始・キックオフを分離し、登録前と試合前に再確認 |

著作権以外にも、他者の権利・法律上保護される利益の侵害について不法行為責任が問題になり得るため、「非著作物ならどんな取り方でもよい」とはしない。[民法709条](https://laws.e-gov.go.jp/law/129AC0000000089?occasion_date=20250401)。訴訟確率や損害額を推定できるデータはない。

実務の掲載例として、[Sporting Newsの2025年日本対アイルランド案内](https://www.sportingnews.com/jp/rugby/news/2025-11-2-rugby-japan-vs-south-africa-schedule-tv-ott-jpn/b21e97a5118aae9353a69337)はWOWOWのテレビ・配信先と21:00開始を記載し、キックオフ21:40と区別している。[Goalの同試合案内](https://www.goal.com/jp/%E3%83%AA%E3%82%B9%E3%83%88/when-japan-ireland-rugby-broadcast-20251108/blt09c14d8b769d0226)も視聴先を紹介する。**こうした掲載は実在するが、両媒体の許諾・提携契約の有無は未確認**で、Trylineへの包括的な許可を証明しない。

依頼書のA型／B型は社内の取得先採否基準であり、法的な適法・違法の分類ではない。特に17条2項は知的財産権という見出しの中にあっても、文言はサービス利用を制限している。見出しだけで「B型だから商用転載可」と処理しない。

## C. 推奨経路

### C-1. 一本の掲載・継続運用経路

1. **OwnerがWOWOWへ一度だけ、利用態様を限定して書面確認する。** 公開番組情報の少数の事実を有料プランのある媒体で紹介することについて、会員規約上の扱いを尋ねる。アカウントを持っていることを隠さない。自動取得や番組自体の再配信の許可を求める話には広げない。
2. 許諾または対象外との回答を得た後、OwnerがA-1の3個別ページを通常の利用環境で開き、カード・配信予定・URLを確認する。TVチャンネルが確認できなければ配信1行だけでよい。
3. 1試合1JSONを既存の `tools/upsert-match-broadcasts.ts` に渡し、**Owner自身が**カード・日時を確認して登録する。Claude CodeもCodexも本番DBへの書き込みは代行しない。
4. `match_broadcasts` → 公開読み取りクエリ → `components/match-header.tsx` の既存経路で「視聴方法／配信／WOWOWオンデマンド」を表示する。登録後はページでカード・リンク・確認日を検収する。
5. 以後はJRFUの日次取り込みを補助として維持し、公式発表を確認したのに未掲載の場合だけ同じCLIで補完する。欠損・実変更に絞った通知へ改修する（D）。WOWOWの常時スクレイピングは追加しない。

問い合わせの入口は[WOWOW公式の問い合わせ案内](https://corporate.wowow.co.jp/contact/)の番組・サービス窓口。公開情報の媒体掲載について担当部署の確認が必要なら転送を依頼する。[カスタマーセンターの連絡方法](https://support.wowow.co.jp/answer/61b9867466cf3b001e9d0916/)も確認できた。問い合わせは本調査では送信していない。

送信文案:

> WOWOW WEBアカウントを保有しています。ラグビー情報サイトTryline（https://www.trylinerugby.com/、有料プランあり）で、日本代表戦を年10〜12試合程度紹介しています。ログイン不要の公開番組案内を人が確認し、対象試合のカード名、放送・配信サービス名、開始予定日時、および公式番組ページへのリンクだけを、自社の試合ページに独自形式で記載したいと考えています。番組映像・写真・ロゴ・番組説明文・番組表全体は転載せず、自動取得もしません。この利用はWEB会員規約14条・17条の制限対象となりますか。対象となる場合、この限定した案内利用を認めていただけますか。まず2026年11月のウェールズ・イングランド・スコットランド対日本を対象とします。継続利用の条件と併せてご回答をお願いします。

無回答は許可と扱わない。返答がない場合は7営業日後に一度状況確認し、それでも解消しなければ本経路は保留する。これは運用上の提案期限であり、WOWOWの回答保証ではない。返答や許諾料・条件によっては年次運用の成立も再評価が必要。Ownerに別の取得手段を次々と選ばせる運用にはしない。

#### 既存CLIで扱える入力

3試合共通のサービス名は、現行自動取り込みの正規形と同じ **`WOWOWオンデマンド`**、`kind` は **`streaming`** とする。スペース入り表記を新たに混在させない。`url` と `source_url` は対応する公式個別ページ。以下は承認・ライブ照合前には実行しない入力例であり、投入済みデータではない。

```json
{
  "match_id": "8461c743-7498-4ecd-b359-b3665f619383",
  "source_url": "https://wod.wowow.co.jp/content/207199",
  "broadcasts": [
    {
      "kind": "streaming",
      "service_name": "WOWOWオンデマンド",
      "url": "https://wod.wowow.co.jp/content/207199"
    }
  ]
}
```

| カード | Trylineの公開大会ハブから確認したリンク先ID | WOWOW個別URLの末尾 |
|---|---|---|
| Wales v Japan | `8461c743-7498-4ecd-b359-b3665f619383` | `/content/207199` |
| England v Japan | `76171330-c00b-4daa-8332-f9181976aa92` | `/content/207205` |
| Scotland v Japan | `6e7e230c-a7d9-43e7-b27f-6c6b8ecaa150` | `/content/207209` |

IDは[Tryline公開大会ハブ](https://www.trylinerugby.com/c/nations-championship/2026)のカードリンクに基づく。試合詳細の直接取得は本調査環境では失敗し、通常ブラウザの利用も許可されなかった。最新DBに対する独立照合は未実施なので、CLIが登録直前に表示するカードと日時をOwnerが照合する。ハブの公開読み取り結果と本番DB照合を同一視しない。

実行は[既存仕様書のCLI手順](../specs/feat-match-broadcasts.md)に従う。必要な環境設定・権限はOwner自身が確認し、キーや環境ファイルの内容をチャットに渡さない。

重要な挙動:

- CLIは `(match_id, service_name)` でupsertする。同じ正規名の再実行で行を増やさないが、**別表記は別行**になる。既存行は登録前に確認する。
- `verified_at` と `display_order` はCLIが設定する。`source_url` は入力全体で共通のため、後から別ソースのTV行を加える際は、それを裏付けるソースの入力に分ける。
- CLIは入力にない既存行を削除しない。JRFU側も追加・更新中心であり、サービス終了や誤登録の自動除去は保証されない。訂正・削除が必要ならOwnerが対象行を確認して扱う。
- CLIにはURLの到達性・カード一致・サービス名正規化を全て検証する機能はない。空でない文字列の検証を過信しない。
- **現行テーブル／UIには放送・配信開始時刻の専用欄がない。** 今回はサービス名と公式リンクを掲載する。開始時刻を`service_name`へ埋めたり、キックオフを書き換えたりしない。開始時刻はリンク先で確認できる。Tryline上にも開始時刻を構造化表示するなら別仕様が必要で、本掲載の前提にはしない。
- 試合詳細と大会ハブは `revalidate = 3600`。CLIに再検証を呼ぶ処理はない。即時反映や「必ず1時間以内」は保証せず、1時間経過後のアクセスで再生成を促し、その後再表示して検収する。更新されなければOwnerが通常の障害調査として扱い、再投入やデプロイを闇雲に繰り返さない。

## D. 現行実装と通知

### D-1. 500の意味を直す

依頼書の原因説明には次の修正が必要。

1. 14日窓は `matchesStillMissing` の検査範囲。`linked` の元になる取得・照合対象は、現在時刻以降、一覧の年の年末までのscheduled試合である。**日本戦が14日窓にないだけでは500は確定しない。** 11月の放送情報がJRFUにあれば9月にも`linked`を作れる。
2. `linked`は新規追加件数ではない。既存と同じ行をupsertする場合も毎日追加される。1行あれば他の欠損を残して200になるため、「緑だから全対象が埋まった」も誤り。
3. [JRFUの2026年日程](https://www.rugby-japan.jp/schedule/)には9/12準決勝と9/19決勝がある。「9/12にPNC終了で日本戦が14日窓から消えた」という説明は日程と矛盾する。
4. 日次500の10日分やクラブ33試合の数値は依頼書の実測として受領したが、本調査で本番ログ・DBを再計数したものではない。9/19試合のDB欠落、未紐付けページ、取得失敗のどれが各日の原因だったかは、その日の安全に共有できる集計結果をOwnerが確認する必要がある。
5. 個別JRFUページの処理失敗は現在`console.error`だけで結果に残らない。欠損判定を単に全部200へ変更すると、実際の取得失敗をさらに見逃す。

推奨するステータスと通知:

| 状態 | HTTP | 通知 |
|---|---|---|
| 取得・解析・DB書き込み成功、変更なし | 200 | 原則通知なし |
| 日本代表の放送欄が正常に空、または14日以内の日本代表のDB放送行が0件 | 200 | 日本代表の未確認事項として1日1回まで集約。HTTP障害にしない |
| 日本代表の放送行が新規追加／サービス・kind・URLが実変更 | 200 | 対象試合と変更内容・確認用試合URLを通知 |
| 未知サービス／0件または複数件で紐付け不可 | 200 | 要確認として可視化し、推測で書かない |
| 取得失敗、必須構造の解析失敗、DB失敗、通知送信失敗 | 500 | 技術障害としてworkflow／運用通知で検知。部分成功でも隠さない |

取得対象の年末までという範囲は維持し、**欠損監視だけ** `home.slug === "japan" || away.slug === "japan"` かつ14日以内に絞る。日本代表の対象が0件なら、クラブが何試合空でも欠損警告しない。正常な「放送未発表」と構造破損は区別する。JRFU一覧で年が読めない・期待構造がない等は正常0件にしない。

### D-2. JRFUの更新に気づく最小の仕組み

**新規ジョブは不要。既存の毎日12:15 JSTの取得結果を、登録前の既存放送行と比較する。** スケジュール時刻は実行予定であり、GitHub Actionsの遅延や取得失敗を含めた検知時刻保証ではない。

- 比較対象は試合IDと正規化サービス名に対する`kind`・`url`。`verified_at`だけの更新は変化と数えない。
- 初めて視聴先が入った試合、追加されたサービス、リンク・kind変更を通知する。同じ候補の毎日upsertを毎日「新規」と通知しない。
- 手動登録済みと同じ情報がJRFUに載っただけなら、視聴可能情報の新規追加としては通知しなくてよい。
- JRFU側から案内が消えた、以前のサービスと矛盾した場合は自動削除せず、Ownerの再確認対象とする。空欄は提供終了の証拠ではない。
- 初回はJRFU以外のソースも含む既存DB行を基準にするので、全件を新着扱いする通知は避けられる。正常な無変化の通知抑制は、新しい監視サービスや永続ハッシュ表なしで実現できる。
- 手動登録後も、欠損0件だけでは情報が最新とは限らない。C-1の試合前確認は残す。

改訂仕様の受け入れテストとして最低限必要なもの:

1. クラブ33試合のみ欠損でも200、日本代表の欠損警告0件。
2. 日本代表が14日以内で未発表なら200＋当該試合の要確認通知。
3. 14日より先の日本代表への新規放送追加も取り込まれ、通知される。
4. 2回目の同一取り込みは重複行・新規通知を増やさない。
5. URL／kind変更を通知し、`verified_at`更新だけでは通知しない。
6. 一部成功していても別ページの取得・解析失敗を消さない。DB・通知失敗も500。
7. 未知サービスと候補複数は書き込まれず、要確認に残る。
8. 手動投入済みの正規名とJRFU表記ゆれで重複を作らない。手動行があるだけで誤った「新規登録」通知を出さない。
9. 日付当日／翌日の照合、対象外日付の拒否、日本代表以外の誤結合防止を維持する。
