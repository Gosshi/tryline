タスク 2: LLMプロンプト・モデル評価

モデル選択（models.ts）

✓ 良い点
  • FAST（gpt-4o-mini）= extract/QA、NARRATIVE（gpt-4o）= preview/recap という分割は適切でコスト最適
  • models.ts で一元管理されているのでアップグレード時の変更箇所が1ヶ所
✗ 課題
  • 2026年5月時点では gpt-4o より gpt-4.1 の方がナラティブ品質が高い可能性がある（実験未実施）

パイプライン設計（pipeline.ts）

✓ 良い点
  • assemble → extract → generate → qa の4ステージ分離が明確
  • pipeline_runs テーブルへの詳細ログとコストアラート機能あり
  • temperature を変えたリトライでナラティブの多様性を確保

🔴 重大な欠陥（2件）

  • 欠陥1（課題#1）: buildQaContentPrompt(contentType, narrative, language) に assembled データが渡されていない。factual_grounding がナラティブ単体の自己評価になっており、ハルシネーションを見逃すリスクがある。winnerCheckBlock も同様に「home_score/away_score を確認すること」と指示しながら実際のスコアが含まれていない。
  • 欠陥2（課題#2）: pipeline.ts:258 の content_md_ja: finalNarrative は language が "en" の場合も同じカラムに保存している。英語コンテンツが日本語カラムに入り、将来の言語別クエリで混乱を招く。

extract-tactical-points.ts（extract@2.0.0）

✓ 良い点
  • JSON スキーマが明確、禁止事項が具体的（数値根拠なし禁止・強調記号禁止等）
  • 戦術次元の例示が豊富で方向性がわかりやすい
✗ 課題
  • match_impact: "high | medium | low" の判断基準が未定義。LLMが恣意的に全部 high にするリスクがある
  • 戦術ポイントが常に3つ固定。データ豊富な試合は4つ、乏しい場合は2つが適切な場合がある

generate-preview.ts / generate-recap.ts（preview@3.0.0 / recap@3.0.0）

✓ 良い点
  • ペルソナ（20年取材ジャーナリスト）が適切
  • 「セクション0：この試合の核心」の必須出力は差別化コンテンツとして機能する
  • 禁止表現リストが充実（「好調」「重要な一戦」「鍵となります」等）
  • データスパースモード対応、プレーオフフェーズ別指示、リーグワンの日本語表記分岐は良い設計
