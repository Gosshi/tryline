## 変えてはいけないもの

**エンドポイントの呼び方を1文字も変えないでください。**

```
POST /api/cron/fetch-sourced-facts?match_id=<id>&content_type=<preview|recap>&force=true
  ↓（成功したときだけ）
POST /api/cron/generate-content   body: {"contentType":"...","matchIds":["<id>"],"language":"ja"}
```

**この順序は「事実を集め直してから記事を作る」という依存そのものです。** 逆にすると入力した事実が反映されません。`fetch-sourced-facts` が失敗した試合で `generate-content` を呼ばない現行の挙動も維持してください。

あわせて次も現行のままにしてください。

- **スケジュール（cron 式）**
- **対象試合の決め方**（カレンダー API の呼び方・日付範囲・`status` フィルタ）
- `workflow_dispatch` の `from` / `to`
- **サマリ行の文言**（`... summary: targets=N success=N failure=N`）
- **`WARN: ... match_id=...` の形式**（どの試合が失敗したかをログから特定するため）

## 実装の方針

### 失敗の可視化

**`failure` が1件以上ならステップを失敗させてください。**

**ただし対象0件は成功で終わってください。** 火曜のレビュー再生成は「手動入力が無ければ0件」が正常です。

### 並列化

**GitHub Actions の matrix で分割してください。**

```
ジョブ1: 対象試合を解決 → チャンクに分けて JSON で出力
ジョブ2: matrix でチャンクごとに並列実行（既存のループをそのまま使う）
ジョブ3: 集計し、失敗があれば失敗させる
```

**チャンクの試合数と `max-parallel` は定数として YAML に書いてください。** 推奨はチャンク5・並列3です。

**並列度を上げすぎないでください。** 同時に走る `generate-content` が増えると OpenAI のレート制限に当たります。

### 上限のガード

**1回あたりの最大試合数を定数で定義し、超えたら先頭だけ処理してログに残してください。推奨40。**

**日付範囲の指定を誤ったときに残高を焼き切らないためです。** 2026-09-05 に実際にクレジットが尽きています。
