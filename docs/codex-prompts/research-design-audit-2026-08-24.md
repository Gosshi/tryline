## 監査で答えてほしい問い

以下 6 軸。各軸で「所見」ではなく**数えられた事実**を出すこと。

### A. `design.md` 適合と視覚的差別化

- `design.md` の Do's and Don'ts / Shapes / Elevation & Depth に対する違反箇所を列挙する
- ページごとに支配的なコンテナ表現（背景・ボーダー・角丸・影）を列挙し、**出現回数を数える**
- 同一の class 組み合わせが複数ページで使い回されている箇所はどこか
- bento 刷新のスコープ外だったページに、旧来の均一カードパターンが残っていないか
- ページを開いた瞬間に「どのページか」が視覚的に判別できる手がかりが各ページにあるか

### B. 情報階層

各ページの見出し・本文のサイズとウェイトを実際に拾い、**スケールの段数**を出す。`design.md` の Typography 節で定義された段数と一致しているかを照合する。

- 主役となる要素が定まっているか、それとも全要素が同じ強さで並んでいるか
- `text-sm` / `text-base` ばかりでコントラストが出ていないページはどれか

### C. デザイントークンの一貫性

`app/globals.css` に定義されたカスタムプロパティ / Tailwind トークンを列挙し、`design.md` の Colors 節と突き合わせたうえで**逸脱**を探す。

- ハードコードされた色（`#rrggbb`、`rgb()`、Tailwind の生パレット `gray-200` 等）が何箇所あり、どのファイルか
- 角丸の値が何種類使われているか（`rounded-lg` / `xl` / `2xl` / `full` の分布）。`design.md` の Shapes 節が許容する種類数に収まっているか
- 余白スケールが体系的か、場当たり的か

### D. インタラクション状態

`hover:` / `focus-visible:` / `active:` / `disabled:` の網羅率を、クリック可能要素の総数に対して出す。

- 押下フィードバック（`active:`）は 9 箇所ある。**それはどの要素で、逆にどのクリック可能要素に無いのか**
- フォーカスリングがキーボード操作で確実に見えるか（`outline-none` を打ち消し忘れている箇所がないか）
- `design.md` の Accessibility 節の要求を満たしているか

### E. 未刷新領域の特定 ★最優先

**この軸が今回の本命。** 過去 3 回の刷新はいずれもホーム / カレンダー / 料金 / 試合詳細が中心で、以下は正面からデザインされたことがない可能性が高い。

- `app/c/[competition]/page.tsx` — 大会ハブ
- `app/c/[competition]/[season]/page.tsx` — シーズンページ
- `app/c/[competition]/[season]/standings/page.tsx` — 順位表（コミット 2 本のみ）
- `app/c/[competition]/[season]/round/[round]/page.tsx` — ラウンド（最終更新 2026-07-08）
- `app/players/[slug]/page.tsx` / `app/teams/[slug]/page.tsx` / `app/h2h/[pair]/page.tsx`
- `app/support/page.tsx`（コミット 1 本のみ）

**優先度の根拠（重要）**: 実測の平均滞在時間は大会ハブ 107 秒 / カレンダー 120 秒に対し、**試合詳細ページは 3.6 秒**。さらに Bing 流入の 86% が大会ハブに着地している。つまり大会ハブ系こそが実際に読まれている面であり、ここのデザイン品質が最も効く。試合詳細ページは刷新済みだが読まれていない。

各ページについて「刷新済みページと比べて何が欠けているか」を具体的に書くこと。

### F. レスポンシブ / オーバーフロー

- 横スクロールを起こしうる箇所（テーブル、固定幅、`min-w-`、長い文字列）を列挙
- `overflow-x-auto` によるスクロール封じ込めが無いワイド要素はどれか

## 各主張の裏取りルール（必ず守る）

前回の監査で **2 件が誤検知**だった（実コードを確認したら既に対応済みだった）。同じ失敗を繰り返さないこと。

1. すべての指摘に `ファイルパス:行番号` を付ける
2. 「〜が無い」と書く前に、必ず `grep` で全体を検索して 0 件であることを確認し、**使った検索コマンドをレポートに併記する**
3. 件数を書くときは推測せず実際に数える
4. 確信度を 3 段階（確実 / 要確認 / 推測）でラベルする。コードで確認できていないものを「確実」にしない

## やらないこと

- コンポーネント / CSS / 設定ファイルの変更
- `specs/` への spec 作成（監査結果を見て Owner が判断する）
- 依存パッケージの追加（Playwright 等は入れない。**スクリーンショットは撮らない**。この監査はコード静的解析のみ）
- 前回監査で解決済みの項目の再指摘
- 「一般的には〜が望ましい」という一般論。Tryline の実コードと `design.md` に紐づかない指摘は書かない
