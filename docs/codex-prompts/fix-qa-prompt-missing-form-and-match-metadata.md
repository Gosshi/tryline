`specs/fix-qa-prompt-missing-form-and-match-metadata.md` の仕様を実装してください。

**着手前に必ず読むこと**: `specs/fix-qa-win-rate-false-positive.md` と `specs/fix-qa-team-stats-new-fields-unsupported.md`（いずれもマージ済み）。両者は**プログラム側ガード**を直したもので、本 spec は **LLM 判定プロンプト**を直します。経路が違うので、既存の修正を巻き戻さないでください。

コンテキスト:
- プロジェクト規約は `AGENTS.md` を読む
- 過去の判断は `docs/decisions.md` を読む
- **調査済みの事実（再調査不要）**:
  - `lib/llm/prompts/qa-content.ts` の `QaMatchContext`（17-29行）に大会名・会場が存在しない
  - `formStats` は型に定義されているが、プロンプトを組み立てる 151-188 行のどのブロックにも**出力されていない**
  - `TeamFormStats`（13-15行）は `win_rate_last_5` のみで、平均得点は型にもガードにも存在しない
  - `formStats` は `lib/llm/stages/qa.ts` 433行でプログラム側ガードには渡っている（LLM 判定者にだけ渡っていない）
  - 2026-08-08 の実例（match_id `c5888e6d-caf9-48b8-963e-ed2355e36edd`）で、DB と完全一致する正しい記述が `factual_grounding: 2` で reject された
- 変更対象:
  - `lib/llm/prompts/qa-content.ts`（型拡張＋ブロック追加）
  - `lib/llm/pipeline.ts`（matchContext の配線）
  - 必要なら `lib/llm/stages/qa.ts`（form stats の文字列化ヘルパー）

実装のポイント:
- **新規ブロックは `derivedStatsBlock` / `teamStatsBlock` の文面と構造をそのまま踏襲すること**。「入力データに基づく正当な記述として扱い factual_grounding を下げないこと」という既存の言い回しを使う。独自の表現を発明しない
- **値の出どころは生成側と同一にすること**。生成プロンプトが参照している `assembled` の値をそのまま QA へ渡す。QA 用に DB を引き直すと、今回と同じ「生成側と判定側が別の入力を見る」構造が再発します
- **フィールド名は `assemble` ステージの既存の型に合わせること**。spec に書いた名前（`avg_points_for_last_5` 等）は候補であって確定ではありません。実コードを確認し、既にある名前があればそれを使ってください
- 値が `null` / `undefined` のときはブロックを出力しない（既存2ブロックと同じ挙動）

エッジケース:
- 大会に紐づかない試合（`competition_id` が null）で大会名ブロックが出力されないこと
- `venue` が null の試合で会場ブロックが出力されないこと
- 直近試合が5件未満のチーム（新規参入チーム等）で平均得点をどう扱うか決めて、テストで固定すること
- 引き分けを含む戦績（例「2勝2敗1分」）が正しく文字列化されること
- ツアーのように順位表が存在しない大会でも破綻しないこと

やらないこと:

- 採点ルーブリックの閾値変更
- **sourced_facts 0件時の指示文（106-109行）の削除や緩和**。この指示自体は正しく、不足していたのは入力データ側です
- 生成プロンプト（`generate-recap.ts` / `generate-preview.ts`）の変更
- 本番コンテンツの再生成（マージ後に Owner が `content-regen` の手順で実施します）

テスト:

- 渡されないときにブロックが出力されないこと
- 直近フォーム（勝敗内訳・平均得点）のブロックについて同様
- **修正前は form stats が一切出力されていなかったことを固定するテスト**（リグレッション防止）

- 既存のプログラム側ガードのテストが引き続き通ること
