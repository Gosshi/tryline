# Codex 指示: sourced_facts の重複蓄積を止める

## 仕様書

`specs/fix-sourced-facts-duplicate-accumulation.md` を読んでから着手すること。以下は補足であり、仕様の置き換えではない。

## 何が問題か（一文）

重複排除が**文字列の完全一致**でしか効かないため、`force=true` で再取得するたびに**同じ事実の言い換えが1セット追加される**。

## 実測（2026-08-21〜23、本番）

同一試合で件数がこう推移した。

```
7 → 15 → 23 → 31 → 36 → 43
```

**情報は増えていない。** 36件時点の実質は**14種類程度**。

```
コリシ欠場・デュ・トワ主将                 4件  ← 全部 rugby.com.au
ホランドがトゥイプロトゥに代わる           4件
ファインバーグ先発・リボックはベンチ       3件
フィットネステスト通過の3人                3件
先発一覧                                   3件
シリーズ第1テストである                    3件
スコット・バレット背中手術で欠場           2件
```

コリシの4件は**すべて同じドメインから、4通りの言い回し**で入っていた。

## 根本原因（自分で確認すること）

```sql
-- supabase/migrations/20260606010000_create_match_sourced_facts.sql:14
unique (match_id, fact)
```

```ts
// lib/llm/sourced-facts/allowlist.ts:334
const key = `${item.fact.toLowerCase()}|${item.source_domain}`;
```

抽出は毎回 LLM が行い**非決定的**。同じ記事から同じ事実を取っても日本語が毎回違う。1文字違えば別行として `upsert`（`fetch.ts:528`）される。

## 何が壊れているか

**密度基準の母数。** `qa-content.ts` に「本文の趣旨に沿う sourced_facts のおおむね**7割以上**を反映」という基準がある（PR #709 で導入）。**実質14種類が36件として数えられるため、全部書いても7割に届かない。** 2026-08-21 の再生成で情報密度が 2/5 に落ちた一因はここにある可能性が高い。

加えて**トークンの無駄**と、**重複の多い事実がプロンプト内で目立つことによる選択の歪み**。

## 先に実読すべきファイル

| ファイル | 何を確認するか |
|---|---|
| `lib/llm/sourced-facts/fetch.ts:526-531` | 無条件 `upsert`。**ここが追記の本体** |
| 同 `:415` | JRFU 経路にも同じ `onConflict: "match_id,fact"` がある |
| `lib/llm/sourced-facts/allowlist.ts:328-348` | バッチ内 dedup。キーが完全一致＋ドメイン |
| `supabase/migrations/20260606010000_create_match_sourced_facts.sql` | `unique (match_id, fact)` と、`content_type` を含むインデックスの**非対称** |
| `specs/fix-recap-sourced-facts-zero-result-retry.md` | **取得が0件になる実例。全消しにしてはいけない根拠** |

## やること

1. 同一 `(match_id, content_type, source_domain)` の再取得で、旧抽出が蓄積しない形にする
2. `unique` 制約に `content_type` を含める（**マイグレーション**）
3. 既存の重複規模を出す読み取り専用スクリプトを `tools/` に追加

## 設計上の注意

**意味的類似の判定（埋め込み等）に走らないこと。** 新しいインフラとコストを伴う。**構造で解く。**

推奨する考え方は「**あるソースからの最新の抽出が、そのソースからの前回の抽出を置き換える**」。意味比較が不要で、他ドメインの事実も守れる。

**実装方式は判断してよいが、3つ全部を満たすこと。**

- コリシ4件（同一ドメイン・別表現・同一事実）が再取得後に**1件へ収束**
- **別ドメインの事実が消えない**（`rugby.com.au` の再取得で `springboks.rugby` の事実を失わない）
- **取得0件のとき、既存を全消しにしない** ← これを外すと `fix-recap-sourced-facts-zero-result-retry.md` の事故が再発する

**マイグレーションはマージ前に本番適用が必要**（`feedback_migration_before_merge`）。既存データに `content_type` 違いの同一 `fact` があると制約変更が失敗しうるので、**適用前に重複の有無を確認する手順まで PR 本文に書くこと**。

## 絶対にやってはいけないこと

1. **埋め込み・ベクトル類似度を導入しない**
2. **抽出プロンプトを変えない。** 非決定性は前提として受け入れる
3. **密度基準「7割」を変えない。** 母数が壊れた状態で閾値をいじると原因の切り分けができなくなる
4. **allowlist・取得元を変えない**
5. **取得0件で既存を全消しにしない**
6. **既存の重複行を削除しない。** 件数を出すまで。削除は Owner 判断
7. **棚卸しスクリプトに書き込み系 SQL を入れない。** SELECT のみ
8. **既存記事を再生成しない**
9. **モデル ID を直書きしない。** `lib/llm/models.ts`

## テストで押さえる点

- 同一 `(match_id, content_type, source_domain)` で2回取得 → **件数が累積しない**
- 同一ドメイン・別表現・同一事実が**1件へ収束**
- **別ドメインの事実が残る**
- **取得0件で既存が残る**
- `unique` 制約に `content_type` が含まれる
- 棚卸しスクリプトが SELECT のみ

  - **棚卸しスクリプトを本番で実行した結果の件数**（推定値ではなく実出力）
