## 状況

PR #731 で取得件数が13→56件に増えた結果、**次の実行が 504 でタイムアウトしました**（2026-08-26）。

```
08:05:08  実行開始
08:06:09  curl: (22) The requested URL returned error: 504
```

ちょうど60秒で打ち切られています。`app/api/cron/collect-news-links/route.ts:14` の `maxDuration = 60` が上限です。

**PR #731 の修正自体は正しく効いています。** Stuff は8件中8件、NZ Herald は11件中5件が紐付きました（修正前は13件中1件）。壊れたのは処理時間だけです。

## 直すのは2点だけ

**1. `maxDuration` を 300 にする**

`app/api/cron/ingest-standings/route.ts:10` が既に 300 を使っており、**前例があります**。

**2. 1回あたりの通知件数に上限を設ける**

これが本質的な修正です。`maxDuration` を上げるだけでは、件数が増えれば再発します。

- 上限は**定数**として持つ（初期値20）
- 数えるのは「**通知した件数**」。該当しなかった記事は上限を消費しない（LLM も Discord も使わないため）
- 上限に達したら**ループを打ち切る**。それ以降は保存も通知もしない
- レスポンスに**打ち切りを示すフィールド**を足す

**取りこぼしません。** cron は1日4回走り、`source_url` が UNIQUE なので既処理分は重複せず、未処理分は次回に持ち越されます。

## 打ち切り時に「保存だけする」をやらないでください

一見親切ですが、`notified_at` が null の行が溜まり、**次回それを拾い直す仕組みが必要**になります。現行はフィードを毎回取り直す設計なので、フィードから消えた記事は永久に通知されません。

**単純にループを抜けてください。** その記事は次回のフィードにまだ載っている可能性が高いです。

## 並列化はしないでください

速くはなりますが、Discord のレート制限（429）と OpenAI の並列度を考える必要があり、複雑になります。

**今回の56件は初回に溜まっていたぶんです。** 定常運用では前回からの差分だけで、1日4回走るので1回あたり数件に収まるはずです。まず上限で確実に完走させ、実運用で本当に遅いと分かってから検討します。
