# Codex 指示: レビュー生成に全得点時点の累計スコアを渡す

## 仕様書

`specs/fix-recap-score-progression-snapshots.md` を読んでから着手すること。以下は補足であり、仕様の置き換えではない。

## 何が問題か（一文）

レビュー生成のプロンプトに**途中経過のスコアが渡っていない**ため、LLM が得点イベントから自分で足し算して途中経過を組み立てており、**その算術を誤って公開できない記事になった**。

## 実際に起きたこと

2026-08-17 の再生成で QA が事実根拠 1/5 で reject。**イベントデータは正しく復旧済みだったのに**、本文がこうなっていた。

> 39分のスコアを「17-19」としており、後段の「19-17」「21-17」と整合していません
> 「34分に14-17とリードし、3点差で折り返した」は誤りで、ハーフタイムは 21-17

正しい累計はこう（home = オーストラリア）。**トライとコンバージョンは別イベントなので、累計も別々に立つ。**

```
 5分 日本try          0-5
 7分 豪try            5-5   →  8分 豪con    7-5
17分 豪try           12-5   → 18分 豪con   14-5
26分 日try           14-10  → 27分 日con   14-12
34分 日try           14-17   ← 日本がリード
39分 豪try           19-17   ← 「19」はここに実在する
40分 豪con           21-17   ← 前半終了時はこの値
51分以降 豪5トライ    56-17
```

> **2026-08-17 訂正。** 初版は「39 分時点が 21-17」「19 という数値は存在しない」と書いたが**誤り**。Codex の指摘のとおり、**39 分は 19-17、40 分が 21-17** である。

## 本文の誤りは 2 種類（どちらも算術そのものではない）

**1. 表記順の揺れ。** 39 分は home 基準で `19–17`。本文はこれを「17-19」と書き、後段では「19-17」「21-17」と書いた。**同じ時点を 2 通りの並びで書いている。**

**2. ハーフタイムの誤認。** 「34分に14-17とリード」は**正しい**。しかし「3点差で折り返した」が誤りで、**実際の前半終了は 21–17（豪州リード）**。39–40 分の得点を見落としている。

**全得点時点の累計を渡せば、どちらも構造的に起きなくなる。**

## 必要なデータは既にある

`lib/llm/stages/assemble.ts:177-183` の `computeScoreTimeline` 内に **`scoringSnapshots`** がある。全得点時点の累計を保持しているが、`ScoreTimeline` 型に含まれず**関数内で捨てられている**。

**新しく計算するのではなく、既にあるものを型に載せてプロンプトへ渡すだけでよい。**

## 先に実読すべきファイル

| ファイル | 何を確認するか |
|---|---|
| `lib/llm/stages/assemble.ts:161-200` | `computeScoreTimeline` と `scoringSnapshots`。**ここが起点** |
| `lib/llm/types.ts:42-59` | `ScoreTimeline` 型。ここに追加する |
| `lib/llm/prompts/generate-recap.ts:164-203` | `scoreTimelineBlock`。**渡している情報が 3 つしかないこと** |
| `lib/format/match-event-points.ts` | ペナルティトライは 7 点 |

## やること

1. `ScoreTimeline` に全得点時点の累計フィールドを追加
2. `computeScoreTimeline` がそれを返す
3. `scoreTimelineBlock` で出力し、**「この表の値をそのまま使い、自分で加算しないこと」**を明示
4. `PROMPT_VERSION` を上げる

## 絶対にやってはいけないこと

1. **新しい得点計算式を書かない。** 既存の `pointsForEvent` を使う
2. **ペナルティトライを 5 点にしない。** 7 点（`type: "try"` ＋ `is_penalty_try`）。過去に 5 点だったバグを `specs/fix-penalty-try-scoring.md` で修正済み
3. **既存フィールドを削除・変更しない。** `ht_home` / `ht_away` / `lead_changes` / `winning_score` / `final_home` / `final_away` はそのまま残す。**追加のみ**
4. **スコアの表記順を変えない。** 「ホーム — アウェイ」のまま。記事の主役チーム基準に動的に変えると別の混乱を生む
5. **`generate-preview.ts` を触らない。** 試合前に得点経過は存在しない
6. **本番で再生成しない。** 受け入れ条件 17・18 の試し焼きは Owner が判断する

## 表記順について（重要）

この問題の背景には、**home が必ず先に来る**という表記がある。日本代表のアウェイ戦では `Australia 21 — Japan 17` となり、記事は日本を主語に書くため LLM が並びを組み替える。

**表記順は変えないが、どちらが先か分かるようにする。** 出力にチーム名を併記し、`21` がどちらの点数か一目で分かる形にすること。数字だけを並べると、今回と同じ取り違えが起きる。

## テストで押さえる点

**実際に壊れたケースを再現すること。**

- 上記の得点経過を入力し、**イベントごとの累計**を検証する。**try と conversion は別イベント**なので合算しないこと
  - 34 分（日本 try）→ **14–17**
  - 39 分（豪州 try）→ **19–17**
  - 40 分（豪州 conversion）→ **21–17**
- ペナルティトライを含む入力で **7 点**として累計される
- `substitution` / `yellow_card` が混ざっても累計に影響しない
