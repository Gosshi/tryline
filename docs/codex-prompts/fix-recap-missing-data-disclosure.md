# Codex 指示: レビュー本文から「データが無い」という報告を消す

## 仕様書

`specs/fix-recap-missing-data-disclosure.md` を読んでから着手すること。以下は補足であり、仕様の置き換えではない。

## 何が問題か（一文）

`lib/llm/prompts/generate-recap.ts` に「データの不在に言及するな」という指示がないため、順位表や次戦データを持たない大会のレビューで、**読者に向けてシステム内部の事情を説明する文**が公開されている。

実際に公開された文（2026-08-16、日本 vs オーストラリア第2戦）:

> オーストラリアの次の対戦相手と日程は、入力データには示されていない。そのため具体的な対戦構図は確定できない

> 順位表は入力データにないため大会順位への直接の影響は判定できない

## これは「稀なケース」ではない

本番実測: **8/9 以降に生成された recap は 4 本中 4 本（100%）でこの表現が出ている。** 7/20 以前は 20 本中 0 本。

原因はプロンプト改版ではない（`recap@4.14.0` は両方の期間に存在する）。**違いは大会の性質で、8 月の 4 本はすべて順位表を持たないテストマッチ・ツアー**（`lipovitan-challenge-cup-2026` / `greatest-rivalry-2026`）だった。

**この構造は続く。** Greatest Rivalry は 9/12 まで、日本代表の 11 月欧州遠征も同種。しかも 8/9 と 8/16 の 2 本はどちらも日本代表戦で、**最も読まれる試合ほどこの表現が出る。**

## やること

`generate-recap.ts` のプロンプトに、**データの不在を本文に書かせない指示**を追加する。preview 側の `dataSparseBlock` と同じ思想でよいが、recap の文脈に合わせること。

指示に含めるべき要素:

1. 「入力データ」「提供されたデータ」等、**システム内部を指す語を本文に出さない**
2. 「確定できない」「判定できない」「断定できない」「示されていない」等、**データ不足を理由に結論を保留する表現を書かない**
3. **書けないなら、その話題に触れない**（不在を述べるのではなく、記述対象から外す）

## 線引きに注意（重要）

**「事実の限界に触れること」自体は禁止しない。**

同じ記事に、こういう文もある:

> 得点記録だけから個々の守備対応や接点の詳細を断定することはできない

**これは残してよい。** 取材・観戦の限界を述べる誠実な記述であり、Tryline の「敵は間違い」という方針とも整合する。

禁止するのは「**入力データにない**」という、システムの内部事情を読者に開示する表現。この違いが指示から読み取れるように書くこと。**一律に「断定できない」を禁止すると、上の良い文まで消える。**

## 絶対にやってはいけないこと

1. **`generate-preview.ts` を変更しない。** 既に同等の指示がある
2. **`assemble` に次戦データや順位表を追加しない。** 「データを渡せば書ける」方向の修正は本 spec の対象外。**DB 上のオーストラリアの次戦は 11/8 だが、sourced_facts には 8/29 のアルゼンチン戦への言及があり、DB にデータ欠落の疑いがある。** 安易に渡すと誤情報を書く
3. **`fabrication-guard.ts` や QA ステージを触らない。** 逃げ表現は捏造ではないので、決定的ガードの対象にしない
4. **本番で再生成しない。** 受け入れ条件 10・11 の試し焼きは Owner が判断する
5. **PR 本文に「バージョンを上げたので既存コンテンツが再生成される」と書かない。** `prompt_version` は `pipeline.ts:733` で記録されるだけで、再生成のトリガーではない
