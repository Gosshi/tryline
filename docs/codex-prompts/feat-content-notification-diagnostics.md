# Codex 指示: コンテンツ生成通知に診断値を載せ、品質回帰を検知する

## 仕様書

`specs/feat-content-notification-diagnostics.md` を読んでから着手すること。以下は補足であり、仕様の置き換えではない。

## 何が問題か（一文）

却下通知が **LLM の作文をそのまま流している**ため矛盾した文言が並び、採点4項目のうち1項目が欠落し、素材の状態も試合名も分からず、**Owner が通知だけでは何も判断できない**。

## 実際に届いた通知（2026-08-21 03:47、本番）

```
⚠️ コンテンツ却下 [preview]
試合ID: d6d5b1ab-58ec-44c8-a31d-54fadc0a662e
QAスコア: 情報密度 2/5 / 日本語品質 5/5 / 事実根拠 3/5
問題点: 本文は1500字以上で、字数要件を満たしています / … / 本文が目標字数の下限未満です
```

**「1500字以上で満たしています」と「下限未満です」が同じリストにいる。** 実測 1,468 字なので前者が誤り。`lib/llm/stages/qa.ts:573-575` のコメントどおり**プログラム側が字数の single source of truth** であり、誤っているのは LLM が書き足した側。

**`tactical_depth` が出ていない。** この回はそれが 2/5 で却下理由の中心の1つだった。

原因特定には本番 DB を6回引く必要があった。通知に必要な値は**すべて呼び出し側が既に持っている**。

## もう1つ: 劣化が通知されない

同日 22:06、cron が同じ試合を再生成して published を上書きした。

```
情報密度 5→4 / 事実根拠 4→3 / 戦術 3→4 / 字数 1944→1844
```

**verdict は publish なので通知はゼロ。** 選手名カタカナが総取り替えになり（マークス→マルクス、ラウ→ルー、ムーアビー→ムービー）、主将コリシの欠場が本文から消えたが、誰も気づかなかった。

## 先に実読すべきファイル

| ファイル | 何を確認するか |
|---|---|
| `lib/llm/notify.ts:53-74` | `notifyContentRejected`。**62行が3項目しか出していない** |
| 同 `:12` | `DISCORD_MESSAGE_CONTENT_LIMIT = 2_000`。診断値を残し issues を切り詰める側にする |
| 同 `:25-51` | `postOpsAlert`。**これを使う。新しい送信経路を作らない** |
| `lib/llm/content-length.ts:3` | `CONTENT_LENGTH_ISSUE`。**プログラム側が付ける正しい指摘。必ず残す** |
| 同 `getContentLengthRequirement` / `measureContentLength` | 実測字数と下限。**値を直書きしない** |
| `lib/llm/stages/qa.ts:480-486`, `:573-575` | 決定的な字数判定と「single source of truth」のコメント |
| `lib/format/kickoff.ts` | JST 整形。**自前で日時整形を書かない** |

## やること

1. `notifyContentRejected` に診断値を追加（4項目全採点 / 対戦カード日本語表記 + キックオフ JST / 実測字数と下限 / sourced_facts 件数 / ラインアップ件数 / 決定的ガードの発火有無）
2. LLM が `issues` に書いた字数言及を落とす。`CONTENT_LENGTH_ISSUE` と完全一致する要素は残す
3. 再生成でスコアが下がったときの通知を新規追加

## 設計上の注意

**回帰検知は上書き前の `qa_scores` が要る。** 更新後では比較できないので、読み出して保持してから書くこと。

**「静かな日は静かに」を守る。** 回帰が無ければ通知しない。毎回何か届くと読まれなくなる。

**取りこぼしより誤削除を避ける。** issues のフィルタは、本物の指摘を落とすくらいなら多少残す方向へ寄せること。

## 絶対にやってはいけないこと

1. **QA の採点ロジック・ルーブリック・閾値を変えない**
2. **`verdict` の判定基準を変えない。** 劣化しても publish されること自体は今回変えない（通知するだけ）
3. **生成プロンプトに触らない**
4. **`postOpsAlert` の送信先・Webhook 設定を変えない。** `fix-ops-notifications-discord.md` の結果を維持
5. **既存の4つの通知関数の出力を変えない**（`notifyCostAlert` / `notifyDataIntegrityReport` / `notifyBroadcastIngestReport` / `notifyNewsletterDelivery`）
6. **字数の下限をコードに直書きしない。** `content-length.ts` から取る
7. **日時整形を自前で書かない。** `lib/format/kickoff.ts`
8. **本番へ通知を送るテストを書かない。** `postOpsAlert` はモックする
9. **却下コンテンツの自動再試行を実装しない**
10. **モデル ID を直書きしない。** `lib/llm/models.ts`

## テストで押さえる点

- **修正前は `tactical_depth` が出力されないことを固定するテスト**
- 実測字数・下限が `content-length.ts` の値と一致
- sourced_facts 0件のとき「0件」と明示される
- 2,000 字超過時に診断値が残り issues が切り詰められる
- LLM が「1500字以上で、字数要件を満たしています」を返しても通知に出ない
- `CONTENT_LENGTH_ISSUE` は残る
- **`{5,4,3,4}` → `{4,3,4,4}` で回帰通知が発火する**（仕様書背景の実例）
- 前回スコア無し（初回生成）では発火しない
- 全項目同点または上昇では発火しない
