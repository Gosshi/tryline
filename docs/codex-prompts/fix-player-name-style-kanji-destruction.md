`specs/fix-player-name-style-kanji-destruction.md` の仕様を実装してください。

**着手前に必ず読むこと**: `specs/feat-preview-player-kanji-glossary.md`（PR #669、マージ済み）。同 spec はグロッサリの**供給源**を扱ったもので、本 spec は**グロッサリに載っていない選手の表記規則**という別レイヤーです。グロッサリ構築ロジックには手を入れないでください。

コンテキスト:
- プロジェクト規約は `AGENTS.md` を読む
- 過去の判断は `docs/decisions.md` を読む
- **調査済みの事実（再調査不要）**:
  - `generate-recap.ts` 288-296行 と `generate-preview.ts` 207-215行 に**同一の `nameStyleInstruction`** がある
  - 該当箇所が「グロッサリにない選手はカタカナで記載すること」と無条件に命じており、入力データ中の漢字を破棄している
  - 姓名の語順を保つ指示が存在しない
  - 2026-08-08 の実例: sourced_facts が「伊藤龍之介」「植田和磨」と漢字で提供したが、recap は「リュウノスケ・イトウ」「カズマ・ウエダ」を出力した
  - 外国籍選手でも「ディラン・ライリー」→「ライリー・ディラン」、「リーチ マイケル」→「レイチ・マイケル」の逆転が発生した
  - `players.name_ja` は日本代表81名中11名のみ。大半の選手はグロッサリ外に留まる
- 変更対象:
  - `lib/llm/prompts/generate-recap.ts`
  - `lib/llm/prompts/generate-preview.ts`

実装のポイント:
- **優先順位を明示する形に書き換えること**。(1) グロッサリにあれば指定の漢字、(2) グロッサリに無くても入力データに日本語表記があればそれをそのまま使う（漢字をカタカナ化しない）、(3) どちらも無ければ英語名をカタカナ変換
- **姓名の語順を入力データから変えない**旨を明示すること。日本人を「名・姓」へ並べ替えない。外国籍選手の「名・姓」を「姓・名」へ入れ替えない
- **文面は既存の言い回しに合わせること**。新しい用語を発明しないでください
- **両ファイルの `PROMPT_VERSION` を上げること**
- **同一文字列が2ファイルに重複している問題を解消してください**。共通定数へ切り出すか、同一性をテストで担保するか、どちらでも構いませんが**片方だけ更新される事故を防ぐ形**にしてください。今回の不具合と同型の「同じ知識が2箇所にあって片方だけ更新される」構造を残さないこと

エッジケース:
- league-one 分岐（`competition?.family === "league-one"`）の文面は**変更しないこと**。別ルールが既に存在し、本件の症状は non-league-one 側で発生しています
- 入力データに日本語表記が一切無い外国籍選手は従来どおりカタカナ変換されること
- 同一選手の表記が入力データ内で揺れる場合（例: sourced_facts が「マキシファウルア」、別記事が「ファウルア・マキシ」）の優先順位を決めて、**判断を報告してください**
- グロッサリと入力データで表記が異なる場合はグロッサリを優先すること

やらないこと:
- グロッサリ構築ロジック（`buildJapanesePlayerNameGlossary` および `assemble.ts` の呼び出し側）の変更
- `players.name_ja` のバックフィル
- チーム名・大会名の表記規則の変更
- QA・採点ルーブリックの変更
- 既存 published 記事の再生成（マージ後に Owner が実施します）

テスト:
- `nameStyleInstruction` に入力データの日本語表記を優先する旨が含まれること
- 語順を変えない旨が含まれること
- league-one 分岐の文面が変わっていないこと
- 両ファイルの `PROMPT_VERSION` が上がっていること
- **2ファイルの instruction が同一であることを担保するテスト**（共通定数化した場合は不要）
