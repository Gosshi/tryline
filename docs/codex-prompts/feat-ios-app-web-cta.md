# Codex 指示: Web からアプリへの導線を作る（通知訴求）

## 仕様書

`specs/feat-ios-app-web-cta.md` を読んでから着手すること。以下は補足であり、仕様の置き換えではない。

## 何をするか（一文）

**iOS アプリが 2026-08-19 に App Store 承認されたが、web に導線が 1 つも無い。**ハブとカレンダーに「試合開始前に通知します」という訴求で導線を置く。

## 訴求を間違えないこと

**「アプリをダウンロード」ではなく「試合開始前に通知します」。**

実測でこうなっている。

```
大会ハブの滞在     107 秒
カレンダーの滞在   120 秒
試合ページの滞在   3.6 秒
再訪              97% がゼロ    ← これが本当の課題
月間ユーザー       約 110
```

**月110人が来て97%が二度と戻らない。**記事を934本書いても動いていない。

**アプリで web に無い機能はプッシュ通知だけ**で、それが再訪問題に直接効く。だから訴求は通知。

進行中の題材も強い。**南アフリカ vs ニュージーランドの4テストシリーズ（8/23〜9/13）はキックオフが日曜 00:10 JST**。「寝ている間に終わる試合」は通知価値が最も伝わる。

## 置く場所と置かない場所

| 面 | 置く | 理由 |
|---|---|---|
| 大会ハブ | ○ | 滞在107秒。**Bing流入の86%がここに着地** |
| カレンダー | ○ | 滞在120秒 |
| **試合詳細** | **×** | **滞在3.6秒。置いても見られない** |

## まず Smart App Banner（コスト最小・効果確実）

`<head>` にメタタグ1行。

```
<meta name="apple-itunes-app" content="app-id=6791587357">
```

**iOS Safari でのみ Apple が描画する。**閉じられる。レイアウトシフトなし。他環境では何も出ない。

**自前で UA 判定を書かないこと。** Apple 側の挙動に委ねる。

## 計測できるようにする

```
https://apps.apple.com/jp/app/id6791587357?ct=<surface>
```

`ct` は App Store Connect の App Analytics でキャンペーンとして集計される。**面ごとに別トークン**（`hub` / `calendar` / `banner`）。**URL を直書きせず定数から生成する。**

これが無いと「どの面が効いたか」が永久に分からない。

## 絶対にやってはいけないこと

1. **試合詳細ページに CTA を置かない**
2. **モーダル・ポップアップ・インタースティシャルを使わない。** UX と SEO の両方を損なう
3. **自前の UA 判定を書かない**（Smart App Banner は Apple が判定する）
4. **レイアウトシフトを起こさない。** ハブは滞在107秒の主要導線
5. **画面上部を占有しない。** ハブの主目的は日程と結果の確認
6. **App Store URL を各所に直書きしない**
7. **Android 向けの導線を作らない。** アプリが存在しない
8. 通知機能そのもの（cron・push 登録）を触らない
9. App Store のメタデータ・キーワードを触らない（ASO は別件）

## テストで押さえる点

- ハブとカレンダーで CTA が描画される
- **試合詳細ページに CTA が無い（回帰防止）**
- `ct` トークンが面ごとに異なる

## 完了の定義

- `specs/feat-ios-app-web-cta.md` の受け入れ条件 1〜14 を満たす
- `pnpm test` と型チェックが green
- **本番確認は Owner が行う**（受け入れ条件 15〜17。iOS 実機での Smart App Banner 表示確認を含む）
- PR 本文に以下を書くこと:
  - Smart App Banner をどの範囲に出したか（全ページか、ハブ・カレンダーのみか）とその理由
  - 各面に付けた `ct` トークンの一覧
  - CTA の主文（実際の文言）
  - レイアウトシフトを避けるためにやったこと
