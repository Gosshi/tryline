# Codex 指示書: `/調査事実を追加` を「試合を選んで、ChatGPT の出力を貼るだけ」にする

仕様書: `specs/feat-discord-research-fact-paste.md`
受け入れ条件は仕様書を正とする。ここでは繰り返さない。

`AGENTS.md` の規約に従う。仕様書と実コードが食い違ったら、実装を進めずその場で止めて Owner に確認する。

## やること

1. モーダル（`buildResearchFactEntryModal`）の入力を「試合」と「ChatGPT の出力（この試合の部分）」の 2 つにする。出典 URL・確度・出典確認は削除する。
2. 新規 `lib/discord/research-paste.ts` に、貼り付けた文章を出典ブロックごとに読み取る純関数 `parseResearchPaste` を作る（読み取りのきまりは仕様書の API サーフェス 2）。
3. `processResearchFactEntry` を、出典ブロックごとに URL を確かめて保存する形にする。確度は `high` 固定。401・403・429 は目視確認済みとして保存し、それ以外の失敗の出典だけを保存しない。
4. 返信を、保存件数・目視確認済みの出典・保存しなかった出典・読み飛ばした行をまとめた形にする。

## 触るファイル

- `app/api/discord/interactions/route.ts`
- 新規 `lib/discord/research-paste.ts`
- テスト（`tests/` の既存の Discord のテストの配置に合わせる）と fixture

## 守ること

- 送信を受けたらいったん「処理中」と返し、確認と保存は `after()` の中で行う今の流れは変えない（出典が増えても Discord の 3 秒の期限にかからないように）。
- Owner の Discord ユーザー ID の確認、試合の候補の出し方、`content_type` の決め方、重複を除く方法は変えない。
- 生成の上限を超えた手動事実の通知（`droppedManual`）は今のまま出す。
- 404 など、401・403・429 以外の失敗の出典は保存しない（存在しない URL を出典として残さないため）。

## 処理すべきエッジケース

1. 貼り付けに `### 出典:` が 1 つも無い: 何も保存せず、「出典のブロックが見つかりません」と返す。
2. 同じ URL の出典ブロックが 2 回出てくる: どちらの事実も保存する（重複する事実は既存の重複除去で落ちる）。URL の確認は 1 回にしてよい。
3. 貼り付けに別の試合の見出し（`## `）が混ざっている: 見出しは読み飛ばすだけなので、下の事実は選んだ試合に入ってしまう。**モーダルの説明文で「この試合の分だけ貼る」ことを明記する**（仕様書の API サーフェス 1）。
4. 事実の行の中にある Markdown リンクや太字は、そのまま保存してよい（行頭の `- **` だけが注記の印）。

## 検証

- `pnpm lint`、`pnpm typecheck`、`pnpm test` を実行する（**3 つとも必ず実行し、結果を完了報告に含める**）。
- 「壊して落ちる」確認（コミットしない）: 403 の出典を保存しない実装に戻すと、受け入れ条件 4 のテストが落ちること。内容と結果を PR 本文に書く。

## やってはいけないこと

- 本番の Discord に送信すること、本番 DB に書き込むこと（テストはモック）。
- Discord のコマンドの再登録（必要なら Owner が行う）。

## 完了時

- PR 本文に書くこと:
  - 変更したファイルの一覧
  - 受け入れ条件 1〜6 のそれぞれについて、確認の方法と結果
  - 「壊して落ちた」確認の内容
  - Discord のコマンドの再登録が必要かどうか
- ブランチは main から新しく切る。共有の作業ツリーにある未コミットの差分を巻き込まない。`git stash -u` は使わない。
- PR の作成まで。マージはしない。
