`/specs/fix-public-page-auth-decoupling.md` の仕様を実装してください。

コンテキスト:
- プロジェクト規約は `AGENTS.md` を読む
- `components/site-header.tsx`（ルートレイアウトに配置、全ページ共通）が `getUser()` を無条件に呼び、`app/page.tsx:112` も独立して再度 `getUser()` を呼んでいる。これらが `next/headers` の `cookies()`（Dynamic API）に依存しているため、サイト全体が強制的にdynamicレンダリングになっていると推測される
- 本specはログイン状態・お気に入りチーム・スポイラー設定・プレミアムバッジ等のユーザー個別状態表示を、ページ本体のサーバーレンダリングから分離することが目的

やること:
- `SiteHeader` を、静的な骨格（ロゴ・ナビリンク・大会ドロップダウン）のみをRSCでレンダリングする形に分解する
- ユーザー個別部分（ログインボタン/ユーザーメニュー切り替え、プレミアムバッジ）は独立したクライアントコンポーネントに切り出し、自身でセッション状態を取得する
- セッション状態の取得方法は spec の「未解決の質問」を踏まえて選択する（軽量APIルート or クライアント側Supabase SDK）。既存の `lib/db/public-server.ts` 等のパターンとの整合性を確認してから決めること
- `app/page.tsx:112-113` の `getUser()` / `getUserProfile()` もページ本体のデータ取得フローから分離する

処理すべきエッジケース:
- 未ログイン→ログイン後の状態切り替えでレイアウトシフト（CLS）が起きないよう、プレースホルダーと実データ表示で同じ要素サイズを保つこと
- お気に入りチームの優先表示は、初回非個別化表示→クライアント側取得後に優先並び替え、という段階的な描画になってよい

完了の定義:
- specs の受け入れ条件1〜6を満たす
- `pnpm test` / `pnpm tsc --noEmit` / `pnpm lint` / `pnpm build` clean
- 変更ファイル一覧を報告する

要件:
- 認証必須ページ（マイページ等）の認証チェック方式は変更しない
- `middleware.ts` の変更は別spec（`fix-middleware-auth-scope.md`）の対象。本specでは触らない
- 曖昧な箇所や仕様書と実環境の食い違いがあれば、その場で実装を停止して質問する

完了時:
- 実装内容・変更ファイルを要約する
- セッション取得の実装方式として何を選んだか、理由とともに報告する
- 本番デプロイ後のTTFB変化はOwnerが別途確認するため、確認用のcurlコマンド例を添えてよい
- 仕様書からの逸脱があれば理由を明示する
- 未解決の質問があれば記載する
