### 2.2 レビュー観点（11 本すべてについて全項目に回答）

1. **受け入れ条件は機械的に検証できるか。** 「〜が表示される」で止まっていないか。Codex が満たしたかどうかを自分で判定できるか
2. **受け入れ条件で潰しきれていない懸念が「未解決の質問」に逃げていないか。** このプロジェクトには「懸念が実装を左右するなら、未解決の質問ではなく受け入れ条件で潰す」という教訓がある（D025）
3. **スコープ対象外が十分か。** Codex が善意で範囲を広げる余地が残っていないか。特に**データの削除・更新**を誘発しないか
4. **参照しているファイルパス・行番号・関数名が実在するか。** 公開リポジトリで確認すること。存在しない参照は実装を誤らせる（Claude Code は本セッションで実際に `reference/api-types.ts` という存在しないパスを書き、自分で気づいて削除した。**他にも残っている可能性がある**）
5. **既存 spec との矛盾。** 484 本ある `specs/` のうち、同じファイルを触る spec・supersede すべき spec を見落としていないか
6. **設計不変条件（§5）に違反していないか**
7. **LLM コストの見積もりが必要な spec でそれが書かれているか。** 逆に「コスト $0」と書いた spec が本当に $0 か
8. **実装順序の依存。** 11 本を同時に Codex へ投げたとき、同じファイルで衝突するものはどれか。**マージ順序を明示すること**
9. **テストが「実装をなぞるだけ」になっていないか。** 特に回帰テストが、実際に起きた事象を再現しているか
10. **この spec で本当に問題が解決するか。** 受け入れ条件を全部満たしても残る穴があれば指摘すること

### 2.3 特に厳しく見てほしい点

- **#1 の V1〜V4**: 対称スコア（24–24 等）での帰属反転を V1 が検出できないことは spec に既知の限界として明記してある。**V4 の fixture 同一性で本当に補えるのか。** 補えないなら何が必要か
- **#2 の副作用**: 不整合が残る試合で recap が生成されなくなる。**棚卸しの結果次第で対象が広がる。** この順序（生成停止を先に入れる）が正しいか、棚卸しを先にすべきか
- **#3 と #2 の相互作用**: 表示を止めても既に公開済みの本文は残る。**読者が見る状態として整合しているか**
- **#4 の C3/C4**: 署名 4 件以上という閾値、C4 の「全件反転」条件は妥当か。**見逃す型の汚染があるか**
- **#8 の応答設計**: `userId` 欠落で 200 を返す判断（再送しても直らないため）は正しいか
- **#10 の閾値 48 時間**: `cron-live-pipeline` が 1 日 4 回であることから導いた。閑散期の誤検知をどう扱うか
